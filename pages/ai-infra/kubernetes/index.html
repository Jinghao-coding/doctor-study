调度体系

Kubernetes 调度体系全景

Scheduling Framework 只是 kube-scheduler 的插件化内核，不是 Kubernetes 调度体系的全部。完整调度体系还包括：调度器进程、调度队列、调度缓存、Pod 约束语义、优先级与抢占、调度配置/Profile、默认插件、扩展调度器，以及批调度/重调度生态。

调度器本体
kube-scheduler 监听未绑定 Pod，为其选择 Node，并把绑定结果写回 API Server。
核心问题是“哪个 Pod 先调度、哪些节点可行、哪个节点最好、失败后怎么处理”。
调度输入语义
PodSpec 中的 requests、nodeSelector、affinity、tolerations、topologySpreadConstraints、priorityClassName 等。
这些字段决定 Filter/Score 的约束和偏好，是面试排查 Pending 的重点。
Scheduling Framework
把调度流程拆成 QueueSort、PreFilter、Filter、Score、Reserve、Permit、Bind 等扩展点。
它解决“如何扩展调度决策”，但不等于全部调度能力。
配置与 Profile
通过 KubeSchedulerConfiguration 配置 plugins、pluginConfig、profiles、percentageOfNodesToScore 等。
多 Profile 可以让不同 Pod 使用不同 schedulerName 和插件组合。
失败与抢占
调度失败后进入队列重试；高优先级 Pod 可触发 PostFilter 抢占。
涉及 UnschedulableQ、BackoffQ、nominatedNodeName、PDB、优雅终止。
扩展生态
多调度器、Scheduler Plugins、Descheduler、Kueue、Volcano、Cluster Autoscaler 等。
AI Infra 面试通常会追问 GPU 拓扑、Gang Scheduling、多租户队列和资源回收。

一图看懂调度链路

Scheduling Framework 的核心价值，是把“给 Pod 选节点”拆成可插拔的多个扩展点。面试时不要只背扩展点名称，更重要的是能说清楚：Pod 如何入队、如何过滤节点、如何打分、如何预占、如何绑定，以及失败后如何重试。

核心概念：两个周期

阶段包含步骤并发特点面试要点
Scheduling CycleQueueSort、PreFilter、Filter、PostFilter、PreScore、Score、Reserve对一个 Pod 的调度决策通常串行执行负责“选哪个节点”，需要保证调度器缓存中的资源预占一致性
Binding CyclePermit、PreBind、Bind、PostBind不同 Pod 的绑定可以并行负责“把选择写回 API Server”，绑定慢不应阻塞后续调度决策

一句话回答：Scheduling Cycle 做决策，Binding Cycle 做落盘；前者要谨慎维护调度器内部状态，后者可以并行提高吞吐。

扩展点与插件应该怎么记

K8s 官方常说 Scheduling Framework 有 11 个主要扩展点。实际学习时可以按“排序、预处理、过滤、失败补救、打分、预占、准入、绑定”来记。NormalizeScore 是 Score 插件可实现的归一化接口，常和 Score 放在一起讲，不必单独当作主扩展点背。

扩展点作用典型插件/场景面试记忆点
QueueSort决定 ActiveQ 中 Pod 的出队顺序PrioritySort通常按优先级和时间排序，一个调度 profile 只能有一个 QueueSort 插件
PreFilter提前计算 Pod 资源需求或校验硬条件NodeResourcesFit、InterPodAffinity减少后续每个节点重复计算，失败可直接拒绝
Filter筛掉不满足硬约束的节点资源不足、NodeAffinity、Taint/Toleration、VolumeBinding硬约束，不满足就是不能调度
PostFilterFilter 找不到节点时的补救DefaultPreemption最重要场景是抢占，但抢占也可能失败
PreScore / Score对可行节点按软偏好打分NodeResourcesBalancedAllocation、ImageLocality、NodeAffinity软偏好，分数会归一化并加权求和
Reserve / Unreserve在调度器缓存中预占资源，失败时回滚资源预留、Gang 调度辅助状态不是写 API Server，而是保护调度器内部一致性

三个队列：调度失败后 Pod 去哪里

ActiveQ
活跃队列。新 Pod、退避结束的 Pod、被事件激活的 Pod 会进入这里，按 QueueSort 排序后等待调度。
BackoffQ
退避队列。调度失败但可重试的 Pod 会先等待指数退避，避免反复占用调度器 CPU。
UnschedulableQ
不可调度队列。当前集群状态下无解的 Pod 会在这里等待集群事件，例如节点加入、Pod 删除、PV 变化。
Q: Pod 调度失败后的完整流转过程？
正常尝试

Pod 从 ActiveQ 出队后进入调度流程，依次经过 Filter、Score、Reserve、Bind 等阶段。

失败处理
  1. 如果 Filter 找不到可行节点，进入 PostFilter。
  2. PostFilter 默认尝试抢占低优先级 Pod。
  3. 抢占成功时设置 nominatedNodeName，并等待被抢占 Pod 终止。
  4. 抢占失败或没有合适牺牲者时，Pod 进入 UnschedulableQ。
重新入队

节点新增、Pod 删除、PV 绑定变化等事件会重新激活 Pod，使其进入 BackoffQ 或 ActiveQ，再次尝试调度。

面试记忆：ActiveQ 出队调度，失败先抢占，仍失败进不可调度队列，等集群事件触发重试。

抢占机制：高优先级 Pod 为什么也可能 Pending

  1. 触发条件：高优先级 Pod 无法通过 Filter 找到可行节点，PostFilter 尝试抢占低优先级 Pod。
  2. 候选节点模拟：调度器在缓存中模拟移除低优先级 Pod，看该节点是否能满足高优先级 Pod 的资源和约束。
  3. 牺牲者选择：优先选择违反 PDB 更少、驱逐 Pod 更少、牺牲者优先级更低的方案。
  4. nominatedNodeName：抢占成功后先标记候选节点，但不会立即绑定，因为被抢占 Pod 还要优雅终止。
  5. 不保证成功：等待过程中节点状态可能变化，或者 PDB/亲和性/新 Pod 干扰导致最终仍然调度失败。

实际场景：实现 GPU 拓扑感知调度插件

假设我们有一个 AI 训练集群，节点上有不同 GPU 拓扑：有些节点 8 张 GPU 之间有 NVLink，有些节点只有 PCIe；多卡训练任务更希望调度到 NVLink 更好的节点，否则 AllReduce 通信会慢。这个场景很适合用 Scheduling Framework 说明“插件应该放在哪里”。

1. 场景输入

输入示例作用
Pod 资源请求requests: nvidia.com/gpu: 4判断是不是多 GPU 任务，以及需要几张 GPU
节点标签gpu.topology/nvlink: "true"快速区分 NVLink 节点和普通 PCIe 节点
节点扩展资源nvidia.com/gpu allocatable由 device plugin 上报，调度器按 requests 做资源判断
拓扑元数据GPU 卡组、NUMA、NVLink fabric生产中可由节点 agent 写入 CRD、annotation 或 scheduler cache

2. 扩展点选择

扩展点做什么为什么
PreFilter解析 Pod 是否请求 GPU、请求几张 GPU，并写入 CycleState避免每个节点重复解析 Pod 资源请求
Filter过滤没有足够 GPU、没有目标 GPU 型号、没有可用卡组的节点硬约束必须放 Filter，不满足就不能调度
Score给 NVLink 更完整、跨 NUMA 更少、模型缓存更近的节点更高分拓扑好坏通常是软偏好，适合 Score
Reserve / Unreserve在调度器缓存里预占具体 GPU 卡组，后续失败则回滚防止两个 Pod 同时选中同一组 GPU
Permit如果是一组训练 Worker，可等待全部 Worker 都可调度后再放行Gang Scheduling 场景需要整体准入

3. 最小可行实现思路

  1. 先做 Filter：没有 GPU、GPU 数量不足、节点标签不满足的节点直接排除。
  2. 再做 Score：对所有可行节点打分，NVLink 节点高分，PCIe 节点低分。
  3. 最后加 Reserve：如果需要选择具体 GPU 卡组，就在 Reserve 阶段预占，失败时 Unreserve 回滚。
  4. 不要一开始就做复杂 Gang Scheduling：如果只是单个多卡 Pod，Filter + Score 通常已经能解释清楚。

4. 伪代码

// PreFilter: 解析 Pod 的 GPU 请求，并写入 CycleState。
func PreFilter(ctx context.Context, state *framework.CycleState, pod *v1.Pod) *framework.Status {
    gpuCount := getGPURequest(pod)
    state.Write("gpuRequest", gpuCount)
    return framework.NewStatus(framework.Success)
}

// Filter: 硬约束，不满足就不能调度。
func Filter(ctx context.Context, state *framework.CycleState, pod *v1.Pod, nodeInfo *framework.NodeInfo) *framework.Status {
    gpuCount := state.Read("gpuRequest")
    if nodeFreeGPU(nodeInfo) < gpuCount {
        return framework.NewStatus(framework.Unschedulable, "insufficient gpu")
    }
    if gpuCount >= 4 && nodeInfo.Node().Labels["gpu.topology/nvlink"] != "true" {
        return framework.NewStatus(framework.Unschedulable, "large gpu job requires nvlink")
    }
    return framework.NewStatus(framework.Success)
}

// Score: 软偏好，节点仍然可用，只是优先级不同。
func Score(ctx context.Context, state *framework.CycleState, pod *v1.Pod, nodeName string) (int64, *framework.Status) {
    node := getNode(nodeName)
    if node.Labels["gpu.topology/nvlink"] == "true" {
        return 100, framework.NewStatus(framework.Success)
    }
    return 30, framework.NewStatus(framework.Success)
}

Q: 面试中怎么讲这个案例？
业务目标

多 GPU 训练任务希望优先使用 NVLink 拓扑更好的节点，减少 AllReduce 通信开销。

FilterGPU 数量、型号、租户隔离是硬约束，不满足直接排除。
ScoreNVLink 更优、跨 NUMA 更少、模型缓存更近是软偏好，用分数表达。
Reserve需要绑定具体 GPU 卡组时，在调度器缓存中预占并支持回滚。
Permit一组分布式训练 Worker 需要整体准入时使用，或直接选 Volcano/Kueue。
面试总结：先讲业务目标，再讲硬约束放 Filter、软偏好放 Score、具体卡组放 Reserve、分布式训练考虑 Gang Scheduling。

面试高频追问

Q: Filter 和 Score 的区别是什么？
Filter硬约束，决定节点能不能用。典型例子：资源不足、NodeSelector 不匹配、Taint 不能容忍。
Score软偏好，决定可行节点中哪个更好。典型例子：资源更均衡、镜像已存在、亲和性更高。
关键点：Filter 不通过的节点不会进入 Score；Filter 是可行性，Score 是优先级。
Q: 为什么调度器只看 requests，不看实时利用率？
为什么看 requests

requests 是 Kubernetes 的资源承诺和调度依据，稳定、可预测，并能和 ResourceQuota、QoS、驱逐机制对齐。

为什么不直接看实时利用率

实时利用率波动很大，直接用于调度容易导致抖动、迁移冲动和决策不稳定。

生产增强方式

如果要引入实时负载，通常通过自定义 Score 插件、Descheduler、离线画像或预测模型增强，而不是替代 requests。

Q: GPU 拓扑感知调度应该放在哪些扩展点？
Filter节点是否有足够 GPU、是否满足 MIG/整卡需求、是否满足同机硬约束。
Score优先选择 NVLink 拓扑更好、跨 NUMA 更少、模型缓存更近的节点。
Reserve需要预占具体 GPU 组合时维护调度器侧状态。
Unreserve后续阶段失败时回滚预占，避免缓存状态泄漏。
判断方式：不能违反的是 Filter；更好但不是必须的是 Score；涉及具体卡组并发冲突的是 Reserve。
Q: Gang Scheduling 为什么常用 Volcano/Kueue，而不是只靠原生调度器？
原生调度器局限

默认 kube-scheduler 更擅长逐 Pod 做调度决策，缺少“这一组 Pod 必须一起满足”的队列语义。

训练任务需求

分布式训练要求一组 Worker 同时达到最小可运行规模，否则部分 Pod 先启动也无法有效训练。

为什么用 Volcano/Kueue

Gang Scheduling 需要 PodGroup、最小成员数、队列、公平性、整体准入和资源回收等能力，Volcano/Kueue 已经提供成熟抽象。

Q: 一个 Pod 一直 Pending，怎么排查？
第一步：看直接原因

先看 Pod Events 和 scheduler 日志，确认 Pending 是资源不足、亲和性/反亲和性、taint/toleration、PVC 未绑定、配额限制还是调度器异常。

第二步：看集群状态

检查节点 allocatable、已有 Pod requests 占用、Pod priority、PDB、namespace quota、节点污点和标签。

GPU 专项

检查 device plugin 是否运行、nvidia.com/gpu 是否上报、MIG 配置是否正确、扩展资源是否已被占满。

排查顺序：Events → scheduler 日志 → 节点资源/约束 → 配额/PDB → GPU device plugin。

终止删除 Pod 后进入优雅终止：PreStop、SIGTERM、terminationGracePeriodSeconds、SIGKILLTerminating优雅终止影响滚动发布、抢占、drain 和服务无损下线

Pod Phase 与 Container State

Pod 的状态经常被混淆。Pod phase 是 Pod 级别的粗粒度状态，Container state 是容器级别的状态。排查问题时要结合 kubectl describe pod、Events、containerStatuses、日志一起看。

概念典型取值解释排查意义
Pod PhasePending、Running、Succeeded、Failed、UnknownPod 生命周期的高层状态只能粗略判断阶段，不能直接定位根因
Container StateWaiting、Running、Terminated单个容器当前状态Waiting reason 常见为 ImagePullBackOff、CrashLoopBackOff、CreateContainerConfigError
Pod ConditionsPodScheduled、Initialized、ContainersReady、Ready由 kubelet 和控制面维护的条件集合Ready 决定是否进入 Service endpoints
EventsFailedScheduling、Pulled、Created、Started、BackOff关键事件流水面试和生产排查中最先看的信息之一

探针：liveness / readiness / startup

探针是 Pod 稳定性面试最高频内容之一。核心是区分“进程是否活着”和“是否可以接流量”。错误配置探针会导致服务抖动、滚动发布卡住或流量打到未初始化实例。

探针判断什么失败后行为适用场景
livenessProbe容器是否还活着kubelet 重启容器死锁、进程假死、主循环卡住
readinessProbe容器是否可以接流量从 Service endpoints 移除，不重启容器依赖未就绪、模型未加载、缓存预热中
startupProbe慢启动应用是否完成启动失败超过阈值后重启容器；成功前抑制 liveness/readinessJava 大应用、模型服务加载权重、初始化时间长
Q: readinessProbe 和 livenessProbe 配错会怎样？
readiness 配得太严

实例会长期不进入 endpoints，Deployment 可能滚动发布卡住，Service 没有足够后端。

liveness 配得太严

应用初始化或短暂抖动时被 kubelet 频繁重启，形成 CrashLoopBackOff。

面试记忆：readiness 控流量，liveness 控重启，startup 保护慢启动。

Workload 控制器对比

控制器的本质是 Reconcile loop：不断比较期望状态和实际状态，并把实际状态收敛到期望状态。面试中经常要求解释不同 Workload 为什么存在，以及如何选择。

DaemonSet每个或部分节点运行一个 Pod日志采集、监控 agent、CNI、CSI、GPU device plugin适合节点级守护进程，新增节点自动部署

滚动发布、回滚与无损下线

Deployment 发布机制是基础设施面试常问的工程题。要说明流量如何从旧版本迁到新版本，以及如何避免把流量打到未就绪或正在退出的 Pod。

maxSurge
滚动发布时允许额外创建的新 Pod 数量或比例。
提高 maxSurge 可以加快发布，但会临时占用更多资源。
maxUnavailable
发布过程中允许不可用的 Pod 数量或比例。
设置过高会影响可用性，设置为 0 通常要求先拉起新实例再下线旧实例。
readinessProbe
新 Pod Ready 后才进入 Service endpoints。
模型服务常用 readiness 等待模型权重加载完成。
preStop + SIGTERM
删除旧 Pod 前先执行钩子并发送终止信号。
应用应停止接新请求、等待存量请求完成，再退出。
Q: 如何解释一次 Deployment 滚动发布？
版本控制

Deployment 创建新的 ReplicaSet，并逐步增加新 ReplicaSet 的副本数，同时减少旧 ReplicaSet 的副本数。

可用性控制

maxSurge 控制可额外创建多少新 Pod，maxUnavailable 控制最多允许多少 Pod 不可用。

流量控制

只有 readinessProbe 成功的 Pod 才会进入 Service endpoints；删除旧 Pod 时依赖 PreStop 和 terminationGracePeriodSeconds 做无损下线。

StatefulSet 与 AI 训练

StatefulSet 不只用于数据库，也常用于需要稳定身份的分布式训练和参数服务器架构。它保证 Pod 名称稳定，例如 trainer-0、trainer-1，配合 Headless Service 可以让 worker 之间互相发现。

能力StatefulSet 表现为什么重要
稳定 Pod 名称按 ordinal 命名：name-0、name-1、name-2训练任务可用 ordinal 推导 rank
稳定网络身份配合 Headless Service 得到稳定 DNSworker 可通过 DNS 互相发现
稳定存储volumeClaimTemplates 为每个 Pod 创建独立 PVC有状态服务重启后仍挂回自己的存储
有序启动/删除默认按 ordinal 顺序处理适合需要主从顺序或成员发现的系统

Service 与网络

Kubernetes 网络模型

Kubernetes 网络面试的核心不是背 CNI 名字，而是讲清楚三个基本要求：Pod 之间可以直接通信、Node 可以和 Pod 通信、Service 为动态 Pod 集合提供稳定访问入口。

对象网络语义实现依赖面试重点
Pod IP每个 Pod 有独立 IP，Pod 内容器共享网络命名空间CNI 插件分配 IP、配置路由和 veth同 Pod 内容器通过 localhost 通信，不同 Pod 通过 Pod IP 通信
Node 网络节点之间可路由，承载跨节点 Pod 通信Overlay、BGP、云厂商 VPC 或 underlay跨节点通信是否封装取决于 CNI 实现
Service IP为一组 Pod 提供稳定虚拟入口kube-proxy 或 eBPF 数据面Service 不等于反向代理进程，通常是节点上的转发规则
DNS把 service name 解析为 ClusterIP 或 Pod IPCoreDNS + kube-dns serviceDNS 故障会表现为服务名不通但 IP 直连可能正常

Pod 跨节点通信链路

一个 Pod 访问另一个节点上的 Pod 时，流量通常从容器网络命名空间出发，经 veth 到宿主机，再由 CNI 配置的路由、隧道或 eBPF 程序转发到目标节点，最后进入目标 Pod。

  1. 源容器发包到目标 Pod IP。
  2. 数据包从容器 eth0 进入 veth pair 的宿主机端。
  3. 宿主机根据 CNI 配置的路由或 eBPF 逻辑决定下一跳。
  4. 如果是 overlay CNI，可能封装 VXLAN/Geneve 后跨节点传输。
  5. 目标节点解封装或路由转发到目标 Pod 的 veth。
  6. 目标容器收到数据包。
Q: CNI 到底负责什么？
创建时

kubelet 创建 Pod sandbox 后调用 CNI 插件，为 Pod 分配 IP、创建 veth、配置路由、配置网络命名空间。

删除时

Pod 删除时 kubelet 调用 CNI DEL，释放 IP、清理网络设备和相关规则。

CNI 解决 Pod 网络接入问题，Service 转发通常由 kube-proxy 或 eBPF 数据面解决。

Service 类型对比

Service 类型作用访问范围典型场景
ClusterIP集群内部虚拟 IP集群内微服务内部访问，默认类型
NodePort每个节点开放固定端口，转发到 Service集群外可通过任意节点 IP + 端口访问简单暴露、测试环境，不适合复杂生产入口
LoadBalancer创建云厂商负载均衡器并转发到 Service集群外云上生产入口
ExternalName把 Service 名称映射到外部 DNS 名称依赖外部 DNS集群内用统一 service name 访问外部服务
Headless ServiceclusterIP: None，不分配虚拟 IPDNS 直接返回后端 Pod IPStatefulSet、数据库、分布式训练 worker 直连

kube-proxy：iptables、IPVS 与 eBPF

Service 的转发能力传统上由 kube-proxy 维护节点规则实现。面试中经常问 iptables 和 IPVS 的区别，近年来也会追问 eBPF 数据面。

模式实现方式优点不足
iptables生成大量 iptables 规则，用随机概率做负载均衡成熟、依赖少、兼容性强规则多时更新和匹配成本高，可观测性一般
IPVS利用 Linux IPVS 内核负载均衡能力性能更好，支持更多调度算法依赖 IPVS 模块，问题排查需要理解 ipvsadm
eBPF在内核 hook 点运行 eBPF 程序转发性能高、可观测性强、可绕过部分 iptables 路径依赖 CNI/内核能力，排查方式不同
Q: Service 是不是一个真正的代理进程？
传统实现

不是。ClusterIP 通常不是某个进程监听的真实 IP，而是 kube-proxy 在每个节点维护的转发规则。

流量路径

访问 ClusterIP 时，内核网络栈命中 iptables/IPVS/eBPF 规则，把流量转发到某个 Endpoint Pod。

Service 是抽象，kube-proxy/eBPF 是数据面实现。

CoreDNS 与服务发现

Kubernetes 中服务名解析通常由 CoreDNS 提供。Pod 的 DNS 配置会指向 kube-dns Service，CoreDNS 根据 Service、EndpointSlice、Pod 等对象生成解析结果。

查询形式含义返回结果
svc-name同 namespace 下服务ClusterIP 或 headless 后端 Pod IP
svc-name.namespace指定 namespace 下服务对应 Service 解析结果
svc-name.namespace.svc.cluster.local完整集群域名最明确，排查 DNS 时常用

先测 DNSnslookup service-name，确认是否能解析。
再测 ClusterIP直接 curl ClusterIP:port，绕过服务名。
再测 Endpoint直接访问 Pod IP:containerPort，绕过 Service 转发。
最后看规则检查 endpoints、EndpointSlice、kube-proxy、NetworkPolicy。

NetworkPolicy

NetworkPolicy 用于限制 Pod 间东西向流量。它本身只是 Kubernetes API 对象，是否真正生效取决于 CNI 是否支持 NetworkPolicy。

概念说明高频误区
默认允许没有 NetworkPolicy 时，Pod 通信默认全允许创建一个 policy 后，被选中的 Pod 会进入默认拒绝模型
podSelector选择被保护的 Pod不是选择访问来源，而是选择策略作用对象
ingress / egress分别控制入站和出站只写 ingress 不会自动限制 egress
CNI 支持Calico、Cilium 等支持策略如果 CNI 不支持，创建 policy 也不生效

存储与 CSI

Kubernetes 存储体系总览

Kubernetes 把“应用如何声明存储需求”和“底层如何创建/挂载具体存储”拆开。面试时要围绕 PV、PVC、StorageClass、CSI 之间的关系来讲。

对象角色谁创建面试重点
VolumePod spec 中声明的挂载来源用户或控制器生命周期通常跟 Pod 绑定，类型很多
PersistentVolumeClaim (PVC)用户对存储的申请用户或 StatefulSet volumeClaimTemplates声明容量、访问模式、StorageClass
PersistentVolume (PV)集群中的真实存储资源抽象管理员静态创建或 provisioner 动态创建PV 与 PVC 绑定后供 Pod 挂载
StorageClass动态供给模板管理员定义 provisioner、参数、reclaimPolicy、volumeBindingMode
CSI Driver存储厂商插件平台管理员部署负责创建、挂载、扩容、快照等存储操作

PV/PVC 绑定流程

  1. 用户创建 PVC，声明所需容量、访问模式和 StorageClass。
  2. 如果存在匹配 PV，控制器将 PVC 与 PV 绑定。
  3. 如果没有现成 PV，且 StorageClass 支持动态供给，external-provisioner 调用 CSI 创建真实存储并生成 PV。
  4. Pod 引用 PVC 后，调度器需要考虑 volume 约束，例如 zone、node affinity。
  5. Pod 调度到节点后，kubelet 通过 CSI node plugin 挂载 volume 到容器。
Q: PVC Pending 常见原因有哪些？
没有匹配 PV静态 PV 容量、accessMode、storageClassName 不匹配。
动态供给失败CSI provisioner 异常、权限不足、云盘配额不足。
WaitForFirstConsumerStorageClass 等待 Pod 调度后再创建 PV，PVC 可能暂时 Pending。
拓扑限制存储所在 zone 与 Pod 可调度节点不一致。

访问模式与回收策略

字段常见取值解释注意事项
accessModesReadWriteOnce单个节点读写挂载云盘最常见；不是单个 Pod，而是单个节点
accessModesReadOnlyMany多个节点只读挂载适合共享只读数据
accessModesReadWriteMany多个节点读写挂载需要 NFS、CephFS、NAS 等支持
reclaimPolicyDeletePVC 删除后底层存储也删除动态供给常用，危险点是误删数据
reclaimPolicyRetainPVC 删除后保留 PV 和底层数据适合重要数据，但需要人工回收

StorageClass 关键字段

字段作用面试解释
provisioner指定由哪个 CSI 或内置 provisioner 创建存储例如云厂商块存储、Ceph、NFS 等
parameters传给 provisioner 的参数磁盘类型、IOPS、文件系统类型、加密等
reclaimPolicyPV 回收策略Delete 自动删除底层资源，Retain 保留数据
allowVolumeExpansion是否允许 PVC 扩容扩容还需要底层 CSI 支持
volumeBindingModeImmediate 或 WaitForFirstConsumer后者能结合 Pod 调度选择合适 zone，避免存储和计算不在同一可用区
Q: WaitForFirstConsumer 为什么重要？
Immediate 的问题

Immediate 会在 PVC 创建时立刻创建 PV。如果云盘先被创建在 zone-a，而 Pod 后续只能调到 zone-b，就会出现存储和计算拓扑冲突。

WaitForFirstConsumer 的价值

等到 Pod 参与调度时，调度器结合节点拓扑和存储拓扑决定 PV 创建在哪个 zone，减少调度失败。

一句话：延迟绑定让存储创建跟 Pod 调度一起考虑，避免跨可用区挂载失败。

CSI 工作机制

CSI 把 Kubernetes 与存储厂商解耦。它通常由 Controller 插件和 Node 插件组成，配合 external-provisioner、external-attacher、external-resizer、external-snapshotter 等 sidecar 工作。

组件位置职责典型操作
CSI Controller Plugin控制面部署，通常是 Deployment管理存储卷生命周期CreateVolume、DeleteVolume、ControllerPublishVolume
CSI Node Plugin每个节点部署，通常是 DaemonSet负责节点本地挂载和卸载NodeStageVolume、NodePublishVolume、NodeUnpublishVolume
external-provisionersidecar监听 PVC 并创建 PV动态供给
external-attachersidecar处理云盘 attach/detach把云盘挂到节点
external-resizersidecar处理 PVC 扩容扩容底层卷和文件系统

常见 Volume 类型

类型生命周期用途风险
emptyDir随 Pod 创建和删除临时缓存、容器间共享临时文件Pod 删除后数据消失
hostPath绑定节点本地路径系统组件访问宿主机文件，如日志、device plugin强节点耦合，有安全风险，不适合普通业务随意使用
configMap volume来自 ConfigMap挂载配置文件配置更新到容器内有延迟；subPath 挂载不会自动更新
secret volume来自 Secret挂载证书、token、密码要注意权限、最小化暴露和审计
PVC volume跟 PVC/PV 生命周期相关持久化数据需要考虑绑定、拓扑、扩容、回收策略

StatefulSet 存储模式

StatefulSet 的 volumeClaimTemplates 会为每个 Pod 创建独立 PVC。例如 mysql-0 对应自己的 PVC，Pod 重建后仍然挂回自己的存储。

Q: StatefulSet 删除后 PVC 会不会自动删除？
传统行为

StatefulSet 删除时，PVC 通常不会自动删除，以避免误删有状态数据。

新能力

较新版本 Kubernetes 支持 persistentVolumeClaimRetentionPolicy，可以控制 StatefulSet 删除或缩容时 PVC 的保留策略。

面试记忆：Pod 可重建，PVC 要谨慎保留；有状态数据默认不应因为控制器删除而丢失。

Pod Pending 排查

Pending 不是单一问题，它可能发生在调度前、调度失败、PVC 未绑定、镜像拉取前等待等多个阶段。最可靠入口是 kubectl describe pod 里的 Events。

FailedScheduling
调度器无法找到合适节点。
检查 CPU/Memory/GPU requests、nodeSelector、affinity、taints、topology spread、quota。
PVC Pending
Pod 引用的 PVC 尚未绑定。
检查 StorageClass、PV 绑定、CSI provisioner、WaitForFirstConsumer、zone。
Unschedulable
调度硬约束无法满足。
重点看 Events 中 scheduler 给出的节点过滤原因。
GPU Pending
GPU 扩展资源不足或未上报。
检查 nvidia-device-plugin、node allocatable、MIG 配置、资源名是否一致。
Q: Pod 一直 Pending，你怎么回答排查流程？
先看事件

先 describe pod，看 Events 是否是 FailedScheduling、FailedMount、PVC Pending 或 quota 限制。

再看资源和约束

如果是调度失败，检查 requests、节点 allocatable、taints/tolerations、nodeSelector、affinity、topologySpreadConstraints。

专项检查

如果是 GPU Pod，检查 device plugin 和 nvidia.com/gpu 上报；如果是有状态 Pod，检查 PVC/PV/StorageClass。

面试顺序：Events → 资源 → 调度约束 → PVC/存储 → GPU/device plugin → scheduler 日志。

CrashLoopBackOff 排查

CrashLoopBackOff 表示容器启动后不断退出，kubelet 按退避策略重启容器。不要只看当前日志，还要看上一次崩溃前的日志。

安全与准入

API Server 请求链路：认证、鉴权、准入

Kubernetes 安全治理的核心入口是 API Server。所有写操作都要经过认证、鉴权、准入控制，再持久化到 etcd。面试中要能把这条链路讲清楚。

阶段问题典型机制面试要点
Authentication你是谁？证书、Bearer token、ServiceAccount token、OIDC认证只确认身份，不决定能做什么
Authorization你能做什么？RBAC、Node、Webhook、ABAC最常见是 RBAC，按 verb/resource/namespace 授权
Admission这个请求是否允许或需要修改？内置 admission、MutatingWebhook、ValidatingWebhook、ValidatingAdmissionPolicy准入发生在鉴权之后、写入 etcd 之前
Persistence状态如何保存？etcd最终状态写入 etcd 后，控制器通过 watch 感知变化

RBAC：Role、ClusterRole、Binding

RBAC 是 Kubernetes 权限面试最高频部分。关键是区分“权限集合”和“把权限绑定给谁”。

对象作用域作用示例
Rolenamespace 内定义一组权限规则允许读取 default namespace 下的 pods
ClusterRole集群级定义集群级或可复用权限规则允许读取 nodes，或作为多个 namespace 的通用权限模板
RoleBindingnamespace 内把 Role 或 ClusterRole 绑定给用户、组、ServiceAccount把 read-pods 权限给某个 SA
ClusterRoleBinding集群级把 ClusterRole 绑定到集群范围给集群管理员权限
Q: Role 和 ClusterRole 的区别是什么？
Role只能定义 namespace 作用域内的资源权限。
ClusterRole可以定义集群级资源权限，也可以作为跨 namespace 复用模板。
RoleBinding可以绑定 Role，也可以绑定 ClusterRole，但权限只在该 namespace 生效。
ClusterRoleBinding绑定后在集群范围生效，要谨慎使用。

ServiceAccount 与 Pod 身份

Pod 访问 API Server 时通常使用 ServiceAccount 身份。ServiceAccount token 会以投射卷形式挂载到 Pod 中，应用可以用它调用 Kubernetes API。

概念说明高频点
ServiceAccount面向 workload 的身份不同于用户账号，常用于 Pod 内访问 API Server
automountServiceAccountToken是否自动挂载 token不需要访问 API 的 Pod 可关闭，降低凭证泄漏风险
TokenRequest按需颁发短期 token新版本推荐短期、可轮转 token，而非长期 secret token
RBAC Binding给 ServiceAccount 授权最小权限原则，只授予必要 verb/resource

Admission Controller

Admission Controller 可以在对象写入 etcd 前对请求进行默认值注入、校验、拒绝或变更。它是平台治理的重要抓手。

类型作用典型场景
Mutating Admission修改请求对象自动注入 sidecar、默认资源 requests/limits、补充 labels/annotations
Validating Admission校验请求对象禁止 privileged、限制镜像仓库、要求必须设置 requests
ValidatingAdmissionPolicy基于 CEL 的内置校验策略不用部署 webhook 即可做部分策略校验
Webhook调用外部服务做变更或校验灵活强，但要注意可用性、超时和失败策略
Q: Admission Webhook 有什么生产风险？
可用性风险

Webhook 服务不可用时，API 写请求可能被阻塞或失败，取决于 failurePolicy。

性能风险

Webhook 增加 API Server 请求延迟，高并发集群下要控制超时和处理耗时。

治理建议

设置合理 timeoutSeconds、namespaceSelector/objectSelector、failurePolicy，并监控 webhook 错误率和延迟。

ResourceQuota 与 LimitRange

多租户集群必须做资源治理，否则单个团队或任务可能耗尽整个集群资源。ResourceQuota 管 namespace 总量，LimitRange 管单个对象的默认值和上下限。

对象控制粒度能限制什么常见用途
ResourceQuotanamespace 总量CPU/Memory requests 和 limits、PVC 数量、Service 数量、Pod 数量、GPU 扩展资源限制租户总资源消耗
LimitRange单个 Pod/Container/PVC默认 requests/limits、最小/最大资源、limit/request ratio防止用户不设置 requests 或设置过大/过小
Q: ResourceQuota 和 LimitRange 怎么配合？
LimitRange

给单个容器设置默认 requests/limits 和上下限，避免用户漏填或填得不合理。

ResourceQuota

限制 namespace 总资源使用量，确保一个租户不能无限创建 Pod 或 PVC。

一句话：LimitRange 管单个对象，ResourceQuota 管整个 namespace。

Pod Security 与运行时安全

安全面试常问 privileged、hostPath、hostNetwork、capabilities、runAsNonRoot 等字段。重点是能解释风险，而不是只背字段名。

字段/能力风险治理建议
privileged容器获得接近宿主机 root 的能力普通业务禁止，系统组件严格审批
hostPath访问宿主机文件，可能读写敏感路径限制路径白名单，尽量用 PVC 替代
hostNetwork共享宿主机网络命名空间端口冲突、网络隔离减弱，谨慎使用
capabilities额外 Linux capabilities 扩大权限默认 drop ALL，只按需添加
runAsNonRootroot 运行增加逃逸风险要求非 root 用户运行
readOnlyRootFilesystem根文件系统可写增加篡改风险尽可能只读，临时写入使用 emptyDir

CRD 与 Operator

CRD 和 Operator 是 Kubernetes 扩展能力的核心。CRD 只是扩展 API 类型；Operator 是围绕 CRD 实现自动化运维逻辑的控制器。

概念作用面试解释
CRD注册自定义资源类型让 API Server 能存储和校验新的对象，例如 TrainingJob、ModelService
Custom ResourceCRD 的实例用户声明期望状态，例如副本数、模型路径、资源需求
Controller监听资源变化并执行 reconcile把实际状态收敛到期望状态
Operator领域化控制器把复杂系统的部署、升级、扩缩容、故障恢复自动化
Q: 为什么 Operator 适合复杂有状态服务？
复杂流程

数据库、训练平台、模型服务往往有备份、扩容、主从切换、版本升级等领域流程，单靠 Deployment 难以表达。

Reconcile

Operator 通过 Informer watch 资源变化，持续执行 reconcile，把实际状态修正到用户声明的期望状态。

CRD 定义 API，Operator 实现自动化运维。

GPU Device Plugin

Device Plugin 是 kubelet 的插件机制，用于把 GPU 这种非标准资源接入 Kubernetes。NVIDIA GPU 通常通过 NVIDIA device plugin 上报为 nvidia.com/gpu 扩展资源。

  1. NVIDIA device plugin 以 DaemonSet 形式运行在 GPU 节点上。
  2. 插件发现本机 GPU 设备，并通过 gRPC 向 kubelet 注册资源名，例如 nvidia.com/gpu。
  3. kubelet 把 GPU 数量写入 Node 的 allocatable/capacity。
  4. 用户在 Pod requests/limits 中声明 nvidia.com/gpu: 1。
  5. scheduler 根据节点 allocatable 和已分配 requests 选择节点。
  6. Pod 落到节点后，kubelet 调用 device plugin Allocate，拿到设备路径、环境变量、mount 信息。
  7. 容器运行时把对应 GPU 注入容器。
Q: 为什么 nvidia.com/gpu 通常只能整数分配？
Extended Resource 语义

Kubernetes 扩展资源按离散资源计数，调度器只做 requests 级别的整数扣减。

设备隔离语义

一张物理 GPU 作为一个设备分配给容器时，默认是整卡语义；调度器并不知道卡内显存、SM、带宽如何切分。

共享方案

如果要细粒度共享，需要 MIG、MPS、time-slicing 或厂商/平台自定义方案把资源抽象成新的可调度单元。

MIG、MPS、time-slicing 对比

方案隔离粒度适合场景优点不足
MIG硬件级切分 GPU 实例A100/H100 等支持 MIG 的推理、多租户隔离隔离更强，资源边界清晰，可作为离散设备上报切分规格固定，重配置成本高，不适合所有训练场景
MPS多个进程共享同一 GPU 上下文小模型推理、提高并发利用率减少上下文切换，提高小任务吞吐隔离弱，显存和错误隔离需要额外治理
time-slicing时间片共享 GPU低优先级任务、开发测试、小推理任务接入简单，提高卡利用率性能抖动明显，不是强隔离，显存仍可能互相影响
Q: 面试中如何比较 MIG、MPS、time-slicing？
MIG硬件隔离更强，适合多租户推理和明确规格切分。
MPS偏运行时共享，提高小 kernel 或小推理任务并发。
time-slicing偏调度共享，简单但抖动更大。
选择原则强隔离选 MIG，吞吐共享看 MPS，开发测试可用 time-slicing。

Topology Manager 与拓扑感知调度

AI 训练对拓扑敏感：GPU 与 GPU 之间是否有 NVLink，GPU 与 NIC 是否同 NUMA，CPU 与 GPU 是否跨 socket，都会影响数据加载和通信效率。

机制工作位置解决什么局限
Topology Managerkubelet 节点侧协调 CPU Manager、Device Manager、Memory Manager 的 NUMA 对齐发生在节点内资源分配阶段，不负责跨节点选择
CPU Managerkubelet 节点侧为 Guaranteed Pod 分配独占 CPU core主要解决 CPU 绑定，不理解 GPU 通信拓扑
Device Managerkubelet 节点侧管理 device plugin 上报设备并调用 Allocate默认调度器只看到资源数量，不知道具体 GPU 拓扑
自定义调度插件scheduler 控制面跨节点选择拓扑更优的节点需要维护拓扑元数据和调度器缓存一致性
Q: Topology Manager 和自定义调度插件分别解决什么？
Topology Manager

节点内做资源对齐，例如 CPU、内存、设备尽量在同一个 NUMA node，避免 kubelet 分配阶段产生差拓扑。

自定义调度插件

调度阶段选择哪个节点更好，例如优先选择 NVLink 完整、GPU/NIC 拓扑更适合训练任务的节点。

一句话：调度插件选节点，Topology Manager 在节点内分配资源。

Gang Scheduling 与分布式训练

分布式训练通常需要一组 Pod 同时运行。例如 8 个 worker 中只有 2 个启动，训练无法有效开始，却已经占用了 GPU。Gang Scheduling 的目标是“要么一起运行，要么都不占资源”。

概念含义为什么重要
PodGroup一组需要整体调度的 Pod表达分布式任务的整体性
minAvailable最小可运行 Pod 数不足则不放行，避免部分 worker 空占资源
Queue任务队列支持租户、公平性和资源配额管理
Preemption / Reclaim抢占或回收资源高优先级训练任务或配额回收需要
Q: 原生 kube-scheduler 能不能做 Gang Scheduling？
理论上

可以通过 Permit、Reserve 等插件实现部分整体准入逻辑。

生产上

Gang Scheduling 还需要 PodGroup、队列、公平性、配额、资源回收、任务生命周期等能力，因此通常使用 Volcano、Kueue 或平台自研调度系统。

面试回答：原生框架能扩展，但完整批调度语义通常交给 Volcano/Kueue。

Kueue 与 Volcano

系统定位核心能力适用场景
KueueKubernetes 原生批任务队列管理ClusterQueue、LocalQueue、ResourceFlavor、admission、quota borrowing批任务准入控制、配额、公平共享，与 Job、RayJob、MPIJob 等集成
Volcano批计算调度系统PodGroup、Queue、Gang、Fair Share、Preemption、多种调度插件AI、大数据、HPC 等批任务调度
原生 scheduler通用 Pod 调度器Filter、Score、Bind、Preemption、插件框架在线服务、通用 workload、基础调度

面试时不要简单说“Volcano 更强”。更准确的表述是：原生 scheduler 是逐 Pod 通用调度器，Kueue/Volcano 提供批任务层面的队列、准入和整体调度语义。

Q: Headless Service 为什么适合分布式训练？
直连需求

NCCL、Parameter Server、MPI 等训练通信需要 worker 之间直接连接，而不是通过 Service 负载均衡随机转发。

稳定发现

Headless Service 配合 StatefulSet 会返回每个 Pod 的稳定 DNS，worker 可以解析其他 worker 地址。

一句话：Headless Service 用于成员发现，不用于负载均衡。

AI 平台要同时考虑资源利用率、公平性、隔离性和任务优先级。单纯 ResourceQuota 只能限制上限，不足以表达队列、公平共享、借用、抢占和回收。

Q: 一个 Pod 从创建到运行经历了什么？
  1. 用户提交 Pod 到 API Server
  2. API Server 验证、持久化到 etcd
  3. Scheduler 通过 Informer 监听到新的未绑定 Pod
  4. Scheduler 执行 Filter → Score → Reserve → Bind
  5. Bind 结果写入 API Server（Pod.spec.nodeName）
  6. 目标节点的 kubelet 通过 Informer 发现分配给自己的 Pod
  7. kubelet 调用 CRI 创建容器，调用 CNI 配置网络，调用 CSI 挂载存储
  8. 容器启动，kubelet 上报状态到 API Server
Q: Informer 机制是什么？为什么不直接轮询 API Server？
机制

Informer 是 client-go 提供的本地缓存 + Watch 机制。首次 List 获取全量数据存入本地 Store，之后通过 Watch 接收 Added/Modified/Deleted 增量事件。

实时性事件驱动，而不是定期轮询。
性能减少 API Server 压力，避免大量重复查询。
可靠性Watch 断线后可以通过 ResourceVersion 续接。
Informer = List/Watch + 本地缓存 + 事件回调 + WorkQueue。
Q: etcd 为什么是性能瓶颈？怎么优化？
为什么是瓶颈

etcd 是集群唯一的持久化存储，写操作需要经过 Raft 共识，至少过半节点确认后才算成功。

大集群压力来源

event、configmap、secret、Pod 状态等频繁写入会增加 fsync 和共识延迟。

磁盘使用 SSD 降低 fsync 延迟。
隔离将 event 分离到独立 etcd 集群。
缓存API Server 启用 watch cache。
维护合理设置 compaction，控制数据库体积。
Q: 如何实现自定义调度器？有几种方案？

三种方案：

  1. Scheduler Plugin（推荐）：实现 Scheduling Framework 的扩展点接口（Filter/Score/Reserve 等），编译进调度器二进制。优点：性能好，原生集成
  2. Scheduler Extender：HTTP webhook 方式，调度器在 Filter/Score 后调用外部服务。优点：不需要重编译调度器；缺点：网络延迟，不支持所有扩展点
  3. 完全自定义调度器：独立二进制，通过 Pod 的 schedulerName 字段指定。优点：完全自由；缺点：不能复用默认插件，维护成本高
Q: K8s GPU 调度的挑战和解决方案？

核心挑战：

  1. 整数分配：nvidia.com/gpu 是 Extended Resource，只能整数分配，不支持 0.5 GPU
  2. 拓扑无感：默认调度器不感知 GPU 间的 NVLink 拓扑，可能把需要通信的 Pod 放到不同 PCIe 树
  3. 无法修改：admit 后 GPU 数量不可调整

解决方案：

  1. GPU 共享：MPS / MIG / 时间片（需要 device plugin 配合）
  2. 拓扑感知：Topology Manager + 自定义 Score 插件
  3. 弹性训练：Elastic Horovod / PyTorch Elastic（运行时加减 worker）
Q: Device Plugin 怎么工作？
定位

Device Plugin 是 kubelet 的扩展机制，用于管理 GPU、FPGA、RDMA 等非标准硬件资源。

  1. Device Plugin 启动后通过 gRPC 向 kubelet 注册资源名称，例如 nvidia.com/gpu。
  2. kubelet 向 API Server 上报节点 allocatable 中的扩展资源数量。
  3. 调度器基于 Pod requests 和节点 allocatable 做过滤和打分。
  4. Pod 调度到节点后，kubelet 调用 Device Plugin 的 Allocate 方法获取设备信息。
  5. 设备路径、环境变量等信息被注入容器。
NVIDIA k8s-device-plugin 就是典型实现：上报 GPU 资源，并在容器启动前分配具体设备。
Q: Headless Service 和 ClusterIP Service 的区别？
ClusterIP有虚拟 IP，由 kube-proxy 做服务转发和负载均衡。
HeadlessclusterIP: None，不分配虚拟 IP，DNS 直接返回后端 Pod IP。
AI Infra 用途

分布式训练需要 worker 之间直接通信，例如 NCCL AllReduce。Headless Service 可以让每个 Pod 解析其他 Pod 的 IP，建立点对点连接。
