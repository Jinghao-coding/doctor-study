Q: Volcano 的核心设计？它的局限性？

Volcano 的核心是 PodGroup + Queue + Policy：PodGroup 定义 Gang scheduling 语义（minMember），Queue 管理多租户配额，Policy（Gang/DRF/Priority）定义调度策略。

Volcano 的局限性：(1) 配额是静态的（min/max），不支持连续保障度信号；(2) 没有干扰感知合用能力；(3) 不做运行时间预测；(4) 抢占是简单的优先级抢占，不考虑沉没成本。在需要弹性配额、干扰感知等能力时，需从 Scheduling Framework 原生构建，获得更大的灵活性。

Q: Kueue 的 ResourceFlavor 是什么概念？

ResourceFlavor 抽象了不同类型的资源——比如 A100 GPU 是一种 Flavor，H100 GPU 是另一种。ClusterQueue 可以关联多个 Flavor，每个 Flavor 有独立的配额。Workload 提交时可以指定 Flavor 偏好，Kueue 根据配额和排队情况分配。这对异构 GPU 集群很有用。

大模型训练通常组合使用 DP + TP + PP。典型配置（8 节点 × 8 GPU = 64 GPU 训练 175B 模型）：

  • TP = 8（节点内 8 卡 NVLink 互联，通信量大需要高带宽）
  • PP = 4（跨 4 个节点做流水线，通信量小，可以走 InfiniBand）
  • DP = 2（两组流水线做数据并行，每个 micro-batch 结束同步梯度）
Q: ZeRO 三个阶段分别做了什么？

训练一个模型需要存储三类数据：优化器状态（如 Adam 的 momentum + variance，每参数 12 字节）、梯度（每参数 4 字节）、模型参数（FP16 每参数 2 字节）。

  • ZeRO-1：切分优化器状态。每张卡只存 1/N 的优化器状态。省最多内存的部分
  • ZeRO-2：切分优化器状态 + 梯度。梯度 reduce 后只保留对应分片
  • ZeRO-3：切分优化器状态 + 梯度 + 参数。前向/反向时按需 AllGather 参数，用完释放。通信量最大但内存最省

ZeRO-3 + 64 卡可以训练 1T 参数的模型（每卡只存 1/64 参数）。

Q: 数据并行的梯度同步有什么优化？

(1) 梯度压缩——只传 top-k 梯度或用低精度传输。(2) 梯度累积——多个 micro-batch 的梯度在本地累积后再同步，减少通信次数。(3) 通信-计算重叠——反向传播过程中，已计算完的层立即开始 AllReduce，不等所有层都算完。(4) Ring AllReduce——通信量 2(N-1)/N × data_size，线性扩展。

Checkpoint 策略

  • 周期性 checkpoint：每 N 步保存一次完整状态（模型 + 优化器 + 数据迭代器位置）
  • 异步 checkpoint：后台线程写入存储，不阻塞训练
  • 增量 checkpoint：只保存变化部分，减少 I/O
  • 分布式 checkpoint：每张卡只保存自己的分片，并行写入

大模型的 checkpoint 可能上百 GB，存储带宽和频率是 trade-off：太频繁影响训练速度，太稀疏丢失进度多。

面试问答

Q: GPU 利用率为什么普遍很低？怎么提升？

原因：(1) 碎片化——剩余 GPU 分散在不同节点，大任务放不进去。(2) I/O 瓶颈——数据加载阶段 GPU 空闲。(3) 配额闲置——有配额但没任务。(4) 通信开销——AllReduce 时 GPU 等待网络。

提升方法：(1) Bin Packing 减少碎片；(2) 弹性配额借用（DRA）解决配额闲置；(3) MPS 合用解决 I/O 阶段空闲；(4) 通信-计算重叠。

Q: 如何监控 GPU 集群？

三层监控：

  1. 硬件层：DCGM（Data Center GPU Manager）收集 GPU 温度、功耗、ECC 错误、SM 利用率、显存使用
  2. 调度层：调度延迟、排队深度、配额使用率（QAD）、抢占频率
  3. 任务层：训练 loss 曲线、吞吐（samples/s）、GPU 利用率、checkpoint 频率

通常 DCGM → Prometheus → Grafana 的技术栈。
