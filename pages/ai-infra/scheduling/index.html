Q: SRTF 和 SJF 的本质区别？什么时候用 SRTF？

SJF 按总执行时间排序，不可抢占——一旦开始执行就必须跑完。SRTF 按剩余时间排序，可抢占——新来的短作业可以打断正在执行的长作业。当作业到达时间不确定时 SRTF 更优：比如多 agent 工作流中，不断有新 stage 到达，SRTF 可以让新来的短 stage 立即执行，避免被长 stage 阻塞。代价是需要抢占机制和更精确的剩余时间预测。

Q: SJF 为什么最优？会有什么问题？

可以数学证明：SJF 最小化平均等待时间（把短作业排前面，它们的等待时间短，长作业无论排哪里都要等，放后面对总和影响最小）。问题是饥饿——如果短作业源源不断到达，长作业可能永远轮不到。解决办法：老化机制（aging），等待时间越长优先级越高；或者混合策略，如词典序先看保障度再看时间。

公平性调度

DRF（Dominant Resource Fairness）

多维资源（CPU + 内存 + GPU）场景下的公平分配算法。核心思想：每个用户的主导资源（demand/capacity 比值最大的资源维度）应该被均等分配。

例子：集群有 100 CPU 和 100GB 内存。用户 A 的任务需要 (2CPU, 8GB)，用户 B 的任务需要 (4CPU, 2GB)。A 的主导资源是内存（8%），B 的主导资源是 CPU（4%）。DRF 让两者的主导资源份额相等。

性质：共享激励（sharing incentive）、无嫉妒（envy-free）、帕累托效率。

QAD vs DRF：DRF 追求均等分配，不区分保障和弹性。QAD 允许超额分配（QAD > 1）但可回收，更适合有配额保障需求的场景。

Max-Min Fairness

按需分配，每个用户至少获得 1/N 份额，不需要更多的用户把多余份额让给需要的人。递归地最大化最小分配。

GPU 集群特有的调度策略

Gang Scheduling

分布式训练任务的所有 worker 必须同时被调度，要么全部启动，要么全不启动（all-or-nothing）。原因：如果只启动部分 worker，NCCL AllReduce 会阻塞等待其余 worker，已启动的 GPU 完全空转。

实现：Volcano 的 PodGroup + minMember 机制。调度器检查集群是否能同时满足 PodGroup 中所有 Pod 的资源需求。不能则整组等待。

Bin Packing vs Spread

策略原理适用场景
Bin Packing尽量把 Pod 塞满已有节点，减少碎片提高资源利用率，适合计算密集任务
Spread尽量把 Pod 分散到不同节点高可用，避免单点故障

GPU 集群通常用 Bin Packing：GPU 是昂贵资源，碎片化（一个节点剩 1 GPU，另一个节点也剩 1 GPU，但需要 2 GPU 的任务无法调度）是大问题。

弹性训练（Elastic Training）

运行中的训练任务可以动态增减 worker 数量，不需要重启。PyTorch Elastic（torchrun）和 Elastic Horovod 支持。优势：(1) 有空闲 GPU 时扩展加速训练；(2) 需要回收 GPU 时缩减而非杀死。挑战：数据并行 batch size 变化、learning rate 需要调整。

Backfill Scheduling

当大作业等待资源时，小作业如果能在大作业预期开始前完成，就"见缝插针"地先执行。SLURM 和 PBS 常用策略。需要预测作业执行时间。

调度算法面试问答

Q: Head-of-line blocking 怎么解决？

三种思路：(1) 预测驱动排序——SRTF/SJF 让短任务先执行，减少被长任务阻塞的概率。(2) 抢占——长任务阻塞时强制让位给高优先级任务。(3) 多队列——不同类型任务分开排队，互不干扰。实际系统中常常同时使用多种：SRTF 排序 + 抢占 + 分队列。

Q: 抢占的代价有哪些？怎么降低？

代价：(1) 进度浪费——被抢占作业已完成的计算全部丢失（除非有 checkpoint）。(2) 重启开销——重新排队、加载模型/数据。(3) 系统开销——保存状态、清理资源。降低代价：(1) checkpoint 机制减少进度损失；(2) 代价基抢占选择沉没成本最小的牺牲者；(3) 在自然间隔（如 stage 边界）抢占，零中断。

Q: 多维资源调度的挑战？

GPU 集群的资源是多维的——CPU、内存、GPU、网络带宽。挑战：(1) 碎片化——某些维度剩余很多，但另一个维度不够，整个节点不可用。(2) 耦合性——GPU 任务通常也需要大量 CPU 做数据预处理。(3) 异构性——不同 GPU 型号性能差异大。DRF 从理论上解决公平性，但实际中还需要拓扑感知（NVLink 拓扑）和亲和性约束。

Q: 调度延迟和调度质量的 trade-off？

更好的调度决策需要更多信息和更多计算，但用户不想等太久。解决：(1) 两阶段调度——Filter 快速排除明显不行的，Score 只在少量候选中精选；(2) 缓存——Informer 本地缓存避免每次查 API Server；(3) 近似算法——不需要最优解，足够好就行；(4) 异步——Bind 阶段异步执行，不阻塞下一个 Pod 的调度。
