ICDCS 2026 Maestro

多 Agent 请求为什么难调度

我介绍的这项工作是 Maestro，研究的是多模型、多 Agent 工作流在资源受限 GPU 集群里的推理调度。一个用户请求往往不是只调用一次模型，而是由规划、搜索、分析、总结等多个阶段组成。不同阶段可能用不同模型，有的要等工具返回，有的连续生成很长的推理内容，所以它们的时间和显存需求差异很大。

这里有两个相互影响的问题。一个是排队：后台长任务可能挡住用户正在等待的短请求，而且上游慢一点，下游就全部跟着等待。另一个是显存：多个模型的权重和请求的 KV Cache 共享有限空间。如果每个请求都按最大输出长度预留，显存会浪费；如果预留太少，又可能在生成中途放不下。模型一旦被换出，下次调用还要付出重新加载的成本。

我们的思路是，把 Agent 的角色、上下文和工作流位置转成可用的资源预测，再让请求排序、节点选择和显存管理使用同一组信号。系统可以分成预测、节点内存管理和集群调度三部分。

先估计阶段成本

预测的起点是这次调用会输出多少 token。我们利用输入长度、阶段位置、调用次数、工具数量和上一阶段输出等信息，同时用 MiniLM 提取输入语义，再通过 PCA 降维后送入预测模型。

这里采用两阶段方法。全局分类器先判断这次调用触发工具的概率，再把连续概率连同其他特征交给 Agent 专属长度回归器。原因是工具调用通常输出较短的结构化内容，直接回答或者推理可能更长；先提供行为模式信号，有助于区分这两类需求。全局分类器共享工具调用规律，各 Agent 的回归器学习自己的长度分布。

得到长度之后，用模型的实测 prefill 耗时和每 token decode 耗时估计执行时间，再根据输入加输出的总长度估计 KV 需求。比如两个请求输入接近，但一个预计输出几十个 token，另一个预计输出上千个，它们的排队成本和显存预算就应该不同。工程上将预测封装成服务，执行后回传真实 token 数和运行信息，通过后台任务整理数据、更新模型，形成运行反馈闭环。

节点内怎样让多模型放得下

节点侧同时管理模型驻留状态和 KV 空间。模型可以正在 GPU 上运行，也可以进入 Sleeping：权重已经移到主机内存，但保留轻量 GPU 运行上下文，降低下次激活成本。再冷一些的模型可以只保留在 CPU、磁盘或者远端。调度器因此知道，“这个节点有模型”究竟意味着马上能运行，还是还需要加载。

在支持 CUDA VMM 的节点上，KV 使用共享虚拟地址池，物理页按需要映射。关键是虚拟地址可以多预留，物理显存仍然要逐次核算。系统在准入时检查模型上下文、现有 KV 和新请求预算，预测外再留安全余量；空间不足时，先考虑对其他执行影响较小的回收动作，并把代价上报给调度器。因此弹性分配必须和容量检查配合，不能把虚拟地址空间当成真实容量。

集群调度怎样使用这些信息

集群侧先排除无法安全准入的节点，再综合网络距离、现有模型的激活成本、节点排队和释放资源的扰动，选择合适位置。已经预热的模型有优势，但如果队列太长，也不一定继续把请求堆过去。

队列还会利用工作流的预计剩余时间，包括当前阶段和历史上相似状态之后的执行时间，让接近完成的工作流更快推进。对交互和后台负载的冲突，系统只在两次模型调用之间做阶段边界抢占，不直接打断正在进行的 decode，并配合冷却和 aging，减少反复切换。

实验与贡献

论文同时报告了物理集群实验和 trace 驱动模拟。在高争用的模拟设置里，SLO 达成率相对 EDF 提高了 23.6 个百分点；显存实验中，KV 预留的 HBM 开销降低了 67.2%。这些指标对应不同实验，不能合并成所有负载下都成立的提升。

这项工作的核心是让工作流信息真正进入资源决策：先估计一次调用的成本，再用节点的真实容量和模型状态约束放置，最后根据运行反馈持续修正。这样既减少长短请求相互阻塞，也让有限显存能够支撑更灵活的多模型服务。

问题背景

传统 LLM 推理面对的是独立的一问一答请求。但现在越来越多的应用把多个 agent 组成协作工作流：比如旅行助手里有"需求分析 agent"、"机票搜索 agent"、"酒店推荐 agent"、"行程整合 agent"，它们之间有 DAG 依赖，一个用户请求触发十几次甚至几十次 LLM 推理调用（称为 stage）。

这带来了三个新挑战：

  1. 输出长度剧烈波动：工具调用输出几十 token（JSON），用户交互输出几百上千 token。KV 缓存需求差异巨大，固定分配要么浪费要么 OOM。
  2. 多模型共存的内存压力：不同 agent 使用不同模型，一块 GPU 需要同时驻留多个模型权重加上所有请求的 KV 缓存。
  3. 混合延迟要求：交互式 stage 要低延迟，批处理 stage 要高吞吐。不区分优先级就会造成队头阻塞。

系统设计

核心思路：不把 LLM 请求当黑盒，利用 agent 上下文做前瞻性预测，指导内存管理和调度。

组件一：两阶段输出长度预测

为什么需要预测输出长度？

Agent 工作流中的调用成本差异很大：生成工具参数通常较短，分析和总结可能较长。提前估计输出长度，可以同时为请求排序、模型驻留和 KV 预算提供依据。按需分配负责执行时的空间管理，预测则帮助系统提前安排未来需求。

两阶段流水线

消息、工具描述 → MiniLM → 384 维语义向量
                              ├→ 全局 PCA 32 维
                              │       + 结构化特征
                              │       → 全局 LightGBM 分类器
                              │       → 工具调用概率
                              │                │
                              └→ Agent PCA 32 维
                                      + 结构化特征 + 工具调用概率
                                      → Agent 专属 LightGBM 回归器
                                      → log(1 + 输出长度)
                                      → expm1 → token 数

MiniLM 负责提取语义，LightGBM 负责分类和回归。分类器传递连续概率，让回归器利用工具调用的可能性，而不是先把请求硬切成两个类别。全局分类器共享跨 Agent 的行为规律，专属回归器适配各 Agent 的输出分布。

服务中的输入特征

当前服务配置使用输入 token 数、工具数量、思考模式、是否为首个阶段、阶段序号、同一 Agent 的调用次数、上一阶段输出长度，以及 PCA 语义特征。Agent 名称用于选择模型包；会话 ID 用于获取上下文。语义编码处理系统提示、对话和工具名称与描述，长文本通过重叠滑动窗口聚合。

分类器使用全局 PCA，回归器使用 Agent 专属 PCA；线上共用同一份原始语义向量，再分别投影。这让分类和回归保留各自关注的语义方向，同时减少重复编码。

训练目标与冷启动

当前服务的分类器学习工具调用标签，回归器对真实输出 token 数做 log1p 变换，采用 alpha=0.5 的分位数回归，预测中位数长度；近期样本获得更高权重。模型包保存模型、PCA 参数和特征顺序，推理按同样的顺序组装输入。

论文方法包含 isotonic 概率校准和冷启动时的共享全局模型。后续服务快照直接使用 predict_proba，缺少 Agent 模型或全局分类器时返回默认 150 token。资源安全余量由预算策略处理，不应把当前中位数回归器称为偏向高估的损失函数。

两阶段带来的价值

工具调用概率为长度回归提供显式的行为模式信号，一阶段直接回归则是自然的对照方法。论文报告输出长度 MAE 为 165.43 token、R² 为 0.7774，相比 Magnus 的 MAE 降低 19.2%。消融显示工具意图特征在非 CoT 场景更有帮助；开启 CoT 后，两种模式都可能包含推理文本，因此收益会随工作负载变化。

组件二：节点级弹性内存管理

模型状态管理：五种状态按层级流转——

  • Running：权重在 GPU，可立即执行推理
  • Sleeping：权重移到 CPU，但 GPU 上保留 CUDA Graph 和 JIT 内核缓存（约 0.5GB），重新激活省 5-8 秒
  • CPU-resident：权重完全在 CPU 内存
  • Disk-resident：权重在本地 NVMe
  • Remote：权重在远程存储

层级化 LRU 逐级淘汰，最热的模型留 GPU，最冷的逐步退到远端。

KV 缓存管理：CUDA VMM 虚拟内存超配——40GB 物理 GPU 上分配 122GB 虚拟地址池（3 倍超配）。关键在于虚拟地址和物理页分离，按需映射物理页。三层防护：(1) 虚拟 vs 物理分离，不会同时达峰；(2) 准入控制——每个 stage 检查剩余物理页是否够；(3) 映射失败时拒绝 stage 而非崩溃。五级降级策略保证极端情况也不会 OOM。

内存核算：M_kv + M_res ≤ M_total，安全裕度 ρ ∈ [0.1, 0.3]，偏向高估以避免低估导致 OOM。

组件三：工作流感知 SRTF 调度

基于预测的剩余执行时间排队（SRTF），优先执行快要完成的工作流。交互式和批处理 stage 分开排队。Stage 边界抢占——只在两次 LLM 调用之间切换，不打断正在解码的请求。

节点选择：适应度评分 S(N,T) = A(N,T) − λ·T_ready − μ·C_deg，综合模型就绪延迟和降级代价。

Maestro 高频问答

Q: 低估输出长度和高估，哪个危害更大？

低估远比高估危害大：(1) KV 缓存方面，低估导致预分配不够，解码到一半 OOM，请求被杀；高估只是暂时多占。(2) SRTF 调度方面，低估剩余时间导致长作业排到队首，造成队头阻塞；高估则长作业排后面，影响较小。所以设计安全裕度 ρ 偏向高估。

Q: CUDA VMM 超配 3 倍不怕 OOM 吗？

三层防护：(1) 122GB 是虚拟地址空间，物理页按需映射，不会同时分配满；(2) 每个 stage 进来先做准入控制，检查剩余物理页是否够预测需求；(3) cuMemMap 返回失败时拒绝该 stage 而非崩溃。多 agent 的 KV 使用弹性大，统计上不会同时达峰，类似内存超卖的思路。

Q: 五种模型状态 vs 四层存储的关系？

四层存储：GPU → CPU → Disk → Remote。五种状态多出一个 Sleeping——权重在 CPU，但 GPU 上保留 CUDA Graph 和 JIT 内核缓存（约 0.5GB），重新激活省 5-8 秒。Sleeping 横跨 GPU 和 CPU 两层。设计原因：模型切换频繁时，CUDA Graph 的重建开销可观。

Q: Stage 边界抢占够用吗？为什么不做 token 级？

Token 级抢占需要和解码引擎深度集成，还要做 KV 缓存迁移，工程复杂度极高。Stage 边界抢占只需更新元数据，实测效果已足够：交互排队从 11 秒降到 2 毫秒。超长解码阶段可作为 future work。

Q: 新 agent 角色上线没有历史数据怎么办？

三级回退：(1) per-role 数据不足时回退到全局模型；(2) 结构化特征（工作流位置、工具可用性）本身就有信号；(3) post-execution profiling 增量更新，几轮执行后适应新角色。

Q: 适应度评分 S(N,T) 的权重怎么设？

S(N,T) = A(N,T) − λ·T_ready − μ·C_deg。默认 λ = μ = 1（毫秒量级）。交互式 stage 增大网络延迟权重。用 robust min-max 归一化（5/95 分位数裁剪），防止异常值主导。验证集上选定后跨负载固定。

Q: 什么是"LLM 多智能体工作流"？给一个具体例子。

比如一个旅行助手 Agent：用户说"帮我规划去东京的行程"，系统会依次调用：需求分析 Agent（解析意图）→ 机票搜索 Agent（调工具查航班）→ 酒店推荐 Agent（查酒店）→ 行程整合 Agent（汇总输出）。每个 Agent 背后是一次 LLM 推理调用（称为 stage），一个用户请求可能触发十几次甚至几十次 LLM 调用。这些 stage 之间有 DAG 依赖关系，不同 Agent 可能使用不同模型，输出长度差异巨大——工具调用返回几十 token 的 JSON，用户交互输出几百上千 token。

Q: "解码成本不确定"为什么是个问题？固定按最大长度预留不行吗？

固定按最大长度预留简单但保守，实际输出较短时会浪费空间。只按需分配能减少浪费，却不能提前判断哪些请求会长时间占用资源。我用 Agent 输入与上下文预测输出长度，帮助排序、模型驻留和 KV 预算；运行时再按真实用量增长，并在空间紧张时执行准入或回收策略。

Q: 为什么分类器和回归器都用 LightGBM（GBDT），而不是用深度学习模型做分类/回归？

MiniLM 负责提取文本语义，LightGBM 将语义特征与输入长度、工具数量、阶段上下文结合起来做分类与回归。这样的分工适合结构化特征与文本信息混合的场景，也便于给不同 Agent 训练专属模型。工程上可以预加载树模型、复用编码结果并控制线程数量。性能评估要把文本编码与接口排队一起计入，不能只拿树模型的一次调用时间代表整个预测服务。

Q: 预测特征具体有哪些？语义特征怎么提取的？

落到当前服务实现，结构化特征是输入 token 数、工具数量、思考模式、首阶段标记、阶段序号、同一 Agent 的调用次数和上一阶段输出长度。Agent 名称用于选择专属模型。语义特征由 MiniLM 对系统提示、对话和工具描述编码，长文本采用重叠滑动窗口，聚合为 384 维向量，再分别通过全局 PCA 和 Agent PCA 降到 32 维。分类器与回归器各用对应投影，回归器还接收工具调用概率。

Q: 预测器出错了怎么办？如果预测输出 100 token 实际输出了 1000 token 呢？

预测给出初始需求，实际分配持续接受容量约束。KV 随生成按需增长，每次追加前检查空间；不足时暂停准入，或选择合适的回收与恢复策略，再将低估反馈到后续预算校准。当前回归器输出中位数，保守余量属于资源预算策略。这样预测负责改善利用率，运行时负责处理超出预算的情况。

Q: KV 预留显存降低 67.2%，但这不就是靠 CUDA VMM 超配"骗"出来的吗？实际物理显存并没有减少啊？

这个问题需要分清两个层面：(1) 预留（reservation）≠ 实际使用。传统方案为每个请求预分配最大 KV 物理空间，即使实际输出很短也占着不放——这是真正的物理显存浪费。CUDA VMM 让虚拟地址远大于物理显存，但物理页按需映射，真正减少的是物理 HBM 占用；(2) 67.2% 降低的是预留的 HBM 物理显存，不是虚拟地址空间。通过输出长度预测来决定实际映射多少物理页——短请求只映射少量物理页，长请求映射更多，而不是所有人都按最坏情况分配。统计复用的前提是多 Agent 的 KV 峰值不重叠（某个 agent 在输出长文本时，其他 agent 可能正在工具调用或空闲），如果所有请求同时输出长文本确实还会 OOM，但实际 trace 中这种概率极低，且有准入控制兜底。

Q: EDF 作为 baseline 是不是太弱了？为什么不和更先进的调度方法比？

不只对比了 EDF。Maestro 的实验对比了 EDF、SRTF（无预测版本，纯按已执行时间排序）、FCFS（先到先服务）、Karma（LLM 推理服务最近的调度工作）。关键在于 Maestro 的核心贡献不是调度算法本身（SRTF 是经典算法），而是把预测信号引入 LLM-MAS 场景并设计了弹性显存机制来利用这些预测。实验设计的目的：EDF → 证明传统实时调度在 LLM-MAS 场景下失效（无法区分长短 stage）；SRTF（无预测）→ 证明纯 SRTF 因为不知道剩余时间只能按已执行时间估计，在双峰分布下偏差大；Maestro → 证明预测信号能显著提升 SRTF 的效果。对比不是为了证明"我的排序算法更好"，而是证明"预测信号有价值"。

Q: 为什么不直接用 vLLM/TGI 这些现成的推理框架？它们已经有 PagedAttention、continuous batching 了。

这是不同层面的优化，两者是互补而非替代关系：vLLM/TGI 优化的是单节点内推理引擎的 batching 和 KV 管理（PagedAttention 解决内部碎片、continuous batching 提高单模型 GPU 利用率）。Maestro 解决的是多节点、多模型、多 Agent 工作流层面的调度问题——一个用户请求涉及十几个 Agent stage、用多个不同模型、分布在多块 GPU 上，需要全局视角决定"哪个 stage 放哪块 GPU、哪个模型该常驻、KV 显存怎么跨请求复用"。Maestro 可以和 vLLM 配合使用：节点内用 vLLM 做推理引擎优化（PagedAttention、continuous batching），节点间用 Maestro 做全局调度和显存管理。事实上我们的原型实现就是基于 vLLM 做的，分级权重缓存和 CUDA VMM 超配是在 vLLM 之上的额外优化。

从 Agent 请求到输出长度

Maestro 把 Agent 请求的执行成本提前转成调度信号：先预测这次调用是否涉及工具，再预测会生成多少 token，最后将长度换算成时间和显存需求。工具调用通常生成较短的结构化参数，分析与总结通常生成较长文本；同样的输入长度，执行成本可能相差很大。

python-predictor 将预测封装成 FastAPI 服务。一次请求携带会话 ID、Agent 名称、消息、可用工具和阶段上下文；响应返回工具调用概率、预测输出长度和输入 token 数。

messages + tools ──→ 输入 token 计数
        │

                 全局 PCA                  Agent 专属 PCA

两阶段之间传递连续概率，不先用阈值把请求硬分成两类。Agent 的差异主要通过选择专属回归器和专属 PCA 来表达。

文本编码与两套 PCA

语义编码使用 all-MiniLM-L6-v2，通过 ONNX Runtime 执行。默认长文本策略将内容切成最多 510 个 token 的窗口，步长为 255；窗口加上特殊 token 后按 512 长度组织，批量编码。每个窗口做带 mask 的 mean pooling 和归一化，再聚合窗口向量，得到 384 维表示。

全局分类器和各 Agent 回归器分别保存自己的 PCA 参数。两者复用同一个原始语义向量，但投影方向不同：全局 PCA 面向多种 Agent 的工具调用模式，Agent PCA 面向该角色的长度变化。降维后，语义特征与结构化特征一起输入树模型。

PCA 的运行时计算为：

低维向量 = (原始向量 - 训练均值) × 主成分矩阵的转置

这将语义模型负责的“理解输入”与树模型负责的“预测成本”分开，也便于复用编码结果。预测器内部支持传入预计算向量；普通 /predict 接口仍从文本调用编码器。

分类和回归怎样训练

全局分类器以 is_tool_call 为标签，采用 LightGBM 二分类；Agent 回归器以真实生成 token 数 usage_completion_tokens 为目标，先做 log1p 变换。全局分类器的预测概率作为额外特征注入回归器训练，与在线预测保持相同的两阶段结构。

项目配置

medium 对应中位数预测。若要针对 KV 低估采用保守预算，应在资源估计与准入策略中设置余量，而不是把这个 alpha=0.5 的回归器解释成已经偏向高估。

论文方法包含分类概率的 isotonic 校准和冷启动时的共享全局模型；当前服务直接使用分类器的 predict_proba，缺少 Agent 模型或全局分类器时返回默认 150 token。这是论文方法与后续服务版本的具体差异。

长度怎样变成调度与 KV 预算

论文将输出长度转换为模型相关的执行时间和显存估计：

阶段执行时间 ≈ 该模型的 prefill 时间(输入长度)
             + 该模型的平均每 token decode 时间 × 预测输出长度

KV 需求 ≈ 该模型每 token 的 KV 字节数 × (输入长度 + 预测输出长度)

例如，一个 32 层、8 个 KV heads、head_dim 为 128 的 BF16 模型，每 token KV 为 128 KiB。输入 2048 token、预测输出 512 token，则全模型 KV 数据量约 320 MiB；若预算另留 20% 余量，则为 384 MiB。实际分配再考虑 block 对齐、TP/PP 分布和其他显存占用。

预测为调度器提供“这次调用预计要运行多久、需要多少空间”的信号。PagedAttention 负责高效管理已经发生的 KV 分配，两者可以配合：利用预测安排任务和模型驻留，再由运行时根据真实容量决定能否继续分配。

/predict 服务本身返回长度和概率，不执行显存页映射。后续 Concerto 通过 predictor_runtime.py 接入这些字段，并用于请求级投机长度选择；这是同一预测能力在新决策层中的复用。

运行反馈与服务开销

节点完成后通过 /callback/node 回传真实 token 用量和运行信息，暂存到 Redis；工作流完成后由 Celery 汇总、补充上下文与 embedding，再持久化。后台任务根据增量计数触发训练，Agent 模型更新后通知服务重载。

这条链路实现的是“运行反馈—异步训练—模型更新”，训练不放在单次请求的同步路径中。新到达的数据可以用于后续更新，具体更新频率由阈值控制；代码快照中的两个训练触发阈值均为 1,000,000。

服务启动时预加载 Agent 模型，预测线程将树模型限制为单线程；文本编码和模型计算放到受限工作线程中，避免阻塞 FastAPI 的事件循环。耗时分别记录编码、特征准备、Redis、分类、回归，以及接口排队与处理时间，便于判断瓶颈究竟在哪里。

设计动机与核心方法

Q1：你的预测器到底解决什么问题？

我做的是面向 Agent 工作流的执行成本预测。一次工作流会多次调用模型，有的阶段只生成工具调用参数，有的阶段要长篇推理或汇总，单看模型大小和输入长度，很难判断这次请求到底会占用多久、需要多少显存。我利用 Agent 的输入语义和阶段上下文，先预测工具调用意图，再预测输出长度，把这个长度转成执行时间和 KV 预算，让调度器能够提前安排，而不是等请求执行起来才发现资源紧张。

Q2：为什么分两阶段，不直接预测输出长度？

因为工具调用和自由文本生成往往对应两种不同的输出模式。比如同一个研究 Agent，有时只是生成检索参数，有时要写一段分析，输出长度差别很大。我先用分类器估计工具调用概率，再把这个概率作为回归器的输入，让长度模型获得一个更明确的行为信号。

这里传递的是连续概率，不是先判成 0 或 1 再硬切换模型。一阶段回归也是合理基线；两阶段的价值在于显式利用行为模式，尤其是工具调用与文本输出长度差别较大的场景。

Q3：为什么用了 MiniLM，还要用 LightGBM？

它们承担不同任务。MiniLM 提取输入的语义，比如当前是在搜索、分析还是总结；LightGBM 把语义向量和输入长度、工具数量、阶段位置等表格特征结合起来，预测工具调用概率与输出长度。这种组合能利用文本信息，也便于按 Agent 单独训练和更新，部署时还可以预加载模型、控制 CPU 线程和复用编码结果。

Q4：具体用了哪些特征？举一个实际例子。

结构化特征包括输入 token 数、工具数量、是否开启思考模式、当前阶段序号、同一个 Agent 已经调用过几次，以及上一阶段输出长度。语义特征来自系统提示、对话内容和工具描述，用 MiniLM 编码后经 PCA 降到 32 维。

比如同一个 Agent 第一次拿到问题，可能需要先调用搜索工具；第二次已经拿到上游信息，就可能进入长文本分析。角色没变，但调用次数、前序输出和当前语义变了，这些信息能帮助模型区分两次调用的成本。

模型训练与工程实现

Q5：为什么每个 Agent 配一个回归器？

不同 Agent 的职责和输出风格相对稳定。检索 Agent、翻译 Agent、总结 Agent 的长度分布不同，使用专属回归器可以减少跨角色混杂。全局分类器共享“是否调用工具”的规律，各 Agent 回归器学习自己的长度模式，因此既有共享信息，也有角色适配。

实现上按完整 Agent 名称保存模型包，包里包含回归器、特征顺序和 PCA 参数。当前服务在 Agent 数据达到 50 条后才训练专属回归器；缺模型时先使用默认长度，待有足够数据后建立专属模型。

Q6：为什么分类器和回归器各有一套 PCA？

分类器要识别所有 Agent 中共同的工具调用模式，回归器要解释某个 Agent 内部的输出长度变化，因此两者关注的语义方向不同。全局 PCA 用全局数据训练，Agent PCA 用该 Agent 的数据训练；线上 MiniLM 只生成一份 384 维向量，再分别投影到两个 32 维空间，既共享编码成本，也保留任务差异。

Q7：长 prompt 怎么处理？直接截断吗？

默认使用重叠滑动窗口。每个窗口最多取 510 个内容 token，步长 255，加上特殊 token 后送入 ONNX 编码器批量处理。先对窗口内 token 做 mean pooling，再聚合各窗口向量。这样能覆盖长对话中的多个部分，避免只看开头或结尾；相应代价是 prompt 越长，需要处理的窗口越多，所以编码成本也要单独监控。

Q8：输出长度是长尾分布，怎么训练？

当前实现先对真实输出长度做 log1p 变换，再训练 LightGBM 分位数回归器，目标分位数是 0.5。log 变换压缩长短输出之间的尺度差异，中位数目标提供一个典型长度估计。线上再用 expm1 还原成 token 数。训练还对较新的样本赋予更高权重，使模型更关注近期运行模式。

预测长度和资源余量是两层决策：模型给出典型需求，调度器结合低估误差和剩余显存决定预留多少。

Q9：怎么把训练、预测和运行反馈接起来？

执行前调用预测服务，执行后通过 callback 回传真实输出长度和运行数据。节点数据先进入 Redis，工作流结束后交给 Celery 汇总入库；后台根据新增数据量决定是否训练，训练完成后让服务热重载模型。这样请求路径只负责预测，数据整理和训练异步进行，避免训练拖慢用户请求。

Q10：预测本身会不会成为瓶颈？你做了哪些工程处理？

会，尤其是长 prompt 和突发并发，不能只看一次树模型推理。我把成本拆成请求排队、文本编码、特征准备、Redis 访问、分类和回归。实现上使用 ONNX Runtime 编码、启动预加载模型、限制原生线程数量，并把同步计算放到受限工作线程中，让 HTTP 事件循环继续处理其他请求。优化时先看哪一段占主导，再决定是复用向量、调整并发，还是减少重复数据访问。

调度价值与 KV Cache 追问

Q11：vLLM 已经按需分配 KV，为什么还需要预测？

按需分配解决的是“已经需要这些 KV，怎样高效存下来”，预测解决的是“这个请求后面还会占多少资源、持续多久”。在多 Agent、多模型场景下，这个未来需求会影响请求排序、模型驻留和节点选择。例如两个请求当前都只占少量 KV，但一个很快结束，另一个会继续生成很长文本，调度策略就不应完全一样。预测提供前瞻信号，分页管理负责高效执行，两者配合才能把资源安排得更好。

Q12：预测 100 token，实际生成 1000 token，怎么办？

把预测作为初始预算，运行时继续按真实需求增长。每次追加前检查可用容量，不够时暂停新请求准入，或者选择低代价的回收与重算策略。与此同时，把这次低估反馈给后续预算校准。这里最关键的是把“提高利用率的预测”和“约束实际分配的容量检查”配合起来，这样预测不准时仍然有明确的处理路径。

Q13：Cache 命中会改变耗时，你的预测怎样适应？

我会把输出长度预测和运行成本估计分开。输出长度主要由任务语义和生成行为决定；相同输出长度在不同缓存、batch 和资源状态下，耗时可能不同。前缀命中后，时间估计要扣除已复用部分的 prefill 成本，再结合当前排队、decode 速度，以及可能的 KV 传输或重算成本。长度预测器提供需求信号，缓存与负载观测负责把需求换算成当前系统上的成本。

现有长度模型没有把前缀命中率作为显式特征，因此这类在线状态更适合先接到成本估计层。

Q14：当前阶段长度和整个工作流剩余时间有什么关系？

预测器先给当前调用的长度，再用模型的 prefill 和 decode profile 转成当前阶段时间。工作流调度还要考虑后续阶段：根据当前进度和相似历史状态估计后续成本，再与当前阶段合起来。工具调用时间也要单独处理，因为预测工具调用参数的 token 数，并不等于预测外部工具要执行多久。

Q15：怎么证明两阶段预测带来了实际价值？

我分两层看：预测层比较长度误差，并分别分析工具调用、非工具调用和思考模式；系统层看这些预测是否改善排序、显存预算和最终完成时间。论文中输出长度预测 MAE 为 165.43 token、R² 为 0.7774，相比 Magnus 的 MAE 降低 19.2%。消融比较直接回归、加入工具调用概率，以及加入语义特征后的变化。然后固定工作负载和运行资源，比较排队、SLO 达成与显存预留，建立从预测到调度收益的联系。

验证时按时间划分训练和测试，并把同一会话的数据关联起来检查，避免未来信息进入当前请求特征。平均误差之外，还要看长输出和低估尾部。

我把 Agent 工作流中的行为差异转化成了系统可用的资源信号：通过工具调用意图与输出长度的两阶段预测，提前估计阶段成本，再把这些估计接到工作流调度和多模型显存管理中。工程上补齐了预测服务、上下文获取、异步反馈和模型更新，使预测能够进入真实请求链路。这项工作的价值在于把模型行为、资源需求和调度决策连起来。

Q: 请介绍一下 DeepShare，包括为什么做、怎么共享，以及怎么抢占。

问题：有人等卡，有人占卡却用不满

DeepShare 这项工作，最开始来自我们实验室使用 GPU 的一个实际问题。

实验室里做深度学习的人很多，大家都需要 GPU 跑训练。最直接的方式，就是一个任务占一张卡。但有些任务虽然一直占着卡，实际上并没有把整张卡用满。比如模型规模比较小，或者训练过程中还有数据准备和 CPU 处理，GPU 并不是一直在高效计算。结果就是，一边有人排队等卡，另一边已经分出去的卡还有剩余能力。

共享：用 MPS 让多个任务并发执行

所以我们就想，能不能让多个训练任务共享同一张 GPU，把这些剩余能力利用起来？我们采用的是 NVIDIA MPS，也就是多进程服务，让多个训练进程能够在同一张 GPU 上并发执行。它提供了共享的执行能力，但具体让哪些任务一起跑、资源不够了让谁退出，仍然需要调度器决定。

真正做起来以后，我们发现，光把任务放到一起还不够，有两个问题必须解决。

第一个是干扰。两个任务单独跑的时候可能都用不满卡，但放在一起，不一定就能互补。比如两个任务都在大量访问显存，就可能争用带宽，导致原来的训练明显变慢。所以显存装得下，只是共享的基本条件，还要判断一起跑以后性能能不能接受。

第二个是资源保障。实验室里不同课题组、不同用户都有自己的资源需求。如果把暂时不用的资源借出去，原来的用户后来提交任务了，系统就得有办法把资源收回来。否则共享虽然提高了利用率，却可能让用户连自己配额内的任务都跑不起来。

因此，DeepShare 同时做两件事：让空闲资源能够被借用，让单卡剩余能力能够被共享；同时保证，当保障需求回来或者共享干扰过大时，系统有明确的回收办法。

保障：哪些资源应该优先兑现

我们先用一个指标来判断，哪个租户现在最需要补资源。这个指标叫 QAD，也就是配额保障度。计算方法是：已经分给保障任务的 GPU 数量，除以配额和当前保障需求中较小的那个。

举个例子，一个团队配额是 8 张卡，但现在只需要 4 张，系统也给了 4 张，那它的保障已经完全满足，QAD 就是 1。如果它需要 8 张，却只拿到 4 张，QAD 就是 0.5。这个值越低，说明当前欠它的资源越多，调度时就越应该优先补上。借用的额外资源单独记账，不拿来抵消这个保障缺口。

在此基础上，我们把作业分成 Guaranteed 和 Best-effort 两类。Guaranteed 是需要优先兑现的配额内需求；Best-effort 可以借用剩余资源，但资源紧张时需要让出来。调度顺序先考虑保障任务，再按租户的 QAD 排序，在同等保障程度下利用预测剩余运行时间，让短任务更早完成。

干扰：装得下，还要一起跑得好

共享的时候，调度器会先检查资源是否够用，再判断干扰是否可接受。我们通过 DCGM 收集 GPU 的硬件指标，用 Random Forest 预测两个任务放在一起以后，各自还能保留多少吞吐。通过判断以后，才允许它们通过 MPS 在同一张卡上运行。开始共享后也继续观察实际表现，如果连续三个采样窗口低于动态容忍阈值，就停止同一张 GPU 上借用资源的 Best-effort 训练任务，释放它占用的资源，让保障任务继续运行。

回收：保障任务来了，谁让出资源

抢占可以用一个具体过程来解释。比如 A 团队配额是 8 张卡，之前只用了 4 张，集群的剩余资源被其他团队的 Best-effort 任务利用起来了。现在 A 又来了一个需要 2 张卡的保障任务。

调度器不会一看到需求增加就直接杀任务，而是先尝试正常放置：有没有空闲 GPU，或者有没有满足干扰要求的共享位置。如果这些方式都安排不下，才进入抢占路径，找哪些 Best-effort 任务可以让出所需资源。

选谁的时候，我们会同时看能释放多少资源、任务预计还要运行多久，以及它之前被抢占的代价。比如其他条件一样，一个任务还有 1 分钟就结束，另一个还有 20 分钟，我们更倾向于让后者让出资源，尽量让快完成的任务先完成。已经反复被打断的任务，也会增加它的抢占代价，避免总是牺牲同一个任务。

还要注意，一张 GPU 上可能同时有两个 Best-effort 任务。如果新任务需要完整的一张卡，只停其中一个，另一个还占着卡，就没有真正回收成功。所以我们会把这张卡上需要一起退出的任务作为一组，计算整体代价，再选择能满足新任务资源需求的组合，同时检查 CPU 和内存等条件。

我们把这些考虑写成一个代价分数：剩余时间越短，代价越高；之前累计的抢占开销越大，代价也越高；如果回收一张卡需要同时打断多个任务，再额外加一个惩罚。最后只在清退后资源足够、卡上全部是 Best-effort 的候选设备中，选整组代价最低的那张。这个函数把刚才的取舍变成了调度器能执行的比较规则。

执行：停止 Pod，确认释放，再安排新任务

选好以后，执行层面做的是删除被选中的 Pod。调度器通过 Kubernetes API 发出删除请求，由所在节点的 kubelet 和容器运行时终止容器，训练进程退出后才会释放它占用的 GPU 资源。这里要区分“已经发出删除请求”和“资源真的释放了”：Pod 还在终止过程中时，不能马上把同一份资源算给新任务；要根据实际终止和资源状态，再完成新任务的调度和绑定。

所以这套抢占做的是作业层面的中断和重新安排。被中断的训练之后重新运行时，能保留多少进度取决于它自己的 checkpoint 支持；删除 Pod 本身不会自动保存训练状态。这也是我们在选任务时要考虑抢占代价的原因。

实现：预测、调度与节点执行怎样配合

这里有两个不同的预测模块。一个是按租户历史训练的 Gradient Boosting，预测任务还要运行多久，用来辅助排队和选择抢占对象；另一个是刚才提到的 Random Forest，预测共享后的性能，用来决定哪些任务适合放在一起。前者解决运行顺序，后者解决共享位置。

工程上，我们把这些策略放到了 Kubernetes 的 Controller 和调度插件里。Controller 管理租户配额和作业类别，调度插件根据运行中的 Pod 更新保障状态，执行排序、共享准入、资源预留和抢占；节点侧提供 MPS 运行环境和 GPU 指标采集。

效果：利用率与任务完成时间一起看

实验上，我们分别做了历史轨迹驱动的仿真和真实 GPU 集群实验。轨迹实验中，GPU 平均利用率达到约 70.6%，平均排队时间相对 Lucid 降低了 46%。真实集群中，相比 Hard+Colocate，平均作业完成时间降低了 34%，保障租户的 QoS 合规率达到 93%。

回到实验室最开始的问题，DeepShare 想做到的是：任务用不满卡的时候，让其他任务用上剩余能力；用户需要自己的保障资源时，能合理地收回来；共享真的拖慢任务时，也能及时调整。这样才能把 GPU 利用率提高，同时让用户愿意接受共享。

Q: 如果只展开抢占，怎么用一分钟讲清楚？

我们的抢占有两个主要入口：一个是保障任务来了，正常放置和安全共享都安排不下，需要回收 Best-effort 占用的资源；另一个是共享后实际干扰持续超标，需要停止同卡上借用资源的 Best-effort 训练任务。

进入回收以后，先找能够满足新任务需求的候选资源，再比较候选任务的剩余运行时间、历史抢占代价，以及需要同时打断多少任务。快结束的任务和已经多次被抢占的任务，会尽量保护。如果需要完整 GPU，就必须把该卡上需要退出的 Best-effort 任务一起考虑，不能只停一个就算释放了一张卡。

执行上是通过 Kubernetes 删除选中的 Pod，由节点终止训练进程。删除请求返回成功不等于 GPU 已经空出来，要等实际退出和资源释放，再给新任务分配。训练进度的恢复依赖任务自身的 checkpoint，Pod 删除不会自动保存进度。

Q: 删除 Pod 后，任务怎么恢复？MPS 会帮忙保存状态吗？

MPS 负责多个 GPU 进程并发执行，不负责保存训练进度。删除 Pod 会终止其中的进程，内存和显存里的状态不能因此自动保留。

后续重建或重新提交任务，需要由作业控制器或提交系统负责；恢复训练还需要训练程序支持 checkpoint，保存模型、优化器和训练步数等状态，并在启动时加载。没有这些支持，就可能需要重新训练。因此，介绍 DeepShare 时可以明确说它完成了代价感知的抢占决策和 Pod 层面的执行，不能把它描述成任意训练任务的透明暂停和原地继续。

Q: 抢占代价函数怎么推导？每一项为什么这样写？

论文使用下面的集合代价，分数越小越优先选择：

$$\Phi(J)=\sum_{j\in J}\frac{1+\alpha C_p(j)}{\hat T(j)}+\frac{\beta(|J|-1)}{\bar T(J)}$$

这里，J 是要回收的一张 GPU 上的全部驻留任务，|J| 是任务数量；T̂(j) 是任务 j 的预测剩余时间，T̄(J) 是这些任务的平均剩余时间；C_p(j) 是归一化后的累计抢占开销。默认 α=0.5、β=0.3，分别控制历史打断和多任务打断的惩罚强度。

第一步，保护快完成的任务。先写 1/T̂(j)。其他条件一样，任务越接近完成，倒数越大，抢占它就越不划算。这是一个调度偏好，不是说剩余时间长的任务一定丢失进度更少。

第二步，减少重复抢占。把分子改成 1+αC_p(j)。没有历史开销时也保留基础代价 1；累计开销增加以后，这个任务的分数会升高，下次就更不容易再次成为抢占对象。累计开销不等同于简单的抢占次数。

第三步，计算整张卡的代价。对卡上的任务求和。回收共享 GPU 时，停止一个任务并不代表整张卡释放，所以必须评价完整集合。

第四步，进一步惩罚一次打断多个任务。加入 β(|J|−1)/T̄(J)。只停一个任务时，这项为零；停多个任务时，这项增加；如果它们平均都快结束了，这项还会更大。前面的求和已经累计每个任务的代价，这一项额外表达了对多任务同时中断的惩罚。

最后，先检查可行性，再最小化代价。设 V(d) 是 GPU d 的全部驻留任务，候选集 D_j^P 只包含这些任务全部为 Best-effort、且清退后能满足新任务显存和节点 CPU/内存约束的 GPU：

$$d^*=argmin_{dinmathcal D_j^P}PhiV(d),qquad J^*=V(d^*)$$

例如统一用分钟、历史开销均为零：GPU A 上一个任务还剩 10 分钟，代价是 0.1；GPU B 上一个任务还剩 100 分钟，代价是 0.01；GPU C 上两个任务都还剩 100 分钟，代价是 (0.01+0.01+0.3/100=0.023)。如果三张卡释放后都满足需求，就选 B。

这个函数是根据上述目标构造的启发式排序代价，不是“会损失多少秒”的精确模型，也不提供全局最优完成时间的证明。论文将 C_p 定义为归一化累计抢占开销，未在该处进一步规定它的归一化计算式。执行时先预留选定设备，再发起 Pod 删除，释放后绑定；没有可行候选就继续排队。

Q: MPS 已经能共享 GPU，为什么还需要你们这个系统？

MPS 解决的是多个进程能在一张 GPU 上并发执行，但它不知道谁有配额保障，也不会替我们决定哪些任务适合一起跑。我们的工作是在它上面做调度：判断是否允许共享、安排哪个任务先运行、保障任务来了回收谁，以及共享干扰超标后停止哪个借用任务。MPS 提供执行能力，DeepShare 根据租户需求和运行表现作决定。

Q: 一次任务提交后，哪些组件实际参与了执行？

首先读取任务所属租户、申请资源和作业类别，结合 TenantQuota 配置判断它进入保障队列还是借用队列。调度插件根据正在运行的 Pod 更新 QAD，决定谁先被安排，然后检查候选 GPU 的资源和共享干扰。找到位置后先预留资源，再完成绑定，由节点启动容器。如果保障任务没有可行位置，就进入 PostFilter 选择抢占对象；删除选中的 Pod、等待资源释放后，再完成放置。Controller 管配置，调度插件作决定，kubelet 和节点上的运行环境负责实际执行。

Q: 预测不准，会不会整个调度器就不能用了？

运行时间预测影响任务顺序和抢占代价，但不会改变保障任务优先于借用任务、不能抢占保障任务这些规则。共享干扰预测则先决定是否允许合用，运行后还要检查实际吞吐；如果连续三个窗口低于阈值，就停止同卡上借用资源的任务。因此预测帮助我们作更好的选择，资源约束和运行反馈仍然持续起作用。

Q: 怎么证明提高利用率没有以拖慢用户任务为代价？

要同时看利用率、排队时间、作业完成时间和保障任务的 QoS。只看利用率不够，因为两个任务相互争用也可能让 GPU 一直忙。我们做了轨迹仿真和真实集群对比；真实集群实验中，相比 Hard+Colocate，平均作业完成时间下降 34%，保障租户 QoS 合规率达到 93%。进一步区分配额借用、预测排序和共享的贡献，要看分别关闭这些机制的消融结果。

问题背景

多团队共享 GPU 集群的核心矛盾：

  • 配额闲置：某个团队暂时没有训练任务时 GPU 空转浪费，实测集群平均利用率只有 40%。
  • 配额不够：另一个团队赶 deadline 想多用几块卡，却因超配额被拒。

固定配额简单但浪费严重，完全共享利用率高但无法保障 SLA。问题本质：在保障每个租户配额的前提下，把闲置资源借给需要的人，原主需要时及时收回。

额外问题：即使 GPU 被分配出去了，很多训练任务在 I/O 或 CPU 预处理阶段 GPU 是空闲的。两个任务合用同一块 GPU 可以提升利用率，但会互相干扰——抢占 SM 和显存带宽，搞不好两个任务都变慢。

系统设计

统一控制信号——配额保障度 QAD，同时驱动三个子系统：

$$Q_i(t)=\frac{A_i^G(t)}{\min\!\left(q_i,\,D_i^G(t)\right)}\quad\left(D_i^G(t)>0\right)$$
部分含义记忆
分子 A_i^G(t)已经分配给租户的 Guaranteed GPU已经兑现多少
分母 min(q_i,D_i^G(t))quota 与当前 Guaranteed demand 取小此刻应该兑现多少
比值 Q_i(t)当前保障兑现率已给 / 该给

边界：没有 Guaranteed demand 时 Q_i(t)=1；Best-effort 借用不计入分子，所以 QAD 位于 [0,1]，不会因为借卡大于 1。完整数字例子见“QAD 记忆模型”。

子系统一：弹性配额借用（DRA）

空闲 GPU 可被其他租户借走跑低优先级任务。原主提交新任务导致 QAD 下降时，按 QAD 优先级回收——最欠缺的租户最先被满足。和固定配额的区别：闲置资源不浪费，但需要时保证能收回。

子系统二：预测性调度

Per-tenant gradient boosting regressor 预测作业剩余运行时间（MAPE 31.84%，R² = 0.7286）。调度排序采用词典序：

$$\big(\tilde{Q}_i(t)\uparrow,\; \hat{T}(j)\uparrow\big)$$

先按 QAD 升序（优先欠缺的租户），再按预测运行时间升序（短作业优先）。

抢占对象选择：对候选 GPU 上全部 Best-effort 任务计算集合代价，选择最小者。

$$\Phi(J)=\sum_{j\in J}\frac{1+\alpha C_p(j)}{\hat T(j)}+\frac{\beta(|J|-1)}{\bar T(J)}$$

剩余时间越短、累计抢占开销越高，代价越高；第二项额外惩罚同时中断多个任务。候选设备必须在清退全部驻留任务后满足新任务的资源约束。

开场：论文定位

我介绍的这篇论文是 DeepShare: Assurance-Driven Resource Management for Multi-Tenant GPU Clusters。它主要研究的是 多租户 GPU 集群中的资源管理问题。

简单来说，这篇论文想解决的问题是：

在多个团队共享一批 GPU 的情况下，如何既保证每个租户的 quota 和 QoS，又尽可能提高 GPU 利用率、降低作业排队时间。

1. 背景和问题

现在很多 AI 平台或者云平台都会有多租户 GPU 集群。比如不同团队、不同项目共用一批 GPU。为了公平，平台通常会给每个租户分配一个 quota，比如 A 团队 32 张 GPU，B 团队 16 张 GPU。

但是实际使用中会有一个矛盾。

如果我们严格按照 quota 静态隔离资源，那么就会出现资源浪费。比如 B 团队当前没有任务，它的 16 张 GPU quota 是空闲的，但 A 团队有很多任务在排队。如果系统不允许 A 使用 B 暂时空闲的 GPU，那么集群整体利用率就会下降。

反过来，如果系统允许 A 临时借用 B 的 GPU，又会出现另一个问题：当 B 后面提交了 Guaranteed 作业，需要拿回自己的 quota 时，资源可能已经被 A 的作业占住了。如果系统不能及时回收资源，就会破坏 B 的 QoS。

所以这里的核心矛盾是：

静态 quota 会降低利用率，过度共享又会破坏 QoS。

论文认为，现有系统的问题不只是某一个调度策略不好，而是 quota 管理、作业调度、抢占回收和 GPU 共享之间缺少一个统一的控制信号。

比如：

  • 调度器可能只看作业优先级；
  • quota 模块只看租户有没有超过 quota；
  • 抢占模块只看哪个作业优先级低；
  • colocation 模块只看 GPU 是否空闲或者干扰是否低。

这些模块如果各自决策，就很难同时保证 QoS 和利用率。

2. DeepShare 的核心思想

DeepShare 的核心思想是引入一个统一指标，叫 QAD，Quota Assurance Degree，也就是 配额保障程度。

它用来衡量：

一个租户当前 Guaranteed 资源需求中，有多少已经被满足。

也就是说，QAD 不是简单看一个租户用了多少 GPU，而是看它 应该被保障的资源有没有被保障到。

论文中 QAD 的作用是连接三个关键模块：

  1. Elastic Quota Regulation，也就是弹性 quota 调节 / DRA；
  2. Predictive Scheduling，也就是基于预测的调度；
  3. Interference-Aware Colocation，也就是干扰感知的 GPU 共享。

这三个模块都围绕 QAD 来做决策。

可以简单理解为：

QAD 低，说明租户保障不足，系统应该优先恢复它的 Guaranteed 作业；QAD 高，说明租户保障充分，系统可以更积极地允许资源借用和 GPU 共享。

3. QAD 是什么？

QAD 的直观定义是：

QAD = 已经兑现的 Guaranteed GPU / 当前应该兑现的 Guaranteed GPU

更具体一点，瞬时 QAD 可以理解为：

如果租户当前没有 Guaranteed demand：
    QAD = 1

否则：
    QAD = 当前已分配的 Guaranteed GPU / min(租户 quota, 当前 Guaranteed demand)

这里分母用 min(quota, demand) 很关键。

举个例子，一个租户 quota 是 32 张 GPU。

如果它当前只需要 8 张 GPU，那么系统只需要保障它 8 张。只要它拿到 8 张，QAD 就是 1，而不是 8/32。

如果它当前提交了 100 张 GPU 的需求，但 quota 只有 32，那么系统只承诺保障 32 张，不会因为它提交了 100 张就认为系统欠它 100 张。

所以 QAD 避免了两个问题：

  1. 租户不能通过提交超大 demand 来放大资源缺口；
  2. 租户当前需求小于 quota 时，也不会因为没用满 quota 而被错误认为保障不足。

论文还对 QAD 做了平滑处理，因为瞬时 QAD 会因为短任务完成、突发任务到来、资源释放等事件频繁波动。

平滑公式是：

Q̃_i(t) = λ Q_i(t) + (1 - λ) Q̃_i(t - 1)

默认 λ = 0.3。

也就是说：

当前平滑 QAD = 30% 当前瞬时 QAD + 70% 上一轮平滑 QAD

这样系统不会因为短期波动频繁重排队列或者抢占 Best-effort 作业，但如果一个租户持续保障不足，平滑 QAD 仍然会逐步下降，从而提高它的恢复优先级。

不要混：Q_i(t) 是瞬时观测，真正进入排序和 colocation 控制的是 EMA 平滑后的 Q̃_i(t)。

4. 模块一：Elastic Quota Regulation / DRA

第一个模块是 DRA，弹性 quota 调节。

它解决的是：

怎么允许租户借用别人暂时不用的资源，同时保证这些资源之后能被回收。

DeepShare 把作业分成两类：

Guaranteed 作业
Best-effort 作业

Guaranteed 作业是 quota 内应该被保障的作业。它们会计入租户的 quota，并且在调度时优先级更高。

Best-effort 作业是机会型作业。它们可以使用集群中暂时空闲的 GPU，或者其他租户当前没有用到的 surplus capacity，但它们是可回收的。

这里的关键是：

Best-effort 可以借资源，但不能破坏 Guaranteed QoS。

当某个租户 Guaranteed 需求回来，导致它的 QAD 降低时，系统会优先回收 Best-effort 作业占用的资源。

所以 DRA 的核心逻辑是：

有空闲资源时，提高利用率；
Guaranteed 保障不足时，回收借出去的资源。

这就是 DeepShare 同时提升利用率和保证 QoS 的基础。

5. 模块二：Predictive Scheduling

第二个模块是 预测调度。

论文正文使用 per-tenant gradient boosting regressor 预测作业剩余运行时间。这个预测信息主要有两个用途。

第一个用途是 队列排序。

DeepShare 的排序不是简单 FIFO，也不是单纯短任务优先，而是：

Guaranteed 优先于 Best-effort；
同一类作业里，平滑 QAD 低的租户优先；
QAD 接近时，预测运行时间短的作业优先。

也就是：

先恢复保障不足的租户，再用短任务优先降低平均排队时间。

这点很重要。预测运行时间只是第二排序键，它不能覆盖 QAD。也就是说，一个已经保障充分的租户，不能仅仅因为它的作业更短，就排到一个保障不足的租户前面。

第二个用途是 抢占代价估计。

如果需要回收 Best-effort 资源，系统不应该随便杀任务，而要考虑：

  • 这个任务已经运行了多久；
  • 剩余运行时间大概多长；
  • 是否有 checkpoint；
  • 重启成本多高；
  • 抢占它能不能真正释放足够 GPU；
  • 抢占后能不能提升低 QAD 租户的保障程度。

所以这里是一个 cost-aware preemption，而不是简单 priority-based preemption。

6. 模块三：Interference-Aware Colocation

第三个模块是 干扰感知的 GPU colocation。

它解决的是：

很多 GPU 作业并不能一直打满一张 GPU，如果让它们完全独占 GPU，会造成利用率浪费；但如果随便共享，又可能互相干扰，破坏 QoS。

GPU 共享的干扰来源很多，比如：

  • 显存容量；
  • 显存带宽；
  • SM 算力；
  • L2 cache；
  • PCIe / NVLink；
  • CPU dataloader；
  • 网络通信。

所以 DeepShare 不只是看 GPU 有没有空，而是预测两个作业放在一起会不会产生过大 slowdown。

论文中提到使用 random forest 模型预测 colocation 干扰。如果预测干扰低于阈值，才允许 colocation。

而且这个阈值不是固定的，会受到 QAD 影响。

如果某个租户 QAD 很低，说明它的 Guaranteed 资源已经保障不足，那系统会更保守，避免它的作业受到共享干扰。

如果租户 QAD 较高，说明保障比较充分，系统可以更激进地允许 colocation，提高 GPU 利用率。

所以 colocation admission 是：

干扰感知 + QAD 感知

而不是单纯基于利用率。

7. Kubernetes 实现怎么落地？

论文说 DeepShare 是 Kubernetes-native，也就是它不是重新造一个集群系统，而是集成到 Kubernetes 生态里。

论文实现拆成：

Controller + Scheduler Plugin

轻量 Controller 负责配置态：

  • reconcile TenantQuota CRD；
  • 读取 Guaranteed / Best-effort class annotation；
  • 生成 per-tenant quota metadata。

Scheduler Plugin 负责实时控制环：

  • 在内存中维护瞬时/平滑 QAD 和两级队列排序；
  • Filter：检查节点 GPU 是否足够、是否允许 colocation；
  • Score：使用 RF 干扰预测和动态 retention 门槛选择位置；
  • Reserve：更新下一周期 GPU claim，避免 double booking；
  • PostFilter：当 Guaranteed 作业调度失败时，选择低代价 Best-effort 作业进行抢占。
  • Permit：等待 CPU/Memory in-place resize 反映到 Pod 状态。

这里有一个关键点：

Controller 管配置态，Scheduler Plugin 管 QAD 和所有实时放置决策；QAD 可从 informer cache 中的运行 Pod 重建，不需要每轮写回 CRD。

Q: 面试官问“QAD 是什么”，怎么一口气讲清楚？

QAD 是租户级的配额保障兑现率。分子 A_i^G(t) 是当前已经分配的 Guaranteed GPU，分母 min(q_i,D_i^G(t)) 是平台此刻真正应该保障的 GPU 数：需求小于 quota 时只保障实际需求，需求超过 quota 时最多保障 quota。如果当前没有 Guaranteed demand，就把 QAD 定义为 1，因为没有未兑现的权益。Best-effort 借用不计入分子，所以 QAD 落在 0 到 1。系统再对瞬时 QAD 做 EMA 平滑，用平滑值优先恢复欠保障租户，并收紧它们的 GPU 共享。

Q: 为什么不能直接用 allocation / quota？

因为租户当前可能只需要 quota 的一小部分。若 quota 是 8、需求只有 4、实际已给 4，用 allocation/quota 会得到 0.5，错误地认为租户受损；DeepShare 用 min(quota, demand) 后得到 1，表示当前需求已完全兑现。

QAD 在哪里维护

QAD 是 Scheduler Plugin 的内存状态

Scheduler Plugin 从 informer cache 里的运行 Pod 推导 A_i^G(t)、D_i^G(t) 和 quota 元数据，计算瞬时 Q_i(t)，再维护 EMA 平滑值 Q̃_i(t)。这样排序、colocation 和抢占看到的是同一份实时状态。

论文没有把每一轮 QAD 写进 TenantQuota.status。发生 leader failover 后，新 leader 可以从运行 Pod 重建瞬时 QAD，并用首轮值 warm-start EMA，避免额外持久化和热路径写放大。

Q: 为什么 QAD 不放在 Controller 里周期性写 CRD？

QAD 是 50ms 调度周期内持续变化的热状态，排序、共享和抢占都要同步消费。若 Controller 计算后再写 CRD，既增加 API Server 写压力，也引入控制环延迟和一致性窗口。放在 Scheduler Plugin 内存里能直接复用 informer cache，并在 leader 切换后重建。

两级队列不要记成两个 Controller

队列符号和职责

队列含义做什么
Q_i^G / Q_i^B租户 i 的 Guaranteed / Best-effort 队列按 quota 与 cap 做租户级 admission
Q^G / Q^B集群级 Guaranteed / Best-effort 队列按平滑 QAD 和预测剩余时间决定放置顺序

Guaranteed 作业只有在 U_i^G + R_j ≤ q_i 时进入集群 Guaranteed 队列。Best-effort 作业只有在没有剩余 Guaranteed 作业能通过独占或安全合用落点，并且 U_i^B + R_j ≤ ηq_i 时才进入候选集。

集群级排序采用词典序：先区分 Guaranteed / Best-effort，再按 (Q̃_i ↑, T̂(j) ↑) 排序。QAD 是第一键，所以运行时间预测误差不会让保障充分的租户跨过保障不足的租户。

QAD 在调度路径中的输入输出

输入：已兑现与应兑现

$$ Q_i(t)= \begin{cases} 1, & D_i^G(t)=0,\\ \dfrac{A_i^G(t)}{\min\!\left(q_i,D_i^G(t)\right)}, & D_i^G(t)>0. \end{cases} $$</div>
  • A_i^G(t)：当前已经分配的 Guaranteed GPU，Best-effort 不计入。
  • min(q_i,D_i^G(t))：当前应兑现的 Guaranteed GPU。
  • Q_i(t)：瞬时兑现率；Q̃_i(t)：EMA 平滑后的控制信号。

输出：同一个 Q̃ 驱动三类决策

  1. 恢复排序：Q̃ 越低，租户越欠保障，越先调度。
  2. 共享收紧：任一租户 Q̃ 低时，提高所需 throughput retention 门槛；极端时停止创建新 colocation。
  3. QoS 报告：用连续的保障度观察长期 deficit，而不是只看“是否超 quota”的二值状态。

注意：QAD 不直接无条件触发删除 Pod。GPU 抢占由 Guaranteed 作业 placement failure 触发，PostFilter 再用代价模型选 Best-effort victims。

五个扩展点怎么串起来

Filter 之后存在分支：有可行节点时进入打分、预留与绑定路径；没有可行节点时才进入 PostFilter 尝试抢占。PostFilter 不在 Reserve 之后顺序执行。Permit 在这里用于等待 CPU / Memory resize 状态，不是等待 GPU 抢占释放的通用屏障。

故障恢复与热路径

  • Plugin 以多副本 Deployment 运行，通过 Lease 选主。
  • QAD 可从 informer cache 的运行 Pod 推导；新 leader 用首轮瞬时 QAD warm-start EMA。
  • 抢占通过 Pod deletion 发起，由节点的 kubelet 和容器运行时执行终止。API 接受删除请求不等于资源释放；后续分配必须依据实际终止与资源状态。Pod 删除本身不提供训练 checkpoint 或透明恢复。
  • 调度端到端延迟低于 50ms，其中特征提取、队列记账和受限候选打分合计低于 25ms。
Q: 面试官问“两级队列和 QAD 到底怎么连起来”，怎么回答？

每个租户先在自己的 Guaranteed / Best-effort 队列做 quota admission；通过后进入对应的集群级队列。集群级排序先保证 Guaranteed 优先，再用平滑 QAD 让欠保障租户先恢复，只有在保障程度相近时才用预测剩余时间做短作业优化。QAD 因此负责跨租户公平，runtime prediction 只负责局部效率。

DeepShare 高频问答

Q: QAD 和 DRF（Dominant Resource Fairness）的区别？

DRF 用 dominant share 在多资源之间追求 max-min fairness；QAD 则衡量单个租户当前 Guaranteed 权益的兑现率。QAD 的分子只算 Guaranteed allocation，Best-effort 借用单独记账，因此 QAD 位于 0 到 1，不用 QAD>1 表示超额资源。QAD 还能同时驱动租户恢复排序、colocation 准入和 QoS 报告，而 DRF 主要回答公平分配问题。

Q: 为什么 JCT 只改善 6.3% 但排队延迟改善 46%？

JCT = 排队时间 + 执行时间。执行时间由计算量决定，对所有调度策略相同。调度只能影响排队部分。当执行时间占 JCT 主要部分时，排队大幅改善只带来 JCT 小幅改善。这恰好说明调度的优化空间集中在排队环节。

Q: nvidia.com/gpu 不可修改，GPU 共享怎么实现？

K8s Extended Resource admit 后不能修改。GPU 共享通过 NVIDIA MPS 在驱动层做多路复用，设 per-client 内存限制。每块 GPU 部署一个 MPS control daemon（DaemonSet 方式）。CPU 和内存可通过 InPlacePodVerticalScaling 动态调整，但 GPU 分配必须在调度时确定。

Q: 干扰模型为什么选 Random Forest 而不用深度学习？

三个原因：(1) 推理延迟——RF 推理 < 1ms，满足实时调度预算；对比 GAN-based 方法需要 50-200ms。(2) 精度足够——R² = 0.902。(3) 硬件计数器特征跨框架泛化，不需要针对每种模型架构重新训练。

Q: 过载时怎么表现？

大约 8% 高峰时段过载：按 QAD 升序优先最欠缺租户；最坏 QAD = 0.72，过载消退后 3.2 个周期（约 160ms）恢复到 ≥ 0.95。Best-effort 排队延迟增加 2.1 倍，Guaranteed 仅增加 14%，体现服务分级。

实现细节高频问答

Q: QAD 存在哪里？调度路径如何读？

论文实现中，Scheduler Plugin 在内存里维护瞬时 Q_i(t) 和平滑 Q̃_i(t)。原始状态来自 informer cache 中的运行 Pod，因此故障切主后可以重建，并用首轮瞬时 QAD warm-start EMA，不需要把每轮 QAD 写回 CRD。Controller 只把 TenantQuota 和作业 class annotation 整理成 quota 元数据，不承担实时 QAD 控制环。

Q: Controller 和 Scheduler Plugin 到底怎么分工？

Controller 管配置态，Plugin 管决策态。Controller reconcile TenantQuota CRD 和 deepshare.io/class annotation，形成租户 quota、Best-effort cap 和作业类别元数据；Scheduler Plugin 维护实时队列与 QAD，完成排序、Filter、Score、Reserve、PostFilter 抢占和 Permit 等待 resize。这样实时信号和所有放置决策留在同一个调度控制环里。

Q: 为什么不全放 Controller？

Controller 是异步 reconcile 配置态的组件，不拥有单次 scheduling cycle 的节点快照、候选打分和 assumed state。DeepShare 的 QAD、队列排序、干扰准入和抢占必须和 Filter / Score / Reserve / PostFilter 处在同一个实时控制环里，所以由 Scheduler Plugin 完成；Controller 只提供 quota 与 class 元数据。

Q: Best-effort 是怎么借用和归还的？

Scheduler 仅在没有可放置的 Guaranteed 作业、且租户 Best-effort 用量满足 U_i^B + R_j ≤ η·q_i 时考虑 Best-effort。Guaranteed 作业放置失败后，PostFilter 才按低代价策略选择 Best-effort victims；所以 QAD 负责决定谁更急需恢复，真正触发 GPU 抢占的是 placement failure。本质：可借、单独记账、需要时可回收。

Q: 不考虑 Gang Scheduling 后流程能简化什么？

不需要讲 PodGroup、minAvailable、等待全部 worker 到齐或整组回滚。论文的五个扩展点是 Filter / Score / Reserve / PostFilter / Permit；其中 Permit 只在 CPU/Memory in-place resize 发起后等待 Pod 状态更新，不用于 Gang Scheduling。如果以后支持多 worker 训练，才需要给 Permit 增加 PodGroup 级等待语义。

论文原文延伸问答（基于 IEEE Cluster 2026 原稿）

下面这组问题对应面试官真正会按论文细节追问的角度：参数选取、消融、敏感性、对比 baseline、工程边界。回答全部出自论文正文与 §V 实验。

Q: 论文里 EMA 系数 λ=0.3、调度周期 50ms，物理意义是什么？

论文 §III-A 给的解析：在 50ms 调度周期下，持续偏差在大约 350ms 内累积到稳态值的 90%，几何收敛速率为 \((1-\lambda)\)。这个区间能 过滤亚秒级抖动（短任务结束、突发请求），同时让真正的"持续 under-service"快速被发现。λ 再调大会被短任务完成的抖动带飞，调小则恢复信号迟滞。

Q: 当租户暂时没有 Guaranteed 需求时 QAD 怎么定？为什么不直接定 0？

论文 Eq.1 显式规定 \(Q_i(t)=1\) 当 \(D_i^G(t)=0\)。这是为了 "暂时不用 quota ≠ 被亏待"：定 0 会让空闲租户被错误识别为最受损者并抢回资源；同时分母用 min(q_i, D_i^G(t)) 又防止租户通过虚报巨大 \(D_i^G\) 压低 QAD、抬高恢复优先级。这两条共同实现"既不奖励虚假 demand，也不惩罚临时空闲"。

Q: 干扰预测为什么选 Random Forest？论文给的理由是什么？

这里问的是干扰预测器，不要和运行时间预测混在一起。论文 §III-C 的考虑包括：(1) sub-millisecond 推理，可以放在 Kubernetes scheduler 关键路径上；(2) RFE 选出的主特征是 SM Active (44.5%)、co-run SM Active (20.6%)、mem copy util (12.3%)，与干扰来源相符且可解释；(3) 输入是 DCGM 硬件计数器，跨 framework / model 更容易泛化。它预测共享吞吐保持率，\(R^2=0.902\)。31.84% MAPE 和 \(R^2=0.7286\) 属于另一个 per-tenant gradient boosting 运行时间预测器，不能拿来证明 Random Forest 的准确率。

Q: 抢占代价为什么按一张卡上的完整任务集合计算？

共享卡上只停一个任务，不能保证整张卡可供新任务使用。因此论文 Eq.3–5 先筛选清退后资源足够、且驻留任务全部为 Best-effort 的设备，再计算其完整任务集合的代价：

$$\Phi(J)=\sum_{j\in J}\frac{1+\alpha C_p(j)}{\hat T(j)}+\frac{\beta(|J|-1)}{\bar T(J)}$$

T̂(j) 是预测剩余时间，C_p(j) 是归一化累计抢占开销，T̄(J) 是集合内的平均剩余时间。第一项保护快完成和累计打断开销高的任务；第二项惩罚同时打断多个任务。取 d*=argmin Φ(V(d))，先预留设备，再清退其全部任务，释放后绑定新任务。没有可行设备就继续排队。默认 α=0.5、β=0.3。这是候选设备代价排序，不是按单任务 GPU-时收益逐个累加的背包贪心。

Q: 共享时光靠 RF 准入会不会被打脸？运行时怎么兜底？

会，所以论文叠了一层在线检测：DCGM 周期采样实际 retention \(\hat{\rho}=t_{shared}/t_{excl}\)，连续 3 个采样窗口 \(\hat\rho<\rho_{tol}\) 就把这一对标 degraded，下一周期把 Best-effort 伙伴抢占。固定窗口规则相比 CUSUM 等顺序检测的好处：检测延迟有界 + 每对只维护一组计数器，落到调度器里行为更可预测。一对 GPU 上发生干扰漂移时不会拖到 Guaranteed 任务才被发现。

Q: 动态容忍 \(\rho_{tol}\) 里的压力 \(P\) 和 \(\gamma\) 是怎么调的？

论文公式：

$$P = \left(\frac{G_p}{G_f+\epsilon}\right)^{\gamma},\quad \rho_{tol} = \min\!\big(1,\;[\rho_{min} + P(1-\rho_{min})] \cdot \max(k-\tilde{Q}_i,\, k-\tilde{Q}_{ie})\big)$$

\(\gamma=0.5\) 让压力亚线性增长，短促 demand burst 不会立刻把所有 colocation 一刀切关掉；最大值再被任一租户的"欠服务度" k - Q̃ 放大，欠服务越严重门槛越高。Sensitivity 显示 \(\rho_{min}=0.7\) 是甜点：0.5 时 GPU 利用 71.2% 但平均放慢 18%，反而 JCT 倒挂；0.9 时干净但只剩 55.3% 利用率。

Q: 31.84% MAPE 是怎么得到的？冷启动用户怎么办？

Venus 23,859 jobs 上采用按租户训练的 gradient boosting regressor。总体 MAPE 为 31.84%，\(R^2=0.7286\)；历史提交 ≥50 的老租户 MAPE<25，新租户落到集群级 fallback 模型，MAPE<60。冷启动不会阻断调度，只是时间排序不那么准。Figure 4 在随机 2000 jobs 上对照 real vs prediction；即使长尾作业误差较大，也不会覆盖 QAD 主排序，因为 \(\hat{T}(j)\) 只是 secondary key。

Q: nvidia.com/gpu 是 K8s Extended Resource，论文怎么绕开"准入后不可修改"？

论文 §IV-B 明确：GPU 数确实改不了，所以 DeepShare 不动 GPU 数；要释放资源时走两条路。
(1) CPU/Memory 走 Pod resize subresource：control plane 必须启用 InPlacePodVerticalScaling，VPA 推荐基础上额外保留 max(10%, 0.5 core) CPU 和 max(10%, 256 MB) memory headroom，避免压缩后 OOM。
(2) GPU 抢占走删 Pod / 重建：通过 PostFilter 选 victim 后由 API server 删除 Pod，新 Pod 重新进入 scheduler。这是为什么论文必须在 §IV 里强调依赖 K8s v1.35 的新 subresource。

Q: 集群过载（\(\sum \min(q_i, D_i^G) > G_{tot}\)）时 DeepShare 怎么降级？数据多少？

论文 §V-D 给出量化：Venus peak-hour 中约 8% 周期会进入过载。Algorithm 1 按 \(\tilde{Q}_i(t)\) 升序排队，近似 max-min fair recovery。可观测后果：
· 单租户最差 \(\tilde{Q}_i=0.72\)；
· spike 之后 3.2 个 cycle (~160ms) 恢复到 \(\tilde{Q}_i\ge 0.95\)；
· Best-effort 排队延迟 2.1×，Guaranteed 仅 +14%——这就是"服务差异化"在论文里的实际兑现。

Q: Ablation 里"DRA 单独"和"DRA + colocation"分别贡献多少？

物理 16-GPU testbed（§V-E Figure 11）：
· DRA 单独 vs Hard：makespan −23%、JCT −18.5%、queue −36%；
· DRA + Colocate vs Hard+Colocate：makespan −32%、JCT −34%、queue −66%；
· DRA + Colocate vs DRA-only 再省 31% 排队（Figure 10），整体 throughput 1.48×。
仿真消融（Figure 7）：去掉 runtime prediction 排队 +18.4%，去掉 interference awareness 排队 +30.1%——结论是 colocation 的贡献 > runtime prediction，但两者必须由 QAD 兜住才不会反过来伤害 SLA。

Q: 为什么平均 JCT 只比 Lucid 好 6.3%，但论文还是把 JCT 当卖点？

论文 §V-C 直接解释了：JCT = queueing + execution，execution 部分各策略基本一样，所以平均 JCT 改善被稀释。真正能差异化的是排队侧——论文给出 queueing −46%（1067s vs 1976s）、P95/P99 tail JCT −23%、idle GPU time −71%（vs Lucid）/ −96.8%（vs FIFO）。面试时讲"为什么 JCT 看起来涨幅有限"是高频反向追问，要答：DeepShare 主战场是 排队公平性 + tail-latency，平均 JCT 不是核心指标。

Q: 论文承认哪些局限？（部署前你会注意什么）

§V-G 明文承认四条：
(1) 干扰预测器在 16 个 DL 模型族（CV/NLP/RL/recommender） 上训练，未见架构（如新型 MoE）可能要重训；硬件计数器为输入提供一定泛化。
(2) 物理 testbed 只有 16 GPU，结论稳妥外推到 部门级集群（数十至低三位数 GPU），更大规模需要重新评估。
(3) 异构加速器（如 H100、TPU、国产卡）需要重新 profiling 并重训 RF 干扰模型。
(4) 论文未覆盖 多 node 分布式训练 / Gang Scheduling 场景，generalize 到 LLM 大集群训练需要补 PodGroup + Permit 扩展点（可主动补充作为面试加分）。

Q: 跟 Lucid、Tiresias、Gavel、HiveD 这些 prior art 的本质差异点是什么？

论文 §VI Related Work 总结：

Q: 请挑一个你最熟悉的工作介绍一下。

1. 背景：固定配额和资源共享存在天然矛盾

我想介绍一下 DeepShare，这是我们面向多租户 GPU 集群设计的、以配额保障为核心的资源管理系统。

它的背景是，企业里的 GPU 集群通常由多个团队共享。平台会给每个租户一个 quota 来保证公平，例如 A 团队 32 张卡、B 团队 16 张卡。但是各团队的需求具有明显的突发性：B 当前没有任务时，如果它的 16 张卡仍被静态保留，A 的作业即使在排队也不能使用，集群利用率会很低；如果允许 A 借用，B 的 Guaranteed 作业回来时，又必须及时拿回自己的资源，否则 quota 只是纸面承诺。

GPU 内部还有第二层浪费。很多训练作业受数据加载、CPU 或通信阶段影响，并不会一直打满 SM 和显存带宽。把两个作业放在同一张 GPU 上可以提升利用率，但盲目合用会产生不可控干扰，反而拖慢 Guaranteed 作业。

因此核心矛盾是：既想通过跨租户借用和卡内合用提升利用率，又必须把租户的配额保障真正兑现出来。

2. 动机：现有方法分别优化局部，却没有统一保障语义

现有工作往往只解决其中一个局部问题：固定 quota 能保证隔离但浪费资源；短作业优先能降低平均等待，却可能让某些租户长期得不到保障；GPU sharing 能提高利用率，却不一定知道当前能否承受干扰。

所以我们的判断是，问题不只是缺少一个更复杂的调度算法，而是 quota 借用、队列排序、抢占回收和 GPU 合用之间，缺少一个统一的反馈信号。系统需要随时回答：哪个租户当前最欠保障？

3. 核心设计：用 QAD 表示配额兑现程度

DeepShare 引入 QAD，也就是 Quota Assurance Degree：

$$Q_i(t)=\frac{A_i^G(t)}{\min\!\left(q_i,D_i^G(t)\right)}$$

分子 A_i^G(t) 是已经分给租户 i 的 Guaranteed GPU 数量；分母 min(q_i, D_i^G(t)) 是系统此刻真正应该保障的 GPU 数量，也就是 quota 和当前 Guaranteed demand 中较小的一个。直观上就是：已经兑现多少 / 此刻应该兑现多少。

如果租户没有 Guaranteed demand，QAD 直接定义为 1，因为“暂时没用 quota”不等于“被系统亏待”。Best-effort 借来的卡不计入分子，所以 QAD 的范围是 0 到 1，不会因为借用资源大于 1。系统还用 EMA 平滑瞬时 QAD，避免短任务完成或突发请求造成频繁抖动。

4. QAD 统一驱动三个机制

第一，弹性配额借用 DRA。租户没有用满 quota 时，闲置 GPU 可以借给其他租户运行 Best-effort 作业；原租户的 Guaranteed demand 回来后，如果资源不足，系统就回收这些可借用资源。这样 quota 从静态分区变成了“可借但必须能还”的保障承诺。

第二，QAD-first 的预测调度。调度器先按平滑 QAD 升序选择租户，保障不足的租户先调度；只有在 QAD 相同或接近时，才使用预测剩余运行时间让短作业优先。抢占时也会结合可释放的资源、剩余时间和抢占代价选择 victim。因此，预测负责优化效率，QAD 负责守住公平性。

第三，QAD-aware 的干扰感知合用。系统预测两个作业共享 GPU 后的吞吐保持率，并结合当前资源压力和租户 QAD 动态调整准入阈值。租户越欠保障，系统对它受到的干扰越保守；保障充分时，才更积极地合用 GPU。

5. 两个预测模块分别怎么做

运行时间预测模块：我们观察到租户的提交具有重复性，78% 的用户会反复提交特征和时长相近的作业，因此论文正文采用 per-tenant gradient boosting regressor，利用每个租户自己的历史作业学习其工作负载规律，输出预测剩余运行时间 T̂(j)。历史不足的新租户使用 cluster-wide fallback model。它有两个用途：一是在 QAD 之后作为第二排序键，降低平均排队时间；二是在抢占时帮助判断一个 victim 还剩多久、现在打断是否划算。Venus 23,859 个作业上的 MAPE 是 31.84%，R² = 0.7286。历史提交不少于 50 次的租户 MAPE 小于 25%，冷启动 fallback 的 MAPE 小于 60%。原文没有进一步列出该模型的具体特征向量，所以面试时不要自行补成 DCGM 特征。

干扰预测模块：这里使用的是 Random Forest。输入不是模型名字，而是 DCGM 采集的硬件遥测，例如 SM activity、显存带宽、L2、PCIe、Tensor Core、DRAM throughput 和功耗等；输出是两个作业合用时的吞吐保持率 ρ̂。采用硬件计数器有两个好处：一是跨框架、跨模型更容易泛化；二是 Random Forest 可以在 scheduler 关键路径上实现亚毫秒级推理。论文中该模型的 R² = 0.902。

预测本身不是安全保证，所以 DeepShare 还做了运行时闭环。DCGM 会持续监控实际保持率；如果连续 3 个采样窗口低于容忍阈值，就把这对合用标为 degraded，并在下一调度周期驱逐 Best-effort 伙伴，优先保护 Guaranteed 作业。

6. 工程实现和实验结果

工程上，我们把系统实现成 Kubernetes 的轻量 Controller 加 Scheduler Plugin。Controller 负责 TenantQuota 和作业类别等静态元数据；Plugin 维护实时 QAD 和两级队列，并在 Filter、Score、Reserve、PostFilter、Permit 等扩展点完成合用准入、放置、资源预留和抢占。

在 Venus 23,859 个作业的 trace-driven 实验中，DeepShare 把 GPU 利用率从 39.64% 提高到 70.58%，相对 Lucid 提升 29.5%；平均排队时间相对 Lucid 降低 46%。消融实验中，移除运行时间预测后排队时间增加 18.4%，移除干扰感知后增加 30.1%。在 16-GPU 物理集群上，完整方案相对 Hard+Colocate 将 makespan 降低 32%、JCT 降低 34%、排队时间降低 66%，租户周期的 QoS 合规率达到 93%。

7. 收尾：这项工作的核心贡献

所以我认为 DeepShare 最关键的贡献，不是单独提出一个预测器或一个共享策略，而是把配额保障变成一个可观测、可反馈的 QAD 控制信号，再让弹性借用、时间调度和空间合用围绕同一个目标闭环。最终实现的是：资源空闲时敢于共享，租户保障不足时能够及时、可解释地收回来。

面试官打断时，用这四句保住主线

  1. 背景：固定 quota 保公平但浪费，动态共享提利用率但可能还不回来，也可能引入干扰。
  2. 核心：QAD = 已经兑现的 Guaranteed GPU / 此刻应该兑现的 Guaranteed GPU。
  3. 设计：QAD 同时控制资源借用与回收、队列排序与抢占、GPU 合用准入。
  4. 预测器：Gradient Boosting 预测剩余时间、优化先后顺序；Random Forest 预测共享干扰、优化放置位置。
Q: 为什么不把两个预测任务合并成一个模型？

因为它们的决策对象、数据和错误后果都不同。运行时间预测面向单个作业和租户历史，回答“还要多久”，主要影响队列顺序和抢占收益；干扰预测面向作业对和硬件遥测，回答“放在一起会慢多少”，直接决定共享准入。拆开后可以独立训练、独立回退，也能分别设置安全边界。

Q: 运行时间预测误差有 31.84%，会不会破坏公平性？

不会直接破坏租户公平性，因为调度是词典序：先比较平滑 QAD，再比较 T̂(j)。预测错误只会让同一保障层级内的短作业排序不够理想，不能让一个高 QAD 租户越过一个低 QAD 租户。也就是说，QAD 是安全主键，运行时间只是效率次键。

Q: 干扰预测错了怎么办？

预测只负责准入，运行时监控负责兜底。系统持续用 DCGM 观察实际吞吐保持率，连续 3 个窗口低于动态阈值就降级这对合用，并抢占 Best-effort 伙伴。这个“离线预测 + 在线纠偏”闭环，比只相信模型输出更适合生产调度系统。

Q: 你认为这项工作里最重要的设计判断是什么？

最重要的判断是把预测放在保障机制之下，而不是让预测结果直接定义公平性。QAD 负责表达租户权益是否兑现，两个预测器只在不越过这条边界的前提下优化时间和空间效率。这样即使模型存在冷启动、分布漂移或预测误差，系统仍然有可解释的保障顺序和在线回退路径。

GPU 作业的资源需求为什么不该是固定值

我介绍的这项工作是 ElastiCo，面向训练和离线推理共同运行的 GPU 集群。离线推理包括批量标注、模型评估等任务，它更关注整体吞吐和完成时间。我们观察到，传统调度通常把一个作业看成固定资源请求：需要几张卡、多少显存，然后寻找能放下的位置。但同一个作业换一种执行配置，资源需求和吞吐都可能变化。

例如训练开启激活重计算，可以少存一些中间结果，代价是反向传播时多做计算；减小 micro-batch 也能降低显存，但可能影响吞吐。推理则可以调整并发 batch、缓存策略和显存预算。如果调度器只接受用户提交时的一种配置，就可能认为作业放不下，而实际上稍微调整配置就能和其他作业共同运行。

但仅仅压缩资源也不够。每个任务都选择占用最少的配置，可能使大家都变慢；直接把能放下的任务堆在一起，又可能因为算力、带宽争用产生严重干扰。ElastiCo 因此联合决定每个作业采用什么配置、占多少资源、与谁合用，以及放在哪里。

先把一个作业变成多种可选配置

第一个模块是资源形态变换。它枚举框架已有的配置开关，例如训练的 micro-batch、激活重计算和混合精度，以及推理的 prefix caching、batch 上限和显存使用比例。对每种可行配置，在预热后采样测量资源占用和吞吐，形成一组资源与性能的候选档案。

这里的形态是多维的，既包括 GPU 显存和计算压力，也包括 CPU、主机内存。同一个训练作业可能有一个吞吐更高但占显存更多的配置，也有一个稍慢、但能腾出空间的配置。系统还保留最低性能要求，不能为了塞进更多作业就无限降低单个作业的吞吐。

用影子价格表达当前什么资源最紧张

有了这些候选，第二个模块用影子价格来选配置。可以把每种资源理解成有一个随供需变化的内部价格。每个作业比较配置的性能损失、占用资源的代价，以及切换配置和干扰的惩罚，选一个综合成本较低的方案。

比如集群显存总需求超过容量，就提高显存价格。此时，高显存配置变贵，一些作业就可能改选启用重计算的配置，用额外计算换取显存。反过来，如果计算资源更紧张，系统就不一定愿意继续增加重计算。这种价格不是给用户计费，而是让各作业在同一套资源稀缺信号下做选择。

每轮选择后，再按总需求与容量的差更新价格，逐步把需求推向可行范围。因为配置是离散的，后面还有放置和干扰约束，所以不能仅凭价格迭代就宣称得到了全局最优解。

把共置干扰反馈回配置选择

第三个模块预测合用后的 slowdown。论文使用一个轻量全连接网络，输入包含硬件利用特征、作业类型与配置，以及两个作业组合后的资源压力。训练数据来自先单独运行、再两两合用的测量，并分别预测两个参与者会慢多少。

假设容量检查允许一个训练作业和一个推理作业共用 GPU，但模型预测其中一个会严重下降，那么系统给这组配置增加干扰惩罚，再重新选择配置和放置，而不是把容量可行直接当成性能可行。合用也不局限于训练和推理这一种组合，还包括训练之间、推理之间；每个参与者都有自己的性能要求。

最后由统一调度循环把它们串起来：为排队作业留出容量，更新价格，选配置，做装箱放置，再检查干扰。必要时反馈惩罚并重复若干轮，之后执行配置切换、放置或迁移。切换本身有成本，重配置可能需要检查点恢复，不能假设所有变化都能毫秒级无损完成。

资源向量包含 GPU SM、GPU 显存、CPU 和主机内存；性能档案记录单独运行的吞吐。配置缺失时，论文采用近邻插值提供临时估计，后续用真实测量替换。这里的“形态变换”指执行配置引起的资源—性能变化，不等于直接切分 SM 或自行映射 VMM 页面。

ESP 怎样选配置

每个作业比较配置的归一化吞吐损失、资源租金与惩罚：

\[ Score_j(c)=1-\frac{T_j(c)}{T_j(c_j^{max})}+\sum_r\lambda_r R_j(c)[r]+\Gamma_j(c) \]

其中价格反映集群中每类资源的稀缺程度，惩罚包括切换配置和过量干扰。选完配置后，再用总需求与容量之差更新价格：

\[ \lambda_r^{t+1}=\max(0,\lambda_r^t+\eta_t(U_r-C_r)) \]

显存需求超过容量时，提高显存价格，推动部分作业选择显存更小的配置；计算资源紧张时，计算密集的替代配置也会变贵。影子价格是内部优化信号，不是实际账单。离散配置与放置仍需要可行性检查，价格迭代不构成全局最优保证。

IAC 怎样预测与反馈

论文使用三层全连接网络，以 36 维特征预测有方向的 slowdown：单独吞吐除以合用吞吐。特征包括每作业硬件利用、作业与配置属性，以及作业对的显存压力和资源互补程度。一对作业产生两个预测，分别描述双方受到的影响。

合用对象覆盖训练—训练、训练—推理、推理—推理。每个参与者都有性能要求，不是固定“训练永远为主、推理永远被驱逐”。超过容忍阈值的组合会给对应配置增加惩罚，重新进入选配置和放置过程。阈值与吞吐约束仍须结合验证，不能把点预测理解成无条件性能保证。

高频追问

Q: 为什么叫资源形态变换，而不是普通资源分配？

普通放置常把资源请求视为固定输入；RST 先用框架配置生成一组资源—性能档案，让调度器能改变作业本身的资源需求。例如重计算改变计算与显存的比例，再决定这个配置适合与谁共置。

Q: 影子价格与 DeepShare 的 QAD 有什么区别？

QAD 衡量租户保障兑现程度，主要约束跨租户服务顺序；影子价格按资源维度表达集群稀缺程度，影响作业配置的选择。前者是保障反馈，后者是多资源优化信号。

Q: 配置切换与 checkpoint 怎样处理？

论文优先考虑配置调整，并计入切换惩罚；需要重配置或迁移时使用框架检查点与恢复，推理可通过引擎排空后重启。训练也可能调整或迁移，不能声称所有变化都只作用于推理，或都有固定的 2–5 秒开销。

Q: 无需修改用户代码是怎么实现的？

论文通过 CUDA 库拦截和硬件计数器进行观测，用 Pod 参数、框架已有配置及恢复接口执行决策。非侵入不代表能任意改动正在运行的程序；具体框架仍需支持所选配置与状态恢复。

Q: MPS 调整需要多长时间，是否逐阶段改变 SM 比例？

不能把这套方法概括为通过修改环境变量实时改变现有进程的 SM 份额。论文的调度对象是配置及其预算，预算通过启动或重启参数下发；调度周期、重配置和迁移时间是不同口径，应分别测量。

Q: 请完整介绍一下你的多目标训练性能预测工作。

问题：新训练任务放到哪种 GPU，不能每次都先跑一遍

我做过一项深度学习训练作业的多目标性能预测工作，目标是在任务真正运行前，估计它在不同 GPU 和执行配置下的性能与资源需求，为异构集群调度提供依据。

这个问题的直接做法是 profiling：把模型分别放到候选 GPU 上，用不同 batch 跑一遍，再记录时延和资源指标。实测很可靠，但模型、batch、精度和 GPU 类型组合起来以后，采样成本会迅速增长。另一种简单方法是看参数量或 FLOPs，但它们主要反映规模，看不到算子类型、张量形状、数据依赖和具体硬件的差异。

因此，这项工作的核心问题是：能不能只根据模型计算图、运行配置和目标 GPU，在不完整执行训练任务的情况下，同时预测速度、容量和设备利用情况？

表示：把 ONNX 计算图变成预测输入

我们先把模型转换成 ONNX 计算图。图中的节点表示算子，包含算子类型、输入输出张量形状和数据类型等特征；边表示张量的数据依赖。图之外再加入 batch、精度和目标 GPU 等执行条件。

这样建模的原因是，相同参数量或相近 FLOPs 的模型，执行行为仍然可能不同。算子组合、串并行依赖、中间张量大小和访存方式都会影响端到端时间与峰值资源；同一张计算图换到不同 GPU 上，算力、显存容量和带宽也会改变结果。

模型：用 Graph Transformer 做七目标联合回归

预测器使用 Graph Transformer 聚合节点和依赖信息，得到整个训练图的表示，再与运行配置和 GPU 条件融合，联合输出七项性能与资源指标。现有材料明确包含训练时延、GPU 利用率、SM 活跃度和显存相关指标；七项指标的完整名称以实验记录为准。

这里采用多目标预测，是因为调度器只知道时延并不够。预测最快的设备可能显存放不下；GPU 利用率很高，也不一定代表有效计算效率高。把时延、容量和硬件活动指标放在一起，调度器才能先做可行性过滤，再比较任务放在哪类 GPU 上更合适。

多目标任务共享同一份计算图编码，但不能仅凭这一点就断言它们一定互相促进。是否优于七个独立模型，需要通过单目标、多目标和不同损失权重的消融实验验证。

训练与泛化：用实测结果监督，按未见组合检验

训练标签来自任务在真实 GPU 上的运行结果。项目材料记录，这套方法在跨模型、batch 和 GPU 的测试中，七项指标的 WAPE 低于 5%。这里的 WAPE 是绝对误差总和除以真实值总和，表示整体加权误差；它不表示每个样本的误差都低于 5%，也不能单独保证显存从不被低估。

泛化评估的关键是数据怎样划分。如果同一个模型的相似 batch 同时出现在训练集和测试集里，误差很低也可能只是学会了这个模型的局部变化。要说明跨模型泛化，应按模型或模型家族留出；要说明跨硬件泛化，则需要留出 GPU 类型或架构组合，再分别报告各目标误差和低估尾部。

如果新模型只是把已见算子重新组合，图结构和算子特征能够提供迁移依据；如果出现新的算子、kernel 或 GPU 架构，就需要补充少量代表性测量做校准或更新模型，并降低调度器对分布外预测的信任。

落地：离线生成资源画像，在线调度查表

系统接入时，我不会要求调度器每次选卡都同步运行一次完整的 Graph Transformer。更实际的方式是离线为常见的模型、batch 和 GPU 组合生成资源画像，在线调度直接查询；遇到新组合时，再异步预测或做少量 profiling 校准。

调度时先用显存等容量指标排除不可行设备，再用时延和资源效率比较剩余候选。预测之外仍然要设置安全余量，并在任务运行后收集真实结果，监测持续偏差。这样即使预测发生漂移，容量检查和调度规则仍然能够工作，而不是让一个回归值直接决定全部资源动作。

贡献：把计算图预测转成调度可以使用的多维资源信息

这项工作的贡献不是简单地“用了 GNN”，而是把 ONNX 图结构、执行配置和异构 GPU 条件统一起来，联合预测调度真正需要的多类指标，并用跨模型、batch 和 GPU 的实验检查泛化。已有材料中的总体 WAPE 低于 5%，说明预测误差较小；最终是否改善作业等待时间、完成时间和集群利用率，还需要在具体调度策略中继续验证。

这项工作在中文材料中是 2025 年 12 月到 2026 年 5 月的独立项目。SagePilot 后续也使用计算图资源预测，但它的研究对象还包括 Agent 工作流的模型准备、链融合和运行编排；面试时我会把两项工作的预测实验和系统贡献分开说明。

Q: 如果只有一分钟，怎么介绍这项工作？

我做过一个深度学习训练作业的多目标性能预测项目。它解决的是异构 GPU 集群里新任务选卡的问题：如果每种模型、batch 和 GPU 组合都先完整 profiling，成本很高；只看参数量或 FLOPs，又看不到算子结构和硬件差异。

我们把模型转换成 ONNX 计算图，节点表示算子并带上张量形状等特征，边表示数据依赖，再加入 batch、精度和目标 GPU 条件，用 Graph Transformer 联合预测训练时延、GPU 利用率、SM 活跃度和显存等七项指标。已有材料中，跨模型、batch 和 GPU 测试的 WAPE 低于 5%。

预测结果可以离线形成资源画像，在线调度先检查显存是否可行，再比较完成时间和资源效率。平均误差之外，我还会关注分布外模型、显存低估尾部以及预测接入调度后是否真的改善作业完成时间。

Q: 为什么需要 Graph Transformer，FLOPs 不够吗？

FLOPs 是有价值的计算量基线，但相同 FLOPs 可能来自不同算子和张量形状，实际执行还受访存、临时工作区、算子依赖和硬件实现影响。计算图能保留这些结构信息，Graph Transformer 再聚合整个图的上下文，因此有机会区分规模相近但执行行为不同的任务。

这不意味着图模型天然优于公式。合理的实验应把参数量、FLOPs、解析估计和传统回归作为基线，同时比较误差、采样成本和最终调度收益。

Q: 七个目标为什么放在一个模型里？会不会互相干扰？

七个目标都由同一份计算图、执行配置和 GPU 条件产生，共享编码器可以复用共同的结构信息；不同输出头再学习时延、容量和利用指标各自的映射。这样还能减少维护多个完全独立模型的成本。

目标之间也可能冲突，例如某个损失量级较大时主导梯度，或者对时延有用的表示不一定最适合显存。需要统一量纲或设置损失权重，并通过单目标与多目标消融、各目标误差和梯度冲突检查判断。没有消融结果时，不能把“共享表示”直接说成准确率提升的原因。

Q: WAPE 低于 5% 能保证调度安全吗？

不能。WAPE 汇总的是整体绝对误差，数值较大的样本权重更高；它不等于每个样本都落在正负 5% 内。少量显存严重低估仍然可能造成 OOM，小的时延误差也可能在两个候选很接近时把排序颠倒。

因此容量指标要额外看低估分位数和覆盖率，调度准入保留安全余量；时延预测则要看排序正确性，以及接入调度后的等待时间和完成时间。运行后继续用真实观测校准，而不是只依赖离线平均指标。

Q: 没见过的模型、算子或 GPU 怎么处理？

新模型如果主要由已见算子重新组合，可以利用算子属性和图结构迁移；真正的新算子如果只有未知类别编码，信息就不足，需要加入计算量、读写量等可解释特征，或者对它做少量 profile。新 GPU 也要提供硬件特征，并用代表性任务校准。

工程上还应做分布外检测或至少设置适用范围。遇到明显超出训练分布的组合，回退到保守估计或 profiling，并限制预测驱动的激进放置。测试集则应按模型家族和 GPU 类型留出，避免随机拆分制造过于乐观的泛化结果。

SagePilot

Q: 请介绍一下 SagePilot 这项工作。

我讲的工作是 SagePilot，它解决的是：多个 Agent 工作流同时使用一小批异构 GPU 时，怎样让用户任务更快完成。

我先解释一下这里的工作流。比如用户提出一个代码修复任务，系统会先分析问题，再生成代码，接着运行测试，测试失败后再修改。这里每一步可能调用模型，也可能调用工具，前后有依赖关系。这样的一个完整任务，就是一个工作流。

当很多用户任务同时到来时，它们会共享底层 GPU，而且不同步骤可能使用不同模型。我们关注的就是：GPU 数量有限，不能让所有模型一直驻留，那模型什么时候加载、请求什么时候执行、用完后模型要不要保留，应该怎么安排？

我们发现，单纯调整请求的执行顺序不够。论文的动机实验里，请求等待时间大约八成都花在等模型可用上。同时，总 GPU 占用时间里，又有约三成是模型已经加载、却没有执行生成。

这意味着，即使一个请求排到了前面，模型没准备好，它还是跑不了；而另一张卡上，可能正放着一个暂时没人使用的模型。所以我们需要把请求调度和模型管理放在一起考虑。

用一个例子说明。假设一个任务有三步：A 用模型 M1 生成初稿，B 继续用 M1 修改，C 再用模型 M2 检查。

如果每一步都独立申请资源，A 完成以后，B 就要重新争取 M1 的执行机会。资源竞争时，中间可能排队，甚至遇到实例被回收。等 B 完成，C 才提出对 M2 的需求，又要等待模型加载。

但从工作流来看，这些需求其实可以提前知道。

首先，A 和 B 连续使用同一个部署。如果它们之间没有分叉、配置也兼容，我们可以把它们作为一组，一次申请实例，在两步完成前保持实例可用。两次生成仍然分别执行，结果也照常传递，只是中间不用重新申请资源。

其次，C 必须等 B 的结果才能开始检查，但加载 M2 不需要等这个结果。因此，如果资源允许，我们可以在 B 运行时提前加载 M2。

这就是 SagePilot 的核心：工作流规定任务之间的依赖，我们利用这些依赖，提前安排底层的实例使用和模型准备。 论文把这个过程叫作从逻辑工作流到物理执行图的转换。

系统用三个模块来完成这件事。

第一个是 SageRadar，负责估计代价。它根据模型结构、请求配置和 GPU 特征，估计一次调用要跑多久、占多少显存、模型加载需要多久。运行时主要查询已经准备好的资源画像。

在刚才的例子里，它提供的信息就是：B 预计还要运行多久，M2 在候选 GPU 上加载需要多久，以及显存够不够。

第二个是 SageGraph，负责找出可以采用的执行方式。比如 A 和 B 能不能一起申请实例，M2 能不能提前准备，其他工作流对 M2 的需求能不能共享同一次加载。

它还会把依赖关系表达清楚：C 要等 B 的结果，也要等 M2 准备完成；但是准备 M2 这个动作，可以和 B 并行。这里只对路径和模型等信息已经确定的后续步骤提前准备。

所以，前两个模块交给调度器的是两类信息：每个动作要花多少时间和资源，以及这些动作之间有哪些依赖、哪些可以提前做。

第三个模块 SageWeaver，才负责决定现在具体执行什么。

还是刚才的例子。假设 B 还要运行 20 秒，M2 加载也需要 20 秒，C 本身生成需要 10 秒。这些是假设数字。

如果等 B 完成再加载 M2，那么从现在到 C 完成，一共需要 50 秒。如果有一张合适的空卡，可以现在加载 M2，让加载和 B 的执行重叠，C 就有机会在大约 30 秒后完成。

但这里不能只看这一个工作流。假如另一个任务已经拿到了全部输入，正等着用这张空卡，我们就要先考虑推进这个已经就绪的任务，而不是直接把卡拿去预取。假如腾出空间需要卸载 B 正在用的 M1，那也不能这么做。

因此，SageWeaver 的优化目标有先后顺序：先尽量让高优先级和等待较久的就绪任务得到执行机会；接纳情况相同时，让这批任务尽早完成；之后再考虑提前准备模型和减少重复加载。

这个完成时间会把输入等待、模型加载、资源排队和实际生成都算进去。

在线算法按照这个思路逐步做决定。先看已有实例能不能接收任务，能接收就复用；不能接收，就考虑加载。如果已有实例排队太长，就评估是否值得增加副本；资源不足，就检查有没有可以安全回收的空闲实例。当前没有可推进的就绪任务动作时，再考虑预取后续模型。

比如一个任务留在原实例里，预计还要 70 秒才能完成；另开实例需要加载 30 秒、生成 20 秒，那么新开副本预计可以省 20 秒。算法会拿这个收益和配置门槛比较，再检查设备、副本数量及其他需求的资源条件，决定是否扩容。

它采用的是事件驱动的启发式，不会枚举所有方案去求全局最优。每轮只发出当前能执行的动作，等加载或任务真正完成，再更新状态，决定下一步。预测帮助安排时机，实际执行仍然要等输入、模型和资源都满足条件。

三个模块的关系也就很清楚了：SageRadar 估计代价，SageGraph 整理执行方式和依赖，SageWeaver 结合当前资源选择具体动作。

多个工作流一起考虑的价值也在这里。比如两个工作流后面都要用同一个部署的 M2，调度器就能看到一次加载可以服务两边的需求，决定提前准备并保留这个实例。共享的是模型和推理后端，各自的输入、结果和完成状态仍然独立。

评估方面，论文初稿覆盖数学求解、代码修复和会议总结三个场景，共 180 个会话，使用 Qwen3 模型、vLLM 后端，以及 V100 和 A100 GPU。

按初稿报告，突发负载下，相比其中的对照策略，整批任务全部完成的时间最多降低了 36.8%，会话的 p95 完成延迟最多降低了 25.9%。消融也表明，跨工作流统一考虑模型生命周期，对整批完成时间帮助明显；连续调用融合，则主要改善慢会话的等待。

我认为这项工作的主要贡献，是让调度器提前看到工作流后面的需求。这样它既能安排当前请求，也能决定连续调用怎样复用实例、后续模型什么时候准备，以及有限的 GPU 应该留给谁，最终减少用户完成整个任务需要等待的时间。

展开：三个模块如何接力，以及调度的一轮决策

同一个例子，三种不同的输出

假设 A 已结束，B 正在 GPU 0 的 M1 实例上运行，C 要用 M2。GPU 1 是可放下 M2 的空卡，M2 尚未加载。以下时间均为解释机制的假设值，不是实验数据。

模块在这个例子里提供什么交给调度器的信息
SageRadar估计 B 还需 20 秒、M2 加载需 20 秒、C 生成需 10 秒，以及显存需求。各动作的预计耗时与资源代价。
SageGraph保留 B → C，增加“准备 M2 → C”；准备 M2 不依赖 B 的输出。兼容的其他工作流也可依赖这次准备。可以选择的执行单元、准备动作和必须满足的依赖。
SageWeaver检查 GPU 1 是否仍空闲、是否有 ready 工作需要它、预取是否到时，再决定是否发出加载。具体命令，例如“现在在 GPU 1 加载 M2”；C 此时仍不开始。

预测给代价，图转换给候选和依赖，调度结合实时资源状态选择动作。这是职责划分；实现时可以交织构造和选择，不要求先枚举完所有物理图。

调度为什么不只是给请求排序

如果只把 C 排到队首，M2 还没有准备好，C 依然跑不了。调度器必须同时决定模型是否准备、在哪里准备，以及哪些实例继续保留。执行顺序只有结合这些资源动作才有意义。

  1. 看当前能推进谁：先按优先级和等待情况处理 ready 任务。C 的输入还没齐，此时只能参与模型准备，不能参与生成。
  2. 检查已有资源：模型已驻留且实例可接纳，就复用；否则考虑加载。模型驻留不等于实例有空余容量。
  3. 处理资源不足：寻找合适空卡，或回收合法的空闲实例；活跃租约保护下的 M1 不能卸载。没有合法动作就等待事件。
  4. 考虑后续需求：这轮没有 ready 准入或模型准备动作可推进时，检查 C 的预取时间、可用设备和资源约束，决定是否加载 M2。
  5. 登记并发出动作：加载前先登记设备占用，防止其他动作重复分配；完成事件返回后，再把实例标为可用。

提前准备具体省在哪里

如果等 B 完成才加载 M2，从现在到 C 完成需要：B 剩余 20 秒 + 加载 20 秒 + C 生成 10 秒，共 50 秒。若符合预取条件并立即加载，B 和模型加载可以重叠，两者都结束后 C 再生成，合计约 30 秒。省下的是关键路径上的模型等待，不是 C 的生成计算。

若加载实际用了 25 秒，C 就到第 25 秒才能开始；若 B 实际用了 30 秒，C 就到第 30 秒才能开始。预测时间到了，不代表数据或模型已经就绪。

同样的 C，资源状态不同，动作就不同

  • M2 已驻留：检查容量后复用，不必再次加载。
  • 空卡可用且没有 ready 动作可推进：满足预取时机和容量条件时，可以提前加载 M2。
  • 另一 ready 任务需要这张空卡：优先推进它，C 的预取推后。
  • 只有 B 正在用的 M1 能腾出位置：不能回收，等待合法资源机会。
  • M2 已有实例但队列很长：比较等待与另开副本的预计完成时间，收益和资源条件都满足才扩容。

“联合优化”描述要一起考虑的决策范围；当前在线算法按上述优先顺序逐步作决定，不是穷举所有方案再找全局最优。此前核对的实现选卡仍采用可行性过滤和固定排序，不能把这个例子讲成每次都会选预计完成最早的 GPU。

展开：目标公式、约束、Algorithm 1 与决策算例

优化对象：当前可推进的任务与已确定的后继

  • 输入状态：已就绪执行单元、紧邻且路径已确定的后继、模型副本与设备占用，以及 SageRadar 给出的运行时间、加载时间和显存估计。
  • 决策变量：复用、加载、扩副本或回收哪些实例；执行单元绑定哪个副本和 GPU；哪些资源冲突动作必须先后执行。
  • 规划范围：当前就绪单元与紧邻的 near-ready 后继。尚未解析的分支不作为确定需求，后续随真实事件更新。

目标函数：按优先顺序比较方案

$$\min_{G,\pi}\;\Phi(G,\pi)=(-A_1,\ldots,-A_K,\hat C_F,-P_N,H_{life})$$

这里采用字典序：前一项相同，才比较后一项。G 表示物理执行图，π 表示绑定和资源执行顺序。

  1. 尽量接纳就绪任务：Aₖ 是第 k 个优先级与等待时间类别中接纳的单元数，高优先级类别先比较。
  2. 缩短当前任务的完成时间：Ĉ_F 是本轮已接纳就绪单元中最晚的预计完成时间。
  3. 增加及时预取：P_N 表示能及时完成的后续模型预取数量。
  4. 减少模型管理代价：H_life 计入面向就绪工作的加载延迟和回收引起的重加载代价。

因此，论文中的时间目标针对当前规划窗口，通过滚动决策改善端到端表现；它不是直接精确求解整批工作流的全局最短完成时间。

代价模型：把依赖等待和资源等待放在同一条时间线上

$$\hat s_u=\max\left(\hat r_u,\max_{v\in pred_G(u)}\hat c_v,\max_{v\in rpred_\pi(u)}\hat c_v\right),\qquad \hat c_u=\hat s_u+\hat T_{u,a(u)}$$
  • 数据就绪：r̂_u 表示任务何时具备输入。
  • 图上依赖：pred_G 包括原有依赖和新增的模型准备依赖。
  • 资源冲突：rpred_π 表示占用同一资源、必须先完成的操作。

例如输入在第 100 秒就绪，模型在第 90 秒加载完成，但不可并发的同卡操作到第 120 秒才结束，那么任务最早第 120 秒开始；运行需要 20 秒，就在第 140 秒完成。只比较模型运行时间，会漏掉前面的等待。数字均为说明机制的算例。

可行性约束：不仅检查模型权重是否放得下

  • 语义与依赖：输入输出依赖保留，数据和模型都实际就绪才能生成；加入资源顺序后不能出现环。
  • 部署与准入：满足设备兼容性、上下文长度和副本并发上限；共享准备动作必须符合所有消费者的设备条件。
  • 显存：论文在每个预计状态变化时刻检查“驻留及过渡态模型显存 + 活跃请求增量显存 ≤ 设备容量”，共享权重不按请求重复计算。
  • 回收：排除正在使用和受保护的实例，不能为了新任务直接卸载正在执行的模型。

Algorithm 1：按事件逐步构造可行方案

  1. RankReady：按优先级和 aging 排列就绪单元，等待较久的任务提高优先级。
  2. BestFeasibleBinding：过滤不可行设备，每个单元至多返回一个绑定；已有实例可接纳时形成准入动作。
  3. PlanReady：对其余就绪任务安排加载、扩副本或安全回收，逐步更新方案。
  4. PlanPrefetch：仅当本轮没有产生推进就绪任务的准入或模型准备动作时，才考虑 near-ready 模型预取。
  5. Propagate 与 Prefix：传播预计完成时间、安排资源冲突并检查容量，只提交当前可执行的动作；新请求、加载完成和任务完成事件触发下一轮。

实现中的具体选择：加载谁、是否扩容、回收谁

决策实际使用的判断说明算例
先加载谁按同一部署的（ready 数 + near-ready 数）÷ 预计加载时间排序；等待过久的请求优先处理。M1：6 ÷ 30 = 0.20；M2：2 ÷ 40 = 0.05。其他条件相同时优先 M1。这是加载优先级，不是生成吞吐。
是否扩副本比较原实例预计完成时间与“当前时间 + 新实例加载 + 执行”的差，检查收益门槛、副本上限和可行设备。原队列还需 70 秒，新实例需 30 + 20 = 50 秒，预计收益 20 秒；不能因此跳过资源检查。
回收谁合法候选中先考虑冗余副本，再比较“距下次使用的时间 − 重加载时间”；缺少可计算信息时回退到冗余优先与 LRU。100 − 20 = 80 秒，比 30 − 25 = 5 秒留下更多重新准备的余量，其他条件相同时更适合回收。

跨工作流的作用就在这些决策里：W1 和 W2 如果需要相同部署，需求可以共同进入加载排序；复用一个实例节省加载，但排队变长时又需要评估扩副本。模型准备、请求等待和设备占用因此被放在同一个决策过程中。

上面的优化目标和累计资源约束来自论文 §3.5、公式 (7)–(12)；Algorithm 1 是遵循目标优先顺序的在线启发式，不是求解所有图与排程组合的精确优化器。

Q: 和普通的模型缓存、换入换出有什么区别？

普通缓存主要根据已经到来的请求决定保留谁、换入谁。我们额外利用工作流依赖：前一步还在运行时，就能看到后续可能需要什么模型，从而评估能不能提前准备；连续兼容的调用可以一次安排，减少阶段间重新调度。落到动作上仍然是加载、调用和回收模型，区别在于决定这些动作时，多了后续需求、就绪时间和整个工作流完成时间这些依据。

Q: 从一个会话到达开始，系统到底怎么跑？

假设 A 调用模型 M1，接着 B 调用工具，再由 C 调用 M2。会话到达后，运行时知道这三个步骤的依赖，A 可以开始，B 和 C 要等待。调度器查 A 的执行代价，检查 M1 是否已有可用实例，决定复用还是加载；实例就绪后 A 开始生成。

A 完成后，运行时把结果交给 B，B 执行工具调用。此时 GPU 不需要继续替这个工具计算，调度器可服务其他请求；结合后续 C 的需求和工具完成时间估计，也可以判断是否提前加载 M2。工具结果真正返回后，C 才能成为可执行任务，拿到 M2 实例并开始生成。C 完成后会话结束，实例上的任务记录更新；没有任务使用的模型可以保留给其他会话，或者在显存紧张时回收。

这里 A 和 C 使用不同模型，中间还有工具调用，因此不作为同模型连续链融合。每一步由真实完成事件推进，预测只辅助提前准备。

Q: 提前加载为什么可能让 p95 更差？你会怎么处理？

比如预测后续很快会用到 M2，提前加载却挤掉了当前请求马上要用的 M1，M1 就要重新加载，等待时间反而增加。还有一种情况是分支最终没走到 M2，这次加载既占了显存，又消耗了加载带宽。

设计上我会先满足已就绪请求，再把预加载限制在可用容量和并发加载预算内；对预测收益接近成本的候选更保守，并持续比较预加载命中率、重加载次数和 p95。如果误差变大，就降低预加载的积极程度。这里的关键是把提前准备当作有成本的优化，具体限额和回退策略还需要结合实现与实验验证。

Q: 两个请求同时申请显存，如何防止超额分配？

当前调度器通过命令队列串行处理核心状态更新。检查容量、登记资源占用和记录实例正在加载，属于同一段受控的状态更新；真正加载可以异步执行，但预留必须先完成。因此后来的请求看到的已经是扣除预留后的容量，不能重复使用它。加载完成后再更新可用状态，失败路径则要撤销对应预留，不能只依赖实时查询显存来避免竞争。

Q: 为什么不只报预测准确率？

因为我们最终优化的是会话完成时间。预测更准，如果没有改变放置或加载决定，未必产生收益；平均误差较小，也可能有少数显存低估导致 OOM。所以我会同时看预测误差、显存低估、加载等待、重加载次数、平均完成时间和 p95，再通过分别关闭融合、预加载等机制，判断收益来自哪里。

Q: SageGraph 连续执行，是不是意味着这条链独占 GPU、不再排队？

连续链只向资源调度器申请一次，中间不再重复准入，并保持实例可用。它不等于独占 GPU，也不消除推理引擎内部的调度；同一实例可以在容量允许时接收其他请求。收益是减少阶段间重新争取资源的开销，代价是这组调用在更长时间内保持资源使用，因此还要观察其他请求的等待和整链显存预算。

Q: 当前实现是不是始终选择预计完成最早的 GPU？

当前选卡先检查上下文、预测桶和显存可行性，再按总显存较小、预测运行时间较短的顺序选择候选。扩副本会比较现有队列和新副本的预计完成时间，但这不等于所有选卡动作都在全局最小化完成时间。A100 与 V100 的时间算例可以用来解释加载与计算重叠的价值，不能当作当前选卡函数必然执行的规则。

Q: LangGraph 调用常驻 vLLM，本来就能复用模型，你们增加了什么？

常见的 LangGraph 加常驻 vLLM 部署里，A 请求结束不会自动卸载模型，B 可以继续调用同一个服务。因此不能把“不重复加载模型”本身作为我们相对常驻服务的贡献。

我们面向多个模型竞争有限 GPU、实例需要动态准备和回收的环境。工作流提供的不只是当前请求，还包括连续兼容的调用和已确定的后续模型需求。系统利用这些信息，把调用成组、模型准备、跨工作流复用和设备分配组织成实际执行方案。收益需要通过阶段等待、重加载次数和端到端延迟验证；如果模型始终驻留、资源又充足，成组执行的收益可能很小。

这里“一次安排”指的是 SagePilot 外层对实例的安排。底层仍逐阶段调用模型，也仍然存在引擎内部的调度。LangGraph 运行机制；vLLM 请求与缓存管理。

Q: 物理方案一定能按预测时间执行吗？

不能。比如 B 实际比预计慢，M2 可能提前准备好，却仍需等 B 的真实输出；如果模型加载更慢，C 就还要等加载。系统只执行当前满足条件的动作，在完成事件到来后调整尚未发出的安排。预测误差会影响准备时机和收益，但不能放宽数据依赖或资源容量约束。

论文描述了更一般的时间线资源约束；此前核对的实现主要采用单卡单副本和副本内 batch 容量检查。不能把这直接描述成已经实现了任意多模型同卡共置，或任意未来时间线的全局最优规划。

Q: 什么时候增加副本，什么时候回收已有模型？

扩副本时，比较继续在已有实例等待的预计完成时间，与加载新实例再执行的预计完成时间。假设前者还需 70 秒，后者加载 30 秒、执行 20 秒，预计能节省 20 秒；只有收益超过配置门槛、设备和副本上限允许，而且不会占掉其他需求最后一个可行位置，才考虑扩容。

回收先排除正在使用和受保护的实例，再优先考虑冗余副本，以及下一次使用较远、重新加载代价较小的实例。假设一个模型 100 秒后才需要、加载需 20 秒，另一个 30 秒后需要、加载需 25 秒，其他条件相同更倾向回收前者。数字用于解释判断，实际动作仍需经过回收条件检查并确认卸载完成。

Q: 调度优化的变量、目标和约束具体是什么？

变量包括物理方案中采用哪些模型准备动作、执行单元绑定哪个副本和设备，以及资源冲突操作的先后顺序。论文公式 (12) 使用字典序目标：Φ = (−A₁, …, −Aₖ, Ĉ_F, −P_N, H_life)，按这个顺序最小化。

Aₖ 是对应优先级与等待时间类别中接纳的已就绪单元数，负号表示越多越好；Ĉ_F 是当前窗口中已接纳就绪单元的最晚预计完成时间，越小越好；P_N 是及时完成的预取数量，越多越好；H_life 则计入面向就绪工作的加载延迟和回收造成的重加载代价。字典序意味着前面的目标相同时才比较后面的目标，不是把所有指标任意加权求和。

硬约束包括依赖和资源顺序无环、上下文长度、部署与设备兼容性、模型可用性、显存容量以及副本并发上限。每个预计状态变化时刻都要考虑驻留与过渡态模型显存，加上活跃请求的增量显存；共享模型权重不能按请求重复计算。共享准备动作还要满足所有消费者共同的设备条件。

需要区分研究目标、窗口目标和求解方法：研究上希望降低端到端完成时间；公式里的完成时间项针对当前已接纳的就绪单元；Algorithm 1 用启发式逐步构造可行方案，并非精确求解全局最优排程。依据：论文初稿 §3.5、公式 (7)–(12)、Algorithm 1。

项目追问

Q: 为什么已经有 vLLM batching，还需要 SagePilot？

实例内 batching 负责组织已进入该实例的请求。SagePilot 还要处理调用之间的依赖、哪个模型何时加载、连续调用是否共享一次租约，以及请求放在哪类设备。两者处在不同层次，上层决定资源与准入，下层执行生成。

Q: 与 Maestro 的预测有什么区别？

Maestro 的相关预测侧重请求输出长度及由此带来的 KV 需求。SageRadar 用模型算子图、请求形状和设备属性估计配置级资源代价，再服务于模型生命周期和工作流调度。SagePilot 的时间估计也会利用近期输出长度，不能把它简化成只预测固定的模型权重大小。

Q: 这项系统工作的难点是什么？

各项动作会改变后续可行性。预取可以隐藏加载，却提前占卡；链融合减少准入，却延长租约；增加副本可以缩短队列，却挤压其他模型。解释效果需要把请求的 ready、等待、加载、生成与完成时间对齐，并用消融区分各机制的贡献。

融合链的上下文包络

初稿公式 (4) 明确考虑后续阶段消费哪些先前输出。令 P_i 为第 i 阶段固定输入的 token 上界，A_i 为其消费的前序阶段集合，O_j 为阶段 j 的输出上限：

\[ I_i=P_i+\sum_{j\in A_i}O_j,\qquad I_c^{adm}=\max_i I_i,\qquad O_c^{adm}=\max_i O_i \]

以下为教学算例：A 的固定输入为 1000 tokens、输出上限 200；B 的固定输入为 300，消费 A 的输出、输出上限 400；C 的固定输入为 500，并消费 A、B 的输出。三个输入包络分别为 1000、300+200=500、500+200+400=1100，整链输入上界取 1100。链的运行时间则是各阶段时间预测之和。

这是初稿的通用定义。此前核对的 worker 使用“首段实际输入 + 前序最大输出上限”的近似；存在更长固定 prompt 或多段累计输出时，两者不等价，需要按具体模板验证。

预测怎样帮助调度

Q: SageRadar 的预测具体怎么做，为什么调度需要它？

调度器知道下一步要调用哪个模型，但还需要知道：放到不同 GPU 上分别要跑多久、需要多少显存，如果模型没加载，还要准备多久。只有这些数值，才能比较一个请求放在哪里更早完成，以及能不能放得下。

所以我们的预测对象是“一次模型调用在某种执行配置下的资源开销”。比如同样调用 Qwen3-8B，输入 2048 tokens、输出预算 512 tokens、batch 为 2，在 V100 和 A100 上就分别对应一组时间和显存估计。输入长度、输出长度和 batch 改了，估计也要跟着变。

具体做法是，把模型在这个配置下的计算过程转成算子图。图上的节点是矩阵乘、Attention 这些算子，边表示张量怎样从一个算子传到下一个算子。每个节点带上计算量、张量形状等特征，边带上数据量，再把 GPU 算力、带宽以及请求配置一起交给图模型。

图模型沿着依赖关系聚合信息，最后汇总出整个计算图的表示，用不同的回归头预测运行时间和峰值显存等指标。训练标签来自实际测量：在对应配置下执行，记录耗时和资源峰值，让模型学习图结构、配置和资源代价之间的关系。

这些预测会提前整理成资源表。在线调度时，根据模型、GPU、batch 和长度配置查表，再结合当前队列、模型是否已经驻留、前驱任务什么时候完成，比较候选位置。模型加载时间也进入这套查询接口，并通过加载实测记录进行校准。

时间和显存的使用方式不同：时间估计帮助选择更快完成的位置，显存估计用来判断能不能接这个请求。显存低估可能直接导致 OOM，所以我们会给预测值做校正、加入余量，而且按配置允许的输出上限检查容量，不因为最近回答比较短就把显存预算一起缩小。

Q: Decode 生成 512 个 token，要把 512 步都展开成图吗？

当前采图实现没有把所有生成步骤展开。它先构造长度为“输入长度 + 输出长度 − 1”的 KV 上下文，再捕获一步 decode，同时把输出长度作为全局特征。输入 2048、输出 512 时，构造的是长度 2559 的已有上下文，再捕获接下来这一步。

这样既能让图反映长上下文下的算子形状，又控制了图的规模。训练时用对应配置的实测耗时作为标签，让模型学习配置到运行时间的关系。不能把这里的一步采图理解为只预测一个 token，也不能直接说实现就是“最后一步耗时乘 512”。

Q: 网络结构和训练目标具体是什么？

核对的训练配置采用 128 维隐藏表示、2 层图网络、8 个 attention heads，读出方式是 mean/sum/max，使用加权 Smooth L1 和 AdamW。共有九个预测目标，其中调度重点使用运行时间、峰值显存和部署时间，标签分别是 run_duration_sec_avg、gpu_mem_used_mb_max 和 deployment_duration_sec_avg；其余目标包括 CPU、主机内存、GPU 活跃度和功率等。

初稿 §3.3 介绍的是运行时间、峰值显存和部署加载时间三类资源输出，上面的网络参数来自关联实现。

预测怎样变成一次放置决策

在忽略额外资源争用、且排队等待可以用一个可执行时刻表示的简化例子中：

\[ t_{finish}(d)=\max\{t_{ready},\ t_{model}(d),\ t_{queue}(d)\}+\hat T_{run}(d) \]

  • \(t_{ready}\)：前驱结束、输入齐备的时刻，由工作流进展估计。
  • \(t_{model}(d)\)：设备 d 上模型准备好的时刻，由驻留状态和加载耗时决定。
  • \(t_{queue}(d)\)：设备上的执行队列允许这个请求开始的时刻。
  • \(\hat T_{run}(d)\)：资源表提供的本次调用执行时间估计。

取最大值是因为三个条件都满足才能开始，再加上实际执行所需的时间。GNN 提供执行代价，当前排队和驻留状态由调度器掌握，整个工作流的就绪时间也不是 GNN 单独输出的。

例如从现在计时，请求预计第 5 秒就绪，两张卡都空闲：A100 没有模型，从现在加载需要 8 秒，执行需要 4 秒；V100 已驻留模型，执行需要 9 秒。

候选能开始执行的时刻预计完成时刻
A100，允许现在开始加载max(5, 8, 0) = 8 秒8 + 4 = 12 秒
V100，模型已经驻留max(5, 0, 0) = 5 秒5 + 9 = 14 秒

在这个例子的资源条件下，A100 更早完成。如果必须等请求就绪后才加载，A100 则要到第 17 秒完成。预测的价值，是把加载能否提前、不同 GPU 的执行速度以及请求就绪时间放到同一次比较里。这是解释决策的算例，真实准入还要检查显存和其他请求的资源占用。

输出长度未知，时间和显存分别怎么估计

资源表按模型、GPU、batch、输入长度和输出长度配置索引。运行时间可以用同一节点近期输出 token 数的 p90 选择覆盖桶；没有历史时使用配置的输出上限。p90 就是近期样本中约 90% 不超过的长度。

例如输出上限为 1024，近期 p90 为 300，如果资源表有 256、512、1024 三个桶，时间估计选择能覆盖 300 的 512 桶；显存仍查询覆盖 1024 上限的配置。时间侧利用近期请求通常较短这个信息，容量侧继续为允许生成的最大长度留空间。

Q: 在线每来一个请求，都跑一次 GNN 吗？实测表和预测表是什么关系？

当前调度接口在线查资源表，离线可以用 GNN 预测或实测 profiling 填充同一套字段，所以图推理不用放在每次调度的关键路径上。GNN 的作用是学习不同配置的资源代价；实际测量则提供训练标签、校准依据，也可以直接形成资源表。

讲实验时，要区分这一轮使用的是预测表还是实测表。当前等预算评估使用已标定的运行时间缓存，具体某次运行是否使用 GNN 表，应以该次配置为准。

显存：点估计、校正值与准入上界

显存低估可能导致 OOM，所以点预测不能直接等同准入预算。当前后处理先拟合线性去偏项，其中 I、B、O 分别是输入长度、batch 和输出长度：

\[ M_{corr}=\max\{1, w^\top[\hat M,\log_2 I,\log_2 B,\log_2 O,1]\} \]

这里的 1 是代码使用的最小正值，单位沿用资源表的 MB。再根据校准集的正向残差分位数加入余量，并至少保留 10%：

\[ M_{upper}=\max(M_{corr}+q_{0.95},\ 1.1M_{corr}) \]

最终准入条件还包括固定余量与该配置的 OOM 惩罚：

\[ M_{upper}+\epsilon_{mem}+penalty_{OOM}\le M_{GPU} \]

显存按配置的输出上限检查，不因近期输出较短而缩小准入容量。 例如时间按 300 tokens 的覆盖桶估计，显存仍按 1024 上限的覆盖桶检查。两者分别服务于完成时间估计与容量安全。

Q: 95% 分位数加 10% 余量，能保证零 OOM 吗？

这是经验上界。运行分布变化、后端额外开销和未建模状态都可能使实际占用超出校准范围。分位数必须用独立数据验证覆盖率，并监测低估尾部与 OOM；它不能作为绝对安全证明。

Q: 为什么不用参数量、FLOPs 或 GBDT？

图特征能表达算子类型、形状和依赖的差异，但有图结构不等于必须用 GNN。应比较解析公式、表格模型和 GNN 的误差、数据成本与下游调度收益，尤其检查显存低估尾部。简单公式在某些目标上可能更有效。

Q: 换成 H100 的设备属性就能保证泛化吗？

设备属性提供条件输入，不构成泛化保证。新架构、kernel、精度与后端版本都可能改变映射。需要留出 GPU 或模型族的测试，并根据目标设备实测做校准。采图与训练本身也有成本，不能把系统表述为完全零 profiling。

Q: 算子图会遗漏哪些运行信息？

模型级图不自动等同真实 serving 的 kernel 执行图，后端融合、kernel 选择、动态 batching 和资源争用都可能造成偏差。要用匹配后端与负载的标签和独立验证检查误差；新增运行特征或 trace 校准属于需要验证的补偿方法。

用过去的重新加载耗时估计下一次

加载时间的 serving 校准来自真实日志：同一个模型过去在同类 GPU 上重新加载用了多久，就用这些记录估计下一次的成本。日志读取 model_load_finished.payload.duration_sec。这项统计可直接替换 GNN 资源表里的原始部署时间预测。

首次加载 Q8 → 使用 → 回收 Q8 的 GPU 副本 → 再次加载 Q8 → 使用
                                        ↑ warm reload 统计对象

每轮运行内，按 (model_key, GPU 类型) 识别首次加载并排除，后续记录进入 warm 统计。这是按事件顺序划分的操作口径；它不直接检查操作系统缓存，不能仅凭“第几次”证明缓存一定热。缓存仍在主机侧时可能更快，但存储拥堵和并发加载也会改变耗时。

初稿 §3.3 只定义部署级加载代价与缓存接口，未展开 warm reload 的两层中位数。这套统计和门槛来自代码后处理路径，不能将其当成初稿公式，也不能仅凭初稿确认 Table 1 的加载误差统计覆盖了该校准。

GPU 比例由合格模型的 warm 实测代表值 / 原估计值 取中位数。例如其他合格模型的代表比例为 0.5，样本不足模型原来估计 80 秒，回退值为 40 秒。这仍是跨模型的粗略校准。

调度怎样使用 30 秒

假设任务预计第 100 秒 ready，加载估计 30 秒，预取余量 5 秒，则预取资格从第 100 - 30 - 5 = 65 秒开始。若资源允许并及时发起，加载可与前驱执行重叠。实际策略仍先推进 ready 工作，所以到第 65 秒不意味着一定加载。

同一加载成本也参与回收决策：预计 100 秒后再用且重加载只需 20 秒的模型，比 30 秒后再用且重加载需 25 秒的模型更适合暂时回收，前提是其他保护条件相同。

Q: 没有神经网络参与，为什么也叫预测？

预测是给尚未发生的事件提供估计。历史中位数本身就是统计预测器：把可比较的过去测量汇总，作为下一次的预计耗时。GNN 可以给原始值，历史数据足够时再用 serving 的真实重加载统计替换。

Q: 这 30 秒能用来估计首次冷启动吗？

不能直接等同。统计特意排除了每轮首次加载，目标是后续重加载成本。首次冷启动的文件读取、缓存与引擎初始化状态可能不同，需要单独的观测口径或估计。

同部署链如何找到

给定工作流 P → A(Q8) → B(Q8) → C(Q8) → D(Q14)，编译器沿拓扑顺序检查相邻边，满足下列条件才合并：

  1. 前后节点都是可融合的 Agent 节点。
  2. 前节点只有该后继，后节点只有该前驱，链内部没有分叉或汇合。
  3. 两者部署的 model_key 相同，涵盖模型路径、dtype 与 serving 配置等身份。
  4. 其余执行配置相同，允许每阶段 max_new_tokens 不同。

链首仍可以接收多个外部前驱，链尾仍可以连向多个外部后继。约束针对链内相邻边，不能误解成整条链两端也必须一对一。

输入：P → A(Q8) → B(Q8) → C(Q8) → D(Q14)
输出：P → Fused[A, B, C] → D(Q14)

编译器延长至最大的合法链，生成 FusedAgentNode，重接外部边、移除链内部边，并保留各阶段的 prompt、system prompt 和输出上限。这里是确定性的合法性扫描，不是枚举所有物理图并搜索全局最优。

执行时究竟省了什么

没有历史时，链运行时间按各阶段估计求和。显存容量需要覆盖后续阶段可能增长的上下文。

当前 worker 使用的输入长度近似为“首段实际输入长度 + 前序阶段最大的输出上限”。如果后续固定提示词更长，或模板累计保留多段输出，这个近似需要扩展。它不能无条件覆盖任意提示词模板。整链预留还可能比逐阶段准入更保守，长租约会影响其他请求的等待。

ready 排序与可行性过滤

cache 策略偏向模型已驻留的 ready 请求，同类按请求顺序，等待过久的请求通过 aging 提升优先级。它降低长期等待风险，但不能据此宣称持续过载下有有限等待上界。

设备选择先检查三个条件：

实际输入长度 + 配置输出上限 ≤ 模型上下文上限
资源表存在覆盖输入、输出和 batch 的桶
显存上界 + 固定余量 + OOM 惩罚 ≤ 设备容量

可行候选按“卡总显存更小 → 预测运行时间更短 → 设备 ID”排序。例如请求在两类卡上都可行时，先倾向显存较小的卡。这一步不是对所有设备全局最小化排队、加载和执行的总时间。

加入已有副本仍要重新检查总 batch。例如已有两个请求，新请求加入后按 batch=3、所有请求中最大的输入桶与最大的输出桶查显存上界，不能只验证新增请求单独能否放下。

多个模型都要加载，先加载谁

当多个模型都有需求、需要决定加载顺序时，优先考虑：花同样的加载时间，哪一个模型能为更多请求准备好服务。

$$ score(m)=\frac{N_{ready}(m)+N_{near-ready}(m)}{\hat T_{load}(m)} $$</div>
  • m：一个待加载的模型部署配置。
  • N_ready：输入已经齐备、正在等待资源的请求数。
  • N_near-ready：前驱已完成或正在执行、接下来可能就绪的任务数；不把整个工作流里所有未来节点都算进来。
  • T̂_load：把这个模型加载到候选设备上预计需要多少秒。
  • score：需求数量除以加载耗时，越大越优先。它是加载优先级分数，不是模型每秒能完成多少请求。

先看一个不用算公式的例子

假设现在只有一张合适的空卡，M1 和 M2 都没有加载，而且加载都要 10 秒。当前及即将就绪的请求中，6 个需要 M1，2 个需要 M2。

先加载 M1：花 10 秒，为 6 个请求准备好了模型；先加载 M2：同样花 10 秒，只为 2 个请求准备好了模型。 在其他条件相同、没有请求等待过久时，我们优先 M1。

这不意味着 6 个请求会在 10 秒内全部完成。10 秒只是模型准备时间，之后仍需进行容量检查、排队和生成。

加载时间不同，就比较需求与耗时的比值

跨工作流为什么要一起统计

假设 W1 有 2 个请求要用 Q8，W2 有 4 个请求也要用相同部署配置的 Q8，分子就合计为 6。一次加载得到的实例可以供多个工作流复用，因此加载决策需要看到这些共同需求，而不是只数 W1 的两个请求。

这个分数用于候选加载动作的排序。资源是否可行、副本是否达到上限等条件还要检查；等待超过阈值的请求会优先于普通分数排序，避免低需求模型一直被推后。

Q: 面试时怎么解释这个加载优先级？

如果几个模型都需要加载，我们会把不同工作流对同一个模型的当前和即将到来的需求加起来，再除以加载时间。这样，同样花一段时间加载模型，我们更倾向于先准备需求更多、加载更快的那个。比如两个模型都要加载 10 秒，一个有 6 个请求需要，另一个只有 2 个，就先准备前者。已经等太久的请求会提高优先级，不能一直让热门模型先走。

何时增加副本

扩容比较原副本排队的预计完成时刻，与新副本加载后完成的预计时刻：

\[ gain=\widehat F_{existing}-(now+\hat T_{load}+\hat T_{run}) \]

例如留在原队列还需 70 秒，新副本需加载 30 秒、执行 20 秒，预计收益为 20 秒。若配置扩容门槛是 10 秒，就通过收益判断；这并不意味着一定扩容，还要检查副本上限、可用设备和其他需求的可行性。

核对的实验配置对每个“部署 × GPU 类型”副本组最多允许两个副本，扩容每 tick 至多发起一次。扩容不得拿走其他有需求模型最后一个可行位置；如果要回收别的模型，还需要覆盖相应扰动。具体阈值属于配置，不能写成普遍常数。

回收谁

先排除活跃租约和受保护副本，检查可回收状态与最短驻留时间。具有可计算复用距离和重加载成本的候选中，优先冗余副本，再比较：

\[ eviction\ score=\text{距下次使用的时间}-\text{重加载成本} \]

差值越大，通常越适合回收。模型 A 为 100 - 20 = 80 秒，模型 B 为 30 - 25 = 5 秒，其他条件相同时优先 A。没有候选具备可计算的距离和加载成本时，回退到冗余优先及 LRU 顺序。不能把这个分值直接用于所有副本而忽略合法性过滤。

何时预取

near-ready 节点的所有前驱均已完成或正在运行，且至少一个仍在运行。未完成前驱的最晚预计完成时刻决定其 ETA：

\[ ETA(u)=\max_{v\in pred(u),\ v\ not\ completed}\widehat{finish}(v) \]

\[ t_{prefetch}=ETA(u)-\hat T_{load}-\epsilon \]

预计第 100 秒 ready，加载 30 秒，余量 5 秒，从第 65 秒起具备预取资格。策略仍优先 ready 工作：已有准入、加载或回收动作推进时，不立即开展推测性预取。这种顺序保护当前需求，也可能错过更激进的重叠机会。

资源账本的实际边界

加载动作发出前，设备归属先交给 LOADING 副本，防止另一动作重复取得同一张卡；加载完成后更新副本状态。执行中的租约、batch 准入与账本校验进一步约束资源使用。

当前模型主要是“一张卡归属一个副本 + 副本内 batch 显存检查”。论文中沿时间线累计多个模型、请求与加载占用的更一般规划，不能直接当成已完整实现的功能。

工程追问

Q: 两个请求同时看到空闲显存怎么办？

把检查、预留、发 grant 放在同一个资源所有者的原子状态转换中。当前调度器核心通过命令队列串行更新状态，并在异步加载前登记 LOADING 归属。解释并发正确性必须指出状态所有者和原子边界，仅说“异步执行”不足以证明不会超卖。

Q: 取消和完成消息同时到达，如何避免重复释放？

作为工程扩展，应按 request / attempt 标识实现幂等状态转换，让资源只释放一次，并用 generation / epoch 隔离旧尝试。超时不等于 worker 已停止，重新分配前需要取消确认、核对或隔离。这些是需要通过故障测试验证的设计要求，不代表当前系统已经具备完整高可用保证。

Q: GPU 利用率低，怎么找到瓶颈？

先拆请求时间：arrival、ready、acquire、加载起止、生成起止、工具起止与 completion，再关联 session、node、replica、device。分清排队、加载、生成还是工具占主导，再深入对应时间线。显存占用、GPU 忙碌比例和有效生成吞吐不是同一指标，不能仅凭一个利用率百分比下结论。

Q: 从十几张卡扩到万卡，如何设计？

当前材料没有验证万卡。扩展可采用全局路由与局部准入：全局维护容量、模型位置摘要，资源域内部做精确预留。摘要过期时，局部仍拒绝不安全准入；还需处理热模型复制、跨域代价和故障隔离。验证应覆盖控制面事件吞吐、p99 决策延迟、数据面吞吐与恢复时间。

Q: 提高吞吐却让 p95 延迟变差怎么办？

明确负载和目标，例如在满足延迟 SLO 条件下最大化可接受吞吐。长链租约、驻留优先与更大 batch 都可能改变等待分布，需要同时测尾延迟、SLO 违反比例和公平性。当前启发式不能被描述为严格 SLO 保证。

Q: 哪种负载下收益可能变小？

所有模型都能常驻、加载已经完全被隐藏、工作流缺少可融合链，或大部分时间花在生成和工具执行时，生命周期优化的空间可能缩小。相反，频繁换模也不保证一定受益：若预取和重加载争抢 I/O，可能引入新瓶颈，需要受控对照验证。

Q: 简历里的个人贡献该如何具体表达？

把真实负责的组件、一个可复现的问题、做出的代码或策略改变，以及有运行记录支撑的结果连起来。团队成果、当前实现和未来扩展分别陈述。未确认的个人职责、投稿状态与实验提升不填成既成事实。

业务背景：一边排队，一边闲置

我在字节国际电商 Lumen 实习时，参与的是训练统一资源池的调度系统建设。当时 GPU 主要按团队固定分配，但不同团队的需求并不同步：有些团队的训练任务一直排队，另一些团队却还有数百张 GPU 空闲。这些空闲资源不能方便地跨团队使用，所以即使集群里还有卡，排队的任务也不一定能用上。

我们要解决的，就是让暂时闲置的资源可以共享，同时保留原团队需要时收回资源的能力。这里既有调度策略的问题，也有工程实现的问题：资源借给了谁、什么时候要还、怎么回收，以及记录中的资源占用和实际运行状态能不能对得上。

我的工作：在 Merlin 上面做跨团队资源协调

我这段工作的重点，是在已有的 Merlin 训练平台之上设计跨团队调度层。这个层统一查看各团队的配额、实际占用和待运行任务，决定资源怎样借用、任务怎样安排，以及需要回收哪些资源，再通过 Thrift 接口交给 Merlin 执行。

也就是说，我关注的是团队之间的资源协调，以及调度决策怎样接到实际执行上。具体工作包括配额借用、优先级调度、低代价回收、任务状态管理和平台对接。

配额借用：空闲时借出去，需要时收回来

第一个策略是配额借用。团队的配额和它此刻实际使用的资源，是两个不同的量。 配额保留在那里，但暂时没用上的部分，可以作为可回收的 Spot 资源借给其他团队。原团队的需求恢复时，再把借出去的资源收回来。

举一个简单的例子，假设一个团队有八张卡的配额，现在只用四张，剩下四张又满足借用条件，就可以让其他团队先用起来。之后原团队又需要两张卡，如果没有其他可用资源，就需要回收相应的借用资源。这些数字只是用来解释机制。

这里要讲清楚的是，借用方获得的是额外的使用机会，不是永久占有这部分资源的权利。所以正常配额使用和借用资源需要区分，否则后面资源紧张时，就说不清哪些任务可以被回收。

优先级：同时考虑任务顺序和资源使用边界

第二个策略是优先级。我们把 A/B/C 任务优先级纳入调度，但调度不能只看优先级标签，还要结合团队配额、资源可用情况，以及资源是否允许回收。

我会把它理解成三个不同的问题：配额决定团队的资源额度，优先级参与决定任务的执行安排，Spot 表示资源具有可回收属性。比如一个借用任务优先级比较高，也不能仅凭这个标签，就推导出它可以一直占着其他团队的资源，具体还要遵守配额保障和借用规则。

A/B/C 的具体分类和当时的排序细节，我现在记得没有那么完整，但这几个维度需要分开处理，不能都混成一个优先级数字。

低代价抢占：决定中断哪些任务

第三个策略是低代价抢占。原团队需要收回 GPU 时，接下来要解决的就是：中断哪些任务，既能释放足够的资源，又能尽量减少损失？

我们结合任务类型、SM Active 和已运行时长来估计中断代价。SM Active 反映计算单元的活跃情况，已运行时长提供任务已经投入多少运行时间的信息，再结合任务类型，选择代价相对较低的任务组合，减少已经完成的计算损失和不必要的中断。

这里不能简单地抢活跃度最低的任务。低活跃可能是因为任务正在通信、读数据或者处于某个执行阶段，不一定说明它没有价值。同样，已运行时长也不等于剩余时长，不能因为任务跑得久，就认定它马上结束了。所以这些信号要放在一起考虑。

抢占选择：还要检查回收后的资源能不能用

具体评分权重和组合算法我已经记不清了。如果从实现思路来展开，我会把这个过程分成几步：先找允许回收的候选，再比较中断代价，最后检查释放出来的资源能不能满足目标任务。

一种可行的做法，是参考中断代价和可释放资源量给候选排序，逐步选出一组任务，再检查放置约束。但不能只凑够卡的总数。比如新任务需要同一个节点上的四张卡，分别在四个节点腾出一张，未必能让它运行。原来的训练任务如果必须多卡整体停止，也不能假设可以随意抽走其中一张卡。

所以这里的目标是找到能满足需求、同时代价较低的回收组合。这部分是我根据机制重新梳理的实现思路，不是对当时代码的逐行还原，也不能说这样的启发式保证全局最优。

工程实现：让调度记录和实际执行对应起来

工程上，我设计了覆盖提交、排队、调度、运行和终止的任务状态机。MySQL 持久化任务和配额状态，Redis 缓存调度需要的高频数据，通过 Thrift RPC 对接 Merlin，完成任务下发、状态同步和资源回收。

任务状态发生变化时，我们更新调度记录，同时持续核对团队配额、记录中的资源分配和实际占用，检测执行异常或者状态不一致。因为上层作出了调度决定，并不代表底层已经执行完成，后续调度还需要知道资源现在到底处于什么状态。

正确性：不能重复分配，也不能提前释放

这部分有两个关键问题。一个是配额检查和资源预留之间的并发问题。比如两个请求同时看到还剩四张卡，如果各自都认为自己能分配四张，就会重复使用同一份资源。另一个是资源回收的确认问题：发出回收请求，不代表 GPU 已经空闲，旧任务可能还在运行。

如果让我现在实现，我会把校验和预留放在同一个并发控制范围里，先持久化预留和待执行操作，再调用执行层。回收请求发出后，资源仍然按占用计算，确认释放之后，才允许分配给新任务。

RPC 超时也不能直接当成执行失败，因为对方可能已经执行，只是响应没有回来。这时候需要核查执行状态，再决定是否重试，并通过可追踪的操作和状态核对，避免重复执行或者重复扣减资源。这些具体事务和重试机制，是我现在对可靠实现的理解；当时的字段和代码细节我已经记不清了。

  • 优先级是调度输入，不等于对所有运行任务的抢占授权。
  • 借用条件决定资源何时必须归还。
  • 保障规则决定原团队需求恢复时如何处理竞争。

为什么不直接抢活跃度最低的任务？

低活跃不等于低中断代价。

简历记载的信号用途不能直接推出的结论
任务类型为中断代价评估提供任务差异信息某类任务一定可无损恢复
SM Active反映计算单元活跃情况任务没价值、显存占用低或很快结束
已运行时长反映已投入的运行时间剩余时间短，或者一定不能抢

口述：“我们结合任务类型、SM Active 和已运行时长评估。低活跃可能与通信或读数据有关，不能只看一个指标；还要看这组任务释放的资源能否满足回收需求。”

抢占策略怎样展开？

简历确认：结合上述三个信号估计中断代价，在释放足够 GPU 的前提下选择代价较低的任务组合。

1. 候选过滤：能不能抢

  • 只考虑允许回收的任务。
  • 检查资源位置、卡型是否有助于本次需求。
  • 保留业务规则保护的任务。

2. 代价选择：抢哪些更合适

  • 结合任务类型、SM Active、已运行时长评估。
  • 兼顾计算损失、需要中断的任务数量和释放资源量。
  • 可选启发式：参考估计中断代价 / 可释放资源量排序，逐步选择候选。

3. 放置检查：抢完能不能用

  • 总卡数够，不代表可以放置：同节点四卡需求不能靠四个节点各一张满足。
  • 多卡作业可能整体回收：不能默认部分 GPU 可直接抽离。
  • 目标是可行且代价较低的集合，不是只凑够 GPU 数量。

实现口径：以上三步是对机制的设计展开；具体过滤规则和排序算法未由原代码证实。该启发式不保证全局最优。

运行越久越不能抢吗？

已运行时长不是剩余时长，也不是完整损失模型。

  • 没有 checkpoint 时，中断可能损失较多已完成计算。
  • 有 checkpoint 时，损失还受保存位置、恢复开销等影响。
  • Lumen 的 checkpoint 能力和评分权重未确认，不能补成既成事实。

口述：“具体权重我记不清了，但不能把已运行时长等同于剩余时长。我会解释当时使用的信号和取舍，不编一个原系统的评分公式。”

错误路径

  1. 请求甲读到剩余 4 张。
  2. 请求乙也读到剩余 4 张。
  3. 两者各分配 4 张，产生重复分配。

设计方案

  1. 检查额度：同时考虑运行中的占用和已预留资源。
  2. 原子预留：可用数据库事务配合行锁，或条件更新与版本校验。
  3. 提交后执行：登记预留与操作意图，再请求执行层启动。
  4. 按结果收敛：确认失败才能撤销；状态不确定时先核查。

配额账本需要记哪些量？

  • 配置配额：团队的资源额度。
  • 保障占用与保障预留：已运行和已承诺、尚未完成启动的资源。
  • 借入与借出占用：跨团队使用关系。
  • 待回收量：已请求回收但尚未确认释放的资源。

借用空间应从配额中扣除保障占用、保障预留和已借出量，再结合等待需求与物理可分配资源约束判断。按资源池和卡型核算，不能把异构卡简单相加。

这些是账本设计含义，不是对历史数据库字段的还原。

发出终止请求，就能把 GPU 分给新任务了吗？

不能。请求回收和确认释放是两个时刻。

概念状态链（名称为设计示意）：

Running → ReclaimRequested → Releasing → Released
  • 请求已发出：任务可能仍在运行，资源继续按占用核算。
  • 释放已确认：更新账本，资源才可再次分配。
  • checkpoint 与恢复：能力未确认，不能默认无损抢占。

口述：“调度层通过 Thrift 请求 Merlin 执行，再同步任务状态并核对实际占用。正确性上必须确认释放，不能发完请求就把卡分给新任务。”

抢占 RPC 超时怎么办？

超时表示结果未知，不等于执行失败。

可能情况处理原则
请求未到执行层核查后重试
已执行，但响应丢失查询状态，避免重复执行或重复释放
执行仍在进行保留待回收占用，等待或核查

可选恢复机制

  1. 持久化操作标识，使一次回收可追踪。
  2. 查询目标任务当前状态。
  3. 按幂等语义重试同一操作。
  4. 同一释放结果只扣减一次占用。

MySQL、Redis 和 Merlin 状态不一致怎么办？

缓存用于加速，执行结果仍需要核对。

简历记载的做法：根据状态变更事件更新记录，持续核对配额、分配记录和实际占用，检测异常。

重建的可靠方案

  • 短事务记录意图：保存预留及待执行操作，提交后调用 Merlin。
  • 崩溃后继续处理：扫描未完成操作，而不是把已提交意图遗忘。
  • 事件去重：按操作标识或版本判断是否已处理。
  • 乱序保护：晚到的 Running 事件不能把已完成任务恢复成运行。
  • 执行状态核对：执行成功但本地未记账时，通过状态核对恢复。

关键限制：普通 MySQL 事务不能把外部 RPC 一起原子提交。最终权威状态、多实例协调及具体重试机制仍需按实际系统确认。

Q: 什么是"LLM 多智能体工作流"？给一个具体例子。

比如一个旅行助手 Agent：用户说"帮我规划去东京的行程"，系统会依次调用：需求分析 Agent（解析意图）→ 机票搜索 Agent（调工具查航班）→ 酒店推荐 Agent（查酒店）→ 行程整合 Agent（汇总输出）。每个 Agent 背后是一个 LLM 推理调用（称为 stage），一个用户请求可能触发十几次甚至几十次 LLM 调用。这些 Agent 之间有 DAG 依赖关系，不同 Agent 可能用不同模型。

Q: "解码成本不确定"为什么是个问题？固定预留不行吗？

LLM 推理的输出长度变化极大：工具调用输出几十 token（JSON 格式），用户交互输出几百上千 token。输出长度直接决定 KV Cache 大小和 decode 时长。固定按最大长度预留会导致严重的显存浪费（利用率低），按平均长度预留则会 OOM。关键挑战是在请求开始前就要预测输出长度来分配资源，但这个预测不准就会出问题。

Q: "两阶段预测器"具体是哪两个阶段？为什么要分两阶段？

第一阶段是工具调用分类器（LightGBM），判断当前 stage 是否会触发工具调用（AUC 0.96）。第二阶段是输出长度回归器，在分类结果的基础上预测具体 token 数（MAE 165 tokens，R² 0.78）。分两阶段是因为输出长度呈双峰分布——工具调用短（几十 token），用户交互长（几百上千 token），单一回归器在双峰上表现差。分类器先识别模式，回归器在各自模式下预测更精准。消融实验去掉分类器后 MAE 从 134 升到 142。

Q: "分级权重缓存"是什么？和普通的 LRU 有什么区别？

多 Agent 场景下一块 GPU 需要同时驻留多个模型权重。设计了五层状态：Running（GPU 上可立即执行）→ Sleeping（权重在 CPU，但 GPU 保留 CUDA Graph/JIT 缓存约 0.5GB，恢复省 5-8 秒）→ CPU-resident → Disk-resident → Remote。Sleeping 状态是关键创新——保留 GPU 侧的 kernel 缓存避免重建开销。层级化 LRU 逐级淘汰，最热模型留 GPU，最冷退到远端。

Q: "弹性显存供给"怎么做的？CUDA VMM 超配 3 倍不怕 OOM 吗？

用 CUDA Virtual Memory Management 实现地址和物理页分离。在 40GB A100 上分配 122GB 虚拟地址池（3 倍超配），物理页按需映射。三层防护防 OOM：(1) 虚拟地址不等于物理内存，多 Agent 的 KV 使用不会同时达峰（统计复用）；(2) 每个 stage 进入前做准入控制，检查剩余物理页是否满足预测需求；(3) cuMemMap 失败时拒绝该 stage 而非崩溃。偏向高估（安全裕度 ρ），低估导致 OOM 的代价远大于高估浪费。

Q: "阶段边界抢占"是什么意思？为什么不做 token 级抢占？

Stage 边界抢占是指只在两个 LLM 推理调用之间切换（一个 stage 完成后、下一个 stage 开始前），不打断正在 decode 的请求。Token 级抢占需要和推理引擎深度集成、做 KV Cache 迁移，工程复杂度极高。Stage 边界抢占只需更新元数据，实测效果已足够——交互排队延迟从 11 秒降到 2 毫秒。

Q: SLO 达成率提升 23.6pp 的 baseline 是什么？怎么算 SLO 达成？

Baseline 是 EDF（Earliest Deadline First），实时系统经典调度策略。SLO 定义为"交互式 stage 的 TTFT（首 token 时间）< 阈值"。在高负载下 EDF 因为没有预测信息，无法区分长短 stage，导致长 stage 阻塞短交互 stage（队头阻塞）。Maestro 用预测的剩余时间做 SRTF，加上工作流感知的优先级（交互式 > 批处理），SLO 达成率从约 60% 提升到 83.6%。

Q: 46,769 条真实 trace 从哪来的？怎么保证实验可信？

Trace 来自内部部署的多 Agent 应用平台，记录了每个 agent stage 的输入/输出 token 数、模型类型、时间戳。实验分为两部分：16 台 V100 做原型实测（端到端延迟、SLO 达成率），46,769 条 trace 做大规模仿真（64 卡级别）验证调度策略的扩展性。仿真器基于真实 trace 回放，关键参数（KV 内存增长、推理延迟）从原型实测校准。

DeepShare（IEEE Cluster 2026）简历追问

简历原文："以连续的「配额保障度（QAD）」为统一运行时控制信号、协调弹性配额借用、预测调度和干扰感知共置四类决策的 Kubernetes 原生调度框架。QAD = 分配量/min(配额, 保障需求)，经 EMA 平滑。空闲配额以 best-effort 借出（DRA），按 QAD+运行时预测做字典序排序，代价感知抢占。干扰感知共置用 RF 预测吞吐损失，MPS 共置无需改代码。23,859 条 Venus trace 仿真 GPU 利用率 70.6%（vs Lucid +29.5%），排队延迟降 46%；16 节点 64 卡 K8S 实测 JCT 降 34%，QoS 达成 93%。"

Q: 什么是"配额保障度 QAD"？为什么不直接用"用了多少 GPU / 配额"？

QAD = 已分配的 Guaranteed GPU / min(配额, 当前 Guaranteed 需求)。分母用 min(quota, demand) 很关键：如果租户 quota 32 但只需要 8 张，保障 8 张就是满足（QAD=1），不需要给满 32 张；如果租户提交 100 张需求但 quota 只有 32，保障 32 张就够（QAD=1），不会因为超额提交就认为系统欠它的。而"使用率"（usage/quota）不区分 Guaranteed 和 Best-effort，也无法区分"需求少"和"被欠服务"。EMA 平滑（λ=0.3）避免瞬时波动频繁触发抢占。

Q: "四类决策"是哪四类？QAD 怎么统一协调它们？

四类决策：(1) 弹性配额借用/回收（DRA）——QAD < 1 时回收 Best-effort 资源恢复保障；(2) 调度排序——Guaranteed 优先，QAD 低的租户优先，QAD 接近时短作业优先；(3) 抢占 victim 选择——抢占效率 Ej = (释放资源 × 剩余时间) / (1 + α × 抢占代价)，选代价最小的 Best-effort 作业；(4) GPU 共置准入——QAD 高时允许更激进的 colocation（利用率优先），QAD 低时收紧（保障优先）。QAD 作为统一信号，让四个模块的决策方向一致——保障不足时偏向 QoS，保障充分时偏向利用率。

Q: "MPS 共置"具体怎么实现？K8s 不是以整卡为单位调度吗？

K8s 的 nvidia.com/gpu 是 Extended Resource，分配后不可修改。GPU 共享通过节点侧 MPS DaemonSet实现——每块 GPU 运行 MPS control daemon，允多个 CUDA context 共享 GPU，通过 per-client SM 限制（CUDA_MPS_ACTIVE_THREAD_PERCENTAGE）做算力隔离。Scheduler Plugin 在 Filter 阶段检查节点是否有足够空闲 SM 和显存来接纳新 Pod（基于干扰预测），允许后 Pod 调度到该节点，Node Agent 配置 MPS 限制。不需要扩展 K8s 资源模型，也不需要改用户代码。

Q: 干扰模型用什么特征？为什么选 Random Forest 不用深度学习？

特征来自 DCGM 硬件计数器：SM activity、memory bandwidth utilization、L2 cache hit rate、PCIe throughput 等——这些是框架无关的，不管你跑 PyTorch 还是 TensorFlow 都能采集。选 RF 三个原因：(1) 推理延迟 < 1ms，满足实时调度（DL 模型要 50-200ms）；(2) R² = 0.902，精度足够；(3) 硬件计数器特征跨模型泛化，不需要每种架构重训。运行时持续监控实际 slowdown，超过动态阈值时驱逐低优任务。

Q: Venus trace 是什么？为什么不直接在大集群上跑？

Venus 是公司内部集群的作业 trace，包含 23,859 个深度学习作业的提交时间、GPU 需求、运行时长等信息。Trace-driven simulation 可以在可控环境下对比多种策略（对比 Lucid、Gandiva 等 baseline），控制变量。同时我们在 16 节点 64 卡的 K8s 原型上做了实测验证，证明仿真结论在真实环境中成立。大规模集群实测成本高且影响生产，仿真是学术研究的标准做法。

Q: 为什么 JCT 只降 34% 而 GPU 利用率提升到 70.6%？

JCT = 排队时间 + 执行时间。调度优化主要影响排队时间，执行时间由计算量决定。当集群负载高时排队时间占比大，JCT 改善明显；负载低时改善小。34% 是平均 JCT 降低，排队延迟降了 46%，执行时间基本不变。GPU 利用率从 39.64% 提升到 70.6%（+29.5% vs Lucid），说明资源确实被更充分利用了——主要来自 DRA 借用空闲配额和干扰感知共置两块收益。

ElastiCo（Performance Evaluation 2026）简历追问

简历原文："训推弹性混部（ElastiCo）：面向训练与离线 LLM 推理在同一 GPU 上的安全共置，提出资源形态变换、弹性影子定价与干扰感知共置三项机制，以原生 Kubernetes 中间件形式实现、无需改动用户代码。64 卡实测与最高 512 卡仿真下，平均完成时间最高降低 2.94×、集群吞吐提升 2.02×、GPU 利用率由约 25% 提升至 46%。"

Q: 为什么要把训练和推理放同一块 GPU？分别放不行吗？

训练集群平均 GPU 利用率只有 25% 左右——训练任务在数据加载、梯度同步通信、checkpoint 保存时 GPU 是空闲的，这些空窗期加起来占了大部分时间。同时离线推理（如批量 embedding、离线评估）有明确 SLO 但不需要独占 GPU。把它们共置可以填补这些空窗，把利用率从 25% 提到 46%。为什么不分开跑？分开跑需要额外 GPU，而 GPU 是最贵的资源——共置用同样的硬件跑更多任务，直接降成本。

Q: "资源形态变换"是什么意思？训练和推理的资源使用有什么互补性？

"形态"指 SM 算力和显存的分配比例随负载动态变化。互补性体现在：(1) 训练在 forward/backward 阶段 SM 利用率高（80-90%），在 dataloader/communication 阶段 SM 空闲；(2) 推理在 prefill 阶段突发 SM 需求，decode 阶段 SM 利用率低但占显存（KV Cache）。通过 MPS 动态调整 SM 比例+ VMM 弹性显存，可以在训练空闲时把 SM 让给推理 prefill，训练繁忙时收回 SM。这和 MIG 静态切分（固定 50/50）的区别是：MIG 切完就不变，ElastiCo 毫秒级动态调整。

Q: "弹性影子定价"是什么？怎么定的价？

给 GPU 上的 SM 和显存定一个动态价格，反映当前稀缺程度。价格由训练任务的实时 GPU 利用率和显存占用决定——训练越忙价格越高，训练空闲价格越低。推理任务有一个"价值"（SLO 优先级 × 剩余工作量），价值大于当前价格才允许共置。本质上是一个基于市场机制的准入控制：价格自动调节供需，比固定阈值灵活——高优推理在资源紧张时仍可进入（付高价），低优推理只在空闲时进入（付低价）。

Q: 和 DeepShare 的区别是什么？你们为什么做了两个系统？

DeepShare 解决的是多租户之间的配额管理（A 团队和 B 团队之间怎么借 GPU），合用对象是训练+训练；ElastiCo 解决的是同一 GPU 上训推的共置问题，两者在不同层级。而且训推共置有特殊挑战：训练是长作业、不能被杀（重启代价大），离线推理是短作业、可以被暂停/驱逐——这种主客不对称性是 DeepShare 没有的。两者可以组合：DeepShare 做集群级租户治理，ElastiCo 做节点级训推填充。

Q: "无需改动用户代码"具体怎么做到的？

三层透明注入：(1) Admission Webhook 自动给 Pod 注入 MPS 环境变量和 VMM 配置；(2) Node Agent（DaemonSet）通过 CUDA Driver API 动态管理显存映射和 SM 限制，不经过用户代码；(3) Scheduler Plugin 在调度时做放置决策，用户只需给 Pod 打上 elastico.sh/class: training 或 inference 标签。底层用 LD_PRELOAD hook 部分 CUDA 内存分配 API 实现显存记账，对训练/推理框架完全透明。

Q: GPU 利用率 46% 也不算高啊？为什么不是更高？

25% → 46% 已经是将近翻倍的提升。为什么不是 70%+？(1) 我们有严格的 SLO 约束——训练 slowdown 不能超过阈值（约 10%），推理 SLO 必须达标；(2) 训练的空窗期不是完全可预测的，有时推理刚加载进来训练就开始计算了，需要保护训练；(3) 显存容量是硬约束——训练占了大部分显存（权重+梯度+优化器状态），推理的 KV Cache 和权重可用空间有限；(4) 46% 是安全共置下的利用率，牺牲部分利用率换 SLO 保证是合理的 trade-off。

SagePilot（撰写中）简历追问

简历原文："结构感知的深度学习负载资源预测与 Agentic 工作流编排（SagePilot）。计算图表征：ONNX 计算图→图样本，融合算子类型、张量形状与拓扑结构。GNN 多目标预测：一次前向预测时延、显存峰值、GPU 利用率，免反复试跑。Benchmark：运行时程序分析自动采集，10W+ 条，覆盖 CNN/Transformer/推荐。工作流编排：冷启动预部署、OOM 风险选卡、显存复用与驱逐。"

Q: 为什么需要"不运行就预测"？直接 profile 不行吗？

Profiling 成本非常高：一个 7B 模型在 A100 上跑一次推理 profiling 需要几分钟到十几分钟，如果要测多个 batch size、序列长度、GPU 型号组合，可能需要几小时、占用多张 GPU。对于大模型（70B），profiling 本身就需要多卡，成本更高。而且在 Agentic 场景下，模型组合是动态的（用户请求决定用哪个模型），无法提前 profile 所有组合。SagePilot 通过 ONNX 图 + GNN 一次前向推理（毫秒级）就能给出多指标预测，零试跑成本。

Q: 为什么用 GNN？计算图和 GNN 的图是什么关系？

ONNX 计算图天然就是 DAG——节点是算子（matmul、conv、layernorm），边是张量（带 shape 和 dtype）。GNN 的消息传递机制恰好模拟了张量在算子间的流动：每个算子节点聚合其输入张量的信息，类似实际执行时算子读入输入计算输出的过程。MLP/CNN 无法处理变长拓扑（不同模型节点数从几百到几万不等），GNN 天然支持。

Q: 多目标预测具体怎么做的？显存预测 OOM 怎么办？

共享 GIN backbone，三个独立 MLP 输出头分别预测时延、显存、利用率。训练时用 uncertainty weighting 自动平衡三个 loss。显存预测使用非对称 loss——低估的惩罚是高估的 3 倍，因为低估导致 OOM（请求直接失败），高估只是浪费显存（可接受）。预测结果加安全裕度 ρ ∈ [0.1, 0.3]。

Q: ONNX 图丢了 kernel fusion 等运行时信息，预测准吗？

这是个好问题。ONNX 静态图确实看不到推理引擎的 kernel fusion 策略，但我们做了补偿：(1) 训练标签来自真实执行的 profiling 数据，fusion 带来的加速已经隐含在标签里，GNN 会学习到哪些算子模式容易被融合；(2) 加入常见 fusion pattern 的特征（如 matmul+bias+gelu 的组合模式）；(3) 对于特定引擎（TensorRT）可以加一个校准步骤，用少量 profiling 数据 fine-tune。当前 R² 在 0.8 左右，对资源调度场景足够。

Q: 你做了这么多调度系统，核心方法论是什么？

贯穿几篇工作的核心理念是用轻量预测为调度器提供前瞻性信号，再设计弹性资源管理和代价感知抢占来利用这些信号。DeepShare 预测作业运行时间来做排序和抢占，Maestro 预测输出长度来做显存分配和 SRTF 调度，ElastiCo 用影子定价（本质也是基于利用率的预测）做共置准入，SagePilot 直接预测模型资源画像。共同模式是：(1) 识别可预测的信号；(2) 选择轻量、低延迟、可泛化的预测模型（LightGBM/RF/GNN，不用大模型）；(3) 设计弹性机制利用预测信号获益，同时有安全兜底应对预测错误。

面试官"挑刺"与陷阱题

面试官可能用挑战性问题试探你对自己工作的理解深度——不是真的否定你，而是看你是否思考过弱点。这些问题如果没准备过很容易卡壳。

Q: Maestro 说 KV 预留显存降低 67.2%，但这不是靠 CUDA VMM 超配"骗"出来的吗？实际物理显存并没有减少啊？

这个问题很尖锐。需要分清两个层面：(1) 预留（reservation）≠ 实际使用。传统方案为每个请求预分配最大 KV 空间（物理显存），即使实际输出很短也占着不放——这是真正的浪费。CUDA VMM 让虚拟地址远大于物理显存，但物理页按需映射，真正减少的是物理显存占用。(2) 67.2% 降低的是预留的 HBM 物理显存，不是虚拟地址。我们通过输出长度预测来决定实际映射多少物理页，短请求只映射少量物理页，其余虚拟地址不占物理内存。统计复用的前提是多 Agent 的 KV 峰值不重叠。如果所有请求同时输出长文本还是会 OOM，但实际 trace 中这种概率极低，且有准入控制兜底。

Q: 预测器出错了怎么办？如果预测输出 100 token 实际输出了 1000 token 呢？

这是所有预测驱动系统都要面对的问题。我们做了三层防护：(1) 偏向高估——训练 loss 对低估加惩罚（类似 SagePilot 的非对称 loss），预测值偏高而不是偏低，宁可浪费不能 OOM；(2) 动态扩容——KV 内存在 decode 过程中按页增长（paged attention 类似 vLLM 的思路），不是一次分配完，如果实际输出超过预测，运行时可以追加映射物理页；(3) 优雅降级——如果物理内存真的耗尽，选择抢占/暂停优先级最低的 stage 释放空间，而不是让整个服务崩溃。预测准确率 R²=0.78 看起来不高，但配合安全裕度和动态扩容，实际 OOM 率 < 0.1%。

Q: DeepShare 的干扰预测 R²=0.902 就敢用来做共置决策？万一预测错了把高优任务拖慢了怎么办？

R²=0.902 是在离线测试集上的指标，真正运行时我们不依赖单点预测做决策，而是：(1) 保守准入——预测 slowdown < 5% 才允许共置，留出足够安全边界；(2) 运行时闭环——共置后持续监控实际 slowdown（通过 DCGM 实时采集 SM 利用率），一旦实测 slowdown 超过阈值（如 10%）立即驱逐 Best-effort 任务，反应时间在秒级；(3) 只对 Best-effort 任务冒险——Guaranteed 任务的资源绝不用于共置，只有空闲配额借出的 Best-effort 任务才参与共置，预测错误最坏情况是杀掉 Best-effort 任务，不影响 Guaranteed QoS。

Q: 你们所有论文都用 trace 仿真+小集群实测，怎么证明在大规模生产环境有效？

这是学术研究的通用方法论局限。我们做了几件事增强可信度：(1) Trace 来自真实生产集群（Venus 23,859 条作业、Maestro 46,769 条 stage），不是合成数据；(2) 仿真器参数从 16 节点原型实测校准，保证仿真结果和真实环境趋势一致；(3) 64 卡 K8s 实测验证了关键结论（端到端 JCT、SLO 达成率），仿真主要用于验证大规模扩展性；(4) ElastiCo 做了 512 卡仿真看 scaling 趋势；(5) 字节实习中验证了核心算法思想在生产环境的可行性——弹性配额借用和代价感知抢占在工业界确实能落地。当然，真正部署到几千卡集群还需要更多工程鲁棒性工作，这也是未来方向。

Q: 为什么不直接用 vLLM/TGI 这些现成的推理框架？它们已经有 PagedAttention、continuous batching 了。

这是不同层面的优化：vLLM/TGI 优化的是单节点内推理引擎的 batching 和 KV 管理（PagedAttention 解决内部碎片、continuous batching 提高 GPU 利用率），Maestro 解决的是多节点、多模型、多 Agent 工作流的调度问题——一个用户请求涉及十几个 Agent stage、用多个不同模型、分布在多块 GPU 上。Maestro 可以和 vLLM 配合使用：节点内用 vLLM 做推理引擎优化，节点间用 Maestro 做工作流感知调度和显存管理。事实上我们的原型就是基于 vLLM 做的，分级权重缓存和 CUDA VMM 超配是在 vLLM 之上的额外优化。

Q: EDF 作为 baseline 是不是太弱了？为什么不和更先进的方法比？

EDF 是实时调度的经典 baseline，但我们的对比不只是 EDF。Maestro 对比了 EDF、SRTF（无预测）、FCFS、Karma（LLM 服务最近的调度工作）；DeepShare 对比了 Lucid（GPU 共享最强无侵入基线）、Gandiva（协同调度）、Tiresias（GPU 调度经典工作）、K8s 默认调度器。关键是 Maestro 的核心贡献不是调度算法本身（SRTF 是经典算法），而是把预测信号引入 LLM-MAS 场景并设计弹性显存机制来利用这些预测。和纯算法 baseline 比是为了证明预测信号的价值，而不是发明新的排序算法。

Q: MPS 有已知的问题啊——一个 CUDA context 段错误会影响 MPS server 下所有进程，你们怎么处理的？

确实，MPS 的一个已知风险是故障隔离差。我们的应对：(1) 只在受控环境下使用 MPS 共置——Best-effort 任务和 Guaranteed 任务共置时，Best-effort 任务是经过准入检查的（短作业、已知模型类型），减少未知风险；(2) 每个 GPU 节点上跑 MPS health monitor，检测到 MPS server 异常立即重启并隔离该节点上的新任务调度；(3) ElastiCo 场景下训练任务直接跑在 GPU 上（不经 MPS），推理任务通过 MPS 共享 SM，训练故障不依赖 MPS；(4) 对于生产环境，长期方案是用 MIG 或时间片（MPS 属于进程级共享，MIG 是硬件级隔离），但 MIG 不支持动态 SM 划分，ElastiCo 的动态资源形态变换目前只能通过 MPS 实现。

Crater 开源平台追问

简历原文："主导基于 Kubernetes 的 GPU 集群管理平台 Crater...已在实验室稳定运行 1.5 年，纳管 250+ 张 GPU、日均调度 200+ 任务，Apache-2.0 开源。"这是工程能力的重要证明。

Q: Crater 和 Volcano/Kubeflow 有什么区别？为什么不直接用现成的？

Volcano 提供了队列、优先级、gang scheduling 等基础能力，但它是通用的批调度器，缺少科研场景需要的功能：(1) 配额管理是硬划分，没有 DeepShare/ElastiCo 那种弹性借用；(2) 没有用户管理、审批流程、账户计费——科研集群需要导师审批学生的 GPU 使用；(3) 没有一键 LLM 训练/推理的作业模板，用户要写完整 YAML；(4) 没有集成 Jupyter/WebIDE/终端开发环境，科研用户需要交互式开发。Kubeflow 更偏 ML pipeline，不是集群管理平台。Crater 在 Volcano 基础上做了面向科研场景的封装和增强，整合了 DeepShare 和 ElastiCo 的调度能力，提供 Web 控制台降低使用门槛。

Q: 250 张 GPU 的集群，你作为项目负责人最头疼的技术问题是什么？

最头疼的是多用户场景下的 GPU 资源争用和占卡不释放问题。实验室场景下学生经常启动 Jupyter 后忘记关，GPU 被占着但利用率为 0。我们做了：(1) 占卡检测——Agent 监控 GPU 利用率，连续 N 分钟低于阈值就通知用户，超时自动回收；(2) 交互式任务有最长运行时间限制（默认 12 小时，可以续期）；(3) 训练任务必须在容器内跑，容器退出自动释放资源；(4) 空闲 GPU 标记和自动推荐。另外一个挑战是多型号 GPU（A100/A800/3090/4090/V100 混合），不同作业对 GPU 型号有不同要求，调度器需要感知拓扑和型号约束。

Q: Crater 的技术栈是 Go/React/Helm，你在其中写了多少代码？哪部分最复杂？

我是项目负责人，核心后端（Go）大约 70% 是我写的，包括自定义 Controller、Scheduler Plugin、API Server、配额管理逻辑；前端（React/TypeScript）主要是两个师弟做的，我做了架构设计和 Code Review；Helm Chart 和部署脚本是我写的。最复杂的部分是调度器和 K8s controller 的设计——队列状态机、配额超分/回收逻辑、和 Volcano 的协同、多维度抢占顺序的正确性保证。调试调度器问题非常痛苦，因为状态分布在 etcd、scheduler cache、node agent 多处，需要全链路 tracing。

论文间深层关系与体系化思考

面试官喜欢问"你的几篇论文之间是什么关系"——这考察你是否有体系化的研究视角，而不是零散地做了几个项目。

Q: 你的几篇工作（DeepShare/Maestro/ElastiCo/SagePilot）是一开始就规划好的 research line，还是逐步演进的？

是从实践中逐步演进出来的，不是一开始就规划好的。最早做 Crater 平台（2023）时发现真实 GPU 集群利用率只有 25-40%，于是做了 DeepShare 解决多租户配额借用问题（集群级）；在 DeepShare 实测中发现训推混部是更大的利用率提升空间，而且有独特的主客不对称挑战，于是做了 ElastiCo（节点级训推）；同时在 LLM Agent 场景下发现输出长度不确定是全新的调度挑战，做了 Maestro（请求级 LLM 推理）；在所有这些工作中反复遇到一个痛点——资源画像预测不准，需要 profiling，于是做 SagePilot（预测底座）。回头看形成了从集群→节点→请求→预测的逐层深入，但当时是跟着实际问题走的。

Q: 如果让你把这四个系统合并成一个超级系统，架构会是什么样？

这是个好问题。分层架构：(1) 预测层（SagePilot）——所有上层决策的基础，提供作业/模型/请求级别的资源画像预测，不需要运行就能给出时延、显存、利用率估计；(2) 集群调度层（DeepShare）——基于 QAD 做多租户配额管理、弹性借用、全局排序和抢占决策，决定作业放到哪个节点；(3) 节点运行时层（ElastiCo + Maestro）——在节点内做精细资源管理：训推共置用 ElastiCo 的资源形态变换和影子定价，LLM 推理用 Maestro 的分级权重缓存和 CUDA VMM 弹性显存，stage 边界抢占。Crater 是产品形态，把这些能力封装成用户友好的平台。共同的设计原则：预测驱动、弹性资源、代价感知、安全兜底。

Q: 你的工作和业界主流方案（K8s + Volcano/YARN/Kubernetes Scheduler）比，最大的 gap 在哪里？为什么工业界没有这样做？

几个原因：(1) 工业界优先稳定性——预测驱动调度如果预测出错会产生线上事故，工业界倾向用简单确定性策略（优先级队列+固定配额），学术界更愿意用预测换效率；(2) 工作负载差异——我们的场景是科研集群+LLM Agent，负载波动大、任务类型多样，弹性收益明显；而大厂在线服务集群负载规律，弹性空间小；(3) 工程复杂度——MPS 共置、CUDA VMM 超配、干扰预测都需要精细的工程实现和监控，大厂有更成熟的隔离方案（如 MIG、物理分区）；(4) 但趋势是工业界也在往这个方向走——字节内部的跨团队 Spot 调度、云厂商的 GPU 共享（如阿里云 cGPU、腾讯 qGPU）本质上都是弹性配额和精细隔离。我们的工作提供了算法和机制上的验证。

Q: ESCAPE（IEEE JCC Best Paper）和你后面的工作有什么关系？

ESCAPE 是我硕士阶段做的微服务资源估算工作，用 GNN + Profiling Engine 预测微服务的资源需求。这是我第一次接触"用 ML 做资源预测"这个方向，GNN 的使用经验直接启发了 SagePilot 的计算图表征思路——微服务调用图和 DNN 计算图在结构上都是 DAG，都可以用 GNN 建模；Profile Engine 的经验让我意识到 profiling 成本问题，才有了 SagePilot "零试跑预测"的动机。可以说 ESCAPE 是 research line 的起点，后面的 DeepShare/Maestro/ElastiCo 都需要预测信号，SagePilot 是回到预测这个基础问题上做深度工作。
