Scheduling Framework 详解

核心流程

K8s 1.19+ 引入 Scheduling Framework，把调度流程拆成 11 个扩展点（extension points），每个扩展点可以挂载多个插件。调度一个 Pod 经过两个阶段：

调度周期（Scheduling Cycle）——串行，对一个 Pod

  1. QueueSort：决定待调度队列中 Pod 的排序。默认按优先级降序 + 时间戳升序
  2. PreFilter：预处理和检查，计算 Pod 需要的资源汇总。如果检查失败直接拒绝，不进入后续流程
  3. Filter（预选）：遍历所有节点，排除不满足硬约束的。常见过滤条件：资源不足、NodeSelector 不匹配、Taint/Toleration 不满足、亲和性冲突。并行执行，默认取 min(numNodes, 100) 个可行节点后停止（percentageOfNodesToScore）
  4. PostFilter：当 Filter 没有找到任何可行节点时触发。默认行为是尝试抢占——找到优先级更低的 Pod 驱逐后能释放出足够资源的节点
  5. PreScore：Score 的预处理，可以共享计算结果给多个 Score 插件
  6. Score（优选）：对 Filter 通过的候选节点打分（0-100）。常见策略：LeastRequestedPriority（资源剩余最多）、BalancedResourceAllocation（CPU/内存比例均衡）、NodeAffinityPriority
  7. NormalizeScore：将各 Score 插件的分数归一化到 [0, 100]，然后加权求和
  8. Reserve：预占资源——在调度器缓存中扣减节点资源，防止后续 Pod 重复分配同一资源。这是乐观并发控制：先占再绑定

绑定周期（Binding Cycle）——可并行，多个 Pod 同时绑定

  1. Permit：最终准入控制。三种决定：Approve（放行）、Deny（拒绝，回退 Reserve）、Wait（挂起，等条件满足后放行）
  2. PreBind：绑定前的准备工作，如挂载 PV
  3. Bind：写入 API Server，告诉 kubelet 在该节点启动 Pod
  4. PostBind：清理和通知，如更新指标、发事件

三个队列

队列用途流转条件
ActiveQ（活跃队列）待调度的 Pod，按 QueueSort 排序新 Pod 加入 / BackoffQ 到期 / 集群事件触发重试
BackoffQ（退避队列）调度失败但可以重试的 Pod等待指数退避时间（1s, 2s, 4s...最大 10s）后移入 ActiveQ
UnschedulableQ（不可调度队列）当前集群状态下无法调度的 Pod等待集群事件（节点加入、Pod 删除等）后移入 BackoffQ 或 ActiveQ
Q: Pod 调度失败后的完整流转过程？

1. Pod 在 ActiveQ 中被取出调度

2. Filter 阶段找不到可行节点

3. PostFilter 尝试抢占，如果成功→标记 nominatedNode，Pod 回 ActiveQ 等待被抢占 Pod 终止

4. 如果抢占也失败→Pod 进入 UnschedulableQ

5. 集群发生变化（节点资源释放、新节点加入）→触发 Pod 移到 BackoffQ

6. 退避时间到期→Pod 移回 ActiveQ 重新调度

抢占机制详解

当一个高优先级 Pod 无法调度时，调度器尝试找到一个节点，驱逐上面优先级更低的 Pod 以释放资源：

  1. 候选筛选：遍历节点，模拟驱逐低优先级 Pod 后是否满足需求
  2. 牺牲者选择：选择需要驱逐最少 Pod 的节点；同等条件下选择驱逐优先级最低 Pod 的方案
  3. 优雅终止：被驱逐 Pod 收到 SIGTERM，等待 terminationGracePeriodSeconds 后强制终止
  4. PDB 保护：PodDisruptionBudget 可以限制同时被驱逐的 Pod 数量，保证服务可用性

InPlacePodVerticalScaling（1.27 alpha）

传统修改资源需要重建 Pod。InPlace 允许在不重启容器的情况下动态调整 CPU 和 Memory 的 requests/limits。

限制：只支持 CPU 和 Memory，不支持 GPU。GPU 是 Extended Resource，admit 后不可修改。GPU 分配必须在调度时确定，运行时只能通过 MPS 等方式做软共享。

K8s 面试高频问答

Q: 一个 Pod 从创建到运行经历了什么？
  1. 用户提交 Pod 到 API Server
  2. API Server 验证、持久化到 etcd
  3. Scheduler 通过 Informer 监听到新的未绑定 Pod
  4. Scheduler 执行 Filter → Score → Reserve → Bind
  5. Bind 结果写入 API Server（Pod.spec.nodeName）
  6. 目标节点的 kubelet 通过 Informer 发现分配给自己的 Pod
  7. kubelet 调用 CRI 创建容器，调用 CNI 配置网络，调用 CSI 挂载存储
  8. 容器启动，kubelet 上报状态到 API Server
Q: Informer 机制是什么？为什么不直接轮询 API Server？

Informer 是 client-go 提供的本地缓存 + Watch 机制。首次 List 获取全量数据存入本地缓存（Store），之后通过 Watch 接收增量事件（Added/Modified/Deleted）。相比轮询：(1) 实时性——事件驱动而非定期拉取；(2) 性能——减少 API Server 负载；(3) 可靠性——Watch 断线后通过 ResourceVersion 续接。Informer 还包含 Indexer（高效查询）和 WorkQueue（去重合并）。

Q: etcd 为什么是性能瓶颈？怎么优化？

etcd 是集群唯一的持久化存储，所有写操作都要经过 Raft 共识（至少过半节点确认）。大集群下 event、configmap、secret 的频繁写入导致延迟上升。优化方法：(1) SSD 磁盘降低 fsync 延迟；(2) 分离 event 到独立 etcd 集群；(3) API Server 启用 watch cache；(4) 合理设置 compaction 周期减小数据库体积。

Q: 如何实现自定义调度器？有几种方案？

三种方案：

  1. Scheduler Plugin（推荐）：实现 Scheduling Framework 的扩展点接口（Filter/Score/Reserve 等），编译进调度器二进制。优点：性能好，原生集成
  2. Scheduler Extender：HTTP webhook 方式，调度器在 Filter/Score 后调用外部服务。优点：不需要重编译调度器；缺点：网络延迟，不支持所有扩展点
  3. 完全自定义调度器：独立二进制，通过 Pod 的 schedulerName 字段指定。优点：完全自由；缺点：不能复用默认插件，维护成本高
Q: K8s GPU 调度的挑战和解决方案？

核心挑战：

  1. 整数分配：nvidia.com/gpu 是 Extended Resource，只能整数分配，不支持 0.5 GPU
  2. 拓扑无感：默认调度器不感知 GPU 间的 NVLink 拓扑，可能把需要通信的 Pod 放到不同 PCIe 树
  3. 无法修改：admit 后 GPU 数量不可调整

解决方案：

  1. GPU 共享：MPS / MIG / 时间片（需要 device plugin 配合）
  2. 拓扑感知：Topology Manager + 自定义 Score 插件
  3. 弹性训练：Elastic Horovod / PyTorch Elastic（运行时加减 worker）
Q: Device Plugin 怎么工作？

Device Plugin 是 kubelet 的扩展机制，用于管理非标准硬件资源。工作流程：(1) Device Plugin 启动后通过 gRPC 向 kubelet 注册资源名称（如 nvidia.com/gpu）；(2) kubelet 向 API Server 上报节点有多少该资源；(3) 调度器基于这些资源做 Filter/Score；(4) Pod 调度到节点后，kubelet 调用 Device Plugin 的 Allocate 方法获取设备信息（如 /dev/nvidia0）；(5) 设备信息注入容器环境。NVIDIA 的 k8s-device-plugin 就是这样实现 GPU 调度的。

Q: Headless Service 和 ClusterIP Service 的区别？

ClusterIP Service 有一个虚拟 IP，kube-proxy 做负载均衡。Headless Service（clusterIP: None）不分配虚拟 IP，DNS 查询直接返回所有后端 Pod 的 IP。在 AI Infra 中的用途：分布式训练需要所有 worker 直接通信（NCCL AllReduce），用 Headless Service 让每个 Pod 能解析其他 Pod 的 IP，建立直连。
