## 用对照实验识别优化来自哪里

多副本推理至少应比较单实例 APC、普通多副本负载均衡、缓存感知路由，以及启用实际 KV 传输后的配置。每次只改变一个机制，并固定模型版本、硬件、TP/PP、最大上下文、输入输出分布与请求速率。下面是实验设计，不是已经运行得到的性能结果。

| 实验组 | 改变项 | 能回答的问题 |
|---|---|---|
| A | 单实例，APC 关闭/开启 | 引擎内部重复 prefill 能省多少 |
| B | 两个相同实例，普通负载均衡，APC 开启 | 流量打散造成多少局部性损失 |
| C | 同两实例，近似前缀路由 | 路由历史能否有效预测缓存位置 |
| D | 同两实例，KV 事件索引 | 更准确的缓存位置是否值得额外开销 |
| E | D 加跨副本 KV 传输 | 热点溢出或迁移时，搬运是否优于重算 |
| F | 对比聚合部署与 PD 分离 | 分离后 SLO 收益是否覆盖传输与容量成本 |

每组至少包括冷缓存、稳定热缓存、热点倾斜、无公共前缀和缓存失效五种输入形态。缓存实验必须记录 warm-up，不能用冷缓存的基线对比预热过的优化组。

## 构造可解释的请求

1. 使用固定长 system/document 前缀，每条请求仅修改后缀，测连续前缀复用。
2. 在前缀中间修改一个 token，检查命中长度是否在变化点附近中断。
3. 构造长度相同但内容不同的输入，检验所谓加速是否只是预热或并发变化。
4. 注入大量新前缀造成淘汰，再重放旧前缀，比较路由预测和引擎实际复用。
5. 测试副本重启/新增后的行为，记录索引清理、缓存冷启动与流量收敛。

模板、tokenizer 与多模态编码必须固定。按字符拼接只能构造文本，实际长度应以引擎 tokenization 为准。避免把 request ID、随机时间戳放到公共前缀开头。

## 指标的统计对象与分母

| 指标 | 定义与单位 | 解释边界 |
|---|---|---|
| TTFT | 客户端发出请求到收到首个输出 token，ms | 包含网络与排队，按请求统计 P50/P95/P99 |
| ITL | 同一请求相邻输出 token 到达间隔，ms | 流式缓冲可能造成多个 token 一次到达，需说明采集口径 |
| TPOT | 常用口径为首 token 后生成耗时/(输出 token 数−1)，ms/token | 单 token 输出不能按此公式计算，均值不能代替 ITL 尾部 |
| 真实前缀复用率 | 引擎实际复用 token / 被查询的 prompt token | 使用同一窗口累计量的比值，不能把各实例比率简单平均 |
| 路由预测命中 | 路由索引预计可用的块/被检查的块 | 与 GPU 实际驻留不同，截断匹配时尤其需要说明分母 |
| 输出吞吐 | 测量窗口内输出 token / 秒 | 固定是否含失败、取消和 warm-up |
| SLO goodput | 同时满足成功条件与延迟目标的请求数 / 秒 | 先明确目标，不能仅凭吞吐增长宣布改善 |
| KV 传输 | 字节数、完成时延、失败率、有效 GB/s | 同时记录有效复用 token，避免大量无益搬运 |
| 负载偏斜 | 各 Pod 在途 token、队列长度和利用率分布 | 请求数均匀不代表 token 工作量均匀 |
