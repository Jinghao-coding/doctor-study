## 多 Agent 协作先解决分工与信息边界

多 Agent 系统让多个模型驱动的执行单元协作完成任务。潜在收益来自可独立并行的工作、不同的工具与知识，以及较小的上下文；成本则来自任务分解、通信、重复查询和结果合并。

如果任务高度串行、共享大量中间状态，增加 Agent 可能延长完成时间。能够用单个 Agent 加按需工具或知识加载解决的任务，应先验证这条基线。[LangChain Multi-agent](https://docs.langchain.com/oss/python/langchain/multi-agent)

## 三种控制关系

| 方式 | 谁控制下一步 | 适用条件与代价 |
|---|---|---|
| Supervisor 调用子 Agent | 主 Agent 委派、收集并汇总结果 | 便于统一目标和校验；主 Agent 可能成为串行瓶颈 |
| Handoff | 将后续处理交给新的 Agent 或角色 | 适合领域或权限切换；需要明确当前负责人和交接状态 |
| 显式 Workflow / DAG | 编排器依据边和条件推进 | 依赖、并行和失败规则清楚；动态任务需要生成或调整图 |

一次 Handoff 不必创建一个新进程。多个 Agent 也不必全部互相对话；控制关系应与任务依赖一致。

以公开技术资料分析为例，来源搜集和代码入口检查可以独立进行；机制解释依赖它们的结果，最终结论还需校验。若两个子任务都直接修改同一段正文，就从信息搜集问题变成了并发写入问题。

## 委派需要结构化任务契约

下面是一个通用任务记录示例：

```json
{
  "task_id": "inspect-source",
  "input_revision": 5,
  "goal": "核对指定提交中的资源释放条件",
  "source_revision": "固定提交或文档版本",
  "allowed_actions": ["read"],
  "depends_on": [],
  "output_schema": "claims-with-locations",
  "status": "ready"
}
```

契约应说明输入、目标、约束、权限和完成依据。输出要包含结论、来源位置、仍未解决的问题及产物引用。仅收到“已完成”不能确认要求已经满足。

对于会改变外部系统的任务，执行者还需要明确的动作所有权。上层委派不应自动扩大用户授权，子 Agent 的报告也不能替代工具回执。

## 并行推进与结果汇合

```flow
分解依赖 | 每个子任务有 ID、输入版本和依赖列表
启动 Ready 任务 | 依赖已满足且预算、并发额度允许
保存局部结果 | 结果关联任务 ID、尝试及输入版本
校验结果 | 检查格式、证据与完成条件
Join | 按预先定义的条件等待、汇总或转入失败处理
提交产物 | 由负责该产物的执行者合并修改
```

Join 可以要求全部成功，也可以容许明确标注的部分结果。若某分支是最终结论的必要证据，它失败时就不能把该结论当作已验证。重复或延迟到达的结果应按任务和版本去重，旧输入的输出不能覆盖新输入的结果。

## 共享状态需要合并规则

两个子 Agent 同时更新 `results` 时，最后写入覆盖可能丢掉另一个结果。LangGraph 的 reducer 用于定义状态字段如何合并；没有自定义 reducer 的字段使用覆盖更新，不能据此假定并发写入天然安全。[Graph API：Reducers](https://docs.langchain.com/oss/python/langgraph/graph-api#reducers)

| 数据 | 可采用的规则 | 需要处理的问题 |
|---|---|---|
| 独立证据集合 | 按证据 ID 合并 | 重复提交、来源版本和互相矛盾的结论 |
| 数值统计 | 按唯一贡献 ID 去重后聚合 | 重试导致重复计数 |
| 共享文件 | 单一负责者提交，其他 Agent 返回建议或补丁 | 同位置修改冲突与旧版本覆盖 |
| 任务状态 | 受版本和合法状态转换约束的更新 | 两个执行者推进、迟到结果改变终态 |

追加列表的 reducer 可以保留两份更新，但也会保留重复数据。涉及外部副作用时，还需要执行端去重；状态合并不能代替外部事务。

## Context、Memory 与 Checkpoint

| 概念 | 内容与作用 | 管理方式 |
|---|---|---|
| Context | 某次模型调用实际看见的输入 | 选择当前约束、必要历史和工具结果，受窗口限制 |
| Memory | 可跨调用检索的事实、偏好或经验 | 保存来源、时间、适用范围和更新规则 |
| Checkpoint | 执行状态及恢复位置 | 按任务或 thread 保存，服务暂停与故障恢复 |

把所有子 Agent 的完整轨迹拼给主 Agent，会增加输入成本，也可能淹没当前问题。较好的交付单元是“结论 + 证据 + 适用条件 + 未解决事项”，必要时再读取原始材料。

摘要必须保留否定、数值、对象身份和最新约束；摘要里没有保留的细节，应能够追溯到原始记录。记忆中的旧结论遇到新证据时需要更新，不能仅因被保存就获得更高可信度。[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

## MCP 与 A2A 的职责

| 协议 | 主要抽象 | 解决的问题 |
|---|---|---|
| MCP | Host、Client、Server，以及 tools、resources、prompts | 应用发现并使用外部工具与上下文 |
| A2A | Agent Card、Task、Message、Artifact | 与远端 Agent 交换任务、状态、消息和产物 |

MCP 连接的 Server 可以位于本地或远端；A2A 的远端 Agent 可以保持其内部工具和执行细节不透明。二者都不能仅凭建立连接，就保证业务动作的幂等性、授权范围和结果正确性。

来源：[MCP Architecture](https://modelcontextprotocol.io/docs/learn/architecture)、[A2A Core Concepts](https://a2a-protocol.org/latest/topics/key-concepts/)。这里比较的是职责与对象，不把具体传输或字段版本当作永久不变的协议要求。

## 用任务结果衡量协作收益

在相同任务集、可访问资料和预算下，对比单 Agent 与多 Agent，至少检查：

- **正确性**：最终产物是否满足任务要求，关键结论是否有支持证据。
- **延迟**：从接收任务到有效结果完成，包含排队、分解、汇合与校验。
- **成本**：所有 Agent 的模型输入输出、工具调用和重复读取之和。
- **协作损失**：冲突修改、重复执行、错误交接和合并时遗漏约束的比例。
- **恢复能力**：局部分支失败后，能否保留已确认结果并只重做必要部分。

独立只读分支的执行部分可近似由最慢分支决定，再叠加分解、汇总与校验耗时。若 API 限流使分支实际串行，或主 Agent 重新完成所有子任务，预期的并行收益就不会出现。多个 Agent 使用相同模型和信息，也可能犯相关错误，不能把多数同意直接当作独立验证。

任务契约、合并规则和评估方式为通用设计分析。来源核对：2026-11-05。
