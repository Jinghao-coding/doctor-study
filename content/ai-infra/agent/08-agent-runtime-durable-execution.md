## Agent Runtime 把模型决策推进成可恢复的任务

模型可以输出下一步动作和工具参数；Agent Runtime 负责执行这些动作、保存进展、控制预算，并在失败或外部输入到来后继续推进。一个长任务可能经过多次模型调用、多个工具、进程重启和人工交互，其生命周期通常比一次 HTTP 请求更长。

| 层次 | 核心职责 | 典型状态 |
|---|---|---|
| 模型决策 | 解释任务，提出动作或生成结果 | 输入上下文、结构化输出、工具调用建议 |
| 任务编排 | 维护依赖与状态，决定继续、等待或终止 | Run、Step、版本、预算、待恢复位置 |
| 工具执行 | 校验调用并操作外部系统 | 调用 ID、幂等键、执行结果、外部对象 ID |
| 持久化 | 保存进展与可查询的执行事实 | Checkpoint、工具回执、产物引用 |

这些职责可以先放在同一个服务中。拆成独立服务的理由应来自并发、隔离或故障恢复需求。

## 一次执行要保留哪些状态

下面是通用设计示例，各字段并非某个框架的固定 API：

```json
{
  "run_id": "run-42",
  "status": "waiting_input",
  "version": 8,
  "next_step": "publish_result",
  "input_revision": 3,
  "artifact_id": "draft-17",
  "remaining_model_calls": 4
}
```

`run_id` 关联整个任务；每个逻辑步骤还应有稳定的 `step_id`，每次尝试有不同的 `attempt`。外部动作使用稳定的幂等键，避免把“同一步的重试”误当作新的业务动作。大型文件可单独存储，状态中保留引用、内容校验值和来源版本。

任务状态可以包含 `queued → running → waiting_input / succeeded / failed`。取消请求还需要记录 `cancel_requested`，等正在执行的动作停止或完成对账后，再确认最终结果。

## Checkpoint 保存进展，不包办外部事务

以 LangGraph 为例，checkpointer 按 thread 保存图状态，完整 checkpoint 位于 super-step 边界；同一步中已成功节点的 pending writes 可以帮助恢复时跳过已完成部分。长期共享信息则由 store 等应用存储管理。[Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)、[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

但外部系统不一定与 checkpoint 使用同一个事务：

```text
1. 工具向外部系统创建对象，创建成功
2. Runtime 尚未保存工具结果，进程崩溃
3. 恢复后重跑该步骤，再次发起创建
```

此时 checkpoint 本身无法判断第一次调用是否已经生效。常用处理是：

1. 在发起副作用前持久化稳定的操作键。
2. 外部服务按该键去重，重复请求返回同一个业务结果。
3. 工具回执记录外部对象 ID，恢复时查询实际状态。
4. 外部接口不支持去重且结果未知时，进入对账流程，避免盲目重试。

把操作拆成更小的 task 可以缩小重放范围；远端已成功、本地尚未记下结果的窗口仍需要幂等或对账来处理。[Fault tolerance](https://docs.langchain.com/oss/python/langgraph/fault-tolerance#retry-boundaries-and-idempotency)

## 重试、恢复与重放的区别

| 行为 | 发生原因 | 需要保留或检查 |
|---|---|---|
| Retry | 某次调用失败 | 同一逻辑动作、尝试次数、错误类型和退避 |
| Resume | 任务在暂停或崩溃后继续 | 原任务 ID、持久状态、未完成步骤 |
| Replay | 从历史位置重新执行以调试或比较 | 历史输入和版本，是否允许再次触发真实副作用 |
| Compensation | 已生效操作需要业务补偿 | 原操作回执、补偿条件和补偿自身的幂等性 |

网络超时通常只表示调用方没及时拿到结果。参数格式错误需要修正输入，权限错误需要处理授权；重复请求不会自动消除这些错误。暂时性故障才适合有上限的退避重试，还应受整项任务剩余时间和预算约束。

## 暂停恢复时绑定具体操作内容

LangGraph 的 `interrupt()` 支持暂停并等待输入；恢复时，被中断的节点会从函数起点重新执行。因此，中断前发生的副作用可能再次运行；即使把副作用移到确认之后，也仍要处理它成功后、节点完成前发生故障的窗口。[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts#side-effects-called-before-interrupt-must-be-idempotent)

对于需要用户确认的动作，可以先生成并保存待执行内容，再让确认记录关联内容版本或校验值。恢复时核对确认对应的内容，避免把对版本 A 的确认用于执行后来生成的版本 B。确认、拒绝和编辑应是不同的状态转换，不能仅用一句自由文本模糊推断。

## 超时与取消需要向执行端传播

用户关闭页面或连接超时，不等于远端工具已经停止。Runtime 应区分连接状态、任务状态和工具状态：

```flow
接收取消 | 保存取消意图，停止调度后续步骤
通知执行端 | 对运行中的子任务发送可用的取消信号
处理已发动作 | 可取消则取消；结果未知则查询，已成功则记录回执
收敛终态 | 确认没有后续动作，记录剩余外部效果
```

已发生的外部写入可能需要补偿，而不是简单将任务标为 canceled。进程内取消协程只能覆盖本地执行，还需要远端接口或工作进程配合。

## 预算与背压控制资源增长

限制单次模型输出长度，无法约束整项任务的成本。任务可能递归调用子 Agent、重复工具查询，或者持续等待外部输入。

| 控制项 | 作用 |
|---|---|
| 总模型调用数、Token 或费用预算 | 限制整条执行链，包括子任务的累计消耗 |
| 总截止时间与单工具超时 | 防止一个工具耗尽整个任务时间 |
| 并发上限 | 避免分解任务时瞬间放大模型、数据库和工具负载 |
| 有界等待队列与租户限额 | 使过载显式表现为排队、延迟接纳或拒绝 |
| 无进展检测 | 对相同参数和相同结果的循环进行诊断，再决定修正或终止 |

重复调用不一定无意义，例如轮询中的对象状态可能变化。无进展判断应结合观测版本、有效信息变化和调用目的，不能仅按工具名重复就终止。

## 用故障注入检查恢复语义

| 注入点 | 应验证的结果 |
|---|---|
| 工具成功后、保存回执前崩溃 | 同一动作不会创建重复业务对象，或能识别并对账 |
| 等待外部输入时重启 | 恢复原任务及原待确认内容 |
| 同一任务被重复投递 | 控制状态不会被两个执行者同时无序推进 |
| 旧执行者延迟返回 | 通过版本或执行权校验阻止覆盖新的状态 |
| 用户取消时工具仍执行 | 后续步骤停止，最终记录与真实外部效果一致 |

单任务推进可采用带版本的条件更新；分布式执行还可能需要租约和执行代次，并由状态存储及执行端核验。以上状态模型与故障处理为通用设计分析，LangGraph 链接用于说明对应的持久化和重执行机制。来源核对：2026-11-05。
