<div class="card-m">
<h3>📌 一句话结论</h3>
<p>GPU 集群管理面试题可归到一条主线：K8S 默认调度器<strong>无 Gang、无公平、无拓扑</strong>，需在 Scheduling Framework 上扩展，靠 Gang + Backfill、弹性配额、拓扑感知（TP 锁 NVLink）和 Checkpoint/弹性恢复，把刚性、强拓扑、Gang 聚合、抢占代价重的 GPU 资源从 30-40% 利用率拉到 70%+。</p>
</div>

<h2>调度框架方向</h2>

<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q1: K8S 默认调度器为什么不适合 GPU 训练调度？如果要改造，你会怎么做？</div>
<div class="qa-a">
<p>K8S 默认调度器的三大不足：</p>
<ol>
<li><strong>无 Gang Scheduling</strong>：默认调度器逐 Pod 调度，如果 8 卡 Job 只调度了 7 个 Pod，第 8 个因资源不足 pending，则前 7 个占着资源却无法训练，造成资源浪费（"资源碎片化"问题）</li>
<li><strong>无队列/公平性</strong>：默认调度器只有 PriorityClass，没有 Queue 级别的公平性保证。大量小 Job 可以饿死大 Job，反之亦然</li>
<li><strong>无拓扑感知</strong>：默认调度器不知道 GPU 之间的 NVLink 拓扑关系，可能把 TP 组的 Pod 调度到 NVLink 不连通的节点上，导致通信性能下降 10 倍</li>
</ol>
<div class="table-scroll">
<table>
<thead><tr><th>方案</th><th>改动量</th><th>效果</th><th>推荐度</th></tr></thead>
<tbody>
<tr><td>Scheduling Framework 扩展插件（如 Volcano）</td><td>中</td><td>解决 Gang + 公平性</td><td>★★★</td></tr>
<tr><td>独立调度层（如 Kueue）</td><td>低</td><td>解决排队 + 配额，不改 K8S 调度器</td><td>★★★</td></tr>
<tr><td>自研调度器替换 kube-scheduler</td><td>高</td><td>完全控制</td><td>★☆☆（维护成本太高）</td></tr>
</tbody>
</table>
</div>
<p>改造的核心原则是<strong>"最小侵入"</strong>——尽量在 K8S 已有框架上扩展，而不是替换。Scheduling Framework 的插件机制正好提供了这个能力。</p>
<p class="qa-summary">💡 K8S 默认调度器对 GPU 训练的三大硬伤：无 Gang、无公平、无拓扑。改造思路是在 Scheduling Framework 上做扩展，而不是替换调度器。</p>
</div>
</div>

<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q2: Volcano 的 Gang Scheduling 是怎么实现的？有什么缺陷？</div>
<div class="qa-a">
<p><strong>实现机制：</strong></p>
<ol>
<li>用户创建 <code>PodGroup</code> CRD，声明 <code>minMember</code>（最少需要同时运行的 Pod 数量）</li>
<li>Volcano 的 <code>gang</code> 插件在 PreFilter 阶段检查：如果当前可调度资源不足以满足 <code>minMember</code>，则整个 PodGroup 的所有 Pod 都不调度</li>
<li>调度成功后，如果部分 Pod 失败导致运行中的 Pod 数 &lt; minMember，则杀死所有 Pod（保证 All-or-Nothing 语义）</li>
</ol>
<pre><code>PodGroup CRD (minMember=8)
    ↓
gang 插件 PreFilter: 可调度 Pod 数 &gt;= minMember?
    ├── Yes → 正常调度所有 Pod
    └── No  → 所有 Pod 状态设为 Unschedulable，等待资源释放</code></pre>
<p><strong>缺陷：</strong></p>
<ol>
<li><strong>资源浪费</strong>：等待期间所有 Pod 占着资源不动（"占坑不拉屎"问题）</li>
<li><strong>死锁可能</strong>：两个 Gang Job 各占部分资源，都等对方释放 → 死锁</li>
<li><strong>无弹性</strong>：minMember 是固定的，不能根据当前资源动态调整</li>
<li><strong>粗粒度</strong>：只有全部调度或全部不调度，没有部分调度 + 排队的中间态</li>
</ol>
<div class="card-d">
<p><strong>改进方案：</strong></p>
<ul>
<li><strong>Coscheduling</strong>：用队列替代 Gang，Job 进入队列排队，资源足够时一次性调度</li>
<li><strong>Elastic Gang</strong>：minMember 支持范围（如 min=4, max=8），根据资源弹性调度</li>
<li><strong>Backfill</strong>：小 Job 填充 Gang 等待期间的空闲资源</li>
</ul>
</div>
<p class="qa-summary">💡 Gang Scheduling 的核心矛盾是 All-or-Nothing 语义和资源利用率之间的博弈——解决思路是弹性 Gang + Backfill 填充。</p>
</div>
</div>

<h2>多租户方向</h2>

<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q3: GPU 集群的资源利用率通常只有 30-40%，你会怎么优化？</div>
<div class="qa-a">
<p>GPU 利用率低的根因是<strong>碎片化</strong>——大量的资源被占而不用或低效使用。优化从四个维度入手：</p>
<div class="card-s">
<p><strong>1. 调度维度</strong>（贡献最大，可提升 20-30%）：</p>
<ul>
<li><strong>Gang + Backfill</strong>：大 Job Gang 等待期间，Backfill 小 Job 填充碎片</li>
<li><strong>拓扑感知</strong>：减少跨节点 TP，提升通信效率 → 提升有效计算时间占比</li>
<li><strong>优先级 + 抢占</strong>：低优先级 Job 被抢占后释放资源给高优先级 Job</li>
</ul>
</div>
<div class="card-m">
<p><strong>2. 多租户维度</strong>（可提升 10-20%）：</p>
<ul>
<li><strong>ElasticQuota</strong>：空闲配额自动共享，避免"我的配额我用不完，你的配额你不够用"</li>
<li><strong>分时复用</strong>：训练（夜间批处理）和推理（白天在线）分时共享 GPU</li>
</ul>
</div>
<div class="card-d">
<p><strong>3. 共享维度</strong>（可提升 10-15%）：</p>
<ul>
<li><strong>MIG</strong>：大卡切小卡，推理/小模型训练复用同一张 GPU</li>
<li><strong>MPS</strong>：多进程共享 GPU，适合推理场景</li>
<li><strong>时间片</strong>：GPU 时间片调度（如 Run:ai），适合轻量级任务</li>
</ul>
</div>
<div class="card-w">
<p><strong>4. 业务维度</strong>（可提升 5-10%）：</p>
<ul>
<li><strong>自动 Batch Size 调优</strong>：避免显存浪费</li>
<li><strong>自动混合精度</strong>：FP16 训练，减少显存占用</li>
<li><strong>Gradient Checkpointing</strong>：用计算换显存</li>
</ul>
</div>
<p class="qa-summary">💡 GPU 利用率优化的核心是降碎片——调度层面 Gang+Backfill，多租户层面弹性配额，共享层面 MIG/MPS，三个维度叠加可以从 30% 提到 70%+。</p>
</div>
</div>

<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q4: 训练和推理混部时，如何保证推理的延迟不受训练影响？</div>
<div class="qa-a">
<p><strong>核心矛盾</strong>：训练任务 GPU 利用率接近 100%，会争抢推理任务的 GPU 时间片，导致推理延迟飙升。</p>
<p><strong>隔离方案（从强到弱）：</strong></p>
<div class="table-scroll">
<table>
<thead><tr><th>方案</th><th>隔离强度</th><th>资源利用率</th><th>适用场景</th></tr></thead>
<tbody>
<tr><td><strong>物理隔离</strong>（不同节点）</td><td>最强</td><td>最低</td><td>延迟敏感的在线推理</td></tr>
<tr><td><strong>MIG 隔离</strong>（同 GPU 不同 Instance）</td><td>强</td><td>中</td><td>A100/H100 推理 + 小训练</td></tr>
<tr><td><strong>MPS 隔离</strong>（同 GPU 共享）</td><td>中</td><td>较高</td><td>推理延迟容忍 &gt; 10ms</td></tr>
<tr><td><strong>时间片</strong>（GPU 分时）</td><td>弱</td><td>最高</td><td>离线推理</td></tr>
</tbody>
</table>
</div>
<p><strong>推荐方案：</strong></p>
<ol>
<li><strong>延迟敏感推理（P99 &lt; 50ms）</strong>：物理隔离，专用节点</li>
<li><strong>中等延迟推理（P99 &lt; 200ms）</strong>：MIG 隔离，推理占 1-2 个 MIG Instance，训练占其余</li>
<li><strong>离线推理</strong>：与训练混部，低优先级，利用训练空闲时间</li>
</ol>
<div class="card-w">
<p><strong>关键细节：</strong></p>
<ul>
<li>MIG 的 Instance 之间有硬件级隔离，训练的显存溢出不会影响推理</li>
<li>MPS 没有硬件隔离，需要通过 <code>CUDA_MPS_ACTIVE_THREAD_PERCENTAGE</code> 限制训练的 GPU 时间片占比</li>
<li>时间片方案需要监控推理延迟，超过阈值时暂停训练任务</li>
</ul>
</div>
<p class="qa-summary">💡 训练和推理混部的关键不是共享，而是隔离——延迟敏感推理用 MIG 硬件隔离，离线推理才考虑时间片共享。</p>
</div>
</div>

<h2>拓扑方向</h2>

<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q5: 如何评估一个 GPU 集群的拓扑质量？哪些指标最重要？</div>
<div class="qa-a">
<p><strong>拓扑质量评估三维度：</strong></p>
<div class="card-s">
<p><strong>1. 节点内拓扑质量：</strong></p>
<ul>
<li>NVLink 全连接度：8 卡 A100 有 6 条 NVLink/GPU，是否全连接？</li>
<li>NVSwitch 有无：有 NVSwitch 则任意两卡间带宽一致（900 GB/s）；无则部分卡对带宽低</li>
<li>PCIe 拓扑：GPU 是否挂在同一个 NUMA Node？跨 NUMA 访问有 20-30% 性能损失</li>
</ul>
</div>
<div class="card-m">
<p><strong>2. 节点间拓扑质量：</strong></p>
<ul>
<li>InfiniBand 网络：是否是 Fat-Tree 拓扑？是否有收敛比？（1:1 无收敛最优）</li>
<li>GPU 直连：是否支持 GPUDirect RDMA？（减少一次 CPU 拷贝，延迟降低 30-50%）</li>
<li>网络带宽：HDR (200 Gbps) vs NDR (400 Gbps)？</li>
</ul>
</div>
<div class="card-d">
<p><strong>3. 全局拓扑一致性：</strong></p>
<ul>
<li>所有节点是否同构？（不同型号 GPU 混部会导致负载不均）</li>
<li>网络是否对称？（某些节点对之间带宽不一致会导致 AllReduce 性能下降）</li>
</ul>
</div>
<p><strong>关键指标排序：</strong></p>
<ol>
<li><strong>NVLink 全连接度</strong>（影响 TP 性能，权重最高）</li>
<li><strong>InfiniBand 收敛比</strong>（影响 DP/PP 通信）</li>
<li><strong>GPUDirect RDMA 支持</strong>（影响跨节点 TP 通信效率）</li>
<li><strong>NUMA 一致性</strong>（影响单节点内数据搬运延迟）</li>
</ol>
<p class="qa-summary">💡 评估拓扑质量的核心是看通信热点——NVLink 全连接度决定 TP 上限，IB 收敛比决定跨节点通信带宽，GPUDirect RDMA 决定跨节点通信延迟。</p>
</div>
</div>

<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q6: GPUDirect RDMA 是什么？为什么对分布式训练重要？</div>
<div class="qa-a">
<p><strong>传统路径</strong>（无 GPUDirect RDMA）：</p>
<pre><code>GPU A 显存 → CPU A 内存 → NIC A → 网络 → NIC B → CPU B 内存 → GPU B 显存
   │                                                           │
   └── 2 次 PCIe 搬运 + 1 次 CPU 拷贝 ──┘── 2 次 PCIe 搬运 + 1 次 CPU 拷贝 ──┘</code></pre>
<p><strong>GPUDirect RDMA 路径：</strong></p>
<pre><code>GPU A 显存 → NIC A → 网络 → NIC B → GPU B 显存
   │                                    │
   └── 省去 CPU 中转，延迟降低 30-50% ──┘</code></pre>
<p><strong>为什么重要：</strong></p>
<ol>
<li><strong>降低延迟</strong>：省去 CPU 内存中转，跨节点通信延迟降低 30-50%</li>
<li><strong>降低 CPU 开销</strong>：CPU 不参与数据搬运，可处理其他任务</li>
<li><strong>提升有效带宽</strong>：减少 PCIe 往返，有效带宽提升 20-30%</li>
<li><strong>NCCL 自动利用</strong>：NCCL 检测到 GPUDirect RDMA 支持后自动启用</li>
</ol>
<div class="card-w">
<p><strong>前提条件：</strong></p>
<ul>
<li>网卡支持 RDMA（InfiniBand 或 RoCE）</li>
<li>GPU 支持 GPUDirect（A100+ 原生支持）</li>
<li>驱动和 NCCL 版本匹配</li>
</ul>
</div>
<p class="qa-summary">💡 GPUDirect RDMA 的本质是让 GPU 绕过 CPU 直接和网络对话——省两次 PCIe 往返和一次 CPU 拷贝，对跨节点 TP 和 PP 性能至关重要。</p>
</div>
</div>

<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q7: 设计一个 GPU 集群调度器，你会怎么设计？</div>
<div class="qa-a">
<pre><code>┌──────────────────────────────────────────────────────────────┐
│                     GPU 集群调度器                              │
├──────────────┬──────────────┬──────────────┬────────────────┤

<div class="card-m">
<p><strong>2. Gang + Backfill</strong>：</p>
<ul>
<li>Gang：保证训练 Job 的 All-or-Nothing 语义</li>
<li>Backfill：填充 Gang 等待期间的碎片资源，提升利用率</li>
</ul>
</div>
<div class="card-d">
<p><strong>3. 多维度资源模型</strong>：</p>
<ul>
<li>GPU 数量 + 显存 + NVLink 拓扑 + InfiniBand 带宽</li>
<li>不只是"GPU 数量"，还要考虑拓扑约束</li>
</ul>
</div>
<div class="card-w">
<p><strong>4. 弹性配额</strong>：</p>
<ul>
<li>ElasticQuota（min/max），空闲配额自动共享</li>
<li>QAD 驱动：保障各团队的 QAD &gt; 0.8</li>
</ul>
</div>
<div class="card-s">
<p><strong>5. 拓扑感知调度</strong>：</p>
<ul>
<li>TP 组 → 同节点 NVLink 全连接</li>
<li>PP 组 → 相邻节点（IB 直连）</li>
<li>DP 组 → 拓扑不敏感，跨机架即可</li>
</ul>
</div>
<div class="card-m">
<p><strong>6. 故障自恢复</strong>：</p>
<ul>

<li>异步分布式 Checkpoint，T* = √(2FC)</li>
</ul>
</div>
<p class="qa-summary">💡 GPU 调度器的设计核心是三个"感知"：感知 Gang 语义、感知 GPU 拓扑、感知多租户公平性。缺了任何一个，要么利用率低，要么性能差，要么团队吵。</p>
</div>

<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q8: GPU 调度和 CPU 调度有什么本质区别？</div>
<div class="qa-a">
<div class="table-scroll">
<table>
<thead><tr><th>维度</th><th>CPU 调度</th><th>GPU 调度</th></tr></thead>
<tbody>
<tr><td><strong>资源粒度</strong></td><td>CPU 核（毫核级别）</td><td>整卡 / MIG Instance（不可细分）</td></tr>
<tr><td><strong>调度语义</strong></td><td>每个 Task 独立</td><td>Gang Scheduling（All-or-Nothing）</td></tr>
<tr><td><strong>拓扑约束</strong></td><td>NUMA（影响较小）</td><td>NVLink/IB（影响 10 倍+）</td></tr>
<tr><td><strong>资源碎片</strong></td><td>毫核级，易填充</td><td>整卡级，碎片大</td></tr>
<tr><td><strong>抢占代价</strong></td><td>低（状态小，迁移快）</td><td>高（显存状态大，Checkpoint 慢）</td></tr>
<tr><td><strong>共享模式</strong></td><td>时间片天然支持</td><td>MIG/MPS 有限支持</td></tr>
<tr><td><strong>故障影响</strong></td><td>单 Task 失败</td><td>整个 Gang Job 失败</td></tr>
<tr><td><strong>监控维度</strong></td><td>CPU/内存</td><td>GPU 温度/ECC/显存/NVLink/功耗</td></tr>
</tbody>
</table>
</div>
<p><strong>本质区别：</strong></p>
<ol>
<li><strong>GPU 是刚性资源</strong>：不能像 CPU 那样切毫核，一张 GPU 要么给一个 Task 要么不给，碎片化严重</li>
<li><strong>GPU 有强拓扑约束</strong>：CPU 调度几乎不关心 NUMA，但 GPU 调度如果忽视 NVLink/IB，TP 性能可能差 10 倍</li>
<li><strong>GPU 任务是 Gang 的</strong>：CPU 的每个 Task 独立运行，GPU 训练 Job 的所有 Pod 必须同时运行</li>
<li><strong>GPU 抢占代价极高</strong>：CPU 抢占只需要保存寄存器，GPU 抢占需要保存几十 GB 的显存状态</li>
</ol>
<p class="qa-summary">💡 GPU 调度 vs CPU 调度的本质区别是四个字：刚、绑、合、重——资源刚性、拓扑绑定、Gang 聚合、抢占代价重。</p>
</div>
</div>

<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q9: 一个 7B 模型需要多少 GPU 资源？请详细计算</div>
<div class="qa-a">
<p><strong>模型参数</strong>：7B (7 × 10⁹)</p>
<p><strong>FP16 显存占用计算：</strong></p>
<div class="table-scroll">
<table>
<thead><tr><th>组件</th><th>计算公式</th><th>大小</th></tr></thead>
<tbody>
<tr><td>模型参数</td><td>7B × 2 bytes</td><td>14 GB</td></tr>
<tr><td>梯度</td><td>7B × 2 bytes</td><td>14 GB</td></tr>
<tr><td>Adam 优化器状态</td><td>7B × (4+4) bytes (momentum + variance, FP32)</td><td>56 GB</td></tr>
<tr><td>激活值 (batch=1, seq=2048)</td><td>约 2-4 GB</td><td>~3 GB</td></tr>
<tr><td><strong>总计</strong></td><td></td><td><strong>~87 GB</strong></td></tr>
</tbody>
</table>
</div>
<p><strong>不同策略下的单卡显存需求</strong>（假设 N 卡）：</p>
<div class="table-scroll">
<table>
<thead><tr><th>策略</th><th>单卡显存</th><th>最少 GPU 数</th><th>备注</th></tr></thead>
<tbody>
<tr><td>纯 DP</td><td>87 GB</td><td>2×A100-80G（放不下）</td><td>单卡 80GB 不够</td></tr>
<tr><td>ZeRO-1</td><td>14 + 56/N + 14 + 3 ≈ 31 + 56/N GB</td><td>2</td><td>N=2 时约 59 GB</td></tr>
<tr><td>ZeRO-2</td><td>14 + 56/N + 14/N + 3 ≈ 17 + 70/N GB</td><td>2</td><td>N=2 时约 52 GB</td></tr>
<tr><td>ZeRO-3</td><td>(14+56+14)/N + 3 ≈ 84/N + 3 GB</td><td>1</td><td>N=1 时 87 GB 放不下，N=2 时 45 GB</td></tr>
<tr><td>TP=2 + ZeRO-1</td><td>(14/2) + (56/2)/N + 3 ≈ 10 + 28/N GB</td><td>2</td><td>N=1 时 38 GB</td></tr>
</tbody>
</table>
</div>
<div class="card-d">
<p><strong>生产推荐：</strong></p>
<ul>
<li><strong>训练</strong>：2-4 × A100-80G + ZeRO-2，显存充裕，通信量低</li>
<li><strong>推理</strong>：1 × A100-80G，14 GB 参数 + KV Cache，单卡足够</li>
<li><strong>微调 (LoRA)</strong>：1 × A100-80G，只训练少量参数，显存绰绰有余</li>
</ul>
</div>
<p class="qa-summary">💡 7B 模型的显存瓶颈不在参数本身（14 GB），而在 Adam 优化器状态（56 GB）——所以 ZeRO-1/2 就能解决，不需要上 TP/PP。</p>

<div class="qa-q">Q10: 你提到了 DCGM，能详细说说 GPU 监控体系吗？</div>
<div class="qa-a">
<p><strong>DCGM 全称</strong>：Data Center GPU Management，是 NVIDIA 提供的 GPU 集群管理中间件。</p>
<p><strong>三层架构：</strong></p>
<pre><code>┌─────────────────────────────────────┐
│       Grafana (可视化 &amp; 告警)        │
└───────────────┬─────────────────────┘
                │ PromQL 查询
┌───────────────▼─────────────────────┐
│       Prometheus (指标存储 &amp; 告警)    │
└───────────────┬─────────────────────┘
                │ HTTP /metrics
┌───────────────▼─────────────────────┐
│    DCGM Exporter (指标暴露)           │
└───────────────┬─────────────────────┘
                │ NVML / DCGM API
┌───────────────▼─────────────────────┐
│    DCGM (底层 GPU 状态采集)           │
└───────────────┬─────────────────────┘
                │ GPU Driver
┌───────────────▼─────────────────────┐
│    NVIDIA GPU 硬件                    │
└─────────────────────────────────────┘</code></pre>
<p><strong>DCGM 的三种使用方式：</strong></p>
<ol>
<li><strong>dcgmi</strong>：命令行工具，用于诊断和排查（<code>dcgmi diag -r 3</code> 完整诊断）</li>
<li><strong>DCGM Exporter</strong>：Prometheus 集成，持续监控（生产环境必备）</li>
<li><strong>DCGM API</strong>：编程接口，用于自定义监控和自动化</li>
</ol>
<p><strong>关键指标分组：</strong></p>
<div class="table-scroll">
<table>
<thead><tr><th>分组</th><th>指标</th><th>用途</th></tr></thead>
<tbody>
<tr><td>健康</td><td>ECC 错误计数、PCIe 降速、NVLink 错误</td><td>故障预警</td></tr>
<tr><td>性能</td><td>GPU 利用率、显存使用率、功耗</td><td>训练效率</td></tr>
<tr><td>环境</td><td>温度、风扇转速、电源电压</td><td>散热和供电</td></tr>
<tr><td>拓扑</td><td>NVLink 带宽、PCIe 带宽</td><td>拓扑质量</td></tr>
</tbody>
</table>
</div>
<div class="card-w">
<p><strong>生产实践：</strong></p>
<ul>
<li>每 15 秒采集一次指标（Prometheus scrape_interval）</li>
<li>ECC 不可纠正错误 → 自动驱逐 Pod</li>
<li>温度 &gt; 85°C → 告警 + 降低频率</li>
<li>GPU 利用率持续 &lt; 10% → 可能卡死，需要检查</li>
</ul>
</div>
<p class="qa-summary">💡 DCGM 是 GPU 监控的基石——它不是可选的，而是必须的。没有 DCGM 的 GPU 集群就像没有仪表盘的汽车，出了问题你连原因都不知道。</p>
