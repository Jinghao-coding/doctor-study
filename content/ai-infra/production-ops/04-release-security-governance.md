## 一句话结论

AI Infra 的生产发布不是把模型服务重启一下，而是让模型、镜像、配置、路由、权限和观测一起受控变更。面试回答要把灰度、回滚、安全边界和事故复盘讲成一条闭环。

## 发布链路

```flow
变更准备 | 模型版本、镜像 digest、serving config、资源预算、评测报告
准入检查 | 离线评测、回放、性能压测、安全扫描、容量评估
灰度发布 | 小流量、指定租户、影子流量或 canary endpoint
实时观测 | 错误率、TTFT、TPOT、P99、GPU 显存、KV cache、日志
自动回滚 | 指标越线、健康检查失败、资源异常或人工确认
复盘沉淀 | 根因、时间线、检测缺口、修复项、预防项
```

## 发布策略

| 策略 | 适合场景 | 风险点 |
|---|---|---|
| Rolling Update | 无状态 API、普通控制面服务 | 版本混跑期间要兼容旧配置 |
| Blue-Green | 回滚要求高、切流明确 | 成本更高，需要双份容量 |
| Canary | 大模型推理服务、调度器策略、Operator 变更 | 指标窗口太短会误判，太长会扩大影响 |
| Shadow Traffic | 新模型或新推理引擎验证 | 影子流量不能影响线上，且要处理隐私数据 |
| Feature Flag | 调度策略、限流、缓存策略 | flag 爆炸会增加排障复杂度 |

## 安全边界

<div class="card card-s">
<h3>权限隔离</h3>
<p>训练和推理平台应按租户、namespace、service account、RBAC、quota 和资源池隔离。用户不能直接拿集群级权限，平台控制器也应最小权限运行。</p>
</div>

<div class="card card-m">
<h3>Secret 与数据权限</h3>
<p>模型下载 token、对象存储 key、数据库密码、私有数据集权限都不能写进镜像或普通 ConfigMap。Secret 要配合访问审计、轮转和最小可见范围。</p>
</div>

<div class="card card-w">
<h3>供应链安全</h3>
<p>镜像要记录 digest、构建来源、依赖版本和扫描结果；模型制品也要记录来源、license、评测和准入状态。不要让未审核镜像或未知来源权重直接进入生产 GPU 池。</p>
</div>

## 事故闭环

| 阶段 | 要回答的问题 | 证据 |
|---|---|---|
| 发现 | 谁发现、哪个 SLO 越线、影响范围多大 | 告警、dashboard、用户反馈 |
| 定位 | 是模型、引擎、GPU、网络、存储、调度还是控制面 | metrics、logs、trace、events、profile |
| 止血 | 限流、回滚、摘节点、切路由、扩容还是禁用策略 | 发布记录、路由记录、变更单 |
| 修复 | 根因修掉了吗，是否有回归测试 | MR、测试、压测、回放 |
| 预防 | 哪个检测缺口导致没有提前发现 | 新告警、准入规则、演练、runbook |

## 常见误区

| 误区 | 正确说法 |
|---|---|
| 模型发布只要 A/B 看效果 | 还要看性能、容量、安全、回滚和观测 |
| 回滚就是切回旧权重 | 需要一起回滚镜像、tokenizer、config、engine 参数和路由 |
| 训练平台不用考虑安全 | 数据集、checkpoint、日志和 shell 权限都可能泄露敏感信息 |
| 调度器改动可以直接全量 | 调度策略影响全局资源，应先影子评估、小流量或按队列灰度 |
| 事故复盘只是写文档 | 复盘要产生检测、准入、自动化和架构改进项 |

## 关联模块

- `Kubernetes 核心`：RBAC、Admission、Secret、Deployment 和 Operator 发布机制。
- `LLM 推理系统`：推理服务灰度、路由和 SLO 指标。
- `GPU 集群管理`：资源池隔离、配额、节点健康和故障域。
- `AI Agent`：工具权限、数据访问边界和审计也属于生产治理。
