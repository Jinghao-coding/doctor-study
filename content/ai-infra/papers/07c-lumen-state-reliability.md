## 上层账本与 Merlin 执行状态

平台统一管理任务入口、团队配额和公共池，通过 **Merlin OpenAPI** 提交、查询和停止任务。MySQL 持久化任务与配额状态，Redis 缓存高频调度数据；状态变化后持续核对记录与实际占用。对外以用户确认的 OpenAPI 描述接入边界，不据此推定具体传输协议或底层 Kubernetes 实现。

下面的字段、原子提交和恢复路径是可靠性设计，用于解释机制；不是对历史数据库和代码的逐项还原。

## 配额与公共池怎样记账

<div class="table-scroll">

| 状态 | 核算用途 |
|---|---|
| 团队配额 | 判断配额内任务的使用资格 |
| 配额内占用与未完成承诺 | 防止运行中和待启动任务重复使用权益 |
| 公共池 Spot 占用与承诺 | 计算还能批准多少 Spot 使用 |
| 回收计划 | 关联目标需求、受害任务、预期释放量和执行状态 |
| 外部任务标识 | 对照 Merlin 中的实际任务，核查不确定结果 |

</div>

公共池统一管理 Spot 使用，不要求维护团队之间一对一的借入/借出关系。已提交到 Merlin 但尚未运行的任务也属于承诺占用，不能只统计 Running。

目标任务的额度承诺和尚未释放的 Spot 实际占用需要分别表达。回收期间两者可以同时存在：前者禁止新的竞争申请，后者反映设备仍被占用。只有确认 Spot 退出，才允许把释放容量用于目标任务，不能将“额度预留”误算成一份已经可用的设备。

## 并发准入如何避免重复分配

两个任务同时读到剩余四卡，不能各自获批四卡。可用短数据库事务结合行锁，或带版本的条件更新，将“检查可用额度”和“登记资源承诺”放在同一个并发控制范围内。

```flow
校验 | 读取本资源域的配额、占用、承诺与回收状态
登记意图 | 原子记录目标任务的额度承诺和待执行操作
请求执行 | 事务提交后调用 Merlin OpenAPI
确认结果 | 成功则关联外部任务，结果未知则进入核查
释放承诺 | 仅在确认失败、取消或完成后按状态处理
```

MySQL 事务不能把外部 API 调用一起原子提交。调用前需要保留可恢复的操作意图，调用后依据查询结果推进；Redis 中的缓存读不能代替最终分配时的并发校验。

## 停止与资源释放的状态链

以下为概念状态名：

```text
Running → StopRequested → Stopping → Released
```

<div class="table-scroll">

| 观察到的状态 | 平台动作 |
|---|---|
| 请求已发出或接口接受 | 保留实际占用，继续查询 |
| 任务仍在停止 | 保留回收计划，不重复选择同一受害者 |
| 已确认任务退出及占用释放 | 幂等扣减 Spot 占用，推进目标任务 |
| 请求失败且任务仍运行 | 保留占用，按规则重试或补选对象 |
| 目标任务取消 | 撤销目标额度承诺，核对已停止/尚在运行的 Spot |

</div>

平台能够中断 Spot，用户任务负责 checkpoint 保存。资源释放确认与训练进度保存是两个不同条件；没有相应接口时，平台不能把停止成功当成 checkpoint 已保存。

Merlin 若将任务退出与资源释放分别暴露，应等待接口定义的可用状态；不能仅凭本地停止标记推断设备已经空闲。

## API 超时、重复事件与重启

<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q: Merlin 提交接口超时，能不能直接再提交一次？</div>
<div class="qa-a"><p>超时只说明没有收到确定结果，任务可能已经创建。我们先保留额度承诺，利用外部任务标识、查询能力或接口支持的幂等键核查。如果确认已经创建，就补齐本地关联；确认未创建后才重试。如果接口无法消除歧义，就保持待核查状态，不能盲目重新创建任务。</p></div>
</div>

<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q: 回收接口超时怎么办？</div>
<div class="qa-a"><p>我会先查目标 Spot 是否还在运行。已经退出就同步释放结果，仍在退出就继续等待，确认未执行才按接口语义重试。同一任务的释放只能记账一次，不能因为重复响应多次增加公共池可用量。</p></div>
</div>

事件处理应按任务标识和可用的版本信息去重；迟到的 Running 事件不能将终态任务重新记为占用。服务重启后，扫描未完成的提交与回收计划，查询 Merlin 并恢复状态。不能把 API 的幂等性当成上层账本天然一致。

## 如何判断公共池是否有效

<div class="table-scroll">

| 目标 | 需要观察的证据 |
|---|---|
| 提高 Lumen 内部使用效益 | 内部公共池使用量、Spot 有效完成量、空闲资源被外层回收的情况 |
| 满足团队配额内需求 | 等待时间、资源兑现情况、回收耗时 |
| 控制中断损失 | Spot 中断次数、重算与恢复开销（可测时） |
| 保持状态正确 | 账本与 Merlin 不一致数量、重复提交、核对恢复耗时 |

</div>

这些是效果评估方法，尚无已核实的提升百分比。GPU 占用率反映分配情况，SM Active 反映计算活动，最终仍要结合任务完成量和等待情况解释效益。

<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q: 这段实习最大的工程难点是什么？</div>
<div class="qa-a">
<p>主要难点是资源账本和 Merlin 执行异步变化，一次接口调用不能同时保证两边状态一致。MySQL 保存任务、配额和未完成操作，Redis 加速高频读取，关键是把资源承诺、实际占用和释放分别管理。</p>
<p>第一是并发准入。多个任务可能同时读到同一份剩余额度，因此检查额度和记录预留需要原子完成。获批但尚未运行的任务也要计入承诺，最终分配时仍需并发校验，不能直接相信缓存读到的可用量。</p>
<p>第二是操作请求与执行结果分开。调用前先持久化任务和额度承诺，再提交给 Merlin。提交超时可能已经创建成功，要先查询核实，不能立即重提或释放额度。停止请求被接受，也不代表资源已释放，必须跟踪到接口确认的释放状态后再推进等待任务。</p>
<p>第三是核对和恢复。持续检查未完成的提交与回收操作，重复结果只能引起一次有效状态迁移和记账。服务重启后根据持久记录查询 Merlin，继续处理未完成操作；这样才能避免重复创建任务、重复归还额度以及占用长期残留。</p>
</div>
