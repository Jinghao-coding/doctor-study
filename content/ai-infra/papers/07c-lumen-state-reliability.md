## 执行链路与职责

| 组件 | 简历记载的职责 |
|---|---|
| **MySQL** | 持久化任务与配额状态 |
| **Redis** | 缓存调度需要的高频数据 |
| **Thrift** | 连接调度层与 Merlin 执行层 |
| **Merlin** | 执行训练任务，提供状态同步与回收对接 |

**实现口径**：事件更新、资源核对属于简历记载的工作。下述原子预留、操作标识、事务与恢复流程是可靠性设计方案，尚未由原代码证实。

```flow
校验并预留 | 同一并发控制范围内检查额度、登记资源预留
请求执行 | 持久化操作意图后调用 Merlin
确认结果 | 根据执行结果推进状态，超时保留待核查状态
回收资源 | 仍按占用核算，确认释放后才允许重新分配
核对状态 | 比较账本与执行层，处理遗漏、重复与乱序
```

## 两个调度请求同时看到还有四张卡，怎么办？

**配额检查与资源预留必须是一个受并发保护的操作。**

### 错误路径

1. 请求甲读到剩余 4 张。
2. 请求乙也读到剩余 4 张。
3. 两者各分配 4 张，产生**重复分配**。

### 设计方案

1. **检查额度**：同时考虑运行中的占用和已预留资源。
2. **原子预留**：可用数据库事务配合行锁，或条件更新与版本校验。
3. **提交后执行**：登记预留与操作意图，再请求执行层启动。
4. **按结果收敛**：确认失败才能撤销；状态不确定时先核查。

口述：“Redis 可以加速读，但缓存中的剩余额度不能直接作为最终分配依据。如果现在实现，我会把校验和预留放进同一并发控制范围。”

## 配额账本需要记哪些量？

- **配置配额**：团队的资源额度。
- **保障占用与保障预留**：已运行和已承诺、尚未完成启动的资源。
- **借入与借出占用**：跨团队使用关系。
- **待回收量**：已请求回收但尚未确认释放的资源。

借用空间应从配额中扣除保障占用、保障预留和已借出量，再结合等待需求与物理可分配资源约束判断。**按资源池和卡型核算，不能把异构卡简单相加。**

这些是账本设计含义，不是对历史数据库字段的还原。

## 发出终止请求，就能把 GPU 分给新任务了吗？

**不能。请求回收和确认释放是两个时刻。**

概念状态链（名称为设计示意）：

```text
Running → ReclaimRequested → Releasing → Released
```

- **请求已发出**：任务可能仍在运行，资源继续按占用核算。
- **释放已确认**：更新账本，资源才可再次分配。
- **checkpoint 与恢复**：能力未确认，不能默认无损抢占。

口述：“调度层通过 Thrift 请求 Merlin 执行，再同步任务状态并核对实际占用。正确性上必须确认释放，不能发完请求就把卡分给新任务。”

## 抢占 RPC 超时怎么办？

**超时表示结果未知，不等于执行失败。**

| 可能情况 | 处理原则 |
|---|---|
| 请求未到执行层 | 核查后重试 |
| 已执行，但响应丢失 | 查询状态，避免重复执行或重复释放 |
| 执行仍在进行 | 保留待回收占用，等待或核查 |

### 可选恢复机制

1. 持久化**操作标识**，使一次回收可追踪。
2. 查询目标任务当前状态。
3. 按**幂等语义**重试同一操作。
4. 同一释放结果只扣减一次占用。

## MySQL、Redis 和 Merlin 状态不一致怎么办？

**缓存用于加速，执行结果仍需要核对。**

简历记载的做法：根据状态变更事件更新记录，持续核对配额、分配记录和实际占用，检测异常。

### 重建的可靠方案

- **短事务记录意图**：保存预留及待执行操作，提交后调用 Merlin。
- **崩溃后继续处理**：扫描未完成操作，而不是把已提交意图遗忘。
- **事件去重**：按操作标识或版本判断是否已处理。
- **乱序保护**：晚到的 `Running` 事件不能把已完成任务恢复成运行。
- **执行状态核对**：执行成功但本地未记账时，通过状态核对恢复。

**关键限制**：普通 MySQL 事务不能把外部 RPC 一起原子提交。最终权威状态、多实例协调及具体重试机制仍需按实际系统确认。

## 怎样验证策略和实现是否有效？

| 目标 | 建议观察的指标 |
|---|---|
| **资源效率** | 可借用闲置资源、队列等待时间 |
| **团队保障** | 保障请求满足情况、回收耗时 |
| **中断成本** | 抢占次数、重算损失 |
| **状态正确性** | 账本与执行层不一致数量、恢复耗时 |

这些是**建议验证项**，不是已记录的上线数据。
