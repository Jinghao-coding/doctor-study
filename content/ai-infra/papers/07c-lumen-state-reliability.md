## 调度状态与执行状态

MySQL 持久化任务与配额，Redis 缓存高频调度数据，Merlin 执行训练任务，Thrift 连接调度与执行。事件更新与资源核对属于简历记载的工作；以下事务、预留字段、幂等标识及恢复流程是重建的可靠实现方案，尚未由原代码证实。

```flow
校验与预留 | 在同一并发控制范围内检查额度并登记占用意图
请求执行 | 提交本地事务后调用 Merlin，保留可追踪的操作标识
确认结果 | 根据执行结果推进任务状态，超时保持待核查
资源回收 | 发出回收请求后仍计为占用，确认释放才可重新分配
状态核对 | 比较持久化记录与执行层状态，修复遗漏、重复与乱序影响
```

## 配额账本与原子预留

一个合理设计是分别记录配置配额、运行中的保障占用、保障预留、借入占用、借出占用与待回收量。字段不一定这样命名，但对应含义不能混淆。按资源池和卡型分别核算，不能把不同卡直接按数量互换。

简化的借用上限是“配置配额减去保障占用和保障预留”的非负部分，再扣掉已经借出的量，并结合等待中的保障需求和实际可分配资源裁剪。这里的数量只是配额账本约束，不能代替物理可放置性检查。

例如两次调度同时看到还剩 4 张卡，各自准备分配 4 张，如果只读取缓存而没有原子预留，就可能重复分配。可靠设计要让校验和预留在同一并发控制范围内完成。若采用 MySQL，可以在事务中锁住相关配额账本行，或使用条件更新/版本检查；具体方案是建议，不能声称当年实际用了某一种。

## 回收确认与超时

可靠的概念状态链：Running → ReclaimRequested → Releasing → Released；名称为设计示意。发出回收 RPC 后，资源仍按占用计算，直到执行层确认释放。是否保存 checkpoint、是否可恢复，简历未说明，不预设“无损抢占”。

若 RPC 超时，可能请求失败，也可能对方执行成功但响应丢失，因此不能直接重发一个全新的操作并释放账本。可选设计是持久化操作标识，查询目标任务当前状态，再按幂等语义重试。同一释放操作只扣减一次占用。

## 执行意图与状态核对

一种可靠设计：短事务记录预留和待执行意图，提交后调用 Merlin，收到响应或事件再推进状态。不能指望 MySQL 事务把外部训练平台也原子提交。若提交意图后进程崩溃，需要能扫描未完成意图继续执行；若执行成功但本地未记账，则靠事件或执行状态核对恢复。

Redis 用于提高读取速度，正确性不能仅依赖可能过期的缓存。状态事件应有去重及乱序保护，例如操作标识、版本或合法状态迁移校验；晚到的 Running 事件不能把已经完成的任务恢复成运行。具体权威数据源及多调度实例协调方式仍需按真实系统确认。

## 效果验证

适合检查的指标：空闲可借用资源、队列等待时间、资源回收耗时、保障请求满足情况、抢占次数与重算损失、账本与执行层不一致数量。它们是建议验证项，不是已记录的上线数据。没有可靠实测结果时，说明机制完成情况，不承诺提升幅度。
