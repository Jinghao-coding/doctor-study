<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 请介绍一下 DeepShare，包括为什么做、怎么共享，以及怎么抢占。</div>
<div class="qa-a">
<p>DeepShare 这项工作的背景，是<strong>高校里多个课题组共同使用 GPU 集群开展科研实验。我们发现，大家提交的单卡训练任务比较多，但很多任务独占一张 GPU 后，又无法充分利用整张卡的计算和显存资源。</strong> 与此同时，其他同学的任务还在排队。所以，我们希望解决的问题是：怎样把这些未充分利用的资源开放给更多任务，同时满足各个课题组的资源保障需求。</p>
<p><strong>先说一下这个问题为什么会出现。</strong></p>
<p>高校中的训练任务有很强的实验性质。大家会反复调整模型、参数和数据配置，提交大量单卡实验。这些任务的资源需求各不相同，其中不少任务虽然需要 GPU 加速，但用不满整张卡。如果平台按整卡分配、让每个任务独占 GPU，那么一张卡只要被分配出去，其他任务就无法继续利用它剩余的能力。</p>
<p>同时，集群通常由多个课题组共享。为了让各个团队有相对稳定的资源预期，平台会设置团队配额。但配额相对固定，科研任务的需求却具有明显的突发性：一个团队可能在某个阶段集中做实验，另一个团队同期暂时没有那么多任务。</p>
<p>因此，资源利用不足出现在两个层面：<strong>团队之间，暂时不用的资源没有充分流动；单张 GPU 内部，已经运行的任务又没有用满设备。</strong> 两者叠加，就会出现集群实际利用率不高，但仍然有不少实验排队的情况。</p>
<p>我们在一个包含 58 个节点、219 张 GPU 的高校集群上做了一周观测。平均 GPU 计算利用率大约是 19.8%，显存利用率大约是 18.5%。另一方面，短任务占提交数量的 62%，其中位运行时间不到 30 分钟，中位排队时间却达到 47 分钟。对科研用户来说，一次本来很快就能完成的实验，要花更多时间等待资源，拖慢整个实验迭代过程。</p>
<p><strong>这些现象给了我们几个直接的优化方向：让团队之间能够借用空闲资源，让合适的单卡任务共享 GPU，同时改善长短任务混合排队时的执行顺序。</strong></p>
<p>但真正设计系统时，我们发现，这几个决策会相互影响。</p>
<p>首先，空闲资源借出去以后，原来的团队随时可能提交新的保障任务。如果借用资源被长任务占住，就需要考虑如何回收，以及打断哪个任务更合适。</p>
<p>其次，单个任务用不满 GPU，只能说明存在共享机会。两个任务放在一起以后，仍然可能争用计算资源或显存带宽。如果共享明显拖慢了原来的任务，虽然卡上运行的任务更多了，用户完成实验的时间却不一定缩短。</p>
<p>任务排序也有类似的取舍。短任务优先能够加快实验周转，但如果只按运行时间排序，一个已经缺少保障资源的团队，其长任务可能不断被后来的短任务推迟。</p>
<p>因此，调度器需要同时知道两件事：<strong>当前有哪些提高效率的机会，以及哪些团队应当得到的保障资源还没有兑现。</strong> 这就是 DeepShare 的核心出发点：用持续更新的租户保障状态，协调任务排序、GPU 共享和资源回收。</p>
<p><strong>具体来说，我们先把保障资源和机会型使用区分开。</strong></p>
<p>系统把任务分成 Guaranteed 和 Best-effort 两类。Guaranteed 是配额支持的保障型任务，优先获得配额范围内的资源；Best-effort 是机会型任务，可以使用剩余容量，但在保障需求增加时允许被回收。</p>
<p>这里，配额代表团队拥有的资源权益，不需要永久对应某几张物理 GPU。团队暂时用不满时，其他机会型任务可以利用剩余资源；保障需求增加以后，调度器再优先安排保障任务，必要时回收机会型任务占用的资源。</p>
<p>但只有任务类别还不够。当多个团队都在等待保障资源时，我们还需要判断谁的保障满足程度更低。因此，我们定义了 <strong>QAD，也就是配额保障满足度</strong>。</p>
<p>它的计算方式是：已经分配给租户保障任务的 GPU 数量，除以配额和当前保障需求中的较小值。</p>
<p>例如，一个团队的配额是 8 张卡，当前只需要 4 张，也已经拿到了 4 张，那么它的保障已经满足，QAD 就是 1。如果它需要 8 张，却只拿到 4 张，QAD 就是 0.5。如果它提交了 16 张卡的保障需求，分母仍然最多按配额 8 张计算，超额提交不会扩大它的保障权利。</p>
<p>这个定义能够区分“暂时不需要资源”和“需要资源但没有拿到”。我们还对它做时间平滑，减少短暂需求变化造成的调度波动，同时保留持续保障不足的信号。</p>
<p><strong>接下来，可以沿着一个任务进入系统后的过程，说明这些机制怎么配合。</strong></p>
<p>任务提交以后，先进入租户级队列，检查是否满足准入条件。保障任务受到保障配额约束，机会型任务受到借用上限约束。每轮准入都会累计已经放行的资源量，避免多个任务重复使用同一份剩余额度。通过准入后，再进入集群级候选队列，参与实际放置。</p>
<p>调度器优先处理保障任务。在同一类别内部，先按照平滑后的 QAD 从低到高排序，让保障满足度更低的团队优先获得调度机会；QAD 相同时，再按照预测剩余运行时间排序，优先处理较短任务。</p>
<p>运行时间预测利用的是租户历史作业中的规律。科研用户经常反复提交相似实验，这给预测提供了基础；新租户缺少历史数据时，则使用集群级模型兜底。<strong>QAD 决定保障恢复的优先顺序，运行时间预测在这个顺序之内进一步改善任务周转效率。</strong></p>
<p>选出任务以后，调度器先寻找满足要求的空闲 GPU。能够独占放置，就直接安排；没有合适的空闲位置，再考虑和已有任务共享。</p>
<p><strong>共享这一步，正好对应前面提到的“单卡任务用不满 GPU”的问题。</strong></p>
<p>我们需要判断哪些任务适合放在一起，而判断依据除了显存能不能容纳，还包括共享后的性能变化。</p>
<p>为此，我们通过独占和共置 profiling，采集 GPU 硬件特征，训练干扰预测模型，预测两个任务共置以后，各自能够保留多少吞吐。比如，吞吐保持率为 0.9，表示共享后的吞吐预计能够达到独占时的 90%。</p>
<p>共享准入要求双方同时满足条件：GPU 显存和节点 CPU、内存要足够，两个任务的预测吞吐保持率也都要达到门槛。默认一张卡最多共置两个任务，而且至少一方是 Best-effort，这样在需要恢复保障时，能够退出机会型伙伴。</p>
<p>这个性能门槛会结合双方租户的 QAD 和集群压力调整。如果某一方的保障还没有满足，或者集群竞争压力上升，系统就提高保持率要求，更保守地接纳新的共享组合。原因是，在保障恢复已经比较困难的时候，继续引入明显的共享干扰，会进一步拖慢正在运行的任务。</p>
<p>共置以后，系统还会根据节点采集的 GPU 指标，持续估计性能保持情况。如果连续多个窗口低于门槛，就退出机会型伙伴，保护保障任务。<strong>这样，预测用于运行前的筛选，运行反馈用于纠正实际不合适的共享决定。</strong></p>
<p><strong>如果独占和共享都无法安排保障任务，就进入资源回收。</strong></p>
<p>回收时，系统先尝试较低扰动的调整。例如，如果放置受限于节点 CPU 或内存，就尝试缩减机会型任务可回收的 CPU、内存资源，然后重新检查能否放置。如果仍然没有可行位置，再选择 GPU 上需要抢占的机会型任务。</p>
<p>选择抢占对象时，我们先检查清退后能否满足新任务的资源要求，再比较候选的代价。这个代价主要考虑任务的预测剩余运行时间、累计抢占开销，以及释放目标 GPU 需要同时中断多少个任务。</p>
<p>快完成的任务会尽量保护，因为让它自然结束，可以避免临近完成时再次被打断。累计抢占开销较高的任务，也会受到更多保护，减少反复牺牲同一个任务的情况。</p>
<p>在共享场景下，还要按完整的任务集合计算代价。例如，一张卡上运行着两个机会型任务，而新任务需要整张 GPU，那么只停止其中一个，并不能腾出完整的设备。因此，要把清退这两个任务的代价一起计算，再与其他可回收 GPU 比较。</p>
<p>选定对象以后，系统先预留目标设备，再清退对应 Pod，等资源实际释放后安排新的保障任务。被打断任务后续能够恢复多少训练进度，取决于它自身的 checkpoint 支持。</p>
<p>这里，QAD 和抢占代价分别承担不同职责：<strong>QAD 决定哪个租户的保障任务先获得调度机会；这个任务放不下时，抢占代价决定为它回收哪些机会型任务。</strong> 资源分配成功后，租户的保障满足度更新，再进入下一轮排序和共享决策。</p>
<p><strong>工程上，我们把这套机制接入了 Kubernetes 的调度流程。</strong></p>
<p>系统主要分成配额控制器、调度插件和节点侧组件。配额控制器整理租户配额与任务类别；调度插件维护租户和设备状态，完成队列排序、共享准入、资源预留和抢占选择；节点侧通过 MPS 支持同卡并发执行，并采集 GPU 运行指标。</p>
<p>在放置过程中，调度插件先检查资源和共享条件，再比较可行位置，最终预留设备与额度，避免后续任务重复占用。涉及回收时，则等待资源实际释放后再推进放置。这样，上层的保障策略能够通过调度和节点执行真正落实到资源状态上。</p>
<p><strong>最后，我们从资源效率和用户体验两个方面评估效果。</strong></p>
<p>轨迹实验中，平均 GPU 利用率达到约 70.6%，相对 Lucid 提升 29.5%，平均排队时间降低 46%。在 16 张 A100 的 Kubernetes 实测中，相比 Hard+Colocate，平均作业完成时间降低 34%，保障租户的 QoS 合规率达到 93%。</p>
<p>我们同时关注利用率、排队时间、作业完成时间和保障情况，因为在高校科研场景下，最终希望改善的是实验周转效率：让更多实验及时启动，让任务更早完成，同时让各个团队的保障需求得到满足。</p>
<p><strong>DeepShare 的主要贡献，就是围绕租户的保障满足状态，把跨团队资源借用、任务排序、单卡任务共置和资源回收连接起来，让集群在利用剩余能力时，也能持续响应团队保障需求的变化。</strong></p>

<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 如果只展开抢占，怎么用一分钟讲清楚？</div>
<div class="qa-a">
<p>我们的抢占有两个主要入口：一个是保障任务来了，正常放置和安全共享都安排不下，需要回收 Best-effort 占用的资源；另一个是共享后实际干扰持续超标，需要停止同卡上借用资源的 Best-effort 训练任务。</p>
<p>进入回收以后，先找能够满足新任务需求的候选资源，再比较候选任务的剩余运行时间、历史抢占代价，以及需要同时打断多少任务。快结束的任务和已经多次被抢占的任务，会尽量保护。如果需要完整 GPU，就必须把该卡上需要退出的 Best-effort 任务一起考虑，不能只停一个就算释放了一张卡。</p>
<p>执行上是通过 Kubernetes 删除选中的 Pod，由节点终止训练进程。删除请求返回成功不等于 GPU 已经空出来，要等实际退出和资源释放，再给新任务分配。训练进度的恢复依赖任务自身的 checkpoint，Pod 删除不会自动保存进度。</p>
</div>
</div>

<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 删除 Pod 后，任务怎么恢复？MPS 会帮忙保存状态吗？</div>
<div class="qa-a">
<p>MPS 负责多个 GPU 进程并发执行，不负责保存训练进度。删除 Pod 会终止其中的进程，内存和显存里的状态不能因此自动保留。</p>
<p>后续重建或重新提交任务，需要由作业控制器或提交系统负责；恢复训练还需要训练程序支持 checkpoint，保存模型、优化器和训练步数等状态，并在启动时加载。没有这些支持，就可能需要重新训练。因此，介绍 DeepShare 时可以明确说它完成了代价感知的抢占决策和 Pod 层面的执行，不能把它描述成任意训练任务的透明暂停和原地继续。</p>
</div>
</div>

<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 抢占代价函数怎么推导？每一项为什么这样写？</div>
<div class="qa-a">
<p>论文使用下面的集合代价，分数越小越优先选择：</p>
<div class="formula">$$\Phi(J)=\sum_{j\in J}\frac{1+\alpha C_p(j)}{\hat T(j)}+\frac{\beta(|J|-1)}{\bar T(J)}$$</div>
<p>这里，J 是要回收的一张 GPU 上的全部驻留任务，|J| 是任务数量；T̂(j) 是任务 j 的预测剩余时间，T̄(J) 是这些任务的平均剩余时间；C_p(j) 是归一化后的累计抢占开销。默认 α=0.5、β=0.3，分别控制历史打断和多任务打断的惩罚强度。</p>
<p><strong>第一步，保护快完成的任务。</strong>先写 1/T̂(j)。其他条件一样，任务越接近完成，倒数越大，抢占它就越不划算。这是一个调度偏好，不是说剩余时间长的任务一定丢失进度更少。</p>
<p><strong>第二步，减少重复抢占。</strong>把分子改成 1+αC_p(j)。没有历史开销时也保留基础代价 1；累计开销增加以后，这个任务的分数会升高，下次就更不容易再次成为抢占对象。累计开销不等同于简单的抢占次数。</p>
<p><strong>第三步，计算整张卡的代价。</strong>对卡上的任务求和。回收共享 GPU 时，停止一个任务并不代表整张卡释放，所以必须评价完整集合。</p>
<p><strong>第四步，进一步惩罚一次打断多个任务。</strong>加入 β(|J|−1)/T̄(J)。只停一个任务时，这项为零；停多个任务时，这项增加；如果它们平均都快结束了，这项还会更大。前面的求和已经累计每个任务的代价，这一项额外表达了对多任务同时中断的惩罚。</p>
<p><strong>最后，先检查可行性，再最小化代价。</strong>设 V(d) 是 GPU d 的全部驻留任务，候选集 D_j^P 只包含这些任务全部为 Best-effort、且清退后能满足新任务显存和节点 CPU/内存约束的 GPU：</p>
<div class="formula">$$d^*=argmin_{dinmathcal D_j^P}PhiV(d),qquad J^*=V(d^*)$$</div>
<p>例如统一用分钟、历史开销均为零：GPU A 上一个任务还剩 10 分钟，代价是 0.1；GPU B 上一个任务还剩 100 分钟，代价是 0.01；GPU C 上两个任务都还剩 100 分钟，代价是 (0.01+0.01+0.3/100=0.023)。如果三张卡释放后都满足需求，就选 B。</p>
<p>这个函数是根据上述目标构造的启发式排序代价，不是“会损失多少秒”的精确模型，也不提供全局最优完成时间的证明。论文将 C_p 定义为归一化累计抢占开销，未在该处进一步规定它的归一化计算式。执行时先预留选定设备，再发起 Pod 删除，释放后绑定；没有可行候选就继续排队。</p>
</div>
</div>

<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: MPS 已经能共享 GPU，为什么还需要你们这个系统？</div>
<div class="qa-a"><p>MPS 解决的是多个进程能在一张 GPU 上并发执行，但它不知道谁有配额保障，也不会替我们决定哪些任务适合一起跑。我们的工作是在它上面做调度：判断是否允许共享、安排哪个任务先运行、保障任务来了回收谁，以及共享干扰超标后停止哪个借用任务。MPS 提供执行能力，DeepShare 根据租户需求和运行表现作决定。</p></div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 一次任务提交后，哪些组件实际参与了执行？</div>
<div class="qa-a"><p>首先读取任务所属租户、申请资源和作业类别，结合 TenantQuota 配置判断它进入保障队列还是借用队列。调度插件根据正在运行的 Pod 更新 QAD，决定谁先被安排，然后检查候选 GPU 的资源和共享干扰。找到位置后先预留资源，再完成绑定，由节点启动容器。如果保障任务没有可行位置，就进入 PostFilter 选择抢占对象；删除选中的 Pod、等待资源释放后，再完成放置。Controller 管配置，调度插件作决定，kubelet 和节点上的运行环境负责实际执行。</p></div>
