<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 请介绍一下 DeepShare，包括为什么做、怎么共享，以及怎么抢占。</div>
<div class="qa-a">
<p>DeepShare 这项工作，最开始来自我们实验室使用 GPU 的一个实际问题。</p>
<p>实验室里做深度学习的人很多，大家都需要 GPU 跑训练。最直接的方式，就是一个任务占一张卡。但有些任务虽然一直占着卡，实际上并没有把整张卡用满。比如模型规模比较小，或者训练过程中还有数据准备和 CPU 处理，GPU 并不是一直在高效计算。结果就是，一边有人排队等卡，另一边已经分出去的卡还有剩余能力。</p>
<p>所以我们就想，能不能让多个训练任务共享同一张 GPU，把这些剩余能力利用起来？我们采用的是 NVIDIA MPS，也就是多进程服务，让多个训练进程能够在同一张 GPU 上并发执行。它提供了共享的执行能力，但具体让哪些任务一起跑、资源不够了让谁退出，仍然需要调度器决定。</p>
<p>真正做起来以后，我们发现，光把任务放到一起还不够，有两个问题必须解决。</p>
<p>第一个是干扰。两个任务单独跑的时候可能都用不满卡，但放在一起，不一定就能互补。比如两个任务都在大量访问显存，就可能争用带宽，导致原来的训练明显变慢。所以显存装得下，只是共享的基本条件，还要判断一起跑以后性能能不能接受。</p>
<p>第二个是资源保障。实验室里不同课题组、不同用户都有自己的资源需求。如果把暂时不用的资源借出去，原来的用户后来提交任务了，系统就得有办法把资源收回来。否则共享虽然提高了利用率，却可能让用户连自己配额内的任务都跑不起来。</p>
<p>因此，DeepShare 同时做两件事：让空闲资源能够被借用，让单卡剩余能力能够被共享；同时保证，当保障需求回来或者共享干扰过大时，系统有明确的回收办法。</p>
<p>我们先用一个指标来判断，哪个租户现在最需要补资源。这个指标叫 QAD，也就是配额保障度。计算方法是：已经分给保障任务的 GPU 数量，除以配额和当前保障需求中较小的那个。</p>
<p>举个例子，一个团队配额是 8 张卡，但现在只需要 4 张，系统也给了 4 张，那它的保障已经完全满足，QAD 就是 1。如果它需要 8 张，却只拿到 4 张，QAD 就是 0.5。这个值越低，说明当前欠它的资源越多，调度时就越应该优先补上。借用的额外资源单独记账，不拿来抵消这个保障缺口。</p>
<p>在此基础上，我们把作业分成 Guaranteed 和 Best-effort 两类。Guaranteed 是需要优先兑现的配额内需求；Best-effort 可以借用剩余资源，但资源紧张时需要让出来。调度顺序先考虑保障任务，再按租户的 QAD 排序，在同等保障程度下利用预测剩余运行时间，让短任务更早完成。</p>
<p>共享的时候，调度器会先检查资源是否够用，再判断干扰是否可接受。我们通过 DCGM 收集 GPU 的硬件指标，用 Random Forest 预测两个任务放在一起以后，各自还能保留多少吞吐。通过判断以后，才允许它们通过 MPS 在同一张卡上运行。开始共享后也继续观察实际表现，如果连续三个采样窗口低于动态容忍阈值，就移走 Best-effort 伙伴，恢复保障任务的性能。</p>
<p>抢占可以用一个具体过程来解释。比如 A 团队配额是 8 张卡，之前只用了 4 张，集群的剩余资源被其他团队的 Best-effort 任务利用起来了。现在 A 又来了一个需要 2 张卡的保障任务。</p>
<p>调度器不会一看到需求增加就直接杀任务，而是先尝试正常放置：有没有空闲 GPU，或者有没有满足干扰要求的共享位置。如果这些方式都安排不下，才进入抢占路径，找哪些 Best-effort 任务可以让出所需资源。</p>
<p>选谁的时候，我们会同时看能释放多少资源、任务预计还要运行多久，以及它之前被抢占的代价。比如其他条件一样，一个任务还有 1 分钟就结束，另一个还有 20 分钟，我们更倾向于让后者让出资源，尽量让快完成的任务先完成。已经反复被打断的任务，也会增加它的抢占代价，避免总是牺牲同一个任务。</p>
<p>还要注意，一张 GPU 上可能同时有两个 Best-effort 任务。如果新任务需要完整的一张卡，只停其中一个，另一个还占着卡，就没有真正回收成功。所以我们会把这张卡上需要一起退出的任务作为一组，计算整体代价，再选择能满足新任务资源需求的组合，同时检查 CPU 和内存等条件。</p>
<p>选好以后，执行层面做的是删除被选中的 Pod。调度器通过 Kubernetes API 发出删除请求，由所在节点的 kubelet 和容器运行时终止容器，训练进程退出后才会释放它占用的 GPU 资源。这里要区分“已经发出删除请求”和“资源真的释放了”：Pod 还在终止过程中时，不能马上把同一份资源算给新任务；要根据实际终止和资源状态，再完成新任务的调度和绑定。</p>
<p>所以这套抢占做的是作业层面的中断和重新安排。被中断的训练之后重新运行时，能保留多少进度取决于它自己的 checkpoint 支持；删除 Pod 本身不会自动保存训练状态。这也是我们在选任务时要考虑抢占代价的原因。</p>
<p>这里有两个不同的预测模块。一个是按租户历史训练的 Gradient Boosting，预测任务还要运行多久，用来辅助排队和选择抢占对象；另一个是刚才提到的 Random Forest，预测共享后的性能，用来决定哪些任务适合放在一起。前者解决运行顺序，后者解决共享位置。</p>
<p>工程上，我们把这些策略放到了 Kubernetes 的 Controller 和调度插件里。Controller 管理租户配额和作业类别，调度插件根据运行中的 Pod 更新保障状态，执行排序、共享准入、资源预留和抢占；节点侧提供 MPS 运行环境和 GPU 指标采集。</p>
<p>实验上，我们分别做了历史轨迹驱动的仿真和真实 GPU 集群实验。轨迹实验中，GPU 平均利用率达到约 70.6%，平均排队时间相对 Lucid 降低了 46%。真实集群中，相比 Hard+Colocate，平均作业完成时间降低了 34%，保障租户的 QoS 合规率达到 93%。</p>
<p>回到实验室最开始的问题，DeepShare 想做到的是：任务用不满卡的时候，让其他任务用上剩余能力；用户需要自己的保障资源时，能合理地收回来；共享真的拖慢任务时，也能及时调整。这样才能把 GPU 利用率提高，同时让用户愿意接受共享。</p>

<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 如果只展开抢占，怎么用一分钟讲清楚？</div>
<div class="qa-a">
<p>我们的抢占有两个主要入口：一个是保障任务来了，正常放置和安全共享都安排不下，需要回收 Best-effort 占用的资源；另一个是共享后实际干扰持续超标，需要移走 Best-effort 伙伴。</p>
<p>进入回收以后，先找能够满足新任务需求的候选资源，再比较候选任务的剩余运行时间、历史抢占代价，以及需要同时打断多少任务。快结束的任务和已经多次被抢占的任务，会尽量保护。如果需要完整 GPU，就必须把该卡上需要退出的 Best-effort 任务一起考虑，不能只停一个就算释放了一张卡。</p>
<p>执行上是通过 Kubernetes 删除选中的 Pod，由节点终止训练进程。删除请求返回成功不等于 GPU 已经空出来，要等实际退出和资源释放，再给新任务分配。训练进度的恢复依赖任务自身的 checkpoint，Pod 删除不会自动保存进度。</p>
</div>
</div>

<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 删除 Pod 后，任务怎么恢复？MPS 会帮忙保存状态吗？</div>
<div class="qa-a">
<p>MPS 负责多个 GPU 进程并发执行，不负责保存训练进度。删除 Pod 会终止其中的进程，内存和显存里的状态不能因此自动保留。</p>
<p>后续重建或重新提交任务，需要由作业控制器或提交系统负责；恢复训练还需要训练程序支持 checkpoint，保存模型、优化器和训练步数等状态，并在启动时加载。没有这些支持，就可能需要重新训练。因此，介绍 DeepShare 时可以明确说它完成了代价感知的抢占决策和 Pod 层面的执行，不能把它描述成任意训练任务的透明暂停和原地继续。</p>
</div>
