<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 请介绍一下 DeepShare，包括为什么做、怎么共享，以及怎么抢占。</div>
<div class="qa-a">
<p>DeepShare 的背景是<strong>实验室里多个课题组共享 GPU 集群</strong>。我们观察到，很多单卡训练实验用不满一张 GPU，但其他任务仍然在排队。一方面，各课题组的需求不同步，存在配额闲置；另一方面，已经分配出去的 GPU 内部也可能还有空闲能力，这些都会影响实验迭代效率。</p>
<p>我们的思路是允许团队使用空闲配额，并让合适的任务共享 GPU。这里的关键问题是：<strong>当团队自己的需求恢复时，怎样优先满足它，同时控制共享干扰和资源回收带来的损失。</strong></p>
<p>为此，我们把任务分成保障型和机会型两类。保障型任务在团队配额内优先获得资源，机会型任务利用剩余容量，并接受回收。我们定义了 QAD，也就是配额保障满足度，用已经分配的保障资源，除以配额和当前保障需求中的较小值，判断哪个团队的资源需求还没有得到满足。</p>
<p><strong>第一，决定先运行谁。</strong>保障型任务优先；同类任务先考虑平滑 QAD 较低的团队，QAD 相同时，再优先安排预测剩余时间较短的任务。这样既考虑团队保障，也利用短任务优先改善等待时间。</p>
<p><strong>第二，决定能否共享。</strong>先尝试空闲 GPU，没有合适位置再考虑通过 MPS 共置。干扰预测器分别估计两个任务共享后的吞吐保持率，双方都满足门槛才允许共享。QAD 用来判断资源保障是否兑现，吞吐保持率用来控制性能干扰。运行后继续监测，如果保障任务与机会型任务共享时，性能连续不达标，就停止同卡上的机会型任务，让保障任务继续运行，减少共享造成的干扰。</p>
<p><strong>第三，保障任务仍然放不下时，回收机会型资源。</strong>我们先检查回收后能否满足放置条件，再结合预测剩余时间、累计抢占开销和被中断任务数量选择对象，尽量保护快完成的任务，减少反复中断。选定后先预留资源，再清退对应任务，确认资源实际释放后安排保障任务。</p>
<p>工程上，系统基于 Kubernetes 扩展实现：调度插件负责排序、共享和回收决策，节点侧通过 MPS 支持并发执行，并利用 DCGM 指标提供运行反馈。两个预测器分别服务于任务排序与抢占选择，以及共享准入，最终优化的是任务完成时间和租户保障效果。</p>
<p>在十六张 A100 的真实部署实验中，相比 Hard+Colocate，平均作业完成时间降低了 34%，保障租户 QoS 合规率达到 93%。这项工作的核心，是把团队的资源保障状态贯穿到排序、共享和回收过程中，让实验室的空闲算力得到利用，同时兼顾各课题组的资源需求。</p>
</div>
</div>

<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 如果只展开抢占，怎么用一分钟讲清楚？</div>
<div class="qa-a">
<p>我们的抢占有两个主要入口：一个是保障任务来了，正常放置和安全共享都安排不下，需要回收 Best-effort 占用的资源；另一个是共享后实际干扰持续超标，需要停止同卡上借用资源的 Best-effort 训练任务。</p>
<p>进入回收以后，先找能够满足新任务需求的候选资源，再比较候选任务的剩余运行时间、历史抢占代价，以及需要同时打断多少任务。快结束的任务和已经承担较高累计抢占开销的任务，会尽量保护。如果需要完整 GPU，就必须把该卡上需要退出的 Best-effort 任务一起考虑，不能只停一个就算释放了一张卡。</p>
<p>执行上是通过 Kubernetes 删除选中的 Pod，由节点终止训练进程。删除请求返回成功不等于 GPU 已经空出来，要等实际退出和资源释放，再给新任务分配。训练进度的恢复依赖任务自身的 checkpoint，Pod 删除不会自动保存进度。</p>
</div>
</div>

<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 删除 Pod 后，任务怎么恢复？MPS 会帮忙保存状态吗？</div>
<div class="qa-a">
<p>MPS 负责多个 GPU 进程并发执行，不负责保存训练进度。删除 Pod 会终止其中的进程，内存和显存里的状态不能因此自动保留。</p>
<p>后续重建或重新提交任务，需要由作业控制器或提交系统负责；恢复训练还需要训练程序支持 checkpoint，保存模型、优化器和训练步数等状态，并在启动时加载。没有这些支持，就可能需要重新训练。因此，介绍 DeepShare 时可以明确说它完成了代价感知的抢占决策和 Pod 层面的执行，不能把它描述成任意训练任务的透明暂停和原地继续。</p>
</div>
</div>

<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 抢占代价函数怎么推导？每一项为什么这样写？</div>
<div class="qa-a">
<p>论文使用下面的集合代价，分数越小越优先选择：</p>
<div class="formula">$$\Phi(J)=\sum_{j\in J}\frac{1+\alpha C_p(j)}{\hat T(j)}+\frac{\beta(|J|-1)}{\bar T(J)}$$</div>
<p>这里，J 是要回收的一张 GPU 上的全部驻留任务，|J| 是任务数量；T̂(j) 是任务 j 的预测剩余时间，T̄(J) 是这些任务的平均剩余时间；C_p(j) 是归一化后的累计抢占开销。默认 α=0.5、β=0.3，分别控制历史打断和多任务打断的惩罚强度。</p>
<p><strong>第一步，保护快完成的任务。</strong>先写 1/T̂(j)。其他条件一样，任务越接近完成，倒数越大，抢占它就越不划算。这是一个调度偏好，不是说剩余时间长的任务一定丢失进度更少。</p>
<p><strong>第二步，减少重复抢占。</strong>把分子改成 1+αC_p(j)。没有历史开销时也保留基础代价 1；累计开销增加以后，这个任务的分数会升高，下次就更不容易再次成为抢占对象。累计开销不等同于简单的抢占次数。</p>
<p><strong>第三步，计算整张卡的代价。</strong>对卡上的任务求和。回收共享 GPU 时，停止一个任务并不代表整张卡释放，所以必须评价完整集合。</p>
<p><strong>第四步，进一步惩罚一次打断多个任务。</strong>加入 β(|J|−1)/T̄(J)。只停一个任务时，这项为零；停多个任务时，这项增加；如果它们平均都快结束了，这项还会更大。前面的求和已经累计每个任务的代价，这一项额外表达了对多任务同时中断的惩罚。</p>
<p><strong>最后，先检查可行性，再最小化代价。</strong>设 V(d) 是 GPU d 的全部驻留任务，候选集 D_j^P 只包含这些任务全部为 Best-effort、且清退后能满足新任务显存和节点 CPU/内存约束的 GPU：</p>
<div class="formula">$$d^*=\arg\min_{d\in\mathcal D_j^P}\Phi(V(d)),\qquad J^*=V(d^*)$$</div>
<p>例如统一用分钟、历史开销均为零：GPU A 上一个任务还剩 10 分钟，代价是 0.1；GPU B 上一个任务还剩 100 分钟，代价是 0.01；GPU C 上两个任务都还剩 100 分钟，代价是 (0.01+0.01+0.3/100=0.023)。如果三张卡释放后都满足需求，就选 B。</p>
<p>这个函数是根据上述目标构造的启发式排序代价，不是“会损失多少秒”的精确模型，也不提供全局最优完成时间的证明。论文将 C_p 定义为归一化累计抢占开销，未在该处进一步规定它的归一化计算式。执行时先预留选定设备，再发起 Pod 删除，释放后绑定；没有可行候选就继续排队。</p>
</div>
</div>

<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: MPS 已经能共享 GPU，为什么还需要你们这个系统？</div>
<div class="qa-a"><p>MPS 解决的是多个进程能在一张 GPU 上并发执行，但它不知道谁有配额保障，也不会替我们决定哪些任务适合一起跑。我们的工作是在它上面做调度：判断是否允许共享、安排哪个任务先运行、保障任务来了回收谁，以及共享干扰超标后停止哪个借用任务。MPS 提供执行能力，DeepShare 根据租户需求和运行表现作决定。</p></div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 一次任务提交后，哪些组件实际参与了执行？</div>
<div class="qa-a">
<p>Controller 根据 TenantQuota 整理租户配额和机会型使用上限，任务 annotation 声明保障型或机会型类别。调度器先做租户级准入，累计本轮已放行的申请量，再按类别、平滑 QAD 和预测剩余时间确定任务顺序。</p>
<p>进入放置后，Filter 检查节点与设备约束，共享组合还必须满足双边性能门槛；Score 比较合格位置，Reserve 在最终预留时重新校验设备和额度，避免并发重复使用，之后完成绑定并由节点启动任务。预留之后失败，需要通过 Unreserve 清理尚未提交的预留。</p>
<p>保障任务没有可行位置时，先尝试缩减 BE 的 CPU、内存占用并重试，解除这些资源造成的阻塞；仍然缺少 GPU 才选择完整的 BE 受害集合。GPU 受害者选择放在 PostFilter 分支，清退前预留目标资源，等实际释放后再重新检查和放置，不能在 Filter 检查时直接删除 Pod。</p>
</div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 预测不准，会不会整个调度器就不能用了？</div>
<div class="qa-a"><p>运行时间预测影响任务顺序和抢占代价，但不会改变保障任务优先于借用任务、不能抢占保障任务这些规则。共享干扰预测则先决定是否允许合用，运行后还会用 DCGM 指标估计吞吐保持率；如果连续三个窗口低于阈值，就在下一调度周期停止同卡上的机会型任务。因此预测帮助我们作更好的选择，资源约束和运行反馈仍然持续起作用。</p></div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 怎么证明提高利用率没有以拖慢用户任务为代价？</div>
<div class="qa-a"><p>要同时看利用率、排队时间、作业完成时间和保障任务的 QoS。只看利用率不够，因为两个任务相互争用也可能让 GPU 一直忙。我们做了轨迹仿真和真实集群对比；真实集群实验中，相比 Hard+Colocate，平均作业完成时间下降 34%，保障租户 QoS 合规率达到 93%。进一步区分配额借用、预测排序和共享的贡献，要看分别关闭这些机制的消融结果。</p></div>
</div>


<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: QAD 具体存在哪里，什么时候更新，怎么影响调度？</div>
<div class="qa-a">
<p>QAD 由调度器维护。按实现设计，用租户 ID 索引状态表，保存配额、有效保障需求、已分配保障量和上轮平滑值。需求包括等待和已分配的有效保障任务，不能只统计 Running Pod；机会型用量单独记账。</p>
<p>每个周期取一致的状态视图，计算已分配保障量除以配额与需求的较小值，没有需求时取 1，再做时间平滑。本周期的队列排序和共享判断使用同一份结果，不在每次节点打分时重新推进平滑值。</p>
<p>它有两个直接使用位置：候选队列先按平滑 QAD 排序，再比较预测剩余时间；共享准入读取双方 QAD，调整吞吐保持率门槛。抢占代价本身不额外加 QAD 权重，而是当前欠保障任务放不下时，触发 BE 回收。</p>
</div>
</div>

<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 两个预测器分别怎么做，结果在哪一步使用？</div>
<div class="qa-a">
<p>两个模型都是离线训练、在线预测。运行时间预测器采用 Gradient Boosting，按租户学习历史任务规律，新租户用全局模型兜底。输出预测剩余时间，用于 QAD 之后的任务排序，以及 GPU 受害集合的代价比较。</p>
<p>干扰预测器采用 Random Forest，通过独占与共置 profiling 建立训练数据，输入包括 SM activity、显存带宽等硬件特征，预测两个任务各自的吞吐保持率。先检查双方是否都达到共享门槛，再在合格组合中优先选择双方较小保持率更高的组合。</p>
<p>如果追问 Go 与 Python 如何对接，我们准备的工程方案是让 Python 预测服务作为调度 Pod 的常驻辅助容器，通过本机 gRPC 提供批量预测，调度器缓存特征并在同一轮复用结果。这个接口部署属于实现设计，论文没有记录实际通信协议，不能当作已核实的历史实现。预测调用失败时，设计上可保留类别和 QAD 优先级、以到达顺序兜底；干扰预测缺失则不新增共享组合。</p>
</div>
</div>

<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: MPS、DCGM 和停止任务之间，执行过程怎么连接？</div>
<div class="qa-a">
<p>调度器选择合适的共享组合，节点侧 DaemonSet 管理 MPS 环境，让两个任务能够在同一张 GPU 上并发运行。MPS 不提供完整的计算和带宽隔离，所以仍需要干扰准入和运行反馈。</p>
<p>节点采集 DCGM 硬件指标，由在线保持率估计器判断共享后的性能表现。DCGM 计数器本身不等于任务的 samples/s。任意一方的估计保持率连续三个窗口低于门槛，就标记该组合退化，下一周期执行回收。对保障型与机会型的组合，停止机会型任务的 Pod，由 kubelet 和运行时终止进程，保障任务继续运行；训练恢复依赖用户任务的 checkpoint。</p>
<p>如果追问调度选中的 GPU 如何交给容器，工程方案需要配套的设备分配适配层，传递任务与 GPU 的分配计划，并由节点准备设备访问和 MPS 环境。不能认为写一个 GPU UUID annotation，标准 Device Plugin 就会自动完成定向共享；具体适配接口需要结合实现核对。</p>
</div>
