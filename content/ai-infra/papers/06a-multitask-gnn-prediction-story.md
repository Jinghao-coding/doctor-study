<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 请完整介绍一下你的多目标训练性能预测工作。</div>
<div class="qa-a">
<h3>问题：新训练任务放到哪种 GPU，不能每次都先跑一遍</h3>
<p>我做过一项深度学习训练作业的多目标性能预测工作，目标是在任务真正运行前，估计它在不同 GPU 和执行配置下的性能与资源需求，为异构集群调度提供依据。</p>
<p>这个问题的直接做法是 profiling：把模型分别放到候选 GPU 上，用不同 batch 跑一遍，再记录时延和资源指标。实测很可靠，但模型、batch、精度和 GPU 类型组合起来以后，采样成本会迅速增长。另一种简单方法是看参数量或 FLOPs，但它们主要反映规模，看不到算子类型、张量形状、数据依赖和具体硬件的差异。</p>
<p>因此，这项工作的核心问题是：<strong>能不能只根据模型计算图、运行配置和目标 GPU，在不完整执行训练任务的情况下，同时预测速度、容量和设备利用情况？</strong></p>

<h3>表示：把 ONNX 计算图变成预测输入</h3>
<p>我们先把模型转换成 ONNX 计算图。图中的节点表示算子，包含算子类型、输入输出张量形状和数据类型等特征；边表示张量的数据依赖。图之外再加入 batch、精度和目标 GPU 等执行条件。</p>
<p>这样建模的原因是，相同参数量或相近 FLOPs 的模型，执行行为仍然可能不同。算子组合、串并行依赖、中间张量大小和访存方式都会影响端到端时间与峰值资源；同一张计算图换到不同 GPU 上，算力、显存容量和带宽也会改变结果。</p>

<h3>模型：用 Graph Transformer 做七目标联合回归</h3>
<p>预测器使用 Graph Transformer 聚合节点和依赖信息，得到整个训练图的表示，再与运行配置和 GPU 条件融合，联合输出七项性能与资源指标。现有材料明确包含训练时延、GPU 利用率、SM 活跃度和显存相关指标；七项指标的完整名称以实验记录为准。</p>
<p>这里采用多目标预测，是因为调度器只知道时延并不够。预测最快的设备可能显存放不下；GPU 利用率很高，也不一定代表有效计算效率高。把时延、容量和硬件活动指标放在一起，调度器才能先做可行性过滤，再比较任务放在哪类 GPU 上更合适。</p>
<p>多目标任务共享同一份计算图编码，但不能仅凭这一点就断言它们一定互相促进。是否优于七个独立模型，需要通过单目标、多目标和不同损失权重的消融实验验证。</p>

<h3>训练与泛化：用实测结果监督，按未见组合检验</h3>
<p>训练标签来自任务在真实 GPU 上的运行结果。项目材料记录，这套方法在跨模型、batch 和 GPU 的测试中，七项指标的 WAPE 低于 5%。这里的 WAPE 是绝对误差总和除以真实值总和，表示整体加权误差；它<strong>不表示每个样本的误差都低于 5%</strong>，也不能单独保证显存从不被低估。</p>
<p>泛化评估的关键是数据怎样划分。如果同一个模型的相似 batch 同时出现在训练集和测试集里，误差很低也可能只是学会了这个模型的局部变化。要说明跨模型泛化，应按模型或模型家族留出；要说明跨硬件泛化，则需要留出 GPU 类型或架构组合，再分别报告各目标误差和低估尾部。</p>
<p>如果新模型只是把已见算子重新组合，图结构和算子特征能够提供迁移依据；如果出现新的算子、kernel 或 GPU 架构，就需要补充少量代表性测量做校准或更新模型，并降低调度器对分布外预测的信任。</p>

<h3>落地：离线生成资源画像，在线调度查表</h3>
<p>系统接入时，我不会要求调度器每次选卡都同步运行一次完整的 Graph Transformer。更实际的方式是离线为常见的模型、batch 和 GPU 组合生成资源画像，在线调度直接查询；遇到新组合时，再异步预测或做少量 profiling 校准。</p>
<p>调度时先用显存等容量指标排除不可行设备，再用时延和资源效率比较剩余候选。预测之外仍然要设置安全余量，并在任务运行后收集真实结果，监测持续偏差。这样即使预测发生漂移，容量检查和调度规则仍然能够工作，而不是让一个回归值直接决定全部资源动作。</p>

<h3>贡献：把计算图预测转成调度可以使用的多维资源信息</h3>
<p>这项工作的贡献不是简单地“用了 GNN”，而是把 ONNX 图结构、执行配置和异构 GPU 条件统一起来，联合预测调度真正需要的多类指标，并用跨模型、batch 和 GPU 的实验检查泛化。已有材料中的总体 WAPE 低于 5%，说明预测误差较小；最终是否改善作业等待时间、完成时间和集群利用率，还需要在具体调度策略中继续验证。</p>
<p>这项工作在中文材料中是 2025 年 12 月到 2026 年 5 月的独立项目。SagePilot 后续也使用计算图资源预测，但它的研究对象还包括 Agent 工作流的模型准备、链融合和运行编排；面试时我会把两项工作的预测实验和系统贡献分开说明。</p>
</div>

<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 如果只有一分钟，怎么介绍这项工作？</div>
<div class="qa-a">
<p>我做过一个深度学习训练作业的多目标性能预测项目。它解决的是异构 GPU 集群里新任务选卡的问题：如果每种模型、batch 和 GPU 组合都先完整 profiling，成本很高；只看参数量或 FLOPs，又看不到算子结构和硬件差异。</p>
<p>我们把模型转换成 ONNX 计算图，节点表示算子并带上张量形状等特征，边表示数据依赖，再加入 batch、精度和目标 GPU 条件，用 Graph Transformer 联合预测训练时延、GPU 利用率、SM 活跃度和显存等七项指标。已有材料中，跨模型、batch 和 GPU 测试的 WAPE 低于 5%。</p>
<p>预测结果可以离线形成资源画像，在线调度先检查显存是否可行，再比较完成时间和资源效率。平均误差之外，我还会关注分布外模型、显存低估尾部以及预测接入调度后是否真的改善作业完成时间。</p>
</div>

<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 为什么需要 Graph Transformer，FLOPs 不够吗？</div>
<div class="qa-a">
<p>FLOPs 是有价值的计算量基线，但相同 FLOPs 可能来自不同算子和张量形状，实际执行还受访存、临时工作区、算子依赖和硬件实现影响。计算图能保留这些结构信息，Graph Transformer 再聚合整个图的上下文，因此有机会区分规模相近但执行行为不同的任务。</p>
<p>这不意味着图模型天然优于公式。合理的实验应把参数量、FLOPs、解析估计和传统回归作为基线，同时比较误差、采样成本和最终调度收益。</p>
</div>
</div>

<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 七个目标为什么放在一个模型里？会不会互相干扰？</div>
<div class="qa-a">
<p>七个目标都由同一份计算图、执行配置和 GPU 条件产生，共享编码器可以复用共同的结构信息；不同输出头再学习时延、容量和利用指标各自的映射。这样还能减少维护多个完全独立模型的成本。</p>
<p>目标之间也可能冲突，例如某个损失量级较大时主导梯度，或者对时延有用的表示不一定最适合显存。需要统一量纲或设置损失权重，并通过单目标与多目标消融、各目标误差和梯度冲突检查判断。没有消融结果时，不能把“共享表示”直接说成准确率提升的原因。</p>
</div>
</div>

<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: WAPE 低于 5% 能保证调度安全吗？</div>
<div class="qa-a">
<p>不能。WAPE 汇总的是整体绝对误差，数值较大的样本权重更高；它不等于每个样本都落在正负 5% 内。少量显存严重低估仍然可能造成 OOM，小的时延误差也可能在两个候选很接近时把排序颠倒。</p>
<p>因此容量指标要额外看低估分位数和覆盖率，调度准入保留安全余量；时延预测则要看排序正确性，以及接入调度后的等待时间和完成时间。运行后继续用真实观测校准，而不是只依赖离线平均指标。</p>
</div>
</div>

<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 没见过的模型、算子或 GPU 怎么处理？</div>
<div class="qa-a">
<p>新模型如果主要由已见算子重新组合，可以利用算子属性和图结构迁移；真正的新算子如果只有未知类别编码，信息就不足，需要加入计算量、读写量等可解释特征，或者对它做少量 profile。新 GPU 也要提供硬件特征，并用代表性任务校准。</p>
<p>工程上还应做分布外检测或至少设置适用范围。遇到明显超出训练分布的组合，回退到保守估计或 profiling，并限制预测驱动的激进放置。测试集则应按模型家族和 GPU 类型留出，避免随机拆分制造过于乐观的泛化结果。</p>
</div>
</div>
