<h3>动机：请求顺序之外，还有哪些等待</h3>
<p>SagePilot 研究多个 Agent 工作流共享有限异构 GPU 时，怎样缩短整个工作流的完成时间。</p>
<p>这类应用包含多次模型调用，步骤之间有依赖，也可能使用不同模型。已有工作已经可以利用依赖关系安排请求顺序。但我们想进一步确认：<strong>工作流慢，主要是因为请求顺序不合理，还是因为底层执行资源没有准备好？</strong></p>
<p>为此，我们在相同的底层服务环境中运行 Parrot 和 Kairos，拆分请求的等待时间。图 1 显示，<strong>77.3%～85.5% 的请求等待与模型尚不可用有关</strong>：有的请求在等模型加载，有的需要的加载还不能开始。同时，没有执行生成的模型空闲驻留，又占用了 28.1%～33.0% 的 GPU 时间。</p>
<p>这说明，单纯决定哪个请求先跑还不够。请求即使排到前面，模型没准备好也只能继续等；但把所有模型一直留在 GPU 上，又会挤占有限资源。<strong>模型什么时候准备、保留和回收，需要和工作流执行一起决定。</strong></p>
<p>我们又观察了连续使用相同模型的多个步骤。在统一底层放置、请求准入、batch 和模型管理机制的实验中，每一步仍分别等待底层安排。图 2 显示，这种阶段间重新获得执行机会的等待，在中位会话中只占 2%～3%，但在 p95 对应会话中占到了 <strong>39%～42%</strong>。这些是原有执行轨迹中的等待占比，不是融合后的实测加速比。</p>
<p>因此，<strong>逻辑上分成几个节点，并不意味着物理执行也必须逐步重新安排。</strong>连续兼容的调用可以作为一组执行，而已经确定的后续模型需求，也可以在输入完全就绪之前进入准备决策。</p>
<h3>核心工作：把逻辑工作流转成实际执行方案</h3>
<p>这就是我们做逻辑到物理转换的动机：<strong>保留原有任务依赖和计算结果，同时重新组织调用的执行单元、模型准备动作和设备安排，把它们放在一起决策。</strong></p>
<p>举一个贯穿的例子：A 用模型 M1 生成初稿，B 也用 M1 修改，C 再用模型 M2 检查。逻辑图写的是 A → B → C，规定了谁先执行、结果传给谁。但它没有决定 A 和 B 是否使用同一个模型实例、M2 什么时候加载，也没有决定多个工作流争用 GPU 时怎样安排。</p>
<h3>从 A、B、C 的依赖，生成模型与设备上的安排</h3>
<p>假设 GPU 0 已经加载 M1，GPU 1 可以容纳 M2，但 M2 还没加载。我们利用工作流结构做两类转换。</p>
<p><strong>首先，把连续且兼容的 A、B 作为一组执行。</strong>如果链内部没有分叉或汇合，模型部署与执行配置兼容，就一起检查这组调用的资源需求，把它们交给同一个 M1 实例，并在两步结束之前保持实例可用。A 生成后，结果填入 B 的提示词，再执行 B。两次生成都保留，改变的是外层调度不必在 A、B 之间重新安排实例，也不会在这个间隙把它回收。</p>
<p><strong>然后，把 C 所需的模型准备动作也放进方案。</strong>C 虽然要等 B 的输出，但路径和模型已经确定。当 B 正在运行、当前已就绪请求没有需要优先推进的动作时，可以根据 B 的预计结束时间，判断何时在 GPU 1 上加载 M2。C 必须等 B 真正完成、M2 真正加载好，而且容量允许，才能开始生成。</p>
<p>例如，B 预计还要运行 30 秒，加载 M2 需要 20 秒。资源允许时，在 B 结束前准备 M2，就有机会把这 20 秒加载与 B 的计算重叠。这里是解释机制的假设数字，实际提前多少、能否提前，要根据当前资源状态判断。</p>
<p>因此，<strong>转换后的方案不仅有“先 A、再 B、再 C”，还有“A、B 使用 GPU 0 上的 M1”“在 GPU 1 上准备 M2”“B 完成且 M2 可用后执行 C”</strong>。原来只表示数据依赖的图，增加了模型准备动作、实例绑定和资源使用的先后约束。</p>
<h3>多个工作流共同决定哪些模型值得准备和保留</h3>
<p>现在再加入另一个工作流 W2，它也即将使用相同部署配置的 M2。如果部署、设备与隔离条件允许，两个工作流可以使用同一个已经准备好的 M2 实例，不必各自重复准备一份模型。它们的提示词、输出和请求状态仍然分开；能共享实例，也不代表两者都能立即执行，还要检查合并后的请求容量。</p>
<p>如果 GPU 1 并不空闲，方案就不能直接发出加载。我们要判断上面的模型是否已经没有任务使用、后续多久还会用到，以及重新加载的代价，再决定是否回收，或推迟准备 M2。正在被执行单元使用的实例不能直接回收，已经就绪的请求也优先于推测性的提前准备。</p>
<p><strong>同一个逻辑工作流，在不同集群状态下会得到不同的执行安排。</strong>有现成实例就复用，有合适容量才加载，需要回收就先确认资源释放。我们的工作是利用多个工作流的当前和后续需求来构造这些安排，而不是把每次模型调用孤立地交给服务端。</p>
<h3>预测提供依据，完成事件推动方案更新</h3>
<p>这里三个模块各有作用。SageRadar 根据模型算子图、请求配置和硬件特征，用实测数据学习执行时间与显存需求；加载耗时也整理进资源表，并结合实际加载记录校准。这些估计回答“放不放得下、运行多久、模型需要准备多久”。</p>
<p>SageGraph 利用工作流依赖，识别可以成组执行的调用，并构造模型准备与复用关系；SageWeaver 再结合当前副本、设备和队列状态，决定哪些动作现在可以执行。<strong>这是逐步构造并调整方案的启发式方法，不是枚举所有方案寻找全局最优。</strong></p>
<p>例如开始在 GPU 1 加载 M2 之前，先登记这张卡已被分配，避免另一个请求重复使用。加载和生成异步执行，完成事件返回后再更新状态，并重新评估尚未执行的安排。因此，预测用于提前准备，实际执行仍以真实完成事件和资源检查为准。</p>
<h3>效果：减少整个会话的等待</h3>
<p>实验最终看整个工作流是否更快完成。在论文初稿报告的突发负载实验中，相比其中的 Kairos 对照策略，整批会话全部完成所需的时间降低了 <strong>36.8%</strong>，会话的 p95 完成延迟降低了 <strong>25.9%</strong>。</p>
<p>我认为这项工作的关键是：<strong>让工作流里的依赖、模型身份和后续需求，真正参与底层执行方案的构造</strong>。连续调用怎样共用实例、后续模型何时准备、多个工作流怎样共享有限资源，都是这个转换中需要解决的具体问题。</p>

<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 和普通的模型缓存、换入换出有什么区别？</div>
<div class="qa-a"><p>普通缓存主要根据已经到来的请求决定保留谁、换入谁。我们额外利用工作流依赖：前一步还在运行时，就能看到后续可能需要什么模型，从而评估能不能提前准备；连续兼容的调用可以一次安排，减少阶段间重新调度。落到动作上仍然是加载、调用和回收模型，区别在于决定这些动作时，多了后续需求、就绪时间和整个工作流完成时间这些依据。</p></div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 从一个会话到达开始，系统到底怎么跑？</div>
<div class="qa-a"><p>假设 A 调用模型 M1，接着 B 调用工具，再由 C 调用 M2。会话到达后，运行时知道这三个步骤的依赖，A 可以开始，B 和 C 要等待。调度器查 A 的执行代价，检查 M1 是否已有可用实例，决定复用还是加载；实例就绪后 A 开始生成。</p><p>A 完成后，运行时把结果交给 B，B 执行工具调用。此时 GPU 不需要继续替这个工具计算，调度器可服务其他请求；结合后续 C 的需求和工具完成时间估计，也可以判断是否提前加载 M2。工具结果真正返回后，C 才能成为可执行任务，拿到 M2 实例并开始生成。C 完成后会话结束，实例上的任务记录更新；没有任务使用的模型可以保留给其他会话，或者在显存紧张时回收。</p><p>这里 A 和 C 使用不同模型，中间还有工具调用，因此不作为同模型连续链融合。每一步由真实完成事件推进，预测只辅助提前准备。</p></div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 提前加载为什么可能让 p95 更差？你会怎么处理？</div>
<div class="qa-a"><p>比如预测后续很快会用到 M2，提前加载却挤掉了当前请求马上要用的 M1，M1 就要重新加载，等待时间反而增加。还有一种情况是分支最终没走到 M2，这次加载既占了显存，又消耗了加载带宽。</p><p>设计上我会先满足已就绪请求，再把预加载限制在可用容量和并发加载预算内；对预测收益接近成本的候选更保守，并持续比较预加载命中率、重加载次数和 p95。如果误差变大，就降低预加载的积极程度。这里的关键是把提前准备当作有成本的优化，具体限额和回退策略还需要结合实现与实验验证。</p></div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 两个请求同时申请显存，如何防止超额分配？</div>
<div class="qa-a"><p>当前调度器通过命令队列串行处理核心状态更新。检查容量、登记资源占用和记录实例正在加载，属于同一段受控的状态更新；真正加载可以异步执行，但预留必须先完成。因此后来的请求看到的已经是扣除预留后的容量，不能重复使用它。加载完成后再更新可用状态，失败路径则要撤销对应预留，不能只依赖实时查询显存来避免竞争。</p></div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 为什么不只报预测准确率？</div>
<div class="qa-a"><p>因为我们最终优化的是会话完成时间。预测更准，如果没有改变放置或加载决定，未必产生收益；平均误差较小，也可能有少数显存低估导致 OOM。所以我会同时看预测误差、显存低估、加载等待、重加载次数、平均完成时间和 p95，再通过分别关闭融合、预加载等机制，判断收益来自哪里。</p></div>
</div>

<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: SageGraph 连续执行，是不是意味着这条链独占 GPU、不再排队？</div>
<div class="qa-a"><p>连续链只向资源调度器申请一次，中间不再重复准入，并保持实例可用。它不等于独占 GPU，也不消除推理引擎内部的调度；同一实例可以在容量允许时接收其他请求。收益是减少阶段间重新争取资源的开销，代价是这组调用在更长时间内保持资源使用，因此还要观察其他请求的等待和整链显存预算。</p></div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 当前实现是不是始终选择预计完成最早的 GPU？</div>
<div class="qa-a"><p>当前选卡先检查上下文、预测桶和显存可行性，再按总显存较小、预测运行时间较短的顺序选择候选。扩副本会比较现有队列和新副本的预计完成时间，但这不等于所有选卡动作都在全局最小化完成时间。A100 与 V100 的时间算例可以用来解释加载与计算重叠的价值，不能当作当前选卡函数必然执行的规则。</p></div>

<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: LangGraph 调用常驻 vLLM，本来就能复用模型，你们增加了什么？</div>
<div class="qa-a"><p>常见的 LangGraph 加常驻 vLLM 部署里，A 请求结束不会自动卸载模型，B 可以继续调用同一个服务。因此不能把“不重复加载模型”本身作为我们相对常驻服务的贡献。</p><p>我们面向多个模型竞争有限 GPU、实例需要动态准备和回收的环境。工作流提供的不只是当前请求，还包括连续兼容的调用和已确定的后续模型需求。系统利用这些信息，把调用成组、模型准备、跨工作流复用和设备分配组织成实际执行方案。收益需要通过阶段等待、重加载次数和端到端延迟验证；如果模型始终驻留、资源又充足，成组执行的收益可能很小。</p><p>这里“一次安排”指的是 SagePilot 外层对实例的安排。底层仍逐阶段调用模型，也仍然存在引擎内部的调度。<a href="https://docs.langchain.com/oss/python/langgraph/pregel">LangGraph 运行机制</a>；<a href="https://docs.vllm.ai/en/latest/design/prefix_caching/">vLLM 请求与缓存管理</a>。</p></div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 物理方案一定能按预测时间执行吗？</div>
<div class="qa-a"><p>不能。比如 B 实际比预计慢，M2 可能提前准备好，却仍需等 B 的真实输出；如果模型加载更慢，C 就还要等加载。系统只执行当前满足条件的动作，在完成事件到来后调整尚未发出的安排。预测误差会影响准备时机和收益，但不能放宽数据依赖或资源容量约束。</p><p>论文描述了更一般的时间线资源约束；此前核对的实现主要采用单卡单副本和副本内 batch 容量检查。不能把这直接描述成已经实现了任意多模型同卡共置，或任意未来时间线的全局最优规划。</p></div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 什么时候增加副本，什么时候回收已有模型？</div>
<div class="qa-a"><p>扩副本时，比较继续在已有实例等待的预计完成时间，与加载新实例再执行的预计完成时间。假设前者还需 70 秒，后者加载 30 秒、执行 20 秒，预计能节省 20 秒；只有收益超过配置门槛、设备和副本上限允许，而且不会占掉其他需求最后一个可行位置，才考虑扩容。</p><p>回收先排除正在使用和受保护的实例，再优先考虑冗余副本，以及下一次使用较远、重新加载代价较小的实例。假设一个模型 100 秒后才需要、加载需 20 秒，另一个 30 秒后需要、加载需 25 秒，其他条件相同更倾向回收前者。数字用于解释判断，实际动作仍需经过回收条件检查并确认卸载完成。</p></div>
