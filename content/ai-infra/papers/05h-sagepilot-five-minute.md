<div class="qa-a">
<p>SagePilot 研究的是<strong>多个大模型 Agent 工作流共享有限的异构 GPU 时，怎样减少用户完成整个任务的等待时间。</strong> 这项工作的出发点是：一个 Agent 任务通常包含多次模型调用和工具调用，执行过程中的等待，除了模型生成本身，还来自模型加载、实例排队，以及不同阶段之间反复申请资源。</p>
<p><strong>先说一下我们关注的场景。</strong></p>
<p>在代码修复、数学求解和文档总结这类应用中，一个用户任务往往需要多个 Agent 协作。以代码修复为例，系统先分析问题、生成修改，再调用工具执行测试；如果测试没有通过，就根据结果继续诊断和修复。这些步骤有前后依赖，也可能使用不同规模、不同配置的模型。</p>
<p>我们关注的是私有部署场景。组织希望把敏感输入和内部数据留在自己的基础设施中，但成本又限制了 GPU 数量，无法为每个模型长期保留充足的独立实例。而且设备可能是逐步采购的，既有 V100，也有 A100，计算能力和显存容量不同。</p>
<p>当多个工作流同时运行时，它们就要共享这批有限的设备。某一步需要的模型可能还没加载，已有实例可能正在服务其他请求；为了加载新模型，又可能需要回收暂时空闲的旧实例。<strong>用户看到的是一个任务迟迟没有完成，底层发生的却是依赖等待、模型准备和资源竞争相互叠加。</strong></p>
<p>这让我们开始关注：只优化单次模型推理，或者调整已经到达的请求顺序，能解决多少端到端等待？</p>
<p><strong>我们从执行时间线上发现了两类值得优化的问题。</strong></p>
<p>第一类是模型可用性和工作流进度没有衔接好。某个后续步骤还没有收到输入，但它要用哪个模型已经确定了。底层如果一直等到请求真正就绪才开始加载，就会把模型准备完整地放在用户等待的路径上。与此同时，其他模型可能没有请求，却仍然驻留在 GPU 上，占着后续任务需要的容量。</p>
<p>在论文初稿的动机实验中，等待模型加载、以及加载暂时无法开始这两部分，合计占请求等待时间的约 77%～86%；空闲模型驻留又占用了约 28%～33% 的总 GPU 时间。这两个比例的统计口径不同，但共同说明：请求在等需要的模型，设备上又留着当前没有执行任务的模型，模型准备和保留时机还有优化空间。</p>
<p>第二类是连续调用之间反复申请资源。一个工作流里的相邻步骤，即使使用相同模型和部署配置，也可能在每一步结束后释放外层资源，再由下一步重新排队申请。在资源紧张的时候，中间可能被其他请求插入，甚至模型被回收，下一步又要重新加载。这种等待在普通会话里可能不明显，但会放大一部分会话的尾延迟。</p>
<p>因此，我们希望利用工作流已经暴露出来的信息，<strong>提前准备确定会用到的模型，并减少连续兼容调用之间重复争取资源的开销。</strong></p>
<p><strong>用一个简化的例子，可以把这个思路说明白。</strong></p>
<p>假设 A 用模型 M1 生成初稿，B 继续用 M1 修改，C 再用模型 M2 检查，依赖关系是 A 到 B，再到 C。</p>
<p>这里有两个机会。A 和 B 如果是一对一依赖，部署与执行配置也兼容，就可以共用一次外层资源申请，在两步结束前保持同一个模型实例可用。它们仍然分别生成、分别传递结果，但 B 不必再从外层资源队列重新竞争一次。</p>
<p>另一方面，C 的生成必须等 B 的结果，但把 M2 的权重和服务实例准备好，并不需要 B 的输出。如果 C 的执行路径和模型已经确定，就可以在资源允许时，让 M2 的加载与 B 的执行重叠。</p>
<p>举一个纯粹用于解释的时间算例：B 还需要 20 秒，M2 加载需要 20 秒，C 执行需要 10 秒。等 B 结束再加载，后面一共需要 50 秒；如果有合适的空闲设备，能够立即并行加载，就有机会缩短到约 30 秒。省掉的是关键路径上的模型等待，C 本身的生成时间没有变化。</p>
<p><strong>但提前准备和保留实例都会占用资源，所以关键是决定什么时候值得做。</strong></p>
<p>如果为了提前加载 M2，把另一条工作流马上要用的模型回收了，反而会制造新的等待。如果一直保留 M1，其他模型也可能进不来。已有 M2 实例时，还要判断是继续排队复用，还是多加载一个副本。异构设备又增加了一层选择：计算更快的卡可能需要重新加载模型，显存较大的卡也可能是另一个请求唯一可用的位置。</p>
<p>所以，我们把工作流的逻辑依赖，与实际执行时的资源安排联系起来。逻辑依赖规定哪些结果必须先产生；物理执行则决定哪些调用一起申请资源、模型何时加载或保留，以及任务交给哪个实例和设备。<strong>SagePilot 保留原来的调用语义，通过调整这些物理执行选择来减少等待。</strong></p>
<p><strong>具体实现时，首先需要估计不同选择的资源代价，这部分由 SageRadar 完成。</strong></p>
<p>调度器需要知道一次调用在不同 GPU 上大约运行多久、占用多少显存，以及模型尚未驻留时需要准备多久。只看模型参数量不够，因为输入输出长度、batch 和设备能力都会改变这些开销；把所有组合逐一完整测量，成本又比较高。</p>
<p>SageRadar 把模型计算表示为算子图，节点描述算子类型、计算量和张量形状，边描述数据依赖，再结合请求配置和 GPU 属性，用实测样本训练图模型，估计执行时间、峰值显存和部署加载时间。预测结果整理成资源表，在线调度直接查询；加载时间还可以结合实际加载记录校准。</p>
<p>这些估计有不同用途：执行和加载时间用于比较等待与准备的代价，显存用于准入判断。显存估计会经过校正并保留余量，按配置允许的输出上限检查容量。工作流中的后继何时可能就绪，则结合前驱进展和执行时间估计得到。</p>
<p><strong>接着，SageGraph 根据工作流依赖，找出可以改变的执行边界和准备动作。</strong></p>
<p>对连续使用同一部署的调用，我们检查链内是否是一对一依赖，以及模型和执行配置是否兼容。满足条件时，把这段链合成一个外层调度单元，一次申请资源，逐阶段执行，最后释放。每个阶段的提示词、生成过程和结果传递都保留，减少的是重复准入和中间重新排队。</p>
<p>对于后续需求，我们只利用路径和模型已经确定、前驱已经完成或正在执行的紧邻节点。没有确定的测试分支，不会直接当成一定到来的模型需求。这样可以利用已经知道的未来信息，又不要求事先知道整个工作流的所有执行路径。</p>
<p>不同工作流如果需要兼容且允许共享的同一模型部署，还可以合并模型准备需求，复用实例及其驻留状态。各自的请求上下文和执行结果仍然独立。这样，一次加载能为哪些工作流服务，就进入了同一个资源决策过程。</p>
<p><strong>最后，SageWeaver 结合实时资源状态，把这些机会变成具体动作。</strong></p>
<p>每轮调度先推进已经就绪的任务。已有模型实例能够接纳，就检查容量并安排执行；否则考虑加载、增加副本，或者安全回收空闲实例，为当前任务准备资源。等待较久的请求会提高优先级，避免一直被推迟。</p>
<p>多个模型都需要加载时，系统把不同工作流对同一部署的当前和即将到来的需求汇总，再结合预计加载时间排序。直观来说，其他条件相同，优先准备能够以较小加载成本服务更多需求的模型。</p>
<p>如果已有实例队列很长，就比较继续排队与加载新副本后的预计完成时间。只有预计收益足够，而且副本上限和设备资源允许，才考虑扩容。选择设备时先过滤不可行配置，再优先使用容量合适的设备，结合预测执行时间排序，尽量保留稀缺的大显存设备。</p>
<p>资源不足需要回收时，先排除正在使用和受保护的实例。在合法候选中，优先考虑冗余副本，再看距离下次使用还有多久、重新加载需要多久。下次使用较远、来得及重新准备的实例，更适合暂时回收。</p>
<p><strong>预加载排在当前就绪需求之后。</strong> 当前这一轮没有可推进的就绪任务准入或模型准备动作时，系统才检查后继的预计就绪时刻和加载成本，在合适的时间、利用允许的剩余容量开始准备。这样，提前准备的机会要服从当前任务和真实资源约束。</p>
<p>回到 A、B、C 的例子，系统可以让 A 和 B 连续持有 M1 的实例，并在条件满足时准备 M2；如果另一条已经就绪的工作流需要那张空卡，就先推进它，推迟 C 的预加载。同样的逻辑工作流，在不同资源状态下会采用不同的执行安排。</p>
<p><strong>这些决定通过事件持续更新。</strong></p>
<p>新请求到达、模型加载完成、工具返回或者模型调用结束，都会触发下一轮调度。系统只提交当前可以执行的动作，尚未发出的安排可以随着新状态调整。预测用于判断时机，真正开始生成仍然需要输入齐备、模型可用，并通过容量检查。</p>
<p>工程上，核心资源状态通过命令队列串行更新，加载和执行异步进行。发出加载命令前先登记设备归属，避免两个请求同时把一张空卡分配给自己；完成事件返回后，再把实例更新为可用。底层推理引擎负责实例内的请求执行，SagePilot 负责工作流层面的准入和模型资源安排。</p>
<p><strong>评估时，我们关注整个会话的完成效果，以及改善来自哪些机制。</strong></p>
<p>工作负载覆盖数学求解、代码修复和会议总结，分别包含并行分支与汇合、工具交错和连续同模型调用。我们同时看整批会话从首个到达到全部结束的时间，也就是 makespan，以及单个会话的 p95 延迟和 GPU 占用时间。</p>
<p>按当前论文初稿的报告值，在突发到达设置下，相比两条参照策略，makespan 降低约 36%，整体 p95 降低约 25%。这组比较在相同 serving 底座上采用参照系统的请求排序规则。关闭链融合后，初稿报告不同到达设置下 p95 增加约 8.5%～44.9%；把生命周期需求限制为按单工作流统计，也会增加整批完成时间。这些结果分别对应减少阶段间重新等待、以及协调跨工作流模型需求的作用。</p>
<p>这组数字目前按初稿报告口径介绍，实验规模和资源表来源仍需要与原始运行记录统一。评估时还需要注意：整批任务更早结束，不代表所有负载下每个会话的尾延迟都最低，因此我们会同时比较完成效率、尾延迟和资源成本。</p>
<p><strong>SagePilot 的核心贡献，是把工作流已经确定的后续需求，转化为提前准备、连续执行和模型保留回收的依据，再结合异构 GPU 的实际状态滚动决策，减少用户完成整个多 Agent 任务所经历的等待。</strong></p>
</div>

<p><strong>预测给代价，图转换给候选和依赖，调度结合实时资源状态选择动作。</strong>这是职责划分；实现时可以交织构造和选择，不要求先枚举完所有物理图。</p>
<h3>调度为什么不只是给请求排序</h3>
<p>如果只把 C 排到队首，M2 还没有准备好，C 依然跑不了。调度器必须同时决定模型是否准备、在哪里准备，以及哪些实例继续保留。执行顺序只有结合这些资源动作才有意义。</p>
<ol>
<li><strong>看当前能推进谁：</strong>先按优先级和等待情况处理 ready 任务。C 的输入还没齐，此时只能参与模型准备，不能参与生成。</li>
<li><strong>检查已有资源：</strong>模型已驻留且实例可接纳，就复用；否则考虑加载。模型驻留不等于实例有空余容量。</li>
<li><strong>处理资源不足：</strong>寻找合适空卡，或回收合法的空闲实例；活跃租约保护下的 M1 不能卸载。没有合法动作就等待事件。</li>
<li><strong>考虑后续需求：</strong>这轮没有 ready 准入或模型准备动作可推进时，检查 C 的预取时间、可用设备和资源约束，决定是否加载 M2。</li>
<li><strong>登记并发出动作：</strong>加载前先登记设备占用，防止其他动作重复分配；完成事件返回后，再把实例标为可用。</li>
</ol>
<h3>提前准备具体省在哪里</h3>
<p>如果等 B 完成才加载 M2，从现在到 C 完成需要：B 剩余 20 秒 + 加载 20 秒 + C 生成 10 秒，共 50 秒。若符合预取条件并立即加载，B 和模型加载可以重叠，两者都结束后 C 再生成，合计约 30 秒。省下的是关键路径上的模型等待，不是 C 的生成计算。</p>
<p>若加载实际用了 25 秒，C 就到第 25 秒才能开始；若 B 实际用了 30 秒，C 就到第 30 秒才能开始。预测时间到了，不代表数据或模型已经就绪。</p>
<h3>同样的 C，资源状态不同，动作就不同</h3>
<ul>
<li><strong>M2 已驻留：</strong>检查容量后复用，不必再次加载。</li>
<li><strong>空卡可用且没有 ready 动作可推进：</strong>满足预取时机和容量条件时，可以提前加载 M2。</li>
<li><strong>另一 ready 任务需要这张空卡：</strong>优先推进它，C 的预取推后。</li>
<li><strong>只有 B 正在用的 M1 能腾出位置：</strong>不能回收，等待合法资源机会。</li>
<li><strong>M2 已有实例但队列很长：</strong>比较等待与另开副本的预计完成时间，收益和资源条件都满足才扩容。</li>
</ul>
<p>“联合优化”描述要一起考虑的决策范围；当前在线算法按上述优先顺序逐步作决定，不是穷举所有方案再找全局最优。此前核对的实现选卡仍采用可行性过滤和固定排序，不能把这个例子讲成每次都会选预计完成最早的 GPU。</p>

<summary>展开：目标公式、约束、Algorithm 1 与决策算例</summary>
<h4>优化对象：当前可推进的任务与已确定的后继</h4>
<ul>
<li><strong>输入状态：</strong>已就绪执行单元、紧邻且路径已确定的后继、模型副本与设备占用，以及 SageRadar 给出的运行时间、加载时间和显存估计。</li>
<li><strong>决策变量：</strong>复用、加载、扩副本或回收哪些实例；执行单元绑定哪个副本和 GPU；哪些资源冲突动作必须先后执行。</li>
<li><strong>规划范围：</strong>当前就绪单元与紧邻的 near-ready 后继。尚未解析的分支不作为确定需求，后续随真实事件更新。</li>
</ul>
<h4>目标函数：按优先顺序比较方案</h4>
<div class="formula">$$\min_{G,\pi}\;\Phi(G,\pi)=(-A_1,\ldots,-A_K,\hat C_F,-P_N,H_{life})$$</div>
<p>这里采用<strong>字典序</strong>：前一项相同，才比较后一项。G 表示物理执行图，π 表示绑定和资源执行顺序。</p>
<ol>
<li><strong>尽量接纳就绪任务：</strong>Aₖ 是第 k 个优先级与等待时间类别中接纳的单元数，高优先级类别先比较。</li>
<li><strong>缩短当前任务的完成时间：</strong>Ĉ_F 是本轮已接纳就绪单元中最晚的预计完成时间。</li>
<li><strong>增加及时预取：</strong>P_N 表示能及时完成的后续模型预取数量。</li>
<li><strong>减少模型管理代价：</strong>H_life 计入面向就绪工作的加载延迟和回收引起的重加载代价。</li>
</ol>
<p>因此，论文中的时间目标针对<strong>当前规划窗口</strong>，通过滚动决策改善端到端表现；它不是直接精确求解整批工作流的全局最短完成时间。</p>
<h4>代价模型：把依赖等待和资源等待放在同一条时间线上</h4>
<div class="formula">$$\hat s_u=\max\left(\hat r_u,\max_{v\in pred_G(u)}\hat c_v,\max_{v\in rpred_\pi(u)}\hat c_v\right),\qquad \hat c_u=\hat s_u+\hat T_{u,a(u)}$$</div>
<ul>
<li><strong>数据就绪：</strong>r̂_u 表示任务何时具备输入。</li>
<li><strong>图上依赖：</strong>pred_G 包括原有依赖和新增的模型准备依赖。</li>
<li><strong>资源冲突：</strong>rpred_π 表示占用同一资源、必须先完成的操作。</li>
</ul>
<p>例如输入在第 100 秒就绪，模型在第 90 秒加载完成，但不可并发的同卡操作到第 120 秒才结束，那么任务最早第 <strong>120 秒</strong>开始；运行需要 20 秒，就在第 <strong>140 秒</strong>完成。只比较模型运行时间，会漏掉前面的等待。数字均为说明机制的算例。</p>
<h4>可行性约束：不仅检查模型权重是否放得下</h4>
<ul>
<li><strong>语义与依赖：</strong>输入输出依赖保留，数据和模型都实际就绪才能生成；加入资源顺序后不能出现环。</li>
<li><strong>部署与准入：</strong>满足设备兼容性、上下文长度和副本并发上限；共享准备动作必须符合所有消费者的设备条件。</li>
<li><strong>显存：</strong>论文在每个预计状态变化时刻检查“驻留及过渡态模型显存 + 活跃请求增量显存 ≤ 设备容量”，共享权重不按请求重复计算。</li>
<li><strong>回收：</strong>排除正在使用和受保护的实例，不能为了新任务直接卸载正在执行的模型。</li>
</ul>
<h4>Algorithm 1：按事件逐步构造可行方案</h4>
<ol>
<li><strong>RankReady：</strong>按优先级和 aging 排列就绪单元，等待较久的任务提高优先级。</li>
<li><strong>BestFeasibleBinding：</strong>过滤不可行设备，每个单元至多返回一个绑定；已有实例可接纳时形成准入动作。</li>
<li><strong>PlanReady：</strong>对其余就绪任务安排加载、扩副本或安全回收，逐步更新方案。</li>
<li><strong>PlanPrefetch：</strong>仅当本轮没有产生推进就绪任务的准入或模型准备动作时，才考虑 near-ready 模型预取。</li>
<li><strong>Propagate 与 Prefix：</strong>传播预计完成时间、安排资源冲突并检查容量，只提交当前可执行的动作；新请求、加载完成和任务完成事件触发下一轮。</li>
</ol>

<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 和普通的模型缓存、换入换出有什么区别？</div>
<div class="qa-a"><p>普通缓存主要根据已经到来的请求决定保留谁、换入谁。我们额外利用工作流依赖：前一步还在运行时，就能看到后续可能需要什么模型，从而评估能不能提前准备；连续兼容的调用可以一次安排，减少阶段间重新调度。落到动作上仍然是加载、调用和回收模型，区别在于决定这些动作时，多了后续需求、就绪时间和整个工作流完成时间这些依据。</p></div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 从一个会话到达开始，系统到底怎么跑？</div>
<div class="qa-a"><p>假设 A 调用模型 M1，接着 B 调用工具，再由 C 调用 M2。会话到达后，运行时知道这三个步骤的依赖，A 可以开始，B 和 C 要等待。调度器查 A 的执行代价，检查 M1 是否已有可用实例，决定复用还是加载；实例就绪后 A 开始生成。</p><p>A 完成后，运行时把结果交给 B，B 执行工具调用。此时 GPU 不需要继续替这个工具计算，调度器可服务其他请求；结合后续 C 的需求和工具完成时间估计，也可以判断是否提前加载 M2。工具结果真正返回后，C 才能成为可执行任务，拿到 M2 实例并开始生成。C 完成后会话结束，实例上的任务记录更新；没有任务使用的模型可以保留给其他会话，或者在显存紧张时回收。</p><p>这里 A 和 C 使用不同模型，中间还有工具调用，因此不作为同模型连续链融合。每一步由真实完成事件推进，预测只辅助提前准备。</p></div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 提前加载为什么可能让 p95 更差？你会怎么处理？</div>
<div class="qa-a"><p>比如预测后续很快会用到 M2，提前加载却挤掉了当前请求马上要用的 M1，M1 就要重新加载，等待时间反而增加。还有一种情况是分支最终没走到 M2，这次加载既占了显存，又消耗了加载带宽。</p><p>设计上我会先满足已就绪请求，再把预加载限制在可用容量和并发加载预算内；对预测收益接近成本的候选更保守，并持续比较预加载命中率、重加载次数和 p95。如果误差变大，就降低预加载的积极程度。这里的关键是把提前准备当作有成本的优化，具体限额和回退策略还需要结合实现与实验验证。</p></div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 两个请求同时申请显存，如何防止超额分配？</div>
<div class="qa-a"><p>当前调度器通过命令队列串行处理核心状态更新。检查容量、登记资源占用和记录实例正在加载，属于同一段受控的状态更新；真正加载可以异步执行，但预留必须先完成。因此后来的请求看到的已经是扣除预留后的容量，不能重复使用它。加载完成后再更新可用状态，失败路径则要撤销对应预留，不能只依赖实时查询显存来避免竞争。</p></div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 为什么不只报预测准确率？</div>
<div class="qa-a"><p>因为我们最终优化的是会话完成时间。预测更准，如果没有改变放置或加载决定，未必产生收益；平均误差较小，也可能有少数显存低估导致 OOM。所以我会同时看预测误差、显存低估、加载等待、重加载次数、平均完成时间和 p95，再通过分别关闭融合、预加载等机制，判断收益来自哪里。</p></div>
</div>

<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: SageGraph 连续执行，是不是意味着这条链独占 GPU、不再排队？</div>
<div class="qa-a"><p>连续链只向资源调度器申请一次，中间不再重复准入，并保持实例可用。它不等于独占 GPU，也不消除推理引擎内部的调度；同一实例可以在容量允许时接收其他请求。收益是减少阶段间重新争取资源的开销，代价是这组调用在更长时间内保持资源使用，因此还要观察其他请求的等待和整链显存预算。</p></div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 当前实现是不是始终选择预计完成最早的 GPU？</div>
<div class="qa-a"><p>当前选卡先检查上下文、预测桶和显存可行性，再按总显存较小、预测运行时间较短的顺序选择候选。扩副本会比较现有队列和新副本的预计完成时间，但这不等于所有选卡动作都在全局最小化完成时间。A100 与 V100 的时间算例可以用来解释加载与计算重叠的价值，不能当作当前选卡函数必然执行的规则。</p></div>

<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: LangGraph 调用常驻 vLLM，本来就能复用模型，你们增加了什么？</div>
<div class="qa-a"><p>常见的 LangGraph 加常驻 vLLM 部署里，A 请求结束不会自动卸载模型，B 可以继续调用同一个服务。因此不能把“不重复加载模型”本身作为我们相对常驻服务的贡献。</p><p>我们面向多个模型竞争有限 GPU、实例需要动态准备和回收的环境。工作流提供的不只是当前请求，还包括连续兼容的调用和已确定的后续模型需求。系统利用这些信息，把调用成组、模型准备、跨工作流复用和设备分配组织成实际执行方案。收益需要通过阶段等待、重加载次数和端到端延迟验证；如果模型始终驻留、资源又充足，成组执行的收益可能很小。</p><p>这里“一次安排”指的是 SagePilot 外层对实例的安排。底层仍逐阶段调用模型，也仍然存在引擎内部的调度。<a href="https://docs.langchain.com/oss/python/langgraph/pregel">LangGraph 运行机制</a>；<a href="https://docs.vllm.ai/en/latest/design/prefix_caching/">vLLM 请求与缓存管理</a>。</p></div>

<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 物理方案一定能按预测时间执行吗？</div>
<div class="qa-a"><p>不能。比如 B 实际比预计慢，M2 可能提前准备好，却仍需等 B 的真实输出；如果模型加载更慢，C 就还要等加载。系统只执行当前满足条件的动作，在完成事件到来后调整尚未发出的安排。预测误差会影响准备时机和收益，但不能放宽数据依赖或资源容量约束。</p><p>论文描述了更一般的时间线资源约束；此前核对的实现主要采用单卡单副本和副本内 batch 容量检查。不能把这直接描述成已经实现了任意多模型同卡共置，或任意未来时间线的全局最优规划。</p></div>

<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 什么时候增加副本，什么时候回收已有模型？</div>
<div class="qa-a"><p>扩副本时，比较继续在已有实例等待的预计完成时间，与加载新实例再执行的预计完成时间。假设前者还需 70 秒，后者加载 30 秒、执行 20 秒，预计能节省 20 秒；只有收益超过配置门槛、设备和副本上限允许，而且不会占掉其他需求最后一个可行位置，才考虑扩容。</p><p>回收先排除正在使用和受保护的实例，再优先考虑冗余副本，以及下一次使用较远、重新加载代价较小的实例。假设一个模型 100 秒后才需要、加载需 20 秒，另一个 30 秒后需要、加载需 25 秒，其他条件相同更倾向回收前者。数字用于解释判断，实际动作仍需经过回收条件检查并确认卸载完成。</p></div>

<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 调度优化的变量、目标和约束具体是什么？</div>
<div class="qa-a">
<p>变量包括物理方案中采用哪些模型准备动作、执行单元绑定哪个副本和设备，以及资源冲突操作的先后顺序。论文公式 (12) 使用字典序目标：<code>Φ = (−A₁, …, −Aₖ, Ĉ_F, −P_N, H_life)</code>，按这个顺序最小化。</p>
<p><code>Aₖ</code> 是对应优先级与等待时间类别中接纳的已就绪单元数，负号表示越多越好；<code>Ĉ_F</code> 是当前窗口中已接纳就绪单元的最晚预计完成时间，越小越好；<code>P_N</code> 是及时完成的预取数量，越多越好；<code>H_life</code> 则计入面向就绪工作的加载延迟和回收造成的重加载代价。字典序意味着前面的目标相同时才比较后面的目标，不是把所有指标任意加权求和。</p>
<p>硬约束包括依赖和资源顺序无环、上下文长度、部署与设备兼容性、模型可用性、显存容量以及副本并发上限。每个预计状态变化时刻都要考虑驻留与过渡态模型显存，加上活跃请求的增量显存；共享模型权重不能按请求重复计算。共享准备动作还要满足所有消费者共同的设备条件。</p>
<p>需要区分研究目标、窗口目标和求解方法：研究上希望降低端到端完成时间；公式里的完成时间项针对当前已接纳的就绪单元；Algorithm 1 用启发式逐步构造可行方案，并非精确求解全局最优排程。依据：论文初稿 §3.5、公式 (7)–(12)、Algorithm 1。</p>
