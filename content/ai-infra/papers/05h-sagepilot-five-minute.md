<h3>问题：工作流为什么会空等</h3>
<p>SagePilot 研究的是多个 Agent 工作流共享异构 GPU 时，如何通过工作流信息来优化调度，减少端到端的完成时间。</p>
<p>我先解释一下为什么要研究这个问题。一个 Agent 应用通常不是调用一次大模型就结束，而是包含多个步骤，比如先分析问题，再检索资料，再生成答案，最后检查和修改。这些步骤有前后依赖，也可能使用不同的模型。同时，集群里会有很多这样的工作流一起运行。</p>
<p>这时，影响完成时间的就不只是模型本身生成得快不快，还有任务排队、模型加载，以及多个工作流之间的资源竞争。尤其是在显存有限的情况下，所有模型不能一直驻留，调度器就需要不断决定保留谁、加载谁，以及把请求放到哪张 GPU 上。</p>
<p>我们观察到，如果调度器只看当前已经到达的模型请求，就会错过很多可以提前利用的信息。</p>
<p>举个例子，一个工作流正在执行第一步，第二步的输入还没生成出来，但第二步需要哪个模型，其实已经由工作流定义确定了。如果一定要等第一步结束，才开始准备第二步的模型，那么模型加载时间就会直接变成用户的等待时间。</p>
<p>另外一种情况是，连续几个步骤使用相同的模型配置。如果把它们当成完全独立的任务，每一步都重新申请资源、进入调度，中间就会产生额外开销，还可能失去原本已经准备好的模型实例。</p>
<h3>设计：让后续需求进入当前决策</h3>
<p>所以我们的核心思路是：<strong>把工作流的结构和依赖关系交给调度器</strong>，让它既知道当前有哪些任务要执行，也知道后面可能需要什么资源。</p>
<p>系统分成三个模块，分别解决代价估计、工作流结构优化和运行时调度。</p>
<h3>资源预测：给调度提供时间和显存依据</h3>
<p>首先是 SageRadar。因为我们面对的是异构 GPU，同一个模型放到不同的 GPU 上，执行时间和显存需求是不一样的，输入长度和生成长度也会影响执行代价。因此，调度前需要先估计不同执行配置的时间和显存开销。</p>
<p>具体来说，我们把一次模型调用转成算子图，节点是矩阵乘、Attention 这些算子，边是张量依赖。把计算量、张量形状、请求长度和 GPU 属性一起输入图模型，<strong>用实际测量的运行时间和显存峰值做监督</strong>，学习这个配置大概要花多少资源。预测结果提前写入资源表，调度时直接查询。</p>
<p>比如一个请求预计 5 秒后就绪，A100 上没有模型，加载要 8 秒、执行要 4 秒；V100 已经有模型，但执行要 9 秒。如果允许现在开始加载，A100 在第 12 秒完成，V100 在第 14 秒完成。这时虽然 A100 需要加载，仍然更合适。这个例子说明，预测要和模型是否驻留、请求什么时候就绪一起使用，才能转化成调度决策。</p>
<p>时间预测用于比较完成时间，显存预测用于判断能否接收请求。显存还会做校正和增加余量，并按配置的输出上限检查，避免因为最近输出比较短，就低估下一次调用需要的容量。</p>
<h3>工作流内部：连续调用共用一次资源安排</h3>
<p>第二个模块是 SageGraph，主要减少一个工作流内部连续调用之间的等待。</p>
<p>比如一个写作工作流，A 生成初稿，B 修改，C 整理格式，三步都用同一个模型。如果每一步分别提交模型请求，A 完成后，B 拿到初稿，再发起下一次调用；B 完成后，C 再发起一次调用。在多个工作流共享模型服务时，这三次请求分别参与服务端调度，后两个阶段就可能再次等待。</p>
<p>工作流框架本来就能按依赖自动推进 A、B、C。我们进一步利用的是：<strong>这几次调用连续依赖，而且模型部署配置相同，可以提前作为一组安排资源。</strong></p>
<p>因此，SageGraph 会检查这段调用是不是没有分支、依赖连续、模型配置兼容。满足条件后，就把它们组织成一个执行单元，<strong>开始时申请一次模型实例，然后依次完成生成、修改和整理</strong>。A 的结果填进 B 的提示词，B 的结果再交给 C，整段执行期间保持这个实例可用，中间不再逐步向资源调度器申请。</p>
<p><strong>三次生成仍然保留，减少的是阶段之间重复申请资源和重新排队的机会。</strong>模型如果本来就一直驻留，就没有重复加载的收益；但在多工作流竞争下，连续调用仍然可以减少阶段间重新争取资源的开销。</p>
<h3>跨工作流：复用模型实例，再决定谁能接着执行</h3>
<p>刚才解决的是一个工作流内部怎样连续执行。接下来还有一个问题：<strong>很多工作流同时需要同一个模型，能不能共用已经加载的实例？</strong>这就交给第三个模块 SageWeaver。</p>
<p>比如 W1 已经在 GPU 0 上使用 M1，W2 也需要相同部署配置的 M1。我们会先考虑让 W2 复用这个实例，避免为每个工作流都单独加载一份模型。W1 和 W2 各自提交提示词、接收结果，共用的是底层模型服务。</p>
<p><strong>能复用模型，不代表一定能立即执行。</strong>调度器还要按 W2 加入后的总 batch、输入和输出长度检查显存，并判断实例是否能接收请求。条件满足，就把 W2 安排进去；暂时接不下，就等待，或者进一步评估增加副本。这样既节省重复加载和模型驻留的资源，也把多个工作流之间的竞争放到一起处理。</p>
<p>所以两部分是衔接的：<strong>SageGraph 把每个工作流中适合连续执行的调用组织好，SageWeaver 再决定这些执行单元何时运行、复用哪个实例，以及是否需要加载或回收模型。</strong></p>
<p><strong>如果等待太久，再比较是否值得增加一个副本。</strong>比如 W2 留在原队列预计还要 70 秒完成；另一张空卡加载 M1 要 30 秒、执行要 20 秒，合计 50 秒，预计能节省 20 秒。这个收益超过配置门槛，并且有可用设备、没有超过副本上限，也不会占掉其他有需求模型最后一个可行位置，才启动新副本。队列里有请求，并不意味着一定扩容。</p>
<p><strong>如果没有空卡，就找可以回收的空闲模型。</strong>正在执行请求的实例不能直接回收。对于满足回收条件的实例，优先考虑还有其他副本可用的冗余实例，再比较下一次使用还有多久、重新加载要多久。比如 M2 预计 100 秒后才用到，重加载要 20 秒；M3 在 30 秒后就要用，重加载要 25 秒。其他条件一样，我们更倾向于回收 M2，因为 M3 很快就需要重新准备。选中后先卸载，确认释放后才能在那张卡上加载新模型。</p>
<p><strong>优先推进已经就绪的请求，再考虑提前准备后续模型。</strong>比如 A 正在生成，后面的 B 需要 M2，预计第 100 秒才能拿齐输入；M2 加载要 30 秒，再留 5 秒余量，那么第 65 秒起就可以考虑预加载。系统会先推进已经就绪的请求，检查是否有可用资源，再执行这个提前准备动作。B 真正开始生成仍然要等 A 的结果回来。</p>
<p>如果多个模型都需要加载，我们还会比较<strong>一次加载能服务多少当前及即将就绪的请求，以及要花多长时间</strong>。不同工作流对同一个模型的需求会合并考虑，等待过久的请求也会被提升优先级。</p>
<h3>工程实现：先登记资源，再异步执行</h3>
<p>工作流执行端负责判断依赖是否完成，模型服务负责实际加载和生成，SageWeaver 负责维护请求队列、实例状态和设备归属。</p>
<p>比如决定在 GPU 1 上加载 M1，调度器会<strong>先把 GPU 1 登记为属于这个正在加载的实例，再发出加载命令</strong>。后一个请求进来时，看到这张卡已经被占用，就不会重复分配。加载完成事件返回后，实例才变成可使用状态；请求结束后更新实例上的任务记录，回收时也要等卸载完成再释放设备归属。</p>
<p>这些状态变化通过命令队列串行处理，加载和生成在外部异步执行。这样既不用让慢速加载阻塞整个调度器，也能让同一张卡的分配和释放有统一的记录。</p>
<p>这几个模块是配合工作的：SageRadar 提供执行代价，SageGraph 把适合连续执行的步骤组织起来，SageWeaver 再根据整个集群的状态安排模型和任务。</p>
<h3>效果：看整个会话完成得是否更快</h3>
<p>实验中，我们关注的是这些优化最终能不能缩短整个工作流的完成时间。在论文报告的突发负载场景下，<strong>整体完成时间最高降低了 36.8%</strong>，<strong>会话的 p95 延迟最高降低了 25.9%</strong>。</p>
<p>我认为这项工作最有价值的地方，是利用了 Agent 工作流天然具备、但单次请求调度很难看到的信息：步骤之间有依赖，后续模型需求可以提前知道，部分连续调用也可以稳定地使用同一个实例。把这些信息用于资源决策，就能减少整个执行过程中的空等，让 GPU 的计算和模型准备衔接得更好。</p>

<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 和普通的模型缓存、换入换出有什么区别？</div>
<div class="qa-a"><p>普通缓存主要根据已经到来的请求决定保留谁、换入谁。我们额外利用工作流依赖：前一步还在运行时，就能看到后续可能需要什么模型，从而评估能不能提前准备；连续兼容的调用可以一次安排，减少阶段间重新调度。落到动作上仍然是加载、调用和回收模型，区别在于决定这些动作时，多了后续需求、就绪时间和整个工作流完成时间这些依据。</p></div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 从一个会话到达开始，系统到底怎么跑？</div>
<div class="qa-a"><p>假设 A 调用模型 M1，接着 B 调用工具，再由 C 调用 M2。会话到达后，运行时知道这三个步骤的依赖，A 可以开始，B 和 C 要等待。调度器查 A 的执行代价，检查 M1 是否已有可用实例，决定复用还是加载；实例就绪后 A 开始生成。</p><p>A 完成后，运行时把结果交给 B，B 执行工具调用。此时 GPU 不需要继续替这个工具计算，调度器可服务其他请求；结合后续 C 的需求和工具完成时间估计，也可以判断是否提前加载 M2。工具结果真正返回后，C 才能成为可执行任务，拿到 M2 实例并开始生成。C 完成后会话结束，实例上的任务记录更新；没有任务使用的模型可以保留给其他会话，或者在显存紧张时回收。</p><p>这里 A 和 C 使用不同模型，中间还有工具调用，因此不作为同模型连续链融合。每一步由真实完成事件推进，预测只辅助提前准备。</p></div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 提前加载为什么可能让 p95 更差？你会怎么处理？</div>
<div class="qa-a"><p>比如预测后续很快会用到 M2，提前加载却挤掉了当前请求马上要用的 M1，M1 就要重新加载，等待时间反而增加。还有一种情况是分支最终没走到 M2，这次加载既占了显存，又消耗了加载带宽。</p><p>设计上我会先满足已就绪请求，再把预加载限制在可用容量和并发加载预算内；对预测收益接近成本的候选更保守，并持续比较预加载命中率、重加载次数和 p95。如果误差变大，就降低预加载的积极程度。这里的关键是把提前准备当作有成本的优化，具体限额和回退策略还需要结合实现与实验验证。</p></div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 两个请求同时申请显存，如何防止超额分配？</div>
<div class="qa-a"><p>当前调度器通过命令队列串行处理核心状态更新。检查容量、登记资源占用和记录实例正在加载，属于同一段受控的状态更新；真正加载可以异步执行，但预留必须先完成。因此后来的请求看到的已经是扣除预留后的容量，不能重复使用它。加载完成后再更新可用状态，失败路径则要撤销对应预留，不能只依赖实时查询显存来避免竞争。</p></div>
</div>
<div class="qa">
<div class="qa-q" onclick="this.parentElement.classList.toggle('open')">Q: 为什么不只报预测准确率？</div>
<div class="qa-a"><p>因为我们最终优化的是会话完成时间。预测更准，如果没有改变放置或加载决定，未必产生收益；平均误差较小，也可能有少数显存低估导致 OOM。所以我会同时看预测误差、显存低估、加载等待、重加载次数、平均完成时间和 p95，再通过分别关闭融合、预加载等机制，判断收益来自哪里。</p></div>
