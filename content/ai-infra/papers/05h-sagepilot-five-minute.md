<div class="qa-a">
<p>SagePilot 研究的是多个 Agent 工作流共享异构 GPU 时，如何通过工作流信息来优化调度，减少端到端的完成时间。</p>
<p>我先解释一下为什么要研究这个问题。一个 Agent 应用通常不是调用一次大模型就结束，而是包含多个步骤，比如先分析问题，再检索资料，再生成答案，最后检查和修改。这些步骤有前后依赖，也可能使用不同的模型。同时，集群里会有很多这样的工作流一起运行。</p>
<p>这时，影响完成时间的就不只是模型本身生成得快不快，还有任务排队、模型加载，以及多个工作流之间的资源竞争。尤其是在显存有限的情况下，所有模型不能一直驻留，调度器就需要不断决定保留谁、加载谁，以及把请求放到哪张 GPU 上。</p>
<p>我们观察到，如果调度器只看当前已经到达的模型请求，就会错过很多可以提前利用的信息。</p>
<p>举个例子，一个工作流正在执行第一步，第二步的输入还没生成出来，但第二步需要哪个模型，其实已经由工作流定义确定了。如果一定要等第一步结束，才开始准备第二步的模型，那么模型加载时间就会直接变成用户的等待时间。</p>
<p>另外一种情况是，连续几个步骤使用相同的模型配置。如果把它们当成完全独立的任务，每一步都重新申请资源、进入调度，中间就会产生额外开销，还可能失去原本已经准备好的模型实例。</p>
<p>所以我们的核心思路是：把工作流的结构和依赖关系交给调度器，让它既知道当前有哪些任务要执行，也知道后面可能需要什么资源。</p>
<p>系统分成三个模块，分别解决代价估计、工作流结构优化和运行时调度。</p>
<p>首先是 SageRadar。因为我们面对的是异构 GPU，同一个模型放到不同的 GPU 上，执行时间和显存需求是不一样的，输入长度和生成长度也会影响执行代价。因此，调度前需要先估计不同执行配置的时间和显存开销。</p>
<p>这个模块给后面的调度提供依据。比如，一个模型能不能放进当前 GPU，选择这个执行配置大概需要多久。否则，调度器虽然知道后续要执行什么，也很难判断怎样安排更合适。</p>
<p>第二个模块是 SageGraph，主要利用工作流结构减少连续调用之间的调度开销。</p>
<p>这里可以举一个很具体的例子：A 负责生成初稿，B 负责修改，C 负责整理最终输出。这三个步骤前后依赖，而且使用相同的模型部署配置。</p>
<p>我们的做法是先检查这段调用是不是满足条件，比如它是一条连续的链，中间没有分支，后一步只依赖前一步，而且模型配置兼容。满足条件后，就把它们合成一个执行任务。</p>
<p>执行的时候，任务开始前只向调度器申请一次模型实例。拿到实例之后，先执行 A，再把 A 的输出填进 B 的提示词，继续调用同一个实例；B 到 C 也是一样。直到整条链执行结束，才向调度器报告这次任务完成。</p>
<p>代码里，调度器会记录这个实例上还有哪些任务没有完成。只要这条链还在执行，模型回收逻辑就会跳过这个实例。因此，相邻阶段之间可以继续使用已经准备好的模型。</p>
<p>这里保留了原来各阶段的提示词和生成过程，A、B、C 仍然分别生成。优化的是它们之间重复申请资源、重新调度，以及可能重新加载模型的开销。</p>
<p>第三个模块是 SageWeaver，负责运行时的资源安排，也就是多个工作流一起运行时，具体怎样使用这些 GPU。</p>
<p>它会结合任务依赖、模型是否已经加载、队列情况和剩余显存，决定一个请求使用已有实例，还是需要加载模型、增加副本，或者回收空闲模型。</p>
<p>比如工作流 W1 已经在一张 GPU 上加载了某个模型，W2 随后也需要相同部署配置的模型，那么只要这个实例满足接收请求的条件，W2 就可以直接使用它。两个工作流分别提交自己的提示词、接收自己的结果，共用的是已经加载的模型服务。</p>
<p>再比如，当前步骤还在执行，但后续步骤需要另一个模型。如果资源条件允许，系统就可以提前加载那个模型，让加载和当前计算同时进行。这样等后续任务真正就绪时，就有机会直接开始执行。</p>
<p>这里的一个关键取舍是，提前准备也有成本。过早加载会占用显存，可能挤占当前任务的资源；加载太晚，又不能有效减少等待。所以需要把后续需求和当前资源状态放在一起判断。类似地，增加副本能缓解排队，但也会占用更多显存，不能只看某一个模型的队列就无限扩副本。</p>
<p>这几个模块是配合工作的：SageRadar 提供执行代价，SageGraph 把适合连续执行的步骤组织起来，SageWeaver 再根据整个集群的状态安排模型和任务。</p>
<p>实验中，我们关注的是这些优化最终能不能缩短整个工作流的完成时间。在论文报告的突发负载场景下，整体完成时间最高降低了 36.8%，会话的 p95 延迟最高降低了 25.9%。</p>
<p>我认为这项工作最有价值的地方，是利用了 Agent 工作流天然具备、但单次请求调度很难看到的信息：步骤之间有依赖，后续模型需求可以提前知道，部分连续调用也可以稳定地使用同一个实例。把这些信息用于资源决策，就能减少整个执行过程中的空等，让 GPU 的计算和模型准备衔接得更好。</p>
