## 工作流里的等待，不只发生在生成阶段

我介绍的这项工作是 SagePilot，研究多个 Agent 工作流共享异构 GPU 时的执行效率。一个工作流可能先并行调用几个模型，再经过工具处理，最后由另一个模型汇总。由于 GPU 数量有限，不同模型不能始终全部驻留，系统需要不断决定加载谁、保留谁、回收谁，以及请求放在哪张卡上。

这里有两个机会。首先，下游节点虽然还没有拿到全部输入，但它会用哪个模型，往往已经确定。等到它 ready 才开始加载，就会把加载时间直接加到等待里。其次，连续几个节点可能使用完全相同的模型部署，如果每次调用后都释放后端、下一次再申请，就会重新排队，还可能在中间遭遇模型被回收和重新加载。

我们的思路是利用工作流依赖，联合决定执行边界、模型生命周期与设备放置。逻辑上仍然完成原有调用，物理上可以让模型更早准备好，并让兼容的连续调用共享一次准入。

## SageRadar 把调用转成资源代价

第一个模块是 SageRadar，提供某种请求配置在某类 GPU 上的运行时间、峰值显存和加载成本。输入包括模型算子图、请求的 batch 和输入输出长度，以及 GPU 的算力、容量和带宽。图网络从算子类型、张量形状和依赖中提取表示，再输出资源预测。

这些结果离线形成代价表，调度时查表，不会每来一个请求就在调度关键路径上跑一遍图网络。运行时间可以根据同一节点近期输出长度的高分位选择合适的桶；但显存准入仍按配置的输出上限加余量，避免因为最近输出短就低估容量。

加载成本还需要贴合真实后端。此前核对的实现会统计同模型、同类 GPU 的 warm reload 时间，分运行取中位数校准。例如多轮统计都在三十秒附近，就用它估计下一次重新加载。这个经验校准是代码实现细节，和初稿里的图网络输出接口需要分开解释。

## SageGraph 改变准入边界

第二个模块是 SageGraph。用 QMSum 举例，三个连续聚合节点都调用 Qwen3-8B，前一个结果传给后一个。只要链内部没有分叉、部署身份相同、执行配置兼容，就可以把它们编译成一个融合单元。

融合之后仍然生成三次，每一阶段的提示词和输出都保留。改变的是它们只申请一次资源，并在整条链执行期间持有同一个副本租约，因此不会在阶段之间重新准入，也不会被正常回收策略移走这个活跃副本。整链预算还必须考虑后续阶段消费前序输出后，上下文可能变得更长。

不同工作流如果都需要同一个兼容部署，也可以共享模型加载和驻留，但各自的请求状态、KV 和结果仍然隔离。这里共享的是后端准备与资源，不是把不同用户的 prompt 合在一起。

## SageWeaver 根据当前状态做选择

第三个模块是 SageWeaver。它先处理已经 ready 的工作：能复用现有副本，就检查 batch 和显存后发放 grant；模型还没有准备好，就考虑加载；已有副本排队太久，就比较新开副本的加载加执行时间，判断扩容是否有收益。

没有空卡时，优先考虑回收没有活跃租约、又不受保护的副本。一个很久之后才会再用、重新加载又便宜的模型，通常比马上要用的模型更适合回收。多个工作流对同模型的需求也会合并，影响一次加载是否值得。

预取只利用已经确定路径的 near-ready 节点，不猜测尚未解析的分支。例如节点预计第一百秒就绪，模型加载三十秒，再留五秒余量，就可以从第六十五秒起考虑预取。但当前策略仍先推进 ready 工作，资源不允许时不会强行抢占容量去预取。

每次只提交当前可执行的动作，实际完成、工具返回或模型状态变化后再更新计划。初稿也明确采用事件驱动启发式，不保证全局最优。此前核对的代码在选卡和显存检查上比初稿的一般时间线模型更具体、更受限，不能把形式化设计全部说成已经实现。

## 怎样解释价值和结果

这项工作主要减少工作流中的等待、重复准入与不必要的驻留，不直接减少模型必须生成的 token。链越适合复用、模型切换成本越高，就越可能有优化空间；如果所有模型都能常驻，收益可能缩小。

初稿报告 burst 条件下 makespan 最高降低 36.8%、整体 p95 最高降低 25.9%。不过这些报告值与此前仓库中的模拟来源、资源表配置仍需统一，所以不能直接说成 GNN 带来的真机提升。系统的核心贡献，是把未来可见的工作流需求变成当前可执行的资源动作，同时保留原有语义、容量约束和运行时反馈。
