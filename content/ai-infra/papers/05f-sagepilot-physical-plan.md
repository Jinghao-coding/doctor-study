## 逻辑图与物理图

SagePilot 初稿的完整题名是 **SagePilot: Latency-Aware Orchestration for Multi-Agent LLM Workflows on Heterogeneous GPUs**。逻辑图规定调用依赖、输入输出与可见结果；物理图决定哪些调用共享准入、模型何时加载或回收、调用绑定哪个副本，以及争用资源时谁先执行。初稿 §3.2–3.5 将这些动作放进同一计划，但明确将 SageWeaver 定义为事件驱动的启发式，没有给出全局最优保证。

<div class="table-scroll">

| 对象 | 初稿定义 | 约束 |
|---|---|---|
| activation | 某模型节点的一次调用；重复修复产生新的 activation | 不能把同角色的多次执行视作同一次 |
| ready | 所有前驱已完成 | 可以参与生成准入 |
| near-ready | 路径、角色、模型、不可变输入前缀和可用设备已确定；前驱已完成或在运行，至少一个仍在运行 | 可以准备模型，生成和外部副作用仍等待原依赖 |
| deployment | 模型及版本与 serving 配置组成的身份 | 跨工作流复用还必须满足隔离授权 |
| grant / lease | 调用单元准入某副本，并在执行期间持有租约 | 有活跃租约的副本不能回收 |
| planning window | ready 单元及其紧邻的 near-ready 后继 | 不把未解析分支当成确定未来 |

</div>

## SageGraph 的两步变换

初稿 §3.4 先做工作流内最大合法链融合，再构造模型生命周期动作。ready 单元可以选择 `Load` 或 `Reclaim → Load`；near-ready 单元可以选择 `Prefetch` 或 `Reclaim → Prefetch`。不需要加载动作时，可以复用已有副本，或延后该单元。

Fig. 4 的两个工作流 W1、W2 都需要当前的 Q8 和随后才 ready 的 Q14，且两个模型都不驻留。兼容的需求可共享一次 Q8 加载和一次 Q14 预取；两个工作流各自的请求状态、工具结果、KV 与完成事件仍然分开。若需增加独立副本，则对应独立的生命周期动作。

```text
W1: Q8 调用 ── 工具 ── Q14 调用
       ↑                   ↑
    共享 Load Q8       共享 Prefetch Q14
       ↓                   ↓
W2: Q8 调用 ── 工具 ── Q14 调用
```

共享动作的可用设备必须满足所有消费者的设备约束，不能只因模型名相同就合并。物理候选是用于启发式构造的隐式空间，不意味着在线遍历所有图。

## 融合链的上下文包络

初稿公式 (4) 明确考虑后续阶段消费哪些先前输出。令 P_i 为第 i 阶段固定输入的 token 上界，A_i 为其消费的前序阶段集合，O_j 为阶段 j 的输出上限：

\[
I_i=P_i+\sum_{j\in A_i}O_j,\qquad
I_c^{adm}=\max_i I_i,\qquad O_c^{adm}=\max_i O_i
\]

以下为教学算例：A 的固定输入为 1000 tokens、输出上限 200；B 的固定输入为 300，消费 A 的输出、输出上限 400；C 的固定输入为 500，并消费 A、B 的输出。三个输入包络分别为 `1000`、`300+200=500`、`500+200+400=1100`，整链输入上界取 1100。链的运行时间则是各阶段时间预测之和。

这是初稿的通用定义。此前核对的 worker 使用“首段实际输入 + 前序最大输出上限”的近似；存在更长固定 prompt 或多段累计输出时，两者不等价，需要按具体模板验证。

## 同一时间线上的依赖与争用

初稿公式 (7) 同时考虑逻辑前驱和资源顺序前驱。某操作即使数据就绪，也可能因为模型准备或同卡前一个操作尚未完成而不能开始：

\[
\hat s_u=\max\left(\hat r_u,\max_{v\in pred_G(u)}\hat c_v,
\max_{v\in rpred_\pi(u)}\hat c_v\right),\qquad
\hat c_u=\hat s_u+\hat T_{u,a(u)}
\]

例如数据第 100 秒就绪，模型第 90 秒加载完，但设备上有不可并发操作到第 120 秒才结束，则最早第 120 秒开始。如果本次执行需 20 秒，预计第 140 秒完成。这里的数字是演示值。

初稿公式 (11) 在每个预计状态变化时刻检查“驻留与过渡态模型内存 + 活跃请求的增量内存”是否超过设备容量。请求项是增量内存，不能给每个请求重复累加同一份权重。副本的 batch 上限也必须满足。此前代码核对的是单卡单副本与副本内 batch 准入，尚不能据此确认一般时间线约束已完整实现。

## Algorithm 1 与字典序目标

<div class="table-scroll">

| 步骤 | 具体含义 |
|---|---|
| RankReady | 按优先级和 aging 排 ready 单元 |
| BestFeasibleBinding | 过滤设备，每个单元至多返回一个绑定；能复用副本则形成 grant |
| PlanReady | 为其余 ready 工作考虑加载、扩副本或安全回收 |
| PlanPrefetch | 仅当没有 ready grant 或生命周期动作推进时考虑预取 |
| Propagate | 传播完成时间、排列资源冲突并检查可行性 |
| Prefix | 只提交当前可执行前缀，后续事件到达后重算未发出的部分 |

</div>

公式 (12) 的排序键为：

\[
\Phi=(-A_1,\ldots,-A_K,\hat C_F,-P_N,H_{life})
\]

按字典序最小化：先尽量服务高优先级 ready 单元，再比较这些单元的最晚完成时间，然后增加及时预取，最后降低加载和回收导致的生命周期代价。它不使用一个任意加权总分来交换这些优先顺序。Algorithm 1 按这个意图逐步构造计划，并非求解所有图与排程组合的精确优化器。
