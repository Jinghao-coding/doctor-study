## 工作流依赖如何影响 GPU 执行

SagePilot 研究多个 Agent 工作流共享异构 GPU 时，模型准备、请求准入与设备放置如何共同影响完成时间。一个工作流包含模型调用和工具调用；下游调用尚未 ready 时，其模型身份可能已经确定，因此存在提前加载的机会。连续同部署调用若每次都重新申请后端，也会增加排队，并留下模型被回收的空隙。

<div class="table-scroll">

| 模块 | 输入 | 具体产物 |
|---|---|---|
| SageRadar | 模型算子图、请求配置、GPU 属性、测量数据 | 运行时间、显存上界和加载时间构成的资源代价表 |
| SageGraph | Agent 工作流依赖与部署身份 | 最大合法同部署调用链；论文还用物理图表达生命周期动作 |
| SageWeaver | ready/near-ready 需求、资源表、副本与设备状态 | 执行 grant、加载、扩副本、回收和预取动作 |

</div>

```flow
模型算子图与设备属性 | 预测并校准，生成资源代价表
Agent 工作流 | 编译合法的同部署调用链
请求进入调度器 | 结合资源表、队列与副本状态判断准入
发放 grant 或准备模型 | 预留资源后异步加载、执行
完成或失败事件 | 更新状态，再进行下一轮决策
```

## QMSum 连续聚合例子

```text
融合前：聚合 A(Q8) → 聚合 B(Q8) → 聚合 C(Q8)
        acquire/complete  acquire/complete  acquire/complete

融合后：Fused[A, B, C]
        一次 acquire → 三次顺序生成 → 一次 complete
```

融合保留每一阶段的提示词、输出上限与结果传递，只把三次准入变为一次，让整条链持有同一模型副本的租约。已有活跃租约的副本不会在两个阶段之间被正常回收。收益来自减少重新准入、排队与可能的重加载；生成次数和 token 计算并未因此消失。

再加入另一个同样需要 Q8 的工作流，就会产生共享副本、合并需求、保留模型与扩副本的取舍：当前请求可能因增加副本更快完成，但新副本也可能占用其他模型唯一能放下的设备。

<div class="qa-q">Q: 为什么已经有 vLLM batching，还需要 SagePilot？</div>

<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q: 与 Maestro 的预测有什么区别？</div>
<div class="qa-a"><p>Maestro 的相关预测侧重请求输出长度及由此带来的 KV 需求。SageRadar 用模型算子图、请求形状和设备属性估计配置级资源代价，再服务于模型生命周期和工作流调度。SagePilot 的时间估计也会利用近期输出长度，不能把它简化成只预测固定的模型权重大小。</p></div>
</div>

<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q: 这项系统工作的难点是什么？</div>
<div class="qa-a"><p>各项动作会改变后续可行性。预取可以隐藏加载，却提前占卡；链融合减少准入，却延长租约；增加副本可以缩短队列，却挤压其他模型。解释效果需要把请求的 ready、等待、加载、生成与完成时间对齐，并用消融区分各机制的贡献。</p></div>
</div>

## 设计与实现的区别

<div class="table-scroll">

| 问题 | 论文的表达 | 当前核对到的实现 |
|---|---|---|
| 图优化 | 用物理图统一表达执行和生命周期选择 | 确定性链融合；生命周期动作由副本状态和策略实现 |
| 放置 | 联合考虑资源与完成时间 | 先过滤可行配置，再按卡容量、预测运行时间、设备 ID 排序 |
| 显存 | 更一般的时间线累计资源约束 | 单卡归属一个副本，副本内 batch 显存准入及账本检查 |
| 性能预测 | GNN 提供资源信号 | 调度器查表；表既可来自预测，也可来自实测，需核对实验配置 |

</div>
