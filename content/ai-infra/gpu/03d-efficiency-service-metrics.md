## FLOP/s、MFU 与 HFU

FLOPs 是浮点运算数量，FLOP/s 是每秒运算速率；TFLOP/s 是每秒万亿次浮点运算，一次乘加通常计两次。比较峰值时要固定型号、精度、稀疏/稠密、Tensor/通用计算路径和卡数。`实际指令运算量/耗时` 与 `模型必要运算量/耗时` 的分子不同，不能混用。

设一步模型必要计算量为 `F_model` FLOPs，包含重计算等额外工作的硬件执行量为 `F_exec`，step 耗时为 `t` 秒，所有参与设备匹配口径的峰值之和为 `P_peak` FLOP/s，则：

- `MFU = F_model / (t × P_peak)`，衡量端到端时间内完成必要模型计算的效率。
- `HFU = F_exec / (t × P_peak)`，把额外实际计算也计入；测量或估计方式要说明。

MFU 高通常意味着同一模型计算更高效，但不能据此证明模型质量更好；MFU 低可能是通信、供给、访存、重计算或峰值分母选错。HFU 高而 MFU 较低，可能是额外计算多。两者与 GPU Util、Tensor 活动比例没有固定换算关系。[PaLM §4.1](https://arxiv.org/html/2204.02311v5#S4.SS1)

教学例子：8 张卡各取 100 TFLOP/s 的匹配峰值，模型每步必要计算量 320 TFLOP，1 秒完成，MFU 为 40%。若加入重计算，实际执行 400 TFLOP、耗时 1.1 秒，HFU 约 45.5%，MFU 约 36.4%。这说明硬件“做更多计算”可能同时伴随有效效率下降。训练达到目标质量的时间还取决于步数和收敛行为。

## Roofline 与算术强度

设计算量为 `F` FLOPs，目标存储层实际传输量为 `B` 字节，算术强度 `I = F/B`，单位 FLOP/B；该层可用带宽为 `BW` B/s，匹配计算峰值为 `P` FLOP/s。Roofline 给出的上界是 `min(P, BW × I)`。转折点 `I* = P/BW`。

低算术强度意味着该模型下带宽上界更低；高算术强度使计算峰值可能成为上界。**上界较低不等于程序已经跑到该上界。** 点位远低于两条上界时，还要查依赖、延迟、并行度、提交或同步。增加没有业务价值的计算也会提高算术强度，不能视作优化。[Nsight Roofline](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html#roofline-charts)

例：计算量 10 GFLOPs，HBM 流量 2 GB，算术强度 5 FLOP/B；若峰值为 100 TFLOP/s、HBM 带宽为 1 TB/s，带宽对应上界为 5 TFLOP/s，理想下界为 2 ms。减少 HBM 流量或提高复用可以抬高带宽上界，仍需实测执行时间。

## 训练 step time、吞吐与扩展效率

Step time 是约定一步训练的墙钟时间，应说明是否覆盖梯度同步、优化器更新、数据准备及累积；吞吐是区间内完成的样本或有效 Token 数除以时间。Step 变短只有在 batch、梯度累积、序列长度和工作量可比时才直接意味着吞吐改善。

设单卡可比吞吐为 `Q1`，`n` 卡吞吐为 `Qn`，线性扩展效率为 `Qn/(n×Q1)`。例如单卡 100 samples/s，8 卡 600，则为 75%。低值可能来自通信、负载不均、不同 batch 的执行效率或输入供给；单卡装不下同一任务时，不能硬套这个基线，应注明所用卡数基线和强/弱扩展口径。

高吞吐、短 step 并不保证更快达到相同质量；padding、无效重试和改变训练语义都可能污染比较。看整体运行时间时，Checkpoint、评估和故障恢复是否计入也要一致。

## TTFT、ITL、TPOT 与端到端延迟

设请求起点为 `t0`，首个输出 Token 时间为 `t1`，最后 Token 时间为 `tL`，输出数为 `N`：`TTFT = t1−t0`；相邻 Token 的 `ITL_i = t_i−t_(i−1)`；当 `N>1` 时，请求平均 `TPOT = (tL−t1)/(N−1)`；完整响应延迟按约定终点减起点计算。客户端时间包含网络与前端路径，服务端时间未必包含，必须说明测量位置。[vLLM Metrics](https://docs.vllm.ai/en/stable/design/metrics/)

<div class="table-scroll">

| 指标升高 | 用户感受或系统影响 | 优先检查 |
|---|---|---|
| TTFT | 开始回复慢 | 排队、输入长度、Prefill、缓存命中、模型冷启动与前端路径 |
| ITL 尾部 | 生成过程中卡顿 | 长 Prefill 插入、抢占、通信、周期性阻塞、资源切换 |
| TPOT | 平均生成速度慢 | Decode 批量、权重/KV 访问、并行通信与竞争 |
| 端到端延迟 | 请求整体完成慢 | 同时对齐 TTFT、输出长度和生成间隔 |

</div>

低值一般改善体验，但要在相同请求分布与负载下比较。为降低延迟而过度缩小 batch，可能损失整体吞吐。平均 TPOT 会掩盖单次长暂停；P99 是对应样本群体的 99 分位，不能将各实例 P99 再取平均当全局 P99。

引擎指标还要核对事件粒度：例如 vLLM 的 inter-token latency 指标可按相邻流式输出事件记录，一个事件可能包含多个 Token，此时它与真正逐 Token 间隔、按请求平均的 TPOT 不完全相同。输出不超过一个 Token 时，上式无定义；有的导出器记零、有的基准工具排除，这会改变聚合结果。[vLLM 延迟口径](https://docs.vllm.ai/en/stable/design/metrics/)

## 吞吐、Goodput、队列与批量

吞吐必须区分 requests/s、输入 tokens/s、输出 tokens/s，以及单请求生成速度和全服务总输出。Goodput 是在指定成功与 SLO 条件下的有效产出率；例如同时满足 TTFT 和 TPOT 上限的成功请求数/s。单位与达标条件由评价明确规定。

大 batch 往往有机会改善计算或权重读取复用，但也增加 KV 占用、单轮时间与等待；小 batch 延迟可能较低，却未必充分利用设备。**总 tokens/s 高，但 SLO 达标率下降，不能直接叫线上服务改善。**

队列长度表示等待请求数；队列等待时间表示请求等待多久。高队列可能是需求超过容量或调度阻塞，低队列可能是容量充足，也可能是请求被前端拒绝。稳定系统中 Little 定律 `L = λW` 联系平均系统内请求数、有效到达率与平均停留时间；三者必须对应同一边界，不能把排队长度套到含执行的停留时间上。

## KV Cache 占用与前缀命中率

KV Cache 使用比例通常比较已使用的缓存块与可用池大小，分母不是整张卡显存。高值可能意味着高并发、长上下文，也可能增加抢占或重算压力；低值可能是负载低、上下文短，不能单独证明配置过大。引擎保留一个大池时，设备显存 Used 高而 KV 逻辑利用率低是可能的。

前缀命中率要说明按请求、Token 还是块统计，以及本地缓存还是外部缓存。高命中可能减少重复 Prefill，但不保证端到端快：若路由引起排队，或远端加载 KV 太慢，收益可能被抵消。低命中可能只是请求本来就不共享前缀。比较策略时同时看节省的 Prefill、缓存传输、TTFT 与吞吐。[vLLM 缓存指标](https://docs.vllm.ai/en/stable/design/metrics/)

| 指标 | 定义与分母 | 高低的意义与问题 |
|---|---|---|
| 资源分配率 | 已分配 GPU 数/纳管可调度 GPU 数，或对应卡时之比 | 高值表示分出去了，不代表实际计算；异构或分片资源需分类型统计 |
