<div class="qa-q">Q: 一个 Pod 从创建到运行经历了什么？</div>
<div class="qa-a">
<ol>
<li>用户提交 Pod 到 API Server</li>
<li>API Server 验证、持久化到 etcd</li>
<li>Scheduler 通过 Informer 监听到新的未绑定 Pod</li>
<li>Scheduler 执行 Filter → Score → Reserve → Bind</li>
<li>Bind 结果写入 API Server（Pod.spec.nodeName）</li>
<li>目标节点的 kubelet 通过 Informer 发现分配给自己的 Pod</li>
<li>kubelet 调用 CRI 创建容器，调用 CNI 配置网络，调用 CSI 挂载存储</li>
<li>容器启动，kubelet 上报状态到 API Server</li>
</ol>
</div>

<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q: Informer 机制是什么？为什么不直接轮询 API Server？</div>
<div class="qa-a">
<div class="qa-section"><div class="qa-section-title">机制</div><p>Informer 是 client-go 提供的本地缓存 + Watch 机制。首次 List 获取全量数据存入本地 Store，之后通过 Watch 接收 Added/Modified/Deleted 增量事件。</p></div>
<div class="qa-grid"><div class="qa-mini"><strong>实时性</strong>事件驱动，而不是定期轮询。</div><div class="qa-mini"><strong>性能</strong>减少 API Server 压力，避免大量重复查询。</div><div class="qa-mini"><strong>可靠性</strong>Watch 断线后可以通过 ResourceVersion 续接。</div></div>
<div class="qa-summary">Informer = List/Watch + 本地缓存 + 事件回调 + WorkQueue。</div>
</div>
</div>

<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q: etcd 为什么是性能瓶颈？怎么优化？</div>
<div class="qa-a">
<div class="qa-section"><div class="qa-section-title">为什么是瓶颈</div><p>etcd 是集群唯一的持久化存储，写操作需要经过 Raft 共识，至少过半节点确认后才算成功。</p></div>
<div class="qa-section"><div class="qa-section-title">大集群压力来源</div><p>event、configmap、secret、Pod 状态等频繁写入会增加 fsync 和共识延迟。</p></div>
<div class="qa-grid"><div class="qa-mini"><strong>磁盘</strong>使用 SSD 降低 fsync 延迟。</div><div class="qa-mini"><strong>隔离</strong>将 event 分离到独立 etcd 集群。</div><div class="qa-mini"><strong>缓存</strong>API Server 启用 watch cache。</div><div class="qa-mini"><strong>维护</strong>合理设置 compaction，控制数据库体积。</div></div>
</div>
</div>

<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q: 如何实现自定义调度器？有几种方案？</div>
<div class="qa-a">
<p>三种方案：</p>
<ol>
<li><strong>Scheduler Plugin（推荐）</strong>：实现 Scheduling Framework 的扩展点接口（Filter/Score/Reserve 等），编译进调度器二进制。优点：性能好，原生集成</li>
<li><strong>Scheduler Extender</strong>：HTTP webhook 方式，调度器在 Filter/Score 后调用外部服务。优点：不需要重编译调度器；缺点：网络延迟，不支持所有扩展点</li>
<li><strong>完全自定义调度器</strong>：独立二进制，通过 Pod 的 schedulerName 字段指定。优点：完全自由；缺点：不能复用默认插件，维护成本高</li>
</ol>
</div>
</div>

<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q: K8s GPU 调度的挑战和解决方案？</div>
<div class="qa-a">
<p>核心挑战：</p>
<ol>
<li><strong>整数分配</strong>：nvidia.com/gpu 是 Extended Resource，只能整数分配，不支持 0.5 GPU</li>
<li><strong>拓扑无感</strong>：默认调度器不感知 GPU 间的 NVLink 拓扑，可能把需要通信的 Pod 放到不同 PCIe 树</li>
<li><strong>无法修改</strong>：admit 后 GPU 数量不可调整</li>
</ol>
<p>解决方案：</p>
<ol>
<li>GPU 共享：MPS / MIG / 时间片（需要 device plugin 配合）</li>
<li>拓扑感知：Topology Manager + 自定义 Score 插件</li>
<li>弹性训练：Elastic Horovod / PyTorch Elastic（运行时加减 worker）</li>
</ol>
</div>
</div>

<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q: Device Plugin 怎么工作？</div>
<div class="qa-a">
<div class="qa-section"><div class="qa-section-title">定位</div><p>Device Plugin 是 kubelet 的扩展机制，用于管理 GPU、FPGA、RDMA 等非标准硬件资源。</p></div>
<ol><li>Device Plugin 启动后通过 gRPC 向 kubelet 注册资源名称，例如 nvidia.com/gpu。</li><li>kubelet 向 API Server 上报节点 allocatable 中的扩展资源数量。</li><li>调度器基于 Pod requests 和节点 allocatable 做过滤和打分。</li><li>Pod 调度到节点后，kubelet 调用 Device Plugin 的 Allocate 方法获取设备信息。</li><li>设备路径、环境变量等信息被注入容器。</li></ol>
<div class="qa-summary">NVIDIA k8s-device-plugin 就是典型实现：上报 GPU 资源，并在容器启动前分配具体设备。</div>
</div>
</div>

<div class="qa-q">Q: Headless Service 和 ClusterIP Service 的区别？</div>
<div class="qa-a">
<div class="qa-grid"><div class="qa-mini"><strong>ClusterIP</strong>有虚拟 IP，由 kube-proxy 做服务转发和负载均衡。</div><div class="qa-mini"><strong>Headless</strong>clusterIP: None，不分配虚拟 IP，DNS 直接返回后端 Pod IP。</div></div>
<div class="qa-section"><div class="qa-section-title">AI Infra 用途</div><p>分布式训练需要 worker 之间直接通信，例如 NCCL AllReduce。Headless Service 可以让每个 Pod 解析其他 Pod 的 IP，建立点对点连接。</p></div>
