# doctor-study 内容写作规范

本文件是 `content/` 下 Markdown 内容的统一写作模板。新 agent 进入项目后，除阅读 `AGENTS.md` 外，也必须阅读本文件；新增或重写学习内容时，应优先遵循这里的结构。

## 总原则

1. 一个 Markdown 文件只解决一个知识点、一个机制或一个面试模块。
2. 内容服务面试复习，不写成百科长文；先给结论，再展开原因、链路、机制和可点击问答。
3. 优先使用 `content/` 中的小文件组织内容，不直接修改 `pages/**/*.html`。
4. 内容多时拆文件，并在对应 `topic.json` 的 `layout.tabs` 中组织为模块。
5. 旧文件不要求一次性全量迁移；当某个页面被重组或某个章节被重点修改时，顺手按本规范迁移。
6. 不为了形式强行填满所有小节；按章节类型选择必要模板。
7. 术语、公式、命令和 API 用行内代码或代码块表达，避免口语化堆叠。
8. 不再写全局 `## 面试回答`、`30 秒版`、`2 分钟版` 这类尾部模板；可复述内容应收敛到 `.qa` 问答块、`qa-summary` 摘要、排障路径或对比表中。

## 通用章节模板

适合大多数知识点文件：

```markdown
## 一句话结论

用 1-3 句话说明这个知识点在面试里要回答什么，以及它为什么重要。

## 核心概念

解释术语、边界和基本定义。

## 系统链路

描述数据流、控制流、调度路径、资源路径或生命周期。

## 关键机制

展开算法、公式、硬件机制、系统实现或工程细节。

## 常见误区

列出容易混淆或面试中容易答错的点。

## 关联模块

列出和其他页面的连接关系，不重复大段解释。
```

## 概念类章节

适合 CPU vs GPU、MIG/MPS、DRF、Prefill/Decode、Informer 等基础概念。

建议结构：

```markdown
## 一句话结论
## 核心概念
## 对比表
## 常见误区
## 关联模块
```

写作要求：

- 对比概念必须用表格压缩边界。
- 不在概念章节里展开太多工程排障细节。
- 面试回答内容放进 `.qa` 块或 `qa-summary`，说明“本质区别”，不是只列定义。

## 机制类章节

适合 CUDA 执行模型、KV Cache、PagedAttention、Scheduler Queue、NCCL、ZeRO/FSDP 等。

建议结构：

```markdown
## 一句话结论
## 系统链路
## 关键机制
## 资源模型
## 常见误区
```

写作要求：

- 先讲链路，再讲机制。
- 涉及资源时说明 CPU、GPU、显存、网络、队列或缓存的消耗。
- 涉及公式时先给直觉，再给公式。

## 排障诊断类章节

适合 GPU 利用率诊断、瓶颈分类、K8S 故障排查、训练 hang/OOM、推理延迟排查等。

建议结构：

```markdown
## 一句话结论
## 诊断入口
## 指标解释
## 排查路径
## 典型现象
```

写作要求：

- 必须给出从粗到细的排查路径。
- 指标必须说明“能说明什么”和“不能说明什么”。
- 优先使用决策树、压缩表和命令表。

示例排障路径：

```text
业务指标异常 -> 粗粒度系统指标 -> timeline -> 单点 kernel/请求/Pod 深挖 -> 修复与复测
```

## 系统设计类章节

适合多模型推理系统、多租户 GPU 调度、KV 缓存管理、分布式训练平台等。

建议结构：

```markdown
## 问题定义
## 目标与约束
## 核心架构
## 数据流 / 控制流
## 关键权衡
## 故障与扩展
```

写作要求：

- 先定义范围和非目标，避免设计题发散。
- 架构必须包含组件职责、关键状态和核心链路。
- 权衡要写清楚为什么这么选，而不是只列方案。

## 论文项目类章节

适合 Maestro、DeepShare、个人项目深挖和面试叙事。

建议结构：

```markdown
## 问题背景
## 核心贡献
## 系统设计
## 实现细节
## 实验结果
## 高频追问
## 面试叙事
```

写作要求：

- 论文页要服务“我做了什么、难点是什么、为什么有效、如何落地”。
- 实验结果必须避免夸大；没有数据就写“待补充”或只讲方向。
- 面试叙事优先写成自我介绍、项目追问和 `.qa` 问答块，不在章节尾部堆长段复述。

## 面试收束类章节

适合每个大主题末尾的总结页，例如 GPU 面试收束、LLM 推理面试收束。

建议结构：

```markdown
## 一句话结论
## 高频追问压缩表
## 排障 / 设计决策树
## 跨模块关联
```

写作要求：

- 这类章节负责把本主题串起来，不再展开重复概念。
- 必须显式写出和其他主题的连接。
- 优先使用表格和流程块，降低复习成本。

## 原始 HTML 组件约定

生成器允许在 Markdown 中直接写 HTML。推荐组件：

```html
<div class="card card-m">
<h3>标题</h3>
<p>内容。</p>
</div>
```

卡片语义：

- `card-m`：主要概念、核心机制、主线结论。
- `card-d`：正向经验、实践方案、推荐做法。
- `card-s`：结构化说明、系统组件、流程拆解。
- `card-w`：注意事项、风险、面试易错点。
- `card-r`：反例、危险点、排障路径。

问答块：

```html
<div class="qa" onclick="this.classList.toggle('open')">
<div class="qa-q">Q: 问题？</div>
<div class="qa-a">
<p>回答。</p>
</div>
</div>
```

摘要块：

```html
<div class="qa-summary">一句话总结。</div>
```

结构化回答块：

```html
<div class="qa-section">
<div class="qa-section-title">小标题</div>
<p>内容。</p>
</div>
```

## 表格与代码块

表格适合：

- 概念对比
- 指标解释
- 工具命令
- 高频追问压缩
- 系统组件职责

代码块适合：

- 命令
- API 示例
- 配置片段
- 决策树
- 数据流

流程型代码块可以使用：

````markdown
```flow
步骤 A | 说明
步骤 B | 说明
```
````

## topic.json 组织规则

1. 内容较多的主题优先使用 `layout.tabs`。
2. tab 分组应体现复习路径，而不是文件创建顺序。
3. 推荐分组：
   - 总览 / 基础直觉
   - 核心机制
   - 工程实践 / 排障
   - 面试收束 / 关联模块
4. 每个 tab item 应有 `title`、`description`、`file`、`level`、`priority`、`time`。
5. `description` 要说明这个模块解决什么问题，不只重复标题。

## 迁移旧内容的步骤

1. 先判断章节类型：概念、机制、排障、系统设计、论文项目或面试收束。
2. 不急着重写所有正文，先补“一句话结论”，再把复述要点整理进 `.qa`、`qa-summary`、表格或流程块。
3. 如果一个文件承担多个主题，优先拆分。
4. 如果两个文件重复，先写清职责边界，再决定是否合并。
5. 修改后运行：

```bash
uv run python tools/build_site.py
git status --short
```

涉及生成脚本时，再运行：

```bash
uv run python -m py_compile tools/build_site.py
```
